# InkCube 编程习惯与规范

## 一、操作纪律
- **禁止执行任何 git 操作**（add、commit、push、pull、checkout、branch、merge 等），由用户手动完成。
- **先确认再动手**。执行任何代码调整前，必须先说明方案并得到用户明确指令。
- **禁止遗留项**。禁止以「遗留项」「供后续决策」「后续再处理」等方式推迟已知问题：
  - 发现的问题要么当场解决，要么明确给出不解决的理由（超出本次范围且影响可控），不得仅登记不动。
  - 盘点范围内同类问题必须一次性清理（如发现一处硬编码文案，则同文件/同模块的同类硬编码全部处理）。
  - 交付时不得附「遗留问题清单」式的待办尾巴；若确需用户决策，必须在动手前问清，而不是做完再留。
- **存量数据现实（2026-10-21 起，替代原「项目未上线，无存量数据」）**。项目已产生存量用户数据（SQLite 库、`data/` 文件产物、settings 配置键），评估任何数据结构变更（表结构、列增删改、主键/哈希算法、文件格式/目录布局、配置键）时必须同步设计存量数据过渡，缺迁移设计即缺陷：
  - 迁移随应用启动自动执行，对齐 `db/database.py` 现有模式：幂等可重入（已迁移即跳过）、失败向上抛阻断启动，禁止静默吞掉；迁移逻辑与 DDL 同文件维护。
  - 按风险选型：加列走 `_migrate_add_column`（可空/带默认值）；改列语义、重建约束等高风险变更须先给出存量数据的清洗/去重/保留策略再动 DDL；删列删表前先全链路确认无消费。
  - 禁止双写与长期版本兼容层；禁止默认「删库重装」替代迁移（仅开发机自用数据可例外，须在方案中显式说明）。

## 二、开发与代码规范

### 2.1 文档与代码双向对齐
- **执行前（文档 → 代码）**：先同步文档内容，再执行开发，确保实现与设计一致。
- **完成后（代码 ↔ 文档）**：
  - 文档 → 代码：设计要求是否全部落地，有无遗漏或偏差。
  - 代码 → 文档：实际实现是否反映在文档中，有无未覆盖的变更。
- 对齐范围：死代码/死接口清理、模块职责与组件层级、命名一致性。

### 2.2 代码质量与问题修复
- **禁止留垃圾代码和死代码**，前后端（含 Electron IPC 层）统一清理：
  - 删前端 → 同步清理后端接口和 IPC。
  - 删后端 → 同步清理前端调用和 IPC。
  - 重构 → 全链路检查死代码。
- **不打补丁**。遇到问题先通过测试找到根因，再制定方案；禁止尝试未经验证的可能方案。
- **兜底不是解决方案**。超时、重试、默认值、降级等防御性措施只能作为根因修复之上的纵深防御，禁止以「加个兜底」替代根因修复：
  - 修复必须回答「为什么会发生」，并用证据（日志、数据、可复现路径）闭环；答不出根因的修复视为未完成。
  - 交付描述必须区分「根因修复」与「兜底防御」两部分，缺一不可：只加兜底不查根因 = 未完成的修复；只修根因不加兜底 = 修复不可验证（同类挂起/异常仍可能杀死进程）。
  - 纵向排查时逐层排除：日志缺失 ≠ 未发生（可能卡在响应前）；同进程其他链路正常/异常是定位挂起点的关键证据。

### 2.3 跨平台与国际化
- 代码适应跨平台要求（Windows / macOS / Linux）。
- 代码适应中英双语要求（UI 文本、日志、错误信息等）。

### 2.4 日志管理
- 项目有统一日志框架，用户可在应用内查看日志：
  - **Python**：使用 `logging` 模块（已配置 RotatingFileHandler → `data/logs/app.log`）。
  - **Electron**：使用 `log-utils.js`（写入同一个 `app.log`）。
- 关键操作必须通过项目日志框架输出，禁止随意 `console.log` / `print`，确保可追溯。

### 2.5 完成验证
每次代码变更后，必须按层级执行验证，确认无破坏再交付：
1. **语法检查**：
   - Python：`python -m py_compile <file>` 或运行 `dev/_check_syntax*.py`。
   - TypeScript：`npx tsc --noEmit`。
2. **构建验证**：`npm run build`（前端）；涉及打包的变更需确认 `npm run pack` 可正常完成。
3. **运行验证**：`npm run dev` 启动完整栈（Vite + Electron + Python），确认功能正常、无启动报错。
4. **全链路回归**：涉及多模块的变更，需验证 IPC 调用链完整、日志无异常输出。

### 2.6 单元测试
- **框架选型**：
  - Python 后端：使用 `pytest`（配合 `pytest-asyncio` 处理异步接口）。
  - 前端（React + TypeScript）：使用 `vitest`（与 Vite 构建工具链一致，零额外配置）。
- **测试文件约定**：
  - Python：测试文件放在被测模块同级 `tests/` 目录下，命名为 `test_<module>.py`。
  - 前端：测试文件与被测文件同目录，命名为 `<Component>.test.ts(x)`。
- **编写要求**：
  - 新增核心功能必须附带单元测试，覆盖正常路径和主要异常路径。
  - 修复 bug 时必须补充对应的回归测试用例。
  - 测试应独立运行，不依赖外部服务或真实数据（使用 mock/fixture 隔离）。
- **执行方式**：
  - Python：`pytest python/tests/ -v`。
  - 前端：`npx vitest run`。

### 2.7 长时活动统一模型
- **适用判定**：凡「排队 → 执行 → 终态」的异步作业（如文件解析、图片描述、报告生成、任务执行、Wiki 编译、模型下载）均为长时活动。
- **禁止为新增长时活动自建**：独立轮询、自定义状态字段语义、「是否运行中」查询端点、前端活跃谓词——重复建设是现有轮询体系碎片化的根源，不允许继续。
- **必须**：后端实现统一 Activity 接口（`kind/id/status/progress/message`）并注册进活动注册表；前端一律经 `useActivity(kind)` 消费，页面级只保留明细查询。
- **前置条件**：统一骨架（注册表 + useActivity）未落地时，先补骨架再接新活动；改造存量活动时禁止复制旧模式。
- **验收信号**：[0.4 §8.1](docs/0.4lifecycle-design.md) 轮询台账只允许收敛、不允许增长；终态为 1 条全局心跳 + 页面明细查询。

### 2.8 设计文档规范
- 架构/功能设计文档必须包含三要素，缺一即为不合格：
  1. **表结构**：涉及的表（DDL）或内存状态结构、索引、读写行为、各自定位；引用其他文档的 DDL 须显式给出链接；
  2. **数据流**：分层组件图 + 端到端路径（读/写/事件分列），标注 IPC 通道名与端点名；
  3. **前端交互**：消费组件清单（组件 × 数据 × 界面呈现）、状态-界面映射（每种状态下用户在哪里看到什么）、关键交互规则与不变量。
- 三要素受 §2.1 双向对齐约束：代码变更涉及任一要素时同步更新文档。
- 禁止以叙述性段落替代结构化表格；现状与设计目标须分别标注（如「现状 / E2 目标」），禁止用现状冒充设计。
- 存量文档不强制追溯，下次修订该文档时补齐三要素。

### 2.9 全链路完整交付（孤儿通道零容忍）
> 缘起：2026-10 usage:taskDetail 复盘——设计标「预留下钻」、实施只落地 IPC 通道、三轮 review 均单向核对未发现前端零消费，构成死代码。
- **端到端完整原则**：每个功能的交付必须覆盖「设计 → 后端端点 → IPC 通道 → 前端消费（invoke/订阅）→ UI 呈现」全链；禁止任何一层的半成品状态（如「后端先行、前端待实现」的预留通道）。禁止预留没有消费方的端点、通道、函数——「预留」本身就是死代码。
- **同步落地**：新增后端端点或 IPC 通道时，必须在同一变更内落地前端消费与 UI 承载；做不到就先不做后端。
- **双向孤儿审计**：交付前必须运行 `node scripts/orphan_channel_audit.js`，四组输出（A 注册无消费 / B 消费无注册 / C 事件类双向 / D python 端点无代理引用）必须为 0，或对剩余项逐条给出显式消费证据（变量通道、动态拼接、内部消费）；已知审计盲区（`ipc.*` 对象、`chatIpcChannel` 类变量转发、模板串拼接通道、`wc.send`/`sender.send` 短变量形态、Sigma 等非 IPC 同名事件）须人工补查，禁止仅凭脚本零输出即宣称无孤儿。
- **删除链完整**：删除任一层时，按「UI → invoke → IPC handler → python 端点 → db 函数 → 测试 → 设计文档行」反向全链清理，并逐层甄别连坐（同端点被其它 handler 或内部调用消费则保留该层，如 `GET /tasks/{id}` 被 tasks:export 内部消费）。

## 三、依赖管理
- 引入第三方库前，必须评估：
  - **打包兼容性**：能否被 electron-builder / PyInstaller 正确打包，有无原生模块问题。
  - **安装便利性**：用户环境能否顺利安装，是否依赖系统级组件（C++ 编译器、特定 OS 库等）。
  - **包体积影响**：对安装包大小的影响。
- 优先使用项目已有依赖，避免重复引入功能相同的库。

## 四、Code Review 规范
- **禁止只做横向对齐式 review**（字段名匹配、死代码清理、UI 状态检查），必须纵向追踪执行路径。
- **纵向追踪**：从入口（API/IPC）到底层（DB/网络调用），逐层检查五个维度：
  1. **报错**：异常在哪一层被捕获？捕获后做了什么（吞掉/重试/上报）？中间层状态是否一致（如 task 状态卡死）？
  2. **重试**：每个可能瞬时失败的层（网络、LLM API、DB 锁）是否有重试？重试粒度是否合理（整个任务 vs 单次调用）？
  3. **并行**：并发访问是否有竞态（check-then-act、重复入队、写覆盖）？锁/信号量是否覆盖了关键区？
  4. **参数**：魔法数字从哪来？用户能否通过 settings 调整？硬编码是否合理？
  5. **消费**：正向核对「设计条目都有代码」之后，必须反向核对「每条注册的 IPC 通道/后端端点都有前端消费方、每段被测代码都对应真实用户路径」（孤儿通道 = 未完成交付，处置见 §2.9）。
- **攻击式思维**：假设系统会在最薄弱环节崩溃，主动去找那个环节，而不是对照清单打勾。
- **列表翻页核查**：新增/改动任何列表功能时，必须检查取数是否考虑了翻页——禁止无界全量拉取，也禁止静默 `limit` 截断（拉 20 条不提示还有更多）；列表接口一律带分页契约（`limit/offset/has_more/total`，`limit=0` 全量供选择器等场景），详见 0.1dev-guide §16。
- **新功能必须核实生命周期闭环**：每引入一类持久化产物（DB 行、磁盘文件/目录、进程内缓存、外部态），设计时必须同步回答「谁创建、谁清理、何时清理」（显式删除/级联/保留期/重置清单四选其一有答案），缺删除或清理设计即缺陷，禁止「只管创建不管清理」。实证（2026-10-20 存储审计 B1-B7）：fetched 抓取产物无任何清理入口且面板不可见（B7）、run 行删除后 `report_path` 副本成孤儿（B5）、知识单清不删 reports 产物（B4）——均为功能上线时有创建、无清理。
