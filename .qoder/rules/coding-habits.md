# InkCube 编程习惯与规范

## 一、操作纪律
- **禁止执行任何 git 操作**（add、commit、push、pull、checkout、branch、merge 等），由用户手动完成。
- **执行任何代码调整前，必须先得到用户的明确指令**。先说明方案，等待确认后再动手。

## 二、文档与代码双向对齐
- **执行前：文档 → 代码**。先同步文档内容，再执行开发，确保实现与设计一致。
- **完成后：代码 ↔ 文档 双向对齐**。
  - **文档 → 代码**：设计要求是否全部落地，有无遗漏或偏差。
  - **代码 → 文档**：实际实现是否反映在文档中，有无未覆盖的变更。
- 对齐范围：代码清理（死代码/死接口）、结构清晰（模块职责、组件层级）、命名一致性。

## 三、代码质量
- **禁止留垃圾代码和死代码**。前后端（含 Electron IPC 层）统一清理。
  - 删前端 → 同步清理后端接口和 IPC。
  - 删后端 → 同步清理前端调用和 IPC。
  - 重构 → 全链路检查死代码。

## 四、问题修复策略
- **不打补丁**。先通过测试找到根因，再制定方案。
- 禁止尝试未经验证的可能方案。

## 五、跨平台与国际化
- 代码适应跨平台要求（Windows / macOS / Linux）。
- 代码适应中英双语要求（UI 文本、日志、错误信息等）。

## 六、日志管理
- 项目有统一日志框架，用户可在应用内查看日志。
  - **Python**: 使用 `logging` 模块（已配置 RotatingFileHandler → `data/logs/app.log`）。
  - **Electron**: 使用 `log-utils.js`（写入同一个 `app.log`）。
- 关键操作必须通过项目日志框架输出，禁止随意 `console.log` / `print`，确保用户可追溯。

## 七、第三方依赖
- 引入第三方库前，必须评估：
  - **打包兼容性**：是否能被 electron-builder / PyInstaller 正确打包，有无原生模块问题。
  - **安装便利性**：用户环境能否顺利安装，是否依赖系统级组件（如 C++ 编译器、特定 OS 库）。
  - **包体积影响**：对安装包大小的影响。
- 优先使用项目已有的依赖，避免重复引入功能相同的库。
