# 长时活动生命周期设计

> **概述**：本文档是 InkCube 长时活动子系统的架构设计权威，覆盖任务执行、文件解析、图片描述、Wiki 编译、报告生成、模型下载六大长时活动（全文统一称「长时活动」）。核心机制：
> 1. **状态与恢复**——DB 状态机为唯一事实，重启即中断判定，按资源代价分级自愈（§1.3 / §2.4）；
> 2. **用户反馈**——Toast / 徽章 / 首页 / 页面详情四反馈面同源（ActivityContext），终态事件经 notifications 表持久化，切页不丢（§5 / §3.2）；
> 3. **统一活动模型**——活跃状态经注册表 + `useActivity` 全局供给，页面轮询谓词全局派生、禁手动布尔；终态事件经 activity_events 框架统一写入 + SSE 即时投递（§2 / §6.4）；
> 4. **轮询治理**——页面轮询台账只收敛不增长，与纯 UI 计时器分账（§5.8 / §8.1）；
> 5. **准入引导**——依赖未就绪时三层防御（首启向导 / 入口弹层 / API 校验），替代事后报错（§7）。
>
> **结构**：§1 设计目标与统一模型 → §2 总体架构 → §3 数据存储（表结构）→ §4 数据流 → §5 前端交互 → §6 接口契约 → §7 准入（Readiness）→ §8 现状台账（轮询 / 终态写入点 / 日志存储 / 验收信号）→ §9 决策记录 → §10 差异与下一步优化建议。不含：各活动的业务执行逻辑（见 1.x / 2.x 系列文档）、进程级看门狗（[0.0architecture §5.1](0.0architecture.md)）。

## 1. 设计目标与统一模型

### 1.1 统一模型

六大长时活动——「排队 → 执行 → 终态」的异步作业——天然形态各异：状态有的落 DB（files / wiki_compile_tasks / reports 表）、有的在内存（task_agent 运行集、model_manager 下载 dict）；有的可断点续跑、有的一次性。若每个功能上线时就近接线，会长成互不相认的多套实现，代价集中三类：

1. **双轨轮询**：监控走自研 setTimeout 循环、其余走 usePolling，防重叠 / 退避 / 超时保障不共享，缺陷只在其中一条轨上发生；
2. **手动布尔卡死**：轮询开关靠手动布尔翻转，只有「成功」路径会关闭时，失败路径无人复位 → 轮询永转；
3. **职责黏连**：一条轮询同时喂并发闸门 + 角标 + 进度，催生难读的复合谓词。

因此收敛为一套统一机制：**活跃状态一个注册表供给、终态事件一个框架收口、反馈一个 Context 分发、轮询谓词一个来源派生。**

### 1.2 目标与边界

1. **活跃状态统一**：一个注册表，`useActivity(kind)` 唯一入口，页面轮询谓词从全局心跳派生；
2. **终态事件统一**：业务代码只声明终态，通知写入 / 事件投递由活动框架（activity_events）一次完成，所有 kind 的完成感知延迟一致（§6.4）；
3. **明细查询页面自治**（边界）：逐文件 / 逐图 / 逐章节进度归页面级查询，本模型只提供其开关谓词，不碰明细内容。

一句话：**管「在不在跑」与「跑完了」，不管「跑到哪了」——但提供后者的开关。**

### 1.3 统一状态机

所有长时活动共享同一状态机形态：

```
触发 → 排队(queued/pending) → 处理中(processing/parsing/generating…)
                                    │
                ┌───────────────────┼────────────────────┐
                ▼                   ▼                    ▼
          ✓ 成功终态           ✕ 失败终态           👀 等待用户
      (done/completed)       (error/failed)            (paused)
```

关键澄清：

- **无 interrupted 中间态**——「重启即中断判定」：应用重启时处于处理中的记录必然已中断（同进程 worker 已消亡），启动扫描直接处置（§2.4），`interrupted`/`resumed` 不落库
- **用户主动退出**（cancelled / stopped / paused）不算事件，通知静默
- **状态全部落 DB（或内存态可重建）**，前端只是只读镜像——可随时重建连接，不依赖内存态

### 1.4 六模块差异矩阵与状态机

统一规则（§1.5）下，六大长时活动的差异一眼看全：

| 维度 | 任务 | 文件解析 | 图片描述 | Wiki 编译 | 报告生成 | 模型下载 |
|---|---|---|---|---|---|---|
| 状态落点 | tasks + task_agent_state | files + images 行级 | images.status | wiki 编译任务 | reports | model_downloads + ModelManager 内存态 |
| 崩溃恢复 | 手动 | 自动 | 自动 | 自动 | 手动 | 手动 |
| 恢复粒度 | 最后完成 iteration 续跑 | 整文件重跑（先清脏数据） | 单张重新描述 | 文件级断点续传（ingest_summaries 跳过已完成） | checkpoint 节级续跑 | HF/ModelScope 断点续传 |
| 用户感知 | 会话内中断提示消息 | 状态回「排队中」，静默重跑 | 基本无感（已完成图片跳过） | `is_resumed`「恢复中」 | 标 error + failed 通知，详情页「重新生成」 | failed 通知，重新点击续传 |
| 终态通知 | done / error | done / error | 不单独通知（文件级已覆盖） | completed / failed | done / failed | completed / failed |
| 切走 / 切回 | bgStates 缓存流式状态，SSE 继续 | 停/拉文件列表 | 随文件 | 停/拉编译状态 | 停/拉看板 | 停/设置页拉状态 |
| 手动出口 | 暂停 / 取消 | —（失败后重传） | —（随文件） | 停止 | 取消 / 重新生成 | —（重新点击） |
| 详细文档 | [1.1](1.1task-agent-design-unified.md) | [2.2](2.2knowledge-base-design.md) | [2.2](2.2knowledge-base-design.md) | [2.6](2.6wiki-design.md) | [2.5](2.5report-design.md) | 本节 |

各模块状态枚举：

**任务**（详见 [1.1](1.1task-agent-design-unified.md)）：`running`（🔄 流式输出）/ `paused`（⏸️ 等待确认）/ `done`（✅ 完成）/ `cancelled`（⛔ 已取消）。Checkpoint：每次 iteration 完成后保存完整 LLM messages + iteration 序号 + recent_errors。

**文件解析**（详见 [2.2](2.2knowledge-base-design.md)）：`pending`（⏳ 排队中）/ `parsing`（🔄 进度条）/ `done`（✅）/ `error`（❌）。进度按阶段推进：解析 0→25% → 向量化 25→75% → FTS 75→95% → 完成 100%。

**图片子状态**：行级存 `images.status`（pending/processing/done/error）；文件级聚合字段 `files.image_status` 由 `update_file_image_status` 从 images 表重算：`none` / `pending`·`describing`（计入文件活跃指示，通知不重复发）/ `done`·`error`。

**Wiki 编译**（详见 [2.6](2.6wiki-design.md)）：`queued`（⏳ 排队中）/ `ingesting`·`storing`（🔄 摄入中·存储中，逐文件连续摄入）/ `completed`·`failed`（✅❌）/ `stopped`（⛔）。单文件失败隔离在文件级 ingest_summaries（不中断队列），任务级终态只有 completed / failed / stopped。崩溃语义：ingesting/storing → queued 自动续跑（按 ingest_summaries 断点续传）；恢复检测 `is_resumed`。

**报告生成**（详见 [2.5](2.5report-design.md)）：`generating`（⏳）/ `done`·`failed`（✅❌）/ `cancelled`（⛔）。Checkpoint：每节完成后持久化，崩溃标 error 保 checkpoint，「重新生成」从 checkpoint 续跑。

**模型下载**：model_downloads 表持久化 + ModelManager 内存态；崩溃中断标 failed + 通知，重新点击后断点续传。

视觉统一状态色（[0.3 §5.3](0.3ux-design.md)）：蓝脉冲运行中 / 灰待处理 / 绿成功 / 红失败 / 琥珀警告。

### 1.5 五条统一规则

| # | 规则 | 内容 | 落地 |
|---|------|------|------|
| 一 | **生命周期 = DB 状态机** | 状态持久化、前端镜像；进度可回放 | §1.3 / §3 |
| 二 | **通知唯一判据 = 用户需要行动吗** | 终态+需行动 → 写通知+Toast；进行中 → 只进活跃列表（徽章/首页）；用户主动行为 → 完全静默；「开始」永不通知 | §3.2 / §6.5 |
| 三 | **呈现 = 单一数据源 + 粒度递进** | 四反馈面全部从 ActivityContext 取数：Nav 数字（有动静）→ 首页卡片（谁在干什么）→ Tab 角标（该项目有几件）→ 页面内进度/日志（详细过程） | §5.1 |
| 四 | **恢复自动化 ⇔ 用户资源消耗成反比** | 可重放、无交互上下文（本地推理）→ 自动续跑；消耗 token / 定制上下文 / 大网络资源 → 标记+通知+等用户 | §2.4 |
| 五 | **准入 = 依赖显式化 + 三层防御** | 必需/可选依赖分级建模，事前引导弹层为主、入口 API 校验兜底 | §7 |

## 2. 总体架构

### 2.1 分层组件图

```
┌─ 前端 React ────────────────────────────────────────────────────────┐
│ 全局反馈面：NavTabs 徽章 / ProjectList 活跃点 / 首页活动区 / Toast   │
│ 页面明细轮询（enabled 谓词一律 ← useActivity(kind)，§5.8）          │
│ 页面挂载期刷新（日志查看器，不经本模型）                             │
│     ▲ useActivity(kind)              ▲ usePolling                  │
│ ActivityContext（前端唯一状态存放处，applyStatus 写入）              │
│     ▲                                │ window.electronAPI.invoke   │
│ ActivityMonitor（#0 心跳 5/15s，唯一拉取者；                          │
│   activity:stream 事件仅作「立即心跳」触发信号，§6.4）               │
└─────┬────────────────────────────────┼──────────────────────────────┘
      │ IPC activities:getStatus       │ IPC 明细通道（models:status、
      │ IPC activities:subscribeStream │ knowledge:getActiveFiles、reports:getReport …）
      │ （SSE 转发，豁免超时）          │
┌─ Electron ──────────────────────────────────────────────────────────┐
│ ipc-handlers.js（纯转发 + fetchWithTimeout 15s；SSE 流转发豁免）     │
└─────┬────────────────────────────────┼──────────────────────────────┘
┌─ Python FastAPI ─────────────────────────────────────────────────────┐
│ GET /activities/status ──▶ activities_registry.snapshot()            │
│ GET /activities/stream ──▶ activity_events 订阅者队列（SSE，§6.4）   │
│ GET /models/status 等 ◀── 页面明细端点（页面自治，不在本模型内）      │
│     activities_registry：FunctionSource × kind（§3.4 清单）          │
│            │ fetch()（只读快照）                                     │
│ 状态源层：files 表 / wiki_compile_tasks 表 / reports 表 /            │
│           task_agent 内存集 / model_manager 内存 dict                │
│ 事件存储层：notifications 表（activity_events 统一写入）             │
│           ＋ main lifespan 启动扫描恢复补发                          │
└──────────────────────────────────────────────────────────────────────┘
```

两层解耦原则：**后端各业务模块互不知晓**（各自向注册表登记查询源）；**前端各页面互不知晓**（都只问 `useActivity(kind)`）。全局层只有一条心跳、一份状态。

### 2.2 活动注册表与前端供给

**后端 activities_registry**（§6.1 契约）：每个 kind 登记一个 ActivitySource（`kind` + `fetch() -> list[dict]`），聚合端点 `GET /activities/status` 只从注册表取快照，按 kind 排序合并；单源异常只降级本源为空，不影响其余源、不抛出。

**前端 ActivityContext + useActivity**（§6.2 契约）：ActivityMonitor 是唯一拉取者（App 级常驻心跳），响应经 `applyStatus` 写入 Context；全局反馈面与页面轮询谓词全部从 Context 派生，无第二份全局状态。

### 2.3 反馈闭环：后端聚合 + 前端分发

```
┌─ 后端 ──────────────────────────────────────────────┐
│ 六大长时活动到达终态 → activity_events 写 notifications │
│   ＋ SSE 投递（§3.2 / §6.4）                          │
│ GET /activities/status = 活跃列表 + 未读/最近通知 + summary │
└────────────────────┬────────────────────────────────┘
                     ↑ App 级唯一常驻轮询 ActivityMonitor
                     │  活跃 5s / 空闲 15s / 不可见 45s（仍拉取）；
                     │  恢复可见立即拉取；失败退避 5→10→20→60s；
                     │  activity:stream 事件 200ms 节流触发立即心跳
┌─ ActivityContext ──┴────────────────────────────────┐
│  ├→ Toast：终态弹出（§5.5）                           │
│  ├→ 徽章：Nav / 项目行 / 基础库区 / Tab 角标（§5.3）   │
│  ├→ 首页：「进行中」+「最近动态」（§5.4）               │
│  └→ 页面详情：页面级轮询承担详细进度（谓词 ← §5.8）     │
└──────────────────────────────────────────────────────┘
```

### 2.4 崩溃恢复：统一模式

#### 2.4.1 重启即中断

应用重启时所有 `processing` 类状态记录必然已中断（§1.3），启动时按模块扫描处置（main.py lifespan）：

```python
def on_startup():
    # 1. 任务：有 saved_state → 插入中断提示消息（不自动恢复，等用户）
    for task_id in db.list_tasks_with_saved_state():
        if not db.has_interrupt_marker(task_id):   # 防重复提示
            db.save_task_message(task_id, "assistant",
                "此任务在上次程序关闭时被中断。点击「恢复」可从上次中断处继续，或发送新消息重新开始。")

    # 2. 文件：parsing → 清理脏数据（ChromaDB/FTS/images）→ pending（无条件，整文件重跑）
    # 3. 图片：images.status='processing' → pending（无条件，单张重跑）
    # 4. Wiki：ingesting/storing → queued（无条件，断点续跑）
    db.reset_interrupted_compile_tasks()

    # 5. 报告：卡在 generating 且超 5 分钟 → 标 error（保 checkpoint，等用户「重新生成」）
    stale = db.recover_stale_generating_reports(timeout_minutes=5)
    for rid in stale:
        activity_events.fail_report(db, rid, "程序异常中断，可重新生成续跑")
        db.create_report_log(rid, "检测到中断报告，已标记失败，可重新生成续跑", level="warn")

    # 6. 模型下载：遗留 downloading 记录 → 标 failed + 发通知
    for dl in db.recover_stale_model_downloads():
        activity_events.fail_download(db, dl["name"], "程序异常中断")

    # 之后：QueueScanner（每 5s）自动拾起 pending 文件/图片 + queued 编译
    # → 文件/图片重跑、Wiki 按 ingest_summaries 断点续跑，全程无需用户操作
```

#### 2.4.2 两种收敛（规则四的展开）

| 收敛方式 | 适用 | 机制 | 为什么 |
|---|---|---|---|
| **自动续跑自愈** | 文件 / 图片 / Wiki | 重置 → 重新入队 → QueueScanner 拾起 | 本地推理零 API 费用、可确定性重放；「重置动作」本身就是状态收敛，无需标失败 |
| **标终态等用户** | 报告 / 任务 / 模型下载 | 标 error/failed + 通知，用户一键触发续跑 | token 费用/对话上下文/大流量需用户知情；不标终态则状态机永不收敛（如报告永久 generating → 看板永久转圈、页面轮询永不停止） |

#### 2.4.3 为何不设运行中超时看门狗（负决策）

**澄清**：报告的「generating 超 5 分钟 → 标 error」是**启动时**扫描（§2.4.1 第 5 步），**不是运行中的定时看门狗**——应用运行期间没有任何模块做任务级超时判定。曾设计过「运行中超时标 failed」（文件 10min / 图片 5min），已否决，理由：

| # | 理由 | 说明 |
|---|------|------|
| 1 | **判据不可靠，误杀合法慢任务** | 文件解析是本地重计算（大 PDF 可达 10min+），进度按阶段粗粒度推进，阶段间长时间无更新是常态。阈值低 = 误杀（标 error 后整文件重头跑，比等待更糟）；阈值高 = 形同虚设 |
| 2 | **标 error 不解决卡死根因** | 卡死本质是 worker 线程死/进程死；标 error 只是换个方式失败，用户仍要重跑。而「重启」本身就是可靠的超时信号——重启 → 启动扫描重置 → 自动续跑，无人自愈 |
| 3 | **报告的超时目的不同** | 报告不自动续跑，标 error 是其状态收敛手段（§2.4.2），文件类用重置收敛，两者不冲突 |

> 若未来确需运行时检测，合理形态是「心跳日志级检测」（worker 每阶段写日志，超 N 倍历史 P95 无日志才判死）；本地解析无历史 P95 积累，收益低于误杀风险，暂不实施（§10）。运行中真正 hang 住的用户出口：进度条停住 → 手动取消/重传/停止；下次启动时启动扫描重置残留。

#### 2.4.4 恢复的通知联动

- 启动扫描将中断报告标记 error 时、发现遗留 downloading 模型时 → **写 failed 通知**（应用离线期间发生的中断也能被感知）；均经 `activity_events` 框架 API（`fail_report` / `fail_download`，内部补 container）
- 文件/图片/Wiki 自动续跑 → **静默**（属「进行中」非终态）
- 任务中断提示 → 走会话内消息，不发全局通知

#### 2.4.5 不可恢复场景

| 场景 | 处理 |
|------|------|
| 文件解析：解析刚开始就崩溃（无部分进度概念） | 整文件从 pending 重跑（代价仅为重复解析） |
| Wiki 编译：项目已被删除 | 标记 failed，原因「项目已删除」 |
| 报告：无 checkpoint（第一节未完成即崩溃） | 用户「重新生成」时整篇从头跑（有 checkpoint 则跳过已完成章节） |
| 任务：DB 中无 agent_state | 无法恢复，用户重新发起对话 |

## 3. 数据存储

### 3.1 存储全景

六大长时活动的存储分四层，各自定位不可混用：

| 层 | 存储 | 定位 |
|---|---|---|
| 状态源层 | files / images / wiki_compile_tasks / reports 表；task_agent 内存集、model_manager 内存 dict | 「在不在跑」的唯一事实；注册表 fetch 的取数对象（§3.4） |
| 事件存储层 | notifications 表 | 「跑完了」的终态事件持久化；重启不丢、未读查重（§3.2） |
| 崩溃检测源 | model_downloads 表 | 内存态重启即丢，本表留痕供启动扫描判定（§3.3） |
| checkpoint 层 | task_agent_state / report_sections / ingest_summaries / task_messages | 断点续跑与恢复提示的依据（§3.5） |

外围波及存储（解析产物，崩溃重跑时清理脏数据）：ChromaDB 向量库 + chunks_fts（FTS5 虚表）。业务表全量 DDL 见各自设计文档：files/images → [2.2](2.2knowledge-base-design.md)、reports → [2.5](2.5report-design.md)、wiki_compile_tasks → [2.6](2.6wiki-design.md)。

### 3.2 notifications 表（事件存储层）

```sql
CREATE TABLE notifications (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    entity_type TEXT NOT NULL,   -- kind：task / file / wiki_compile / report / model_download
    entity_id TEXT NOT NULL,
    project_id TEXT,             -- 所属项目；任务/模型下载无项目时为 NULL
    container TEXT DEFAULT 'project', -- 挂载容器 project / baselib（§3.6 导航分流；task/model_download 无项目实体保持默认）
    kind TEXT NOT NULL,          -- completed / failed
    entity_title TEXT NOT NULL,  -- 展示名（用户数据，后端零文案，前端 i18n 渲染）
    detail TEXT,                 -- 自由文本（截 200 字符；结构化见 §10）
    read_at TEXT,                -- NULL = 未读；「弹出即已读」
    created_at TEXT NOT NULL
);
CREATE INDEX idx_notifications_unread ON notifications(read_at, created_at);
```

| 行为 | 规则 | 代码 |
|------|------|------|
| 写入 | 未读查重：同 `(entity_type, entity_id, kind)` 已有未读则跳过（幂等：同实体同状态重复声明不重复弹） | `add_notification` |
| 读 | 未读按时间**正序**（逐条弹出）；最近 N 条含已读**倒序**（首页动态） | `list_unread_notifications` / `list_recent_notifications` |
| 已读 | 批量按 id 标记 `read_at` | `mark_notifications_read` |
| 清理 | 启动时保留最近 100 条，防无限增长 | `cleanup_old_notifications` |

定位：**终态事件的持久化存储层**——重启不丢、未读查重天然幂等；后端零文案（表存 entity_title 用户数据，展示文案由前端 i18n 按 entity_type + kind 渲染，§6.5）。写入仅经 activity_events 框架（§6.4），业务模块 `add_notification` 零直调。

### 3.3 model_downloads 表（崩溃检测源）

```sql
CREATE TABLE model_downloads (
    name TEXT PRIMARY KEY,      -- 模型名
    status TEXT NOT NULL DEFAULT 'downloading',   -- downloading / completed / failed
    error TEXT,
    started_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

定位：**崩溃检测源**——进度不落库（内存态），启动扫描 `recover_stale_model_downloads` 把遗留 `downloading` 标记为 failed（提示用户重新下载）。正常进度查询走 model_manager 内存（§3.4），不查本表。

### 3.4 活动状态源清单（注册表五源，覆盖六大长时活动：file 源含文件解析与图片描述）

| kind | 状态存放 | fetch 实现 | 活跃条件 |
|------|---------|------|----------|
| file | files 表 `status` + `image_status` | `_active_files` | `status IN (pending, parsing)` OR `(done AND image_status IN (pending, describing))`（图片描述期全局指示不断档） |
| wiki_compile | wiki_compile_tasks 表 `status` | `_active_compiles` | `status IN (queued, ingesting, storing)` |
| report | reports 表 `status` | `_active_reports` | `status = 'generating'` |
| task | task_agent 内存集 `_running_task_ids` | `_active_tasks` | 运行集非空 |
| model_download | model_manager 内存 dict `_downloads` | `_active_model_downloads` | `dl.downloading = True` |

**基础库同构覆盖**：基础库与项目共用数据模型（`projects.kind='base_lib'`，[2.7](2.7baselib-rag-design.md)），file 与 wiki_compile 源的 SQL 不过滤 kind——基础库的文件解析 / 图片描述 / Wiki 编译活跃时进入**同一 kind** 的 active 名单（project_id / project_name 为基础库行），summary 计数同理。基础库不是第七种活动；其交互区分设计见 §5.7。

### 3.5 checkpoint 与恢复存储

| 存储 | 内容 | 写入时机 | 恢复消费 |
|------|------|---------|---------|
| `task_agent_state`（state_json + paused_at） | 完整 LLM messages + iteration 序号 + recent_errors | 每次迭代完成 | 启动扫描插入中断提示；用户点「恢复」后从最后完成 iteration 续跑 |
| `task_messages` | 会话消息（role/content/metadata） | 每条消息；恢复时写中断提示 | 切回任务页重建会话；中断提示展示 |
| `report_sections`（content + status，节级） | 每节产出内容/字数/状态 | 每节完成 | 「重新生成」跳过已完成章节 |
| `wiki_compile_tasks` 内 `ingest_summaries` | 每文件摄入摘要 | 每文件摄入完成 | 断点续传跳过已完成文件；`is_resumed` 恢复检测 |
| `reports` 表 checkpoint 列（token_usage 等） | 逐节 token 消耗等 | 逐节更新 | 恢复后统计续接 |

## 4. 数据流

### 4.1 D1 · 读路径①：全局心跳快照（活跃状态 + 终态事件，5/15s）

```
ActivityMonitor ─IPC activities:getStatus─▶ GET /activities/status
  ─▶ registry.snapshot() 逐源 fetch 合并「当前在跑名单」
  ─▶ db.list_unread_notifications / list_recent_notifications(10)
  ─▶ 汇总 summary 五字段 ─▶ 响应（结构见 §3.6）
  ─▶ 前端 ActivityContext.applyStatus ─▶ 反馈面重渲染 + useActivity 订阅者谓词翻新
```

### 4.2 D2 · 读路径②：页面明细查询（进度细节，页面自治）

```
页面 usePolling（enabled = useActivity(kind).isActive 派生，全局心跳驱动）
  ─▶ IPC 明细通道（models:status / files/active / reports/{id} …）
  ─▶ 页面本地 state ─▶ 进度条 / 逐项状态
```

明细端点**不在本模型内**——页面自治是边界（§1.2 第 3 条）；本模型只决定 D2 的开关何时开。谓词派生标准形态与两条时序约定见 §5.8 / §6.3。

### 4.3 D3 · 写路径：状态流转

**状态持久化归各业务模块自身的状态更新函数**（`update_file_status` / `update_report_status` / `update_compile_task_status` 等，均为纯状态更新，无内嵌通知钩子）；**终态事件归 activity_events 框架统一收口**——业务在终态处声明 `complete_*` / `fail_*`，框架一次完成通知写入（notifications）+ SSE 事件投递（§6.4），业务不感知投递细节。

### 4.4 D4 · 事件路径：终态通知

- **写入**：终态事件统一经 activity_events 写入 notifications 表（去重幂等见 §3.2），通知携带 `project_name` 与 `container` 容器事实（`notifications.container` 列，§3.2），前端不再反查；
- **投递**：全局 `activity:stream` SSE 推所有 kind 终态（推为主），心跳拉兜底；`task:stream` 保留为任务高频流式输出，终态归全局流。三层通道：Python `GET /activities/stream`（15s keep-alive 注释行；断连 finally 反注册）→ Electron `activities:subscribeStream` 转发 `activity:stream`（断线退避重连 2s→15s 封顶，同 sender 去重防双流）→ ActivityMonitor 事件仅作「立即心跳」触发信号（200ms 节流合并风暴；Toast/基线/markRead 与轮询共享同一实现，避免逻辑分叉），心跳拉照旧兜底（事件丢帧/重启窗口）；详见 §6.4。

### 4.5 端到端时序（T0-T5，一次模型下载）

- **T0 点击**：`handleDownload` → `invoke('models:download')`（后端起线程 + 同步置内存 `downloading`）→ **立即手动拉一次明细**（启动间隙约定，§6.3）；
- **T1 心跳查到**：Monitor 下一圈 → D1 → model_download 源返回 `bge-m3, progress 40` → summary.downloading_models=1；
- **T2 谓词翻真**：`useActivity('model_download')` items 非空 → 明细轮询自动开始刷进度条；
- **T3 启动间隙**：T0 的手动拉取填补心跳粒度空窗，随后全局接管；
- **T4 完成**：线程推 100 → 写 notifications + SSE 投递 → 清内存标记 → 下一心跳名单移除（SSE 事件触发立即心跳则更早）→ Toast（Monitor 带回）→ 谓词翻假 → 轮询自动停；
- **T5 失败同理**：error 通知 + 内存清位 → 轮询停。谓词不记历史只看现在，不会像手动布尔那样卡死。

## 5. 前端交互

### 5.1 四反馈面

**设计动机**：六大长时活动后端互相独立且不依赖前端，若反馈只挂在页面内轮询上，用户切走页面后完成/失败无人感知（反馈断链）。统一活动中心修复：后端聚合活跃状态 + 持久化终态通知，前端单一常驻监控分发到全部反馈面（架构图见 §2.3）。

| 反馈面 | 界面位置 | 回答的问题 | 出现时机 |
|--------|----------|-----------|----------|
| **Toast** | 右下角浮层，任意页面可见 | 「刚刚发生了什么需要我知道？」 | 仅终态时刻，弹出即已读，点击直达源头 |
| **徽章** | 侧栏三层（§5.3） | 「现在有没有东西在跑/在等我？」 | 持续性，活跃期间一直在 |
| **首页** | 「进行中」卡片区 + 「最近动态」列表 | 「全局概览如何？」 | 常驻展示 |
| **页面详情** | 各功能页内（进度条/编译对话框/日志面板） | 「具体过程细节如何？」 | 用户进入页面时 |

### 5.2 主界面布局

```
┌─ 侧栏（常驻） ──────────┬─ 内容区（随 Nav 切换） ───────────┐
│ NavTabs                  │                                  │
│  ├ 首页                  │  Toast = 右下角浮层               │
│  ├ 任务           [L1 n] │  （任意页面可见，弹出即已读）        │

│                          │  ┌─ 首页（home Nav） ──────────┐ │

│  ├ XX科技   ● 活跃呼吸点  │  │ 「进行中」活动卡区（活跃时）     │ │
```

### 5.3 徽章体系（三层）

| 层级 | 位置 | 内容 | 触发条件 | 数据源 |
|------|------|------|----------|--------|
| L1 全局导航 | NavTabs「任务」 | 运行中任务数（数字） | `summary.running_tasks > 0` | ActivityContext |
| L1 全局导航 | NavTabs「项目」 | 活跃旋转图标 | `activeProjectIds` 非空 | ActivityContext |
| L1 全局导航 | 设置入口（齿轮） | 下载中呼吸点 | `summary.downloading_models > 0` | ActivityContext |
| L2 项目列表 | 项目行 | 活跃呼吸点 + hover 概要（如「Wiki 编译中 3/8」） | 该项目存在活跃活动 | ActivityContext |
| L2 项目列表 | 基础库区行（BaseLibFooter，常驻底部） | 活跃呼吸点（与项目行对齐） | 该基础库存在活跃活动 | ActivityContext |
| L3 详情页 Tab | 素材 | 活跃文件数（数字） | `active_files > 0`（含图片描述期） | ActivityContext |
| L3 详情页 Tab | Wiki | 编译中（呼吸点） | 编译中 | ActivityContext（心跳） |
| L3 详情页 Tab | 报告 | 生成中报告数（数字） | `generating_reports > 0` | ActivityContext |

**运行机制**：

- **刷新延迟上界 = 一个轮询周期**：非实时推送，活跃期最旧 ≈ 5s、空闲期 ≈ 15s；终态事件另有 `activity:stream` 推送触发立即心跳（§6.4，终态 Toast 亚秒级），两者互补
- **数字 vs 呼吸点**：数字 = 需关注/行动的可数实体（任务数、活跃文件数、生成中报告数）；呼吸点 = 纯活跃指示（知道「在干活」即可）
- **点击语义**：L1/L2 仅指示不可点；L3 角标与 Toast 共享导航事件（`app:navigate-project-tab`）

**为什么三层缺一不可**：

| 层 | 回答的问题 | 若缺失 |
|---|---|---|
| L1 全局 Nav | 「整个应用有没有动静」 | 任务页/首页看不到项目在干活（L2 仅项目 Nav 下可见） |
| L2 项目列表 | 「哪个项目/基础库在干什么」 | 多项目时无法定位活跃源 |
| L3 Tab 角标 | 「这个项目的哪类事有多少」 | 进入项目后需逐 Tab 翻找未处理量 |

### 5.4 首页活动区

- **「进行中」**（服务状态与快捷操作之间，无活跃活动时整块隐藏）：每卡 = entity_type 图标 + 项目名/实体名 + 概要（count/进度）；任务/模型下载以无项目独立卡入区；点击直达（`app:navigate-project-tab` / 任务页 / 设置页）
- **「最近动态」**（recentGrid 右列，与最近项目并排）：最近 10 条通知（含已读），kind 状态点 + i18n 文案 + 相对时间；点击直达；空态占位文案

### 5.5 Toast 触发与已读策略

| 规则 | 说明 |
|------|------|
| 触发 | ActivityMonitor 轮询发现 `unread` 非空 → 逐条弹出 |
| 类型映射 | completed → success / failed → error |
| 动作按钮 | 「前往查看」按 entity_type 路由：file / wiki_compile / report → 按 `container` 分流项目 Tab 或基础库详情页（`app:navigate-project-tab`）；task → 任务页（`app:navigate-tasks`）；model_download → 设置页 |
| 已读 | **弹出即已读**（立即批量 markRead）；无未读管理 UI，首页「最近动态」仅历史展示 |
| 防重弹 | 内存 Set(通知 id) 会话内防重 + read_at 跨会话防重；首次拉取只建基线不弹（防启动历史轰炸） |
| 频控 | 同周期多条逐条弹出；超 5 条合并为汇总 Toast（「3 个任务已完成」） |

### 5.6 事件→反馈面时间线与切页行为

以「上传 3 个文件后切走去首页」为例：

| 时刻 | 后端 | 徽章 | 首页 | Toast / 页面详情 |
|---|---|---|---|---|
| T0 上传 | 3 × pending | 项目行呼吸点亮起；素材 Tab 角标 3 | 「进行中」出现文件卡 | （在素材页）进度条排队中 |
| T1 解析中 | 1 parsing / 2 pending | 同上，hover 提示「文件解析 1/3」 | 卡片概要「文件解析 3 个」 | （已切走）页面轮询停止，后端继续 |
| T2 全部完成 | done ×3 | 呼吸点 / 角标消失 | 「最近动态」追加 ✓ 记录 | Toast「文件《xx》解析完成」；点进素材页看详情 |

**切走与切回**：

- **切走**：页面级轮询停止（组件卸载）；后端任务继续、状态/日志持续写 DB；徽章/首页/Toast 由 App 级 ActivityContext 驱动，不随页面卸载中断
- **切回**：一次性拉取最新状态 → 重建轮询（间隔自适应）→ 有日志面板则重新拉取并随轮询刷新（报告日志倒序 tail / 任务日志 tail，§8.3）
- 任务模块特例：切走时流式状态缓存到 `bgStates`（Map），后端 SSE 继续推送；切回恢复缓存，无缓存则从 DB 重建。见 [1.1](1.1task-agent-design-unified.md)。

| HomePage | `useActivity()` | status / feed | 活动区进行中计数 + 最近动态列表 |
| InternalModelSettings | `useActivity('model_download')` | isActive（任一下载中） | 模型列表明细轮询开关（进度条） |
| ActivityMonitor | `useActivity()` | applyStatus / markRead / summary | 无渲染；唯一写入者 + Toast 派发者（规则见 §5.5） |

**Toast 派发**：ActivityMonitor 独有职责，页面不自产完成提示——检测 / 类型映射 / 防重弹（含首拉基线）/ 频控合并 / 已读时机 / 点击导航路由，统一规则见 §5.5。

**状态-界面映射**（用户视角：一种活动从起到终，在哪些界面看到什么）：

| 活动阶段 | 全局面（所有页面可见） | 活动所在页面（明细） |
|---------|---------------------|-------------------|
| 触发瞬间（点击） | — | 触发动作后立即手动拉一次明细（启动间隙约定，§6.3），进度条不等心跳 |
| 排队/执行中 | 项目/基础库活跃点亮；Tab / 首页计数 +1 | 在跑名单含本 kind → isActive 翻真 → 明细轮询自动开启（进度条/逐项状态） |
| 完成/失败 | Toast 弹出；首页最近动态 +1 | 在跑名单移除 → isActive 翻假 → 明细轮询自动停，无残留状态 |

**交互不变量**（前端交互的验收标准）：

1. 明细轮询的启停对用户透明：谓词从 `useActivity(kind)` 派生，自动开停，无手动开关、无卡死；
2. 一个事件、四个反馈面同源：心跳带回 → Context 更新 → 徽章 / 活跃点 / 动态同帧重渲染，Toast 由 Monitor 统一派发，任何页面不得自建「完成提示」；
3. 明细刷新节奏归页面自治（如 models/status 1s），本模型只约束开关与全局状态一致，不约束内容。

**同构数据的交互区分设计**（基础库与项目数据同构、非独立 kind——区分是前端呈现职责，靠容器类型字段衔接。裁决原则：**后端提供事实（id / name / container），前端按容器分流**）：

| 交互面 | 区分机制 |
|--------|----------|
| active 名单 / summary 计数 | 故意不区分——全局面只答「有没有活动」，不关心挂在哪个容器 |
| byProject 聚合 | 天然区分——Map 按 id 分桶，ProjectList / BaseLibFooter 各查各的桶 |
| 页面明细 | 天然区分——ProjectDetailPage 与 BaseLibDetailPage 本就是两个页面，各自轮询 |
| 首页动态（进行中） | 条目带 project_name →「{{project}}：N 个文件处理中」 |
| 终态 Toast | 文案带容器参数（通知携带 project_name + container，§4.4） |
| 点击导航 | 容器决定路由目标（项目 Tab vs 基础库详情页），读 `container` 字段分流 |

**容器类型契约**：`_active_files` / `_active_compiles` / `_active_reports` 输出 `container: 'project' \| 'baselib'`（DB 真值 `p.kind` 为 `base_lib`，SQL 层 `CASE WHEN` 归一化后直出，契约见 §6.1）；通知侧 `notifications.container` 列同理（§3.2）。已否决：前端包含性判断（projects 未加载完时时序误判）、id 前缀推断（自定义库为 uuid，不可靠）。

### 5.8 页面轮询治理规则

**轮询 = 组件生命周期绑定的定时任务。** 全部网络轮询经统一 hook `usePolling`（src/hooks/usePolling.ts）实现，随宿主组件挂载启动、卸载注销。启动条件四级分类：

| 级别 | 含义 | 覆盖 |
|------|------|------|
| 常驻 | App 挂载期始终运行 | #0 全局心跳 |
| 活跃谓词 | 挂载期 + `enabled` 一律从 `useActivity(kind)` 全局心跳派生，禁止自建手动布尔 | 全部明细轮询 |
| 页面挂载期 | 宿主组件卸载即停，无谓词 | 日志查看器 |
| 手动开关 | 用户显式控制 | 任务执行日志 |

**切页时序**（机制示例）：素材页有文件解析中（#5 enabled=true，2s）→ 切到任务页 → `KnowledgePage` 卸载，usePolling cleanup 注销 #5；任务页挂载，#2 启用（3s）；#0 照常运行。素材解析在后端继续：#0 聚合端点维持概要（项目行/首页/角标），终态经 notifications 表投递 Toast；切回素材页时 #5 重新挂载、谓词重新求值，拉取最新状态接上进度条。**看哪盯哪（页面级细节），不在的兜底（全局概要 + 完成事件）。**

**统一实现约定**（全部轮询一致）：

- 防重叠：上一次调用未返回不发起下一次（setTimeout 链式调度）；在飞期间立即触发（visibilitychange / SSE kick 等）不并发启动，仅标记完成后 0ms 补一轮（inFlight / rerunAfter 守卫，防轮询链分叉与空转 timer 叠加）；
- 失败退避：连续失败指数拉长间隔（封顶 60s），成功复位；
- 可见性：ActivityMonitor 不可见时降频 45s **仍真实拉取**，禁止 hidden 早退跳过（Windows Chromium 窗口遮挡检测会把被完全遮挡的窗口判为 hidden，早退曾致心跳死区：下载进度冻结 0%、呼吸点不出现、Toast 延迟到窗口置前），并监听 `visibilitychange` 恢复可见立即拉取；页面级 usePolling 同规则：hidden 按倍数降频仍真实拉取，回前台立即刷新；
- 防挂起：单次调用未在时限内 settle 视为失败（退避重试）——ActivityMonitor invoke 8s / usePolling task 15s（`taskTimeoutMs` 可配）；Electron 侧 `ipc-handlers.js` 统一 `fetchWithTimeout`（默认 15s，上传 120s / LLM 测试连接 60s / zip 导出 60s，SSE 流转发豁免）。背景：Uvicorn 默认 5s 关闭空闲 keep-alive 连接，Node fetch 复用半关闭 socket 且无默认超时会永久挂起；
- 教训：轮询循环体内禁止 return 跳过末尾调度——曾致 ActivityMonitor 首次拉取后循环死亡（表观轮询实为 effect 重建反复首拉），回归用例 tests/ActivityMonitor.test.tsx「keeps polling when invoke hangs forever」防复发。

纯 UI 计时器（倒计时/耗时显示，非网络轮询）不经 usePolling、不入台账（分账原则；现状清单见 §8.1）。

## 6. 接口契约

### 6.1 后端注册表（python/activities_registry.py）

| 成员 | 契约 |
|------|------|
| `ActivitySource` 协议 | `kind: str` + `fetch() -> list[dict]` |
| `register(source)` | 同 kind 后注册覆盖（热替换 / 测试隔离） |
| `unregister(kind)` | 不存在时静默 |
| `snapshot()` | 全源快照按 kind 排序合并；**单源异常只降级本源为空**，不影响其余源、不抛出 |
| `FunctionSource(kind, fetch_fn)` | 轻量包装；`fetch_fn` 必须以 lambda 引用模块级函数（运行时名字查找），保证测试 monkeypatch 生效 |

条目 dict 契约：至少含 `entity_type`（= kind，与 notifications.entity_type 一致）；可选 `entity_id / project_id / project_name / entity_title / count / status / progress_text / progress / container`。`container`（`'project' \| 'baselib'`，DB 真值 `base_lib` 经 SQL 层 CASE 归一化）：容器类型，file / wiki_compile / report 三 SQL 源必带（JOIN projects 现成顺带输出；前端导航分流 / Toast 容器文案的裁决依据，§5.7）；task / model_download 无跨容器场景，不带。`fetch()` 只读快照，禁止副作用。

路由侧约束（routers/activities.py）：活跃侧**只从注册表取**，禁止再往该文件加私有聚合函数；新增长时活动一律实现 ActivitySource 后注册。

### 6.2 前端 hook（src/features/activity/ActivityContext.tsx）

| 调用 | 返回 | 语义 |
|------|------|------|
| `useActivity()` | 全量 Context（status / summary / byProject / feed…） | 全局反馈面取数 |
| `useActivity(kind)` | `{ kind, items, isActive }` | 按 kind 过滤全局心跳快照；items 粒度 = 心跳 5/15s |

页面级明细轮询标准形态（唯一写法）：

```ts
const { items } = useActivity('model_download')
usePolling({ enabled: items.length > 0 /* 全局派生，禁手动布尔 */, task: fetchDetails })
```

### 6.3 两条时序约定及原因

| 约定 | 原因 | 示例 |
|------|------|---------|
| **启动间隙**：触发动作后立即手动拉一次明细 | 心跳 5/15s 粒度，点击后头几秒 `useActivity(kind)` 尚未翻真，进度条不能空白 | `handleDownload` 末尾 `await fetchStatus()` |
| **终态边沿**：谓词翻 false 时若终态标志在快照之外，补拉一次明细 | 心跳停轮与最后一次快照间存在窗口，终态渲染可能滞留一个轮询间隔 | `useEdgeRefetch(enabled, refetch)` 公共 hook（src/hooks/useEdgeRefetch.ts），落地七处：InternalModelSettings / KnowledgePage / ImageGallery / ReportPreview（正文+日志双补拉）/ ProjectDetailPage / ReportsTab / TaskStatusMonitor，各自带回归测试 |

事件推送（§6.4）将终态感知延迟压缩到 200ms 节流窗口内，但两条约定仍保留——启动间隙补拉保证点击后进度立即上屏（不等事件/心跳），终态边沿补拉作为事件丢帧与心跳间隔内的兜底（事件流断连重连窗口、后端重启窗口）。

### 6.4 终态事件框架（activity_events）与全局事件流

**框架统一终态 API**（python/activity_events.py）：业务在终态处只声明 complete / fail，框架一次完成事件存储（notifications 表）+ 事件投递（SSE）；状态持久化仍归业务自身的状态更新函数（纯状态更新，DB 层不设内嵌通知钩子，§4.3）。

| kind | API | 语义要点 |
|------|-----|---------|
| file | `complete_file(db, file_id, detail=None)` / `fail_file(db, file_id, error_message=None)` | detail 可携带降级说明（如 Office→PDF 转换回退内置解析，§7.4）；文本截 200 字符；文件已删静默跳过 |
| report | `complete_report(db, report_id, detail=None)` / `fail_report(db, report_id, error_message=None)` | error_message 由调用方显式传入，不回读 reports.error_message 列（避免读列早于错误落库的时序问题） |
| wiki_compile | `complete_compile(db, task_id)` / `fail_compile(...)` | 项目已删时 LEFT JOIN 回退、通知照发 |
| task | `complete_task(db, task_id)` / `fail_task(db, task_id, error_message=None)` | project_id / container 恒空（前端导航固定任务页）；title 查表，查无静默跳过 |
| model_download | `complete_download(db, name)` / `fail_download(db, name, error_message=None)` | 无项目实体（导航固定设置页内部模型锚点）；model_manager 经 `_notify_download` 薄委托 |

**统一收口 `_store_and_publish`**：`add_notification` 的唯一生产调用点（写入含 container 容器事实）→ 查重跳过时**同步跳过投递**（前端已见或即将见到）→ `_publish` 投递全部 SSE 订阅者。事件写入失败不影响业务主流程（状态已落库，通知是增益，各 `_emit_*` 内部 try/except 降级为日志）。

**投递机制（线程安全）**：写入方多为 worker 线程（pipeline / task_queue / task_agent / 下载线程），而 `asyncio.Queue` 非线程安全——订阅者按 `(loop, queue)` 注册，经 `loop.call_soon_threadsafe` 投递；慢消费者队列满即丢弃不反压（`_QUEUE_MAX=200`，心跳拉兜底）；单订阅者异常不影响其余。

**SSE 三层通道（`activity:stream`，推为主 / 心跳拉兜底）**：

| 层 | 通道 | 机制 |
|----|------|------|
| Python | `GET /activities/stream` | StreamingResponse；15s 无事件发 `: keep-alive` 注释行防中间层掐空闲连接；客户端断开由 uvicorn 取消生成器 → finally 反注册 |
| Electron | `activities:subscribeStream` → 渲染进程 `activity:stream` | fetch + reader 手工解析（对标 task:stream 先例）；AbortController + sender.destroyed 清理；同 sender 去重防双流；断线退避重连 2s→15s 封顶 |
| 前端 | ActivityMonitor 事件订阅 | 事件**仅作「立即心跳」触发信号**（pollKick 200ms 节流合并事件风暴），不做第二套解析；Toast / 首拉基线 / markRead 与轮询共享同一实现，避免逻辑分叉 |

事件体 = notifications 行（含 id / entity_type / kind / detail…）。`task:stream` 保留为任务高频流式输出通道，终态事件归全局流。

### 6.5 通知策略与 i18n

- **去重**：写入前查同 `(entity_type, entity_id, kind)` 且 `read_at IS NULL` 的记录，存在则跳过
- **清理**：保留最近 100 条，启动时清理更早记录
- **后端零文案**：表存 entity_title（用户数据），展示文案由前端 i18n 按 entity_type + kind 渲染

**i18n 文案 key 全表**（zh / en 同构）：

### 6.6 新增长时活动接入清单

> **接入路径（强制）**：活跃侧必须实现 ActivitySource 并注册（通常一行 FunctionSource，§6.1），页面轮询谓词一律 `useActivity(kind)` 派生——**禁止**绕过注册表自写聚合函数、禁止自建 enabled 手动布尔；契约与验收信号见 §6.1 / §8.4。

生命周期语义按本档规则：

1. 定义状态机（含终态枚举）并落 DB，同时确定崩溃恢复语义（自动重置重入队，或标记 + 等用户，§2.4.2）

4. i18n 补 `activity.<type>.<kind>` 文案（zh / en，§6.5）
5. 徽章落点（§5.3）与首页卡片图标（§5.4）按需接入

## 7. 初始化与前置条件（Readiness）

过程性生命周期（§1-§6）解决「运行后」的状态与反馈；准入性生命周期解决「运行前」——功能依赖未就绪时，用户能否得到显式、友好、可行动的引导。

### 7.1 问题：准入性缺口

| # | 层 | 仅事后报错的缺口 |
|---|---|------|
| R1 | 数据层 | `/health` 4 服务检查是服务视角（code + 文本 suggestion），无**功能视角**依赖矩阵（「生成报告需要什么」未定义）；VLM 被当全局必需，实际仅影响图片描述 |
| R2 | 应用级 | 首页状态卡若纯展示、suggestion 无锚点直达，则用户见红卡不知从何下手；无首次启动引导 |
| R3 | 功能入口 | 无前置校验时，LLM 未配可进报告向导走到一半才失败；embedding 缺失可上传文件 → 逐文件 error（技术化错误信息） |
| R4 | 运行时 | useErrorHandler CONFIG/CREDENTIAL → 跳设置的兜底依赖 LLM 调用失败才触发，入口 API 本身无校验 |

### 7.2 功能就绪度模型

`GET /health` 扩展 `features` 段（功能 → 依赖矩阵，必需 / 可选分级；python/readiness.py `_FEATURE_MATRIX` + `compute_features`）：

| 功能 | 必需依赖 | 可选依赖（缺失时降级） |
|------|----------|------------------------|
| file_parsing（上传解析） | parsing 模型（docling-layout-heron + tableformer-v2）+ embedding 模型（bge-m3） | VLM 配置（缺失 → 图片描述失败，文本解析不受影响，配置后可 retry） |
| wiki_compile | LLM 配置 + embedding 模型 | — |
| report | LLM 配置 + embedding 模型 | — |
| task | LLM 配置 | — |
| knowledge_search（基础库/检索） | embedding 模型 | — |

```jsonc
"features": {
  "file_parsing": {
    "ready": false,
    "missing": [{"kind": "model", "id": "bge-m3", "action": "settings:internal"}],
    "optional_missing": [{"kind": "config", "id": "vlm", "action": "settings:external", "impact": "image_description"}]
  },
  "report": {
    "ready": false,
    "missing": [{"kind": "config", "id": "llm", "action": "settings:external"}]
  }
}
```

- `action` 编码：`settings:external`（设置 > 外部模型锚点）/ `settings:internal`（设置 > 内部模型锚点），前端映射为直达导航
- readiness 为低频数据（配置 / 模型变化才变），复用现有 `system:getHealth` 轮询通道；功能入口检查读前端缓存，**不新增轮询**；入口校验 `ensure_ready` 走 10s TTL 缓存（`get_features_cached`），`/health` 端点不走缓存（用户刚改完配置立即反馈）

### 7.3 三层准入防御

**第一层【应用级】首次启动引导（一次性向导）**

- 首次判定：无 `api_key` && 无已下载内部模型 && 无项目 && 无任务（任一有数据视为老用户，不弹）
- 流程：欢迎页 → ① 配置 LLM（直达设置外部模型锚点，可跳过）→ ② 下载内部模型（直达内部模型页 + 一键「全部下载」，可跳过）→ ③ 进入首页
- `onboarding_done` 写入 settings 表，此后不再弹；全部步骤可跳过（不强制配齐）

**第二层【功能入口】事前引导弹层（不硬禁用）**

触发点：素材上传 / 知识检索 / Wiki 编译 / 报告生成入口 / 任务发送（useFeatureGuard，落地于 KnowledgePage / ReportWizard / WikiTab / TaskChatView 四组件）。点击时读就绪度缓存：

- 缺必需项 → 轻量引导弹层：「该功能需要 X」+ 动作按钮（「去配置」/「去下载」，锚点直达）+「取消」
- 仅缺可选项（VLM）→ 放行操作 + 提示条「图片描述将失败，可稍后在设置中配置 VLM」
- 原则：按钮保持可点击（禁用为反模式——避免死界面、允许探索）；配置完成返回后缓存刷新即可用

**第三层【运行时兜底】入口 API 前置校验**

upload / compile / generate / send 等入口 API 加前置检查（`ensure_ready(feature)`，readiness.py），未就绪时抛结构化 CONFIG 类 InkCubeError → 前端 useErrorHandler 弹错 + 跳设置（链路已有）。防御 IPC 直调 / 缓存过期的绕过路径。

覆盖范围：不止首入口——**所有因缺配置而必然失败的入口同等拦截**，含重试/继续类（报告 retry、文件 retry / retry-failed / batch-reprocess、Wiki compile、单页 retry）、独立组合入口（知识库问答：embedding + LLM 双依赖，以 `ensure_ready("knowledge_search")` + `ensure_ready("task")` 复合实现，不新增矩阵项）、Wiki 衔接 LLM 端点（lint 按 mode 条件拦截：semantic/full 拦、structural 纯本地放行；dedup-detect / dedup-merge / enrich-wikilinks LLM 必需；sweep-reviews 为 LLM 可选降级设计、overview 为纯 DB，核实后豁免）。豁免：图片 retry（VLM 为可选依赖，事中显式已闭环）、纯本地操作（export / 归档 / 任务文件上传）。

调用约定：`ensure_ready` 必须放在端点函数 try 块**之外**——`InkCubeError` 需直接冒泡到全局 handler 转结构化响应；放入 try 块会被 `except Exception → HTTPException(500)` 吞掉结构化字段，前端退化为不可行动的通用错误（端点级回归测试防此回归）。

分层职责：后端 ensure_ready = 必达防线（全入口，防漏防绕过）；前端 useFeatureGuard = 体验增强（高频入口的模态弹层，不再扩张）。前端 guard 判定数据源即后端就绪度矩阵（/health features），单一真相在后端。

### 7.4 运行中配置类错误与降级的显式引导

三层防御覆盖「事前」；本节覆盖「事中」——运行过程中配置劣化（Key 失效 / 欠费 / 限流 / 模型名错）与设计内降级（Tavily 不可用、Office 转换缺失）不能静默：文案必须自带修正指引，且呈现在用户可见界面（日志是专业兜底，显式呈现是默认要求）。仅文字级，不做运行中挂起 / 自动恢复。

**错误分类与可行动文案（结构化错误体系）**

- `llm/client.py::_raise_api_error` 统一三路径（chat / chat_full / chat_stream）非 200 分类：401→LLMInvalidKey / 429→LLMRateLimited / 402・403→LLMQuotaExhausted / 404→LLMModelNotFound（均 CREDENTIAL，message+suggestion 自带「设置 > 外部模型」指引）；400+tools 保留 function calling 提示；其余 LLMCallFailed。
- `errors.actionable(e)` 为所有后台任务失败落库统一入口：InkCubeError 拼 `message。suggestion`，其余透传。落库点全覆盖：任务聊天（task_agent `_llm_error_msg`，网络类保留 ⏱️ 超时 / 🔌 连接双分支文案）、报告（runner error 事件 + reports.py error_msg）、报告软失败（card_builder reason）、Wiki 编译（task_queue 终态 + 逐文件失败摘要 ingest_summaries）、VLM 图片、文件解析（pipeline + task_queue 兜底）。
- 配置/凭据类错误重试无意义：runner `_generate_with_retry` 结构化类优先三分支（配置类 fatal / 限流网络 retry / 字符串规则兜底）；Wiki 连续编译单文件失败不重试、不中断队列（actionable 摘要入 ingest_summaries，修正凭据后重新编译即重跑失败文件）。

**降级显式呈现（不静默）**

- 报告检索：`retrieval.py` 通道契约为三元组 `(results, usage, warnings)`；Tavily 失败（401/403 Key 无效、402 额度、429 超限、网络不通、服务异常）经 `_tavily_failure_warning` 生成带指引文案（set 去重），`RetrievalResult.warnings` → runner `ProgressEvent("warning")` → reports.py 写 `create_report_log(level="warning")`，报告详情页日志区可见；总开关开启但 Key 缺失在 `_prepare` 后即预警。
- 报告章节降级：材料不足但章节以分析推理模式继续时，runner `section_done` 事件携带 `degraded` 标记，reports.py `_section_done_log` 写 warning 级日志「章节降级： X（材料不足，已以分析推理模式生成，内容可能缺乏数据支撑，建议补充项目材料后重新生成）」——非 optional 章节无材料不再静默显示"章节完成"（skipped 优先于 degraded，跳过比降级更终态）。
- 文件解析：Office→PDF 转换不可用 / 失败回退内置解析器时，降级说明随 `ParseResult.metadata["warnings"]` 上抛 → `activity_events.complete_file(detail)` → completed 通知 Toast 显式呈现（§6.4）。
- 前端零新增：报告日志 warning 渲染（ReportPreview `log_${level}` 样式分支）与通知 Toast detail（ActivityMonitor）均为既有能力。

### 7.5 呈现增强

- 首页服务状态红卡可点击 → 直达设置对应区块（对齐设置页 HealthStatus「去修复」模式，复用 `app:navigate-settings`）
- `/health` 的 suggestion 文本动作化：文案保留，点击行为 = 按 action 编码导航

### 8.2 终态通知写入点

六 kind 全部经 `activity_events` 框架声明终态（通知携带 container；业务模块 `add_notification` 零直调）：

| 模块 | 触发时机 | kind | 写入位置 |
|------|----------|------|----------|
| 文件解析 | 单文件到达 done / error | completed / failed | `activity_events.complete_file / fail_file`（pipeline / task_queue 显式声明） |
| 图片描述 | 不单独通知（文件级已覆盖，避免噪音） | — | 单图状态页面内可见 |
| Wiki 编译 | 终态 | completed / failed | `complete_compile / fail_compile`（V2 连续路径 task_queue.py 显式声明；stopped 用户主动静默不发） |
| 报告 | 终态 done / failed | completed / failed | `complete_report / fail_report`（reports.py 事件循环显式声明，fail 显式携带 error_msg；崩溃恢复 main.py 同） |
| 任务 | 终态 done / error | completed / failed | `complete_task / fail_task`（task_agent run() finally 显式声明；user_stopped 含 pause 静默不发；task title 查表，查无静默跳过） |
| 模型下载 | 单模型到达终态 | completed / failed | `complete_download / fail_download`（model_manager `_notify_download` 薄委托） |
| 崩溃恢复 | 启动扫描标记中断报告 / 遗留下载 | failed | `fail_report`（main.py，内部 JOIN 补 container）/ `fail_download`（main.py） |

> 不发通知：用户主动操作（cancelled/stopped/paused）静默；「开始」事件不通知。（与规则 §1.5 二一致。）

### 8.3 进度日志存储三分

过程日志不统一建模，按消费者语义分流（统一表是形式统一，不减少任何前端代码；本档统一的对象是「活动状态 + 终态通知」，过程日志不在其列）：

| 落点 | 形态 | 消费者 / 场景 | 选型依据 |
|------|------|------|------|
| 报告 | `report_logs` 表（FK CASCADE + (report_id, created_at) 索引 + level 结构化） | 报告详情页日志面板：面向用户的过程叙述（章节进度、降级 warning 显式告知 §7.4） | 需持久回放（完成后可查）+ 结构化 level 过滤 |
| 任务 | `data/tasks/{id}/execution.log` 文件（`GET /tasks/{id}/logs` tail，#10 手动开关） | 任务详情日志 Tab：技术排查 agent 行为（工具调用 input/result 预览/duration） | 高频追加（单任务数百行 × 2000 字符截断）+ tail 读取 + 随任务目录删除自动清理（入 DB 反需清理机制且与业务写竞争单写锁） |
| 文件/图片 | 无逐条日志，status + progress 字段推进 | 进度条 + 全局心跳 summary | 纯数值推进，逐条日志无消费场景 |
| Wiki | wiki_change_log 页面审计 + ingest_summaries 断点摘要 | 页面历史 Tab / 编译明细对话框 | 审计（谁改了哪个页面）与断点续传语义，非过程日志流 |

**选型契约**（防第五种写法泛滥）：新增过程日志必须按消费者语义三选一——① 面向用户过程叙述 + 需持久回放 → DB 表（参照 report_logs 模式）；② 高频技术流 + 随实体目录生命周期 → 文件 tail（参照 execution.log 模式）；③ 纯状态推进 → 实体表 status/progress 字段，不建日志。读取端点语义限全量 / tail（limit），不新增游标增量协议；违反选型须先修订本节。

### 8.4 验收信号

- §8.1 轮询台账**只允许收敛、不允许增长**；新增轮询必须先入台账；
- 终态 = 1 条全局心跳（#0）+ 页面明细查询；
- `git grep pollUntil` 为空；`useActivity(kind)` 为页面谓词唯一来源；
- 前端 `usePolling({` 调用点全量归属 §8.1 台账；
- 后台异步作业（`threading.Thread` / `asyncio.create_task` / `BackgroundTasks`）全部归属六 kind 本体或基础设施（watchdog / venv 预装 / shutdown）；新增长时活动必须实现 ActivitySource 注册，禁止裸起线程承载「排队→执行→终态」作业；
- `add_notification` 生产调用仅存于 `activity_events` 框架与 DB 层，业务模块零直调；
- 所有 kind 终态 Toast 延迟一致（activity:stream 事件推送触发立即心跳，非等心跳轮询；断流时心跳拉兜底）。

## 9. 决策记录

### 状态与恢复

| 决策 | 理由 |
|------|------|
| DB 是状态源，前端是镜像 | 前端可随时重建连接，不依赖内存状态 |
| 无 interrupted 中间态，重启即中断判定 | 同进程 worker 已消亡，重启就是可靠的中断信号；状态机直接收敛 |
| 统一启动检测流程 | 所有模块共享恢复逻辑，减少遗漏 |
| 文件/图片/Wiki 崩溃静默自动恢复 | 本地推理零费用、可重放；用户无需感知 |
| 任务/报告恢复需用户触发 | 避免启动时自动消耗 LLM token；shell 副作用与对话上下文需用户知情 |
| 模型下载状态持久化 + 不自动重下 | 内存态重启即丢；大流量下载由用户明确意图驱动，断点续传代价可控 |
| 运行中不设任务级超时看门狗 | 见 §2.4.3 负决策记录 |
| 任务与项目 Nav 双徽章（L1） | 侧栏内容随 Nav 切换，L1 保证任何页面下全局活动可见 |

### 反馈与通知

| 决策 | 理由 |
|------|------|
| notifications 表持久化通知 | 重启/崩溃后完成事件不丢；未读查重天然去重 |
| 单一常驻轮询聚合端点（#0） | 全局层收敛为 1 个轮询，带可见性/退避；替代多个各自为政的监控 |
| 全局/页面两级轮询分离 | 全局层只给概要，详细进度归页面，互不重复 |
| 后端只存数据、前端渲染文案 | entity_title 是用户数据不翻译，文案走 i18n，中英双语 |
| 弹出即已读 | 无未读管理 UI，避免过度设计；最近动态仅历史展示 |
| 用户主动取消/停止静默 | cancelled/stopped/paused 是用户意图内行为，通知即噪音 |
| 图片描述不单独通知 | 文件级通知已覆盖，单图状态页面内可见 |
| file 活跃定义含图片描述期 | 文件 done 后图片仍在描述时，项目行/首页/素材角标指示不断档；通知仍只发文件级一次 |
| 模型下载纳入通知 | 下载历时分钟级且用户大概率切走，完成事件断链与 §5.1 设计动机同构；设置页进度条只覆盖「盯着看」场景 |
| 降级必须显式告知 | Tavily 失败 / Office 转换缺失等设计内降级不阻塞主流程，但用户必须知道「本次未使用互联网材料 / 解析质量可能降低」及修正路径；仅落日志对普通用户不可见——显式呈现（报告 warning 日志 / 通知 detail）是默认要求，日志是专业兜底 |

### 轮询

| 决策 | 理由 |
|------|------|
| 轮询为主、SSE 为辅 | 低频状态 + 跨进程 + 本机通信场景轮询是最优解；SSE 仅给高频流式输出与终态即时化 |
| 自适应轮询间隔 | 活跃时实时反馈，非活跃时降低资源消耗 |
| usePolling 收敛页面级轮询 | 防重叠/退避/可见性统一；不做 PollingManager 单例（无全局暂停需求，避免过度设计） |
| 长时活动统一模型 | 页面轮询 enabled 谓词一律从 `useActivity(kind)` 全局心跳派生，禁止自建手动布尔；后端活跃侧统一经 activities_registry 快照，单源异常隔离降级 |
| 单次调用强制超时（前端 race + Electron fetchWithTimeout） | Uvicorn 5s 关空闲 keep-alive 连接，Node fetch 复用半关闭 socket 无超时会永久挂起；超时是纵深防御而非根因修复——根因修复是循环调度结构不得被任何路径跳过（见 §5.8 教训） |
| 禁止循环体内 return 跳过调度 | 曾致 ActivityMonitor 首次拉取后死亡、UI 快照冻结；表观轮询是 effect 重建首拉的假象（详见 §5.8） |
| 禁止 hidden 早退跳过拉取 | Windows Chromium 窗口遮挡检测使被完全遮挡的窗口 `document.hidden=true`，早退曾致心跳断流——下载进度冻结 0%、呼吸点不出现、Toast 延迟到置前；不可见只降频不跳过，恢复可见 `visibilitychange` 立即拉取（usePolling 页面级轮询同步对齐，全仓唯一语义） |

### 准入（详见 §7）

| 决策 | 理由 |
|------|------|
| 首启向导 | 首次用户最大流失点是「打开全是红卡不知从何下手」；一次性向导 + 全部可跳过，不弹老用户 |
| 入口引导用弹层不硬禁用 | 禁用造成死界面、阻断探索；可点击 + 引导弹层保持界面活性 |
| VLM 定位为可选降级 | 仅影响图片描述，文本解析/向量化不依赖；缺失时放行 + 降级提示 |
