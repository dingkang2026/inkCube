# 生命周期管理设计

> 版本: 1.0 | 日期: 2026-09-29
>
> 统一考虑任务、文件解析、图片解析、Wiki 编译、报告生成五大长时操作的状态管理、异常恢复、导航反馈与消息通知。

---

## 1. 通用状态模型

### 1.1 统一状态机

所有长时操作共享一套基础状态机，各模块按需扩展：

```
                 触发
                  │
                  ▼
          ┌── queued ───┐
          │              │
          │        程序崩溃/异常
          ▼              │
      processing         │
       │     │           │
       │   用户取消       │
       │     │           │
       │     ▼           │
       │  cancelled      │
       │                 │
   全部完成         中断时机
       │                 │
       ▼                 ▼
     done           interrupted
                        │
                  重启后自动检测
                        │
               ┌───────┴───────┐
               ▼               ▼
           resumed           failed
          (续跑成功)       (不可恢复)
```

### 1.2 通用设计原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **DB 是状态源** | 所有状态持久化到 DB，前端是状态的只读镜像 |
| 2 | **后端不依赖前端** | 前端切走/关闭不影响后端任务执行 |
| 3 | **启动时自动检测** | 应用启动时扫描所有 `processing` 状态记录，判断是否需要恢复 |
| 4 | **轮询重建连接** | 前端切回时重新拉取状态 + 建立轮询，不依赖内存缓存 |
| 5 | **日志持久化** | 所有进度日志写入 DB，切走/崩溃后可完整回放 |
| 6 | **超时判定崩溃** | `updated_at` 超过阈值未更新 → 标记 `failed` |

### 1.3 启动恢复流程（通用）

```
应用启动
  │
  ├─→ 扫描各表: WHERE status IN ('processing', 'queued')
  │
  ├─→ 对每条记录：
  │     ├─ 读取 updated_at / checkpoint
  │     ├─ 距今 > 阈值 → 标记 failed，原因「程序异常中断」
  │     └─ 距今 ≤ 阈值 → 尝试恢复（从 checkpoint / 断点续跑）
  │
  └─→ 前端加载时自动发现恢复中的任务
```

## 2. 各模块状态定义

### 2.1 任务（Task Agent）

**状态流转：**

| 状态 | 含义 | 前端显示 |
|------|------|----------|
| `running` | Agent 循环执行中 | 🔄 流式输出 |
| `paused` | 用户暂停 / 等待确认 | ⏸️ 等待确认 |
| `done` | 完成（有最终回答） | ✅ 完成 |
| `cancelled` | 用户取消 | ⛔ 已取消 |

**Checkpoint 机制：**
- 每次 iteration 完成后自动保存 `task_agent_state`（完整 LLM messages + iteration 序号 + recent_errors）
- 崩溃恢复时从最后完成的 iteration 续跑

**前端导航：**
- 切走：流式状态缓存到 `bgStates`（Map），后端 SSE 继续推送
- 切回：从 `bgStates` 恢复 UI 状态；若已无缓存则从 DB `loadMessages` 重建
- 后台任务流式事件：通过 `handleBgStreamEvent` 累积到 bgState

**崩溃检测阈值：** 启动时检查 `task_agent_state` 表，有保存状态即视为可恢复。

### 2.2 文件解析

**状态流转：**

| 状态 | 含义 | 前端显示 |
|------|------|----------|
| `pending` | 等待处理 | ⏳ 排队中 |
| `parsing` | 解析中（Docling + 向量化） | 🔄 进度条 |
| `done` | 完成 | ✅ 完成 |
| `error` | 失败 | ❌ 错误 |

**图片子状态（`image_status`）：**

| 状态 | 含义 |
|------|------|
| `none` | 无图片 |
| `pending` | 等待 VLM 描述 |
| `describing` | VLM 描述中 |
| `done` | 描述完成 |
| `error` | 描述失败 |

**进度追踪：** 0-100%，按阶段推进（解析 0→25% → 向量化 25→75% → FTS 75→95% → 完成 100%）。

**崩溃检测：**

| 场景 | 恢复策略 |
|------|----------|
| `parsing` 超过 10 分钟未更新 | 标记 `error`，原因「解析中断」 |
| `pending` 状态 | 启动时重新入队 |
| `describing`（图片）超过 5 分钟未更新 | 重置为 `pending`，重新入队 |

### 2.3 Wiki 编译

**状态流转：**

| 状态 | 含义 | 前端显示 |
|------|------|----------|
| `queued` | 等待编译 | ⏳ 排队中 |
| `ingesting` | 摄入中（LLM 生成 Wiki 页面） | 🔄 摄入进度 |
| `storing` | 存储中（向量化 + 索引） | 🔄 存储中 |
| `waiting_review` | 监督模式：等待用户审阅 | 👀 待审阅 |
| `completed` | 完成 | ✅ 完成 |
| `failed` | 失败 | ❌ 失败 |
| `partial` | 部分完成 | ⚠️ 部分完成 |
| `stopped` | 用户停止 | ⛔ 已停止 |

**监督模式（Supervised）：** 每处理完一个文件后暂停（`waiting_review`），用户审阅后点击「继续」或「停止」。

**崩溃检测：**
- `ingesting` / `storing` 超过 10 分钟未更新 → 标记 `failed`
- `queued` 且有 `ingest_summaries`（已有部分进度）→ `is_resumed = true`，续跑
- 已有恢复检测：`get_compile_status` 返回 `is_resumed` 标志

**前端轮询策略（自适应）：**

| 状态 | 轮询间隔 |
|------|----------|
| `ingesting` / `storing` | 5 秒 |
| `waiting_review` | 10 秒 |
| 其它 | 30 秒 |

### 2.4 报告生成

详见 [2.5report-design.md §3.8](2.5report-design.md)。

**状态流转：**

| 状态 | 含义 | 看板显示 |
|------|------|----------|
| `generating` | 生成中 | ⏳ 60% |
| `done` | 已完成 | ✅ 完成日期 |
| `failed` | 失败 | ❌ 失败 |
| `interrupted` | 程序中断（内部过渡态） | ⏸️ 恢复中... |
| `cancelled` | 用户取消 | ⛔ 已取消 |

**Checkpoint 机制：** 每节完成后持久化（outputs / digests / registry / order / token_usage / current_section / updated_at）。

**崩溃检测：** `generating` 超过 5 分钟未更新 → 尝试从 checkpoint 恢复，无 checkpoint 则标记 `failed`。

## 3. 前端导航与反馈

### 3.1 通用导航模型

```
┌─────────────┐          ┌─────────────┐
│  模块 A      │          │  模块 B      │
│  (生成中)    │  切走    │  (其它页面)  │
│             │ ──────→  │             │
│  后端继续跑  │          │  侧边栏徽章  │
│  前端停轮询  │          │  显示通知    │
│             │  切回    │             │
│  重建轮询   │ ←──────  │             │
│  加载历史   │          │             │
└─────────────┘          └─────────────┘
```

**切走时：**
1. 前端停止轮询（组件卸载），不清理定时器引用
2. 后端任务继续运行，日志/状态持续写入 DB
3. 侧边栏对应 Tab 显示徽章（活跃任务数）

**切回时：**
1. 组件挂载 → 一次性拉取最新状态（GET API）
2. 重新建立轮询（间隔按状态自适应）
3. 如有历史日志面板 → 加载全部历史日志 + 继续实时追加

### 3.2 各模块导航行为

| 模块 | 切走行为 | 切回行为 | 跨项目行为 |
|------|----------|----------|-----------|
| **任务** | bgStates 缓存流式状态，后端 SSE 继续 | 恢复 bgStates 或 loadMessages | 任务绑定项目，切项目 = 切任务 |
| **文件解析** | 停止轮询文件列表 | 重新拉取文件列表（状态已更新） | 文件绑定项目 |
| **图片解析** | 随文件解析一起停止 | 重新拉取（image_status 已更新） | 随文件 |
| **Wiki 编译** | 停止轮询编译状态 | 重新拉取编译状态 + 自适应轮询 | 编译绑定项目 |
| **报告** | 停止看板轮询 | 重新拉取报告列表 + 恢复轮询 | 报告绑定项目 |

### 3.3 侧边栏徽章

| Tab | 徽章内容 | 触发条件 |
|-----|----------|----------|
| 任务 | 运行中任务数 | 有 `running` 状态任务 |
| 知识库 | 处理中文件数 | 有 `parsing` / `pending` 状态文件 |
| Wiki | 待审阅数 + 编译中 | 有 `waiting_review` 或活跃编译 |
| 报告 | 生成中报告数 | 有 `generating` 状态报告 |

## 4. 崩溃恢复

### 4.1 统一启动检测

应用启动时，按模块顺序扫描：

```python
def on_startup():
    """应用启动时的统一恢复检测"""
    
    # 1. 任务：检查是否有保存的 agent_state
    for task_id in db.list_tasks_with_state():
        state = db.load_agent_state(task_id)
        if state:
            logger.info(f"Task {task_id} has saved state, will resume on next user message")
            # 不自动恢复，等用户点击「继续」
    
    # 2. 文件解析：检查卡在 parsing 的文件
    for file in db.list_files_by_status('parsing'):
        if minutes_since(file.updated_at) > 10:
            db.update_file_status(file.id, 'error', error_message='解析中断')
        else:
            db.update_file_status(file.id, 'pending')  # 重新入队
    
    # 3. 图片解析：检查卡在 describing 的图片
    for img in db.list_images_by_status('describing'):
        if minutes_since(img.updated_at) > 5:
            db.update_image_status(img.id, 'pending')  # 重新入队
    
    # 4. Wiki 编译：检查活跃的编译任务
    for task in db.list_compile_tasks_by_status(['queued', 'ingesting', 'storing']):
        if minutes_since(task.updated_at) > 10:
            db.update_compile_task_status(task.id, 'failed', error_message='编译中断')
        # queued + 有 ingest_summaries → is_resumed，前端自动检测
    
    # 5. 报告：检查 generating 状态的报告
    for report in db.list_reports_by_status('generating'):
        cp = db.load_report_checkpoint(report.id)
        if not cp:
            db.update_report_status(report.id, 'failed', error_message='程序异常中断')
        elif minutes_since(cp.updated_at) > 5:
            db.update_report_status(report.id, 'failed', error_message='程序异常中断')
        else:
            db.update_report_status(report.id, 'interrupted')
            # runner 自动从 checkpoint 恢复
```

### 4.2 恢复策略汇总

| 模块 | 可恢复？ | 恢复粒度 | 用户感知 |
|------|---------|----------|----------|
| **任务** | ✅ | 从最后完成的 iteration 续跑 | 用户点击「继续」触发恢复 |
| **文件解析** | ✅ | 整个文件重新解析 | 文件状态回到「排队中」 |
| **图片解析** | ✅ | 单张图片重新描述 | 图片状态回到「等待描述」 |
| **Wiki 编译** | ✅ | 从最后完成的文件续跑 | 显示「恢复中」标记 |
| **报告** | ✅ | 从最后完成的章节续跑 | 看板显示「恢复中...」 |

### 4.3 不可恢复场景

| 场景 | 处理 |
|------|------|
| 文件解析：无 checkpoint（解析刚开始就崩溃） | 重新从 `pending` 开始 |
| Wiki 编译：项目已被删除 | 标记 `failed`，原因「项目已删除」 |
| 报告生成：归一化阶段中断（无 checkpoint） | 标记 `failed`，用户重新生成 |
| 任务：DB 中无 agent_state | 无法恢复，用户需重新发起对话 |

## 5. 日志与回放

### 5.1 日志存储

所有模块的进度日志统一写入 DB，格式一致：

| 字段 | 说明 |
|------|------|
| `entity_type` | `task` / `file` / `image` / `wiki_compile` / `report` |
| `entity_id` | 对应实体 ID |
| `level` | `info` / `warn` / `error` |
| `message` | 日志内容 |
| `created_at` | 时间戳 |

### 5.2 回放机制

**通用模式：** 用户进入详情页时，一次性加载全部历史日志，随后轮询追加新日志。

```
进入详情页
  │
  ├─→ GET /{entity}/{id}/logs  → 加载全部历史日志
  ├─→ 日志面板渲染历史日志（按时间序）
  └─→ 轮询 GET /{entity}/{id}/logs?after={last_timestamp}
        └─→ 追加新日志到面板底部
```

### 5.3 各模块日志内容

| 模块 | 日志示例 |
|------|---------|
| **任务** | `迭代 3：调用 shell 工具` / `迭代 3：工具执行完成` |
| **文件解析** | `开始解析 report.pdf` / `解析完成：12 个文本块，3 张图片` |
| **图片解析** | `开始 VLM 描述 figure_001.png` / `描述完成：「柱状图显示...」` |
| **Wiki 编译** | `摄入文件 1/5: 技术方案.docx` / `创建页面: 系统架构` |
| **报告** | `第 3 章：检索完成，获取 12 条知识卡片` / `第 3 章：生成完成（1,203 字）` |

## 6. 消息通知

### 6.1 通知方式

| 方式 | 场景 | 说明 |
|------|------|------|
| **Toast** | 操作完成/失败 | 右上角弹出，5 秒自动消失 |
| **侧边栏徽章** | 有活跃后台任务 | 数字徽章，点击进入对应 Tab |
| **日志面板** | 实时进度 | 详情页内，自动滚动 |
| **卡片状态** | 看板/列表视图 | 状态图标 + 进度百分比 |

### 6.2 通知事件矩阵

| 事件 | 任务 | 文件 | Wiki | 报告 |
|------|------|------|------|------|
| 开始 | — | — | — | — |
| 完成 | Toast「任务完成」 | Toast「解析完成」 | Toast「编译完成」 | Toast「报告生成完成」 |
| 失败 | Toast「任务失败」 | Toast「解析失败」 | Toast「编译失败」 | Toast「报告生成失败」 |
| 需审阅 | — | — | Toast + 徽章「待审阅」 | — |
| 崩溃恢复 | 日志「从迭代 N 恢复」 | 静默重新入队 | 日志「恢复中」 | 看板「恢复中...」 |

> 注：「开始」事件不发 Toast，避免打扰用户（后台静默执行）。

### 7.3 设计说明

**轮询 vs 事件推送：**

当前所有轮询均为前端主动拉取（pull）。任务对话已使用 SSE 流式输出，但状态查询仍用轮询，因为状态变化频率低、逻辑简单。后端异步任务（文件解析、Wiki 编译、模型下载）没有主动推送通道。

**常驻轮询 vs 条件触发：**

- **常驻**（#1、#4）：始终运行，#4 采用自适应频率降低空闲开销
- **条件触发**（其余）：特定操作进行时启动，结束或离开后自动停止

**防重叠机制：**

- #3（WikiTab 编译进度）使用 `polling` 标志位防止请求重叠
- 其他轮询依赖 `setInterval` 自然间隔，通常后端响应远小于间隔

### 7.4 优化建议

#### [P0] Wiki 编译状态重复轮询（#3 + #4）

**问题**：#3 和 #4 调用同一后端接口，编译对话框打开时两个轮询同时运行，2 秒内被请求 1.4 次。

**方案**：`wikiCompileState` 统一由 #4 管理，WikiTab 通过 props 消费，删除 #3 独立轮询。对话框打开时 #4 临时降至 2s，关闭后恢复自适应。

**预期收益**：编译期间请求量减少 50%+。

#### [P0] 缺少窗口可见性感知

**问题**：窗口最小化或被遮挡时仍全速运行。后台时常驻轮询每分钟约 14 次无效请求。

**方案**：
1. Electron 监听 `focus`/`blur`，广播 `window:visibility` 事件
2. 前端封装 `useWindowVisibility()` hook
3. 常驻轮询 `blur` 时降频至 1/3（#1: 5s→15s，#4 空闲: 30s→90s）
4. `focus` 时立即恢复频率 + 即时刷新

**预期收益**：后台常驻请求量减少约 70%。

#### [P1] 审阅状态检测重叠（#1 + #4）

**问题**：#1 每 5s 检测全局 `waiting_review` 弹 Toast，#4 每 10s 也检测 `waiting_review` 显示 Tab 角标。

**方案**：#4 复用 #1 的全局数据，按 `project_id` 匹配当前项目。

#### [P1] 缺少错误退避机制

**问题**：请求失败时仍以固定频率重试（后端未启动时每 5s 一次必定失败的请求）。

**方案**：指数退避——连续失败时拉长间隔，成功时恢复。封装到通用 `usePolling` hook。

#### [P1] 缺少请求防重叠保护

**问题**：仅 #3 有 `polling` 标志位，其余轮询在后端响应慢时可能请求堆积。

**方案**：统一加 `inFlight` 保护，推荐封装 `usePolling` hook。

#### [P2] 报告生成双重轮询可合并（#7 + #8）

**问题**：#7 和 #8 触发条件一致，合计每 2 秒 2 个请求。

**方案**：
- A：后端新增组合端点 `GET /reports/{id}/progress`，一次返回状态 + 日志
- B（轻量）：#8 日志刷新从 2s 降至 5s

#### [P2] #1 间隔偏激进

**问题**：#1 每 5s 轮询，但编译耗时分钟级，延迟 10-15s 通知完全可接受。

**方案**：#1 间隔从 5s 调整为 15s，配合窗口可见性感知。

#### [P3] 统一轮询管理架构

**问题**：12 个轮询分散在 8 个组件中，无统一生命周期控制。

**方案**：创建 `PollingManager` 单例或 React Context，支持全局暂停/恢复、频率调整、状态查询。

**优化优先级总结：**

| 优先级 | 问题 | 预期收益 | 改动范围 |
|--------|------|---------|----------|
| P0 | #3 和 #4 重复轮询 | 编译请求减少 50%+ | WikiTab + ProjectDetailPage |
| P0 | 缺少窗口可见性 | 后台请求减少 70% | Electron main + 全局 hook |
| P1 | #1 和 #4 审阅重叠 | 减少 1 个轮询源 | App.tsx + ProjectDetailPage |
| P1 | 缺少错误退避 | 避免请求风暴 | 通用 hook |
| P1 | 缺少请求防重叠 | 防止请求堆积 | 通用 hook |
| P2 | #7 和 #8 可合并 | 报告请求减少 30-50% | ReportWizard + Preview + 后端 |
| P2 | #1 间隔过短 | 常驻请求减少 66% | App.tsx |
| P3 | 统一轮询架构 | 长期可维护性 | 新建 hook + 逐步迁移 |

## 8. 设计决策一览

| 决策 | 理由 |
|------|------|
| DB 是状态源，前端是镜像 | 前端可随时重建连接，不依赖内存状态 |
| 统一启动检测流程 | 所有模块共享恢复逻辑，减少遗漏 |
| 自适应轮询间隔 | 活跃时实时反馈，非活跃时降低资源消耗 |
| 日志持久化 + 增量拉取 | 切走/切回/崩溃均可追溯完整过程 |
| 崩溃阈值按模块差异化 | 文件解析耗时长（10 min），图片描述短（5 min） |
| 任务恢复需用户触发 | 避免启动时自动执行 LLM 调用，用户可控 |
| 文件/图片崩溃静默恢复 | 用户无需感知，重新入队即可 |
| 侧边栏徽章统一 | 用户一眼看到所有后台活跃任务 |
