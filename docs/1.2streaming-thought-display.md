# 任务流式渲染设计

## 1. 大模型输出结构

每次 LLM 调用返回 3 个字段：

| 字段 | 说明 | 是否必有 |
|---|---|---|
| `reasoning` | CoT 内部推理（如 `<think>` 标签内容） | 否，仅推理模型 |
| `content` | 模型文本输出 | 否，可能为空 |
| `tool_calls` | 函数调用列表 | 否，没有则为最终回答 |

**关键**：`content` 有两种语义——
- 有 `tool_calls` 时：中间分析（模型在解释为什么要调用这些工具）
- 无 `tool_calls` 时：最终回答

前端在流式期间**无法区分**这两种情况，只有后续事件才能判定。

## 2. 后端事件映射

后端将 LLM 输出转为前端事件流：

| 后端事件 | 来源 | 时机 | 说明 |
|---|---|---|---|
| `reasoning` | `reasoning` | 流式中 | CoT 推理内容 |
| `answer_chunk` | `content` 的每个 chunk | 流式中（实时） | content 的实时片段 |
| `thought` | `content` 的完整文本 | 流式结束后 | **仅有 tool_calls 时**发送 |
| `action` | `tool_calls` 逐个 | tool 执行前 | 工具名 + 参数 |
| `observation` | tool 执行结果 | tool 执行后 | 输出 + diff + 文件路径 |
| `done` | 无 tool_calls | 最终 | 表示任务完成 |

### 事件时序

**FC 迭代（有 tool_calls）**：
```
reasoning → answer_chunk* → thought → action₁ → observation₁ → action₂ → observation₂ → ...
```

**最终回答（无 tool_calls）**：
```
reasoning? → answer_chunk* → done
```

### `answer_chunk` 与 `thought` 的关系

两者来自**同一份 `content`**：
- `answer_chunk`：content 的流式版本（实时，逐 chunk）
- `thought`：content 的完整版本（流式结束后一次性发送）

`thought` 事件同时是一个**迭代边界信号**：告诉前端"当前迭代结束，还有后续迭代"。

## 3. DB 消息类型

| DB role | 来源 | 说明 |
|---|---|---|
| `reasoning` | CoT reasoning | 模型内部推理过程 |
| `thought` | content（有 tool_calls） | 中间分析文本 |
| `action` | tool_calls | 工具调用 |
| `observation` | tool 执行结果 | 工具输出 |
| `assistant` | content（无 tool_calls） | 最终回答 |
| `user` | 用户输入 | 用户消息 |

**同一份 `content` 的两种归宿**：
- 有 tool_calls → DB 存为 `thought` 消息
- 无 tool_calls → DB 存为 `assistant` 消息

### 后端每次迭代保存的消息结构

后端在每次 LLM 调用时都会保存 `reasoning`（`task_agent.py` 第 1261/1327 行），不论该迭代是否有 tool_calls：

**有 tool_calls 的迭代**：
```
DB: reasoning → thought → action → observation
```

**最终回答（无 tool_calls）**：
```
DB: reasoning → assistant
```

**关键**：最后一次迭代也有 `reasoning` 消息（LLM 给出最终回答前的思考），因此 DB 中天然存在"只有 reasoning 没有 action"的迭代。

## 4. 前端渲染方案

### 4.1 最终渲染效果

```
用户消息泡
    ↓
┌─ IterationCard 1 ─────────────────────┐
│  ▸ 推理: CoT 推理内容                  │  ← ReasoningBlock
│  ▸ 分析: “让我搜索新能源数据...”      │  ← ThoughtBlock（中间分析文本）
│  ▶ web_search("新能源")     ✓ 3s      │
│  ▶ file_ops(write report)   ✓ 5s      │
└───────────────────────────────────────┘
┌─ IterationCard 2 ─────────────────────┐
│  ▸ 推理: CoT 推理内容                  │
│  ▸ 分析: “来分析这些数据...”          │
│  ▶ code_executor(analyze.py) ✓ 2s     │
└───────────────────────────────────────┘
┌─ IterationCard 3 ─────────────────────┐
│  ▸ 推理: “现在可以给出最终回答...”    │  ← 只有 reasoning，没有工具调用
└───────────────────────────────────────┘     （LLM 最终回答前的思考）
    ↓
┌─ 消息泡 (MessageBubble) ──────────────┐
│  "根据以上分析，新能源产业..."         │  ← 只有最终回答
└───────────────────────────────────────┘
```

**IterationCard 内部结构**：每个 IterationCard 包含 `ReasoningBlock`（推理）和可选的 `ThoughtBlock`（分析）。有 tool_calls 的迭代同时有推理和分析；最后一次迭代可能只有推理没有工具。

**注意**：`thought` 事件到达时，流式期间的分析文本（StreamThoughtBlock）会自然收回 IterationCard 内，成为 ThoughtBlock 的内容（见 4.2 节）。

### 4.2 流式期间的渲染

```
流式中:
┌─ IterationCard 1 ─ 收缩态 ────────────┐
│  Iter 1  搜索新能源数据...  2步  ●     │
└───────────────────────────────────────┘
┌─ IterationCard 2 ─ 展开态（当前）─────┐
│  推理: "让我分析这些数据..."  ▍       │  ← reasoning 实时流式
│  ▶ web_search [spinner]               │  ← action 执行中
└───────────────────────────────────────┘
    ↓
流式文本块 (StreamThoughtBlock)          ← answer_chunk 累积
    "正在整理分析结果..."  ▍              ← 不知道是中间分析还是最终回答
```

#### 分析文本的生命周期：外面 → 自然收回

流式期间，`answer_chunk` 累积的分析文本（StreamThoughtBlock）显示在 IterationCard **外面**（下方）。这是因为流式中前端无法判定它是中间分析还是最终回答，只能先放在卡片外面。

当后续事件到达时，文本会**自然收回**到它应在的位置：

- **`thought` 到达**（判定为中间分析）→ 文本收回 IterationCard 内，成为 ThoughtBlock 的内容，卡片收缩，进入下一个 iter。没有视觉跳变，因为卡片本身在收缩、用户注意力跟着新 iter 走
- **`done` 到达**（判定为最终回答）→ 文本变成独立的 MessageBubble，通过 fadeIn 动画过渡

```
流式中:  IterationCard(展开) + StreamThoughtBlock(外面)

thought 到达 → 文本收回卡片内，卡片收缩，进入下 iter
done 到达    → 文本变成 MessageBubble (fadeIn 动画)
```

### 4.3 展开/收缩逻辑

| 场景 | 行为 |
|---|---|
| 流式期间：当前迭代 | 自动展开 |
| 流式期间：之前的迭代 | 自动收缩 |
| 用户手动展开/收缩 | 覆盖自动行为 |
| 历史加载后 | 全部收缩，用户可手动展开 |

### 4.4 `thought` 事件的处理

`thought` 到达时的处理逻辑：

1. **判定**：这是 FC 迭代的中间 content（有 tool_calls）
2. **收纳**：将 `streamContent`（answer_chunk 累积的文本）保存为当前迭代的 thought（独立于 reasoning）
3. **清空**：清空 `streamContent`，为下一轮 answer_chunk 腾出空间
4. **推进**：迭代计数器 +1，清除 reasoning，清除当前迭代的 steps

```
answer_chunk("搜索新能源") → streamContent = "搜索新能源"
thought 到达              → iterationThought[0] = streamContent  ← 独立保存为 thought
                             streamContent = ""
                             iteration++
action(web_search)         → 工具卡片
```

### 4.5 `done` 事件的处理

`done` 到达时的处理逻辑：

1. **保存**：将当前 reasoning 保存到 reasoningMap
2. **转换**：遍历 reasoningMap，为每个迭代创建 `reasoning` 消息 + 该迭代的 `thought` 消息（如有）+ `action`/`observation` 消息
3. **转换**：将 streamContent（最终回答）→ `assistant` 消息
4. **清空**：清除所有流式状态
5. **不 reload DB**：所有数据已在内存中

#### done 创建的消息与 DB 的一致性

`done` handler 遍历 `reasoningMap`（key = 迭代编号），为每个迭代创建 `reasoning` 消息。这与后端 DB 保存行为完全一致：

| 迭代 | reasoningMap 内容 | done 创建的消息 | DB 中的消息 |
|---|---|---|---|
| 迭代 0（有 tool_calls） | reasoning + thought | `reasoning` + `thought` + `action` + `observation` | `reasoning` + `thought` + `action` + `observation` |
| 迭代 1（有 tool_calls） | reasoning + thought | `reasoning` + `thought` + `action` + `observation` | `reasoning` + `thought` + `action` + `observation` |
| 迭代 2（最终回答前） | 仅 reasoning | `reasoning`（无 thought、无 action） | `reasoning` |

**注意**：最后一个迭代可能只有 `reasoning` 没有 `action`——这是 LLM 给出最终回答前的思考过程，由后端主动保存（`task_agent.py` 第 1261 行），是设计行为。

#### 渲染结果

`done` 后 `isGenerating` 变 false，`renderList` 处理 `enrichedMessages`：
- 每个 `reasoning` 消息 → 创建一个 IterationCard（可能只有推理块，没有工具）
- `assistant` 消息 → 创建 MessageBubble（最终回答）

```
渲染: user → IterationCard₁(reasoning+tools) → IterationCard₂(reasoning+tools) → IterationCard₃(reasoning only) → assistant bubble
```

#### 流式→消息泡的视觉过渡

`done` 到达后，`isGenerating` 变 false，IterationCard 和 StreamThoughtBlock 消失，assistant 消息作为 MessageBubble 出现。

过渡策略（思路 A）：
- StreamThoughtBlock 和 assistantBubble 共享相同的 `background: var(--bg-secondary)`、padding、font-size、line-height，减少视觉跳变
- 新出现的 assistant MessageBubble 带 `fadeIn` 动画（0.3s，从下方 6px 淡入），让切换更自然
- 历史消息不受动画影响（动画仅作用于新渲染的 `.message.assistant`）

## 5. 流式状态管理

### 核心状态（useTaskChat.ts）

| 状态 | 类型 | 说明 |
|---|---|---|
| `streamContent` | string | 当前 answer_chunk 累积文本 |
| `streamReasoning` | string | 当前推理内容（实时） |
| `streamSteps` | StreamStep[] | 当前所有工具操作步骤 |
| `streamIteration` | number | 当前迭代编号 |
| `streamIsThought` | boolean | 是否已进入最终回答阶段 |
| `streamIterationReasoning` | Map<number, string> | 各迭代推理内容快照 |
| `streamContentRef` | Ref<string> | streamContent 的 ref（解决闭包问题） |
| `streamReasoningRef` | Ref<string> | streamReasoning 的 ref |
| `streamIterationRef` | Ref<number> | streamIteration 的 ref |
| `streamStepsRef` | Ref<StreamStep[]> | streamSteps 的 ref |

### 闭包问题与解决

`handleStreamEvent` 定义在组件体内，但 `useEffect([], ...)` 只捕获第一次渲染的版本。
所有在事件处理器中需要读取的状态值，都必须通过 **ref** 来访问最新值。

## 6. 前端显示对应关系总结

| 后端事件 | 前端流式显示 | done 后 DB 消息 | done 后前端显示 |
|---|---|---|---|
| `reasoning` | IterationCard 内 ReasoningBlock | `reasoning` | IterationCard ReasoningBlock（收缩） |
| `answer_chunk` | StreamThoughtBlock（卡片外） | `thought` 或 `assistant` | IterationCard ThoughtBlock 或 消息泡 |
| `thought` | 迭代边界信号（收纳 streamContent → ThoughtBlock） | `thought` | IterationCard ThoughtBlock（收缩） |
| `action` | IterationCard 内 ToolCard | `action` | IterationCard ToolCard（收缩） |
| `observation` | ToolCard 展开区 | `observation` | 合入 action 的 ToolCard |
| `done` | — | — | — |

## 8. 工具链问题修复记录

### 8.1 file_ops 写目录导致 Permission Denied

**问题**：LLM 调用 `file_ops.write` 时 `path` 为空或目录，导致对目录调用 `write_text()`，Windows 抛 `PermissionError`。错误信息误导 LLM 以为是权限问题，浪费多次迭代。

**修复**：
- `write`/`create` action 开头加 `target.is_dir()` 检查，返回清晰错误
- `prompt_description` 加显式提醒："path 必须包含文件名，不能为空或目录"

### 8.2 max_tokens 设置不一致

**问题**：`schemas.py` 默认值为 8192，但 DB 中存储的是旧值 4096。设置迁移缺失导致默认值更新不会覆盖 DB 已有值。

**修复**：直接将 DB 中的 `max_tokens` 更新为 8192。

### 8.3 doc_generator md_to_pdf 依赖 weasyprint（GTK 问题）

**问题**：`md_to_pdf` 使用 weasyprint，底层依赖 GTK3 动态库。Windows 不自带 GTK，导致 PDF 转换永远失败。

**修复**：移除 weasyprint 依赖，改用 pandoc（已内置）+ LibreOffice/MS Office（运行时检测）两步组合：
```
md_to_pdf: pandoc (md→docx) + LibreOffice/MSO (docx→pdf)
```
跨平台通用，无额外系统依赖。
