# 任务流式渲染设计

> **概述**：本文档定义任务会话的流式渲染机制——LLM 输出的三种字段（reasoning / content / tool_calls）如何映射为后端事件流、事件流如何在前端聚合为迭代卡片（IterationCard）与消息泡、以及流式状态如何在不重拉 DB 的前提下转为持久消息。核心问题与解法：
> 1. **content 双语义**——流式期间前端无法区分 content 是「中间分析」还是「最终回答」，只有后续事件（thought / done）才能判定；分析统一渲染在当前迭代卡的分析区（工具区之下），thought 到达时原地锁定，done 到达时最终回答转出为消息泡（§1 / §4.2）；
> 2. **迭代边界**——`iteration` 事件（每轮 LLM 调用开始时发送）是唯一的迭代边界信号，与 content 是否为空解耦；`thought` 仅作「本轮分析锁定」信号，不再推进计数（§2 / §4.4）；
> 3. **双份一致性**——前端 done 时本地重建的消息序列与后端 DB 保存序列完全一致，切换任务/重启后按 DB 回放得到相同视图；历史分组编号遇 user 消息重置，与即时渲染一致（§3 / §4.5）。
>
> 事件协议全表（9 种，含 plan / confirm 类）见 [1.1 §9.2](1.1task-agent-design-unified.md)；本文档聚焦渲染语义。

## 1. LLM 输出结构

每次 LLM 流式调用（`chat_stream`）产出四种 chunk，聚合为三个字段：

| 字段 | 说明 | 是否必有 |
|---|---|---|
| `reasoning` | CoT 内部推理（如 `<think>` 标签内容） | 否，仅推理模型 |
| `content` | 模型文本输出 | 否，可能为空 |
| `tool_calls` | 函数调用列表 | 否，没有则为最终回答 |
| `finish_reason` | 结束原因（stop / tool_calls） | 是 |

**关键**：`content` 有两种语义——

- 有 `tool_calls` 时：中间分析（模型在解释为什么要调用这些工具）
- 无 `tool_calls` 且 `finish_reason=stop` 时：最终回答

前端在流式期间**无法区分**这两种情况，只有后续事件才能判定。

## 2. 后端事件映射

后端（`task_agent.py`）将 LLM 输出转为前端事件：

| 事件 | 来源 | 时机 | 说明 |
|---|---|---|---|
| `iteration` | 主循环 `for iteration in range(...)` | 每轮 LLM 调用开始 | **唯一的迭代边界信号**（携带轮号），与 content 有无解耦 |
| `reasoning_chunk` | `reasoning` 的每个 delta | 流式中（实时） | 推理逐字流式；DB 仍在 flush 点存一次全量 |
| `reasoning_reset` | LLM 瞬时错误重试分支 | 重试重置累加器时 | 通知前端清空已渲染的部分推理，重试流从头累积 |
| `answer_chunk` | `content` 的每个 delta | 流式中（实时） | content 的实时片段（分析 / 最终回答） |
| `answer_reset` | LLM 瞬时错误重试分支 / LLM 最终失败兜底 | 重试或失败兜底前（已流过部分 content 时） | 通知前端清空已渲染的部分 content，与 `reasoning_reset` 对称 |
| `thought` | `content` 完整文本（剥 `Thought:` 前缀） | 流式结束后 | **仅当有 tool_calls** 时发送；锁定本轮推理+分析快照，不推进轮号 |
| `action` | `tool_calls` 逐个 | 工具执行前 | 工具名 + 参数（归属当前轮号） |
| `observation` | 工具执行结果 | 工具执行后 | 输出 + diff + 文件路径 |
| `done` | 无 tool_calls 且 finish=stop | 最终 | 表示任务完成 |

### 2.1 事件时序

**FC 迭代（有 tool_calls）**：
```
iteration(N) → reasoning_chunk* → answer_chunk* → thought → action₁ → observation₁ → action₂ → observation₂ → ...
```

**最终回答（无 tool_calls）**：
```
iteration(N) → reasoning_chunk* → answer_chunk* → done
```

同轮的思考与工具归属同一轮号：`thought` 先锁定快照、工具后执行，两者都在 `iteration(N)` 与 `iteration(N+1)` 之间，渲染为同一张卡。分析文字（answer_chunk）物理上先于工具执行到达——渲染位置固定在卡内工具区之下，流式期间可能出现「分析已出字、上方工具还在转圈」，这是用户确认的交互。

### 2.2 `answer_chunk` 与 `thought` 的关系

两者来自**同一份 `content`**：

- `answer_chunk`：content 的流式版本（实时，逐 chunk），渲染在当前迭代卡的分析区
- `thought`：content 的完整版本（流式结束后一次性发送）

`thought` 事件是**本轮分析锁定信号**：告诉前端「本轮 LLM 响应结束，后续还有工具执行与下一轮」；迭代推进由 `iteration` 事件负责。

### 2.3 reasoning 的转发与落库

- **流式转发**：每个 reasoning delta 即时 yield `reasoning_chunk`（前端逐字渲染）；LLM 瞬时错误重试时先 yield `reasoning_reset` 清空前端已渲染内容；content 同理——重试与最终失败兜底前先 yield `answer_reset`（已流过部分 content 时）
- **落库**（一次性全量，保证消息表 reasoning 在 content 之前）：
  - 流式 flush：首个 content chunk 到来时保存
  - 收尾 flush：模型只输出 reasoning 没有输出 content 时（常见于直接进入工具调用的迭代），流结束后补存
- 例外：**空响应**（无 content 无 tool_calls）的迭代不保存 reasoning，直接按 continue 进入下一轮

## 3. DB 消息类型

| DB role | 来源 | 说明 |
|---|---|---|
| `user` | 用户输入 | 用户消息 |
| `reasoning` | CoT reasoning | 模型内部推理过程 |
| `thought` | content（有 tool_calls） | 中间分析文本 |
| `action` | tool_calls | 工具调用（参数在 metadata） |
| `observation` | 工具执行结果 | 工具输出（metadata 含 diff / file_path / action_id） |
| `assistant` | content（无 tool_calls） | 最终回答；LLM 失败时的错误文案也存为此角色 |

**同一份 `content` 的两种归宿**：

- 有 tool_calls → DB 存为 `thought` 消息
- 无 tool_calls（finish=stop）→ DB 存为 `assistant` 消息

### 后端每次迭代保存的消息结构

**有 tool_calls 的迭代**：
```
DB: reasoning → thought → action → observation
```

**最终回答迭代（无 tool_calls）**：
```
DB: reasoning → assistant
```

**关键**：最后一次迭代也有 `reasoning` 消息（LLM 给出最终回答前的思考，经流式 flush 落库），因此 DB 中天然存在「只有 reasoning 没有 action」的迭代——这是设计行为，前端渲染依赖它（§4.1）。

另：shell 确认请求本身也会落一条 action 消息（metadata 含 `confirm_shell` + 命令），保证回放时能看到「等待过确认」这一步。

## 4. 前端渲染方案

### 4.1 最终渲染效果

```
用户消息泡
    ↓
┌─ IterationCard 1 ─────────────────────┐
│  ▸ 推理: CoT 推理内容                  │  ← ReasoningBlock
│  ▶ web_search("新能源")     ✓ 3s      │  ← ToolCard
│  ▶ file_ops(write report)   ✓ 5s      │
│  ▸ 分析: 「让我搜索新能源数据...」      │  ← ThoughtBlock（中间分析文本）
└───────────────────────────────────────┘
┌─ IterationCard 2 ─────────────────────┐
│  ▸ 推理: CoT 推理内容                  │
│  ▶ code_executor(analyze.py) ✓ 2s     │
│  ▸ 分析: 「来分析这些数据...」          │
└───────────────────────────────────────┘
┌─ IterationCard 3 ─────────────────────┐
│  ▸ 推理: 「现在可以给出最终回答...」    │  ← 只有 reasoning，没有工具调用
└───────────────────────────────────────┘     （LLM 最终回答前的思考）
    ↓
┌─ 消息泡 (MessageBubble) ──────────────┐
│  "根据以上分析，新能源产业..."         │  ← 只有最终回答
└───────────────────────────────────────┘
```

**IterationCard 三区结构**：每张卡片固定三区——`ReasoningBlock`（推理）→ `ToolCard`×N（工具）→ `ThoughtBlock`（分析）。有 tool_calls 的迭代三区俱全（分析解释本轮工具选择）；最后一次迭代可能只有推理没有工具。分析区位于工具区之下是用户确认的交互（§2.1）。

分组规则（`buildHistoryItems`）：按消息顺序扫描，每条 `reasoning` 开启新分组，`thought` / `action` 归入当前分组，`observation` 已由 `enrichMessages` 并入对应 action（按 `action_id` 配对，无 id 时按顺序配对），`user` / `assistant` 作为消息泡切出分组。**迭代编号遇 user 消息重置**——每轮对话从 Iter 1 重新计数，与即时渲染一致。

### 4.2 流式期间的渲染

```
流式中:
┌─ IterationCard 1 ─ 收缩态 ────────────┐
│  Iter 1  搜索新能源数据...  2步  ●     │
└───────────────────────────────────────┘
┌─ IterationCard 2 ─ 展开态（当前）─────┐
│  ▸ 推理: "让我分析这些数据..."  ▍     │  ← reasoning_chunk 逐字流式
│  ▶ web_search [spinner]               │  ← action 执行中
│  ▸ 分析: "正在整理分析结果..."  ▍     │  ← answer_chunk 逐字流式（卡内）
└───────────────────────────────────────┘
```

流式分组由 `buildStreamGroups` 现算，**数据集驱动：有内容才建卡**——迭代号取 `streamIterationReasoning` / `streamIterationThoughts` 快照键 ∪ `streamSteps` 轮号 ∪ 当前轮流式文本，因此当前轮与历史轮永不重叠、稀疏轮号（resume）不产生空卡。已锁定迭代从快照取数；当前迭代的推理 / 分析直接消费 `streamReasoning` / `streamContent` 实时文本并标记 `liveReasoning` / `liveThought`（带光标），步骤不全有输出时状态为 running。流式分组追加在全部历史消息之后。

#### 分析文本的生命周期：卡内流式 → 原地锁定 / 转出为泡

流式期间，`answer_chunk` 累积的文本直接渲染在当前迭代卡的分析区（工具区之下）。分析文字物理上先于工具执行完成到达——可能出现「分析已出字、上方工具还在转圈」，这是用户确认的交互（§2.1）。

当后续事件到达时，文本去向由事件判定：

- **`thought` 到达**（判定为中间分析）→ 文本原地锁定为分析区快照（位置不变、光标消失），轮号不变，下一轮 `iteration` 事件再开新卡
- **`done` 到达**（判定为最终回答）→ 文本转出为独立的 MessageBubble，通过 fadeIn 动画过渡

```
流式中:  分析区在当前卡内逐字出字（liveThought 光标）

thought 到达 → 卡内原地锁定（光标消失），轮号不变
done 到达    → 文本转出为 MessageBubble (fadeIn 动画)
```

### 4.3 展开/收缩逻辑

展开状态由双集合管理：`expanded`（当前展开的迭代）+ `autoExpanded`（由自动机制展开、允许被自动收缩的迭代）：

| 场景 | 行为 |
|---|---|
| 流式期间：新迭代开始 | 自动展开新迭代；收缩旧的**自动展开**项 |
| 用户手动展开/收缩 | 覆盖自动行为（该迭代移出 autoExpanded，不再被自动收缩） |
| 生成结束（isGenerating=false） | 展开状态整体重置；历史加载后全部收缩，用户可手动展开 |

列表滚动跟随：messages / streamContent / streamSteps / streamIteration 任一变化时平滑滚动到底部。

### 4.4 `thought` 事件的处理

`thought` 到达时的处理逻辑（useTaskChat）：

1. **判定**：这是 FC 迭代的中间 content（有 tool_calls）
2. **锁定**：将当前 `streamReasoning` / `streamContent` 分别快照到 `streamIterationReasoning` / `streamIterationThoughts`（本轮轮号）
3. **清空**：清空当前流式文本（渲染层分析区内容改由快照供给，位置不变、光标消失）
4. **不推进轮号**：迭代推进由后端 `iteration` 事件负责

```
answer_chunk("搜索新能源") → streamContent = "搜索新能源"（卡内分析区流式）
thought 到达              → iterationThoughts[0] = streamContent  ← 锁定
                           streamContent = ""，streamReasoning = ""
                           轮号不变（等待 iteration(1)）
action(web_search)         → 工具卡（归属轮 0，与思考同卡）
iteration(1)              → 轮号推进为 1，开新卡
```

### 4.5 `done` 事件的处理

`done` 到达时的处理逻辑：

1. **保存**：将当前 reasoning 保存到 reasoningMap（最终轮无 thought 事件，由 done 兜底快照）
2. **转换**：遍历 reasoningMap ∪ thoughtsMap ∪ 步骤轮号的全部迭代键（tool-only 轮不丢 action），为每个迭代创建 `reasoning` 消息 + 该迭代的 `thought` 消息（如有）+ `action` / `observation` 消息（observation 的 metadata 含 action_id 关联）
3. **转换**：将 streamContent（最终回答）→ `assistant` 消息
4. **清空**：清除所有流式状态与 bgStates 缓存
5. **不 reload DB**：所有数据已在内存中，onDone 回调触发任务列表刷新

#### done 创建的消息与 DB 的一致性

`done` handler 遍历迭代快照 Map，为每个迭代创建的消息序列与后端 DB 保存行为完全一致：

| 迭代 | 前端快照内容 | done 创建的消息 | DB 中的消息 |
|---|---|---|---|
| 迭代 0（有 tool_calls） | reasoning + thought | `reasoning` + `thought` + `action` + `observation` | `reasoning` + `thought` + `action` + `observation` |
| 迭代 1（有 tool_calls） | reasoning + thought | `reasoning` + `thought` + `action` + `observation` | `reasoning` + `thought` + `action` + `observation` |
| 迭代 2（最终回答前） | 仅 reasoning | `reasoning`（无 thought、无 action） | `reasoning` |

最后一个迭代可能只有 `reasoning` 没有 `action`——这是 LLM 给出最终回答前的思考过程，由后端经流式 flush 落库，前端快照同样保留，两侧一致。

#### 渲染结果

`done` 后 `isGenerating` 变 false，`renderList` 消费 enrichedMessages：每条 `reasoning` 消息开启一个 IterationCard（可能只有推理块），`assistant` 消息成为 MessageBubble。

```
渲染: user → IterationCard₁(reasoning+tools) → IterationCard₂(reasoning+tools) → IterationCard₃(reasoning only) → assistant bubble
```

#### 流式→消息泡的视觉过渡

`done` 到达后，IterationCard 转为持久消息，最终轮分析区内容转出为 assistant MessageBubble。过渡策略：

- 最终回答的最终轮分析区与新 assistant 气泡共享相同的 `background: var(--bg-secondary)`、padding、font-size、line-height，减少视觉跳变
- 新出现的 assistant MessageBubble 带 `fadeIn` 动画（0.3s ease-in，TaskMessageList.module.css）
- 历史消息不受动画影响（动画仅作用于新渲染的 assistant 气泡）

## 5. 流式状态管理

### 核心状态（useTaskChat.ts，挂在 App 级）

| 状态 | 类型 | 说明 |
|---|---|---|
| `messages` | TaskMessage[] | 已持久消息（DB 加载 + done 本地追加） |
| `isGenerating` | boolean | 是否有任务在流式执行 |
| `streamContent` | string | 当前 answer_chunk 累积文本 |
| `streamReasoning` | string | 当前迭代推理内容（实时） |
| `streamSteps` | StreamStep[] | 工具步骤（含 iteration 归属） |
| `streamIteration` | number | 当前迭代编号 |
| `streamIterationReasoning` | Map\<number, string\> | 各迭代推理快照 |
| `streamIterationThoughts` | Map\<number, string\> | 各迭代分析快照 |
| `planData` | PlanData \| null | 结构化执行计划（Planner） |
| `pendingShellConfirm` / `pendingSkillConfirm` | 确认数据 \| null | 待用户确认的请求 |
| `bgStates` | Map\<taskId, 快照\> | 后台任务流式状态缓存（多任务切换，见 [1.1 §9.3](1.1task-agent-design-unified.md)） |

每个流式状态配套同名 `ref`（`streamContentRef` / `streamReasoningRef` / `streamStepsRef` / `streamIterationRef`）。

**ref 与 state 的分工（不变量）**：ref 是写侧真相（事件处理器同步维护），state 仅是渲染投影；每个写点必须成对更新 ref + setState。**禁止用 state→ref 回写 effect 同步**（`useEffect(() => { ref.current = state })`）：高频流式下渲染提交滞后于 ref 前进，effect 会把 ref 回滚到过期 state，两次渲染间的增量永久丢失（曾导致长回答实时渲染丢字的根因，已移除，勿恢复）。

### 闭包问题与解决

`task:stream` 事件监听在 `useEffect([], ...)` 中注册一次，只捕获第一次渲染的 handler；因此 handler 经 `handleStreamEventRef` 间接引用最新实现，事件处理中读取的状态一律走 ref 取最新值。

### App 级挂载的原因

`useTaskChat` 挂在 App.tsx（而非 TaskPage）：task:stream 监听必须跨页面存活（用户切去其他页面时后台任务事件继续累积进 bgStates），TaskPage 卸载不中断状态。

## 6. 前端显示对应关系总结

| 后端事件 | 前端流式显示 | done 后 DB 消息 | done 后前端显示 |
|---|---|---|---|
| `iteration` | 开新迭代卡（轮号驱动） | — | — |

| `reasoning_reset` | 清空当前卡推理区（LLM 重试） | — | — |
| `answer_chunk` | 当前卡分析区逐字流式（光标） | `thought` 或 `assistant` | IterationCard 分析区 或 消息泡 |
| `answer_reset` | 清空当前流式 content（LLM 重试 / 失败兜底） | — | — |
| `thought` | 锁定本轮推理+分析快照（不推进轮号） | `thought` | IterationCard 分析区（收缩） |
| `action` | 当前卡工具区 ToolCard | `action` | IterationCard ToolCard（收缩） |
| `observation` | ToolCard 展开区 | `observation` | 并入 action 的 ToolCard |
| `done` | — | — | — |

（`plan` / `confirm_shell` / `confirm_skill` 三种事件不参与思维渲染分层，见 [1.1 §9.2](1.1task-agent-design-unified.md)。）

## 8. 差异与下一步优化建议

### 8.1 本轮重建的事实修正

| # | 原文档说法 | 现状 |
|---|-----------|------|
| 1 | 状态表含 `streamIsThought` | 不存在该状态；最终回答判定完全由事件时序（thought / done）驱动 |
| 2 | reasoning 「每次迭代保存（第 1261/1327 行）」 | 行号已漂移；实际是两个时机：流式 flush（首个 content 前）+ 收尾 flush（无 content 时）；空响应迭代不保存 |
