# 开发指南

> 面向开发者的环境搭建、日常开发、调试与打包指引。架构总览见 [0.0architecture.md](0.0architecture.md)；打包细节见 [0.2packaging-design.md](0.2packaging-design.md)。

## 1. 概述

开发栈由三部分组成：Vite + React 前端、Electron 主进程、Python FastAPI 后端。`npm run dev` 一键拉起完整栈；Python 后端也可单独启动以便断点调试（Electron 会自动探测并复用）。打包产物为 NSIS 安装包，后端依赖以 site-packages 目录装配（无 PyInstaller）。

## 2. 环境要求

| 工具 | 版本 | 说明 |
|---|---|---|
| Node.js | >= 20 | 推荐 LTS（开发使用 npm） |
| Python | 3.12 | 通过 Conda 管理 |
| Conda | miniconda3 | [下载地址](https://docs.conda.io/en/latest/miniconda.html) |
| Git | 任意 | 克隆仓库 |

打包所需工具链（uv/rg/ruff/pandoc/python-build-standalone）由 `scripts/prepare-tools.ps1` 按锁定版本自动下载到 `resources/tools/`（网络受限可加 `-MirrorPrefix` 走加速代理，或按 [0.2 §6.2](0.2packaging-design.md) 手动放置）；后端依赖装配与安装包构建由 `scripts/build-installer.ps1` 一键完成。

## 3. 国内环境配置

国内网络下安装和打包可能因 GitHub 资源下载缓慢而卡住，建议设置以下镜像：

```bash
# npm 镜像（所有平台通用）
npm config set registry https://registry.npmmirror.com
```

设置镜像环境变量（按你的终端选择对应语法）：

**PowerShell：**

```powershell
$env:ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/"
$env:ELECTRON_BUILDER_BINARIES_MIRROR="https://npmmirror.com/mirrors/electron-builder-binaries/"
```

**CMD（命令提示符）：**

```cmd
set ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/
set ELECTRON_BUILDER_BINARIES_MIRROR=https://npmmirror.com/mirrors/electron-builder-binaries/
```

**Bash（Git Bash / Linux / macOS）：**

```bash
export ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/
export ELECTRON_BUILDER_BINARIES_MIRROR=https://npmmirror.com/mirrors/electron-builder-binaries/
```

> 以上变量仅对当前终端窗口生效。设置后执行 `npm install` 或 `npm run pack` 即可。下载一次后会缓存到本地，后续无需重复设置。

## 4. 开发安装

### 1. 克隆仓库

```bash
git clone https://github.com/your-org/inkcube.git
cd inkcube
```

### 2. 安装前端依赖

```bash
npm install
```

### 3. 创建 Python Conda 环境

```bash
conda create -n inkcube python=3.12 -y
conda activate inkcube
```

### 4. 安装 Python 依赖

```bash
pip install -r python/requirements.txt
```

依赖分组（详见 `python/requirements.txt`）：

| 分组 | 主要依赖 |
|---|---|
| Web 框架 | `fastapi`、`uvicorn[standard]`、`httpx`、`pydantic`、`python-multipart` |
| 校验 | `jsonschema`（模板结构校验） |
| 向量与 Embedding | `chromadb`、`FlagEmbedding`（bge-m3）、`numpy` |
| 文档解析 | `docling`、`python-docx`、`Pillow`、`PyMuPDF`（PDF 样例提取）、`pywin32`（Office COM 探测/转换） |
| OCR | `rapidocr-onnxruntime` |
| 模型下载 | `huggingface_hub`、`modelscope`、`requests` |
| 异步与网络 | `aiohttp`、`html2text`（任务 venv 预装，browser-fetch 用） |
| 智能体工具 | `tiktoken`（精确 token 计量；编码器在后台线程初始化——数据文件需从 OpenAI CDN 下载且无 timeout，禁止在模块 import 时同步加载，未就绪/不可用时回退启发式）、`tree-sitter` + python/javascript/typescript 语言包（repo_map 动态 import，必须显式声明）、`networkx`（Wiki 图谱）、`PyYAML`（SKILL.md front-matter） |
| 测试 | `pytest` |

> `FlagEmbedding`/`chromadb`/`docling` 首次导入会拉取本地模型；生产环境已强制 `TRANSFORMERS_OFFLINE=1`（见 `python/main.py`），开发环境首次运行需联网下载 bge-m3。

### 5. 启动开发模式

```bash
npm run dev
```

该命令通过 `concurrently` 同时启动：

- Vite 开发服务器（`http://[::1]:5173`；2026-10-24 起全链路统一 IPv6 回环——127.0.0.1:5173 被本机代理/TUN 类软件黑洞化，Chromium IPv4 优先会 SYN 超时轮询致窗口白板约 3 分钟，实测 `[::1]` 0.006s）
- Electron 桌面窗口（`wait-on` 等待 Vite 就绪后自动打开）
- Python FastAPI 后端（由 Electron 自动管理，随机空闲端口）

## 5. npm 脚本一览

| 脚本 | 作用 |
|---|---|
| `npm run dev` | 启动完整开发栈（Vite + Electron，Python 由 Electron 拉起） |
| `npm run dev:vite` | 仅启动 Vite 开发服务器 |
| `npm run dev:electron` | 仅启动 Electron（等待 Vite 就绪） |
| `npm run python:dev` | 在 `127.0.0.1:8765` 单独启动 uvicorn（热重载） |
| `npm run python:debug` | 以 debugpy 监听 5678 启动后端（等待调试器接入） |
| `npm run dev:debug` | 三进程联调（python:debug + Vite + Electron） |
| `npm run build` | 前端构建（`vite build` → `dist-renderer/`） |
| `npm run pack` | 构建前端 + `electron-builder` 生成当前平台安装包（**不装配后端**：python-backend 取 `resources/` 现有快照；含后端代码变更的构建一律走 `build-installer.ps1`，见 §11） |
| `npm run test` | 前端单元测试（vitest，`tests/` 目录） |
| `npm run test:watch` | 前端测试 watch 模式 |

## 6. 单独启动 Python 后端

```bash
npm run python:dev
```

这会在 `127.0.0.1:8765` 启动 uvicorn 并开启热重载。Electron（开发模式）启动时会探测 8765-8767 端口，发现已运行的实例直接复用，不会重复拉起。

## 7. PyCharm 调试

开发时可以分两步启动，手动运行 Python 后端以便在 PyCharm 中直接 Debug。

### 第一步：在 PyCharm 中配置 Run/Debug

1. Run → Edit Configurations → + → Python
2. 填写以下信息：
   - **Script path**: 选 `Module`，填 `uvicorn`
   - **Parameters**: `main:app --host 127.0.0.1 --port 8765`
   - **Working directory**: `<项目路径>/python`
   - **Python interpreter**: 选择 `inkcube` conda 环境
   - **Environment variables**: 添加 `PYTHONUNBUFFERED=1`
3. 点击 **Debug** 按钮（虫子图标），即可打断点、单步调试

### 第二步：启动 Electron 前端

直接启动即可，Electron 会自动检测到已运行的 Python 实例并连接：

```bash
npm run dev
```

> 生产环境不受影响——未检测到已运行的 Python 时，Electron 会自动启动后端。

## 8. Conda 路径说明

开发模式下，Electron 按以下默认路径查找 Conda 环境。如果你的 Conda 安装在其他位置，需要修改 `electron/python-manager.js` 中的 `condaBase` 变量。

| 平台 | 默认路径 |
|---|---|
| Windows | `%USERPROFILE%\.conda\envs\inkcube\python.exe` |

## 9. 测试与验证

按层级执行验证（详见 `.qoder/rules/coding-habits.md`）：

| 层级 | 命令 | 说明 |
|---|---|---|
| Python 语法 | `python -m py_compile <file>` | 单文件语法检查 |

## 10. 错误契约（error code + 前端 i18n）

后端错误传递到前端遵循双协议，按错误载体二选一：

| 载体 | 形态 | 前端还原 |
|---|---|---|
| Router 同步响应（HTTP 4xx / 200 业务失败） | 响应体 `{"error": "<中文原文>", "code": "<CODE>"}` | `apiErrorText(code, fallback, t)`：命中映射 → 当前语言文案；未命中 → 降级原文 |
| 长时活动落库（error_message / ingest summary / 助手消息） | 协议串 `INKCUBE_CODE:<CODE>|<detail>`（detail 可省略） | `translateStoredError(text, t)`：渲染前还原为当前语言；非协议串原样返回 |

### 1. 后端产出

| 产出方 | 位置 | 说明 |
|---|---|---|
| 同步错误体 | `python/routers/*.py` | 面向用户的错误一律带 `code`（大写蛇形）；中文原文保留在 `error`/`message`，作未知 code 的降级文案与日志线索 |
| 协议串 | `python/errors.py::actionable()` | `InkCubeError`（携带 `code`/`detail`）→ `INKCUBE_CODE:<CODE>|<detail>`；长时活动失败统一经它落库（如 `knowledge/task_queue.py` 文件摄入失败） |
| HTTP 拒绝 | `JSONResponse(status_code, content={"error", "code"})` | 替代 `HTTPException(detail=中文)`，避免错误语义藏进 detail |

### 2. 链路与前端消费

| 层 | 职责 |
|---|---|
| `electron/ipc-handlers.js::handlePythonResponse` | 所有 invoke 通道的统一响应桥：`!res.ok` 时抛错并透传 `err.errorCode = body?.code`；`message` 依次降级 `body.error → body.message → detail(字符串) → HTTP 状态文案` |
| `src/i18n/errorCodes.ts` | `ERROR_CODE_I18N` 映射表 + `apiErrorText` / `apiErrorSuggestion` / `translateStoredError` 三入口 |
| `src/hooks/useErrorHandler` | invoke catch 路径统一消费：`errorCode` 命中映射 → 双语文案 + 建议槽位 |
| 渲染点 | 同步错误（toast / setError）用 `apiErrorText`；落库错误（error_message 类字段、助手消息渲染与复制）用 `translateStoredError` |

- 映射表只列前端实际消费的 code；每条 `msg` 必填（对应 `locales/*/errors.codes` 段 key，中英双语，文案含可行动指引），可选 `sug` 为建议文案。
- 降级规则：未知 code → fallback 原文（同步）/ `code: detail`（落库），后端新增 code 未同步前端时降级可读，不阻塞。
- 历史数据兼容：不含协议串的落库文本（历史中文 / 第三方异常串）原样展示，零成本兼容。

### 3. 新增 code 步骤

1. 后端：定义 `InkCubeError` 子类（`errors.py`）或 Router 返回体加 `code`；
2. 前端：`errorCodes.ts` 加映射条目，`locales/zh-CN.json` 与 `en-US.json` 的 `errors.codes` 段加对应 key；
3. 测试：后端协议串断言（`python/tests/`）与映射完整性断言（`tests/errorCodes.test.ts`）随变更更新。

## 11. 打包发布

> **重要**：后端依赖（torch/docling 等二进制 wheel）与工具链均为平台绑定，必须在目标平台上构建。例如，打 Windows 安装包需要在 Windows 上执行，打 macOS 安装包需要在 macOS 上执行。

### 1. 准备工具链

运行 `powershell scripts/prepare-tools.ps1`：按 [0.2 §6.2](0.2packaging-design.md) 锁定的版本下载 uv / rg / ruff / pandoc / python-build-standalone 并放置到 `resources/tools/`，逐件 `--version` 回读校验后自动生成 `tool-versions.json`（可选 `-MirrorPrefix` 走加速代理；脚本失败时可按 §6.2 手动放置，此时版本须与 manifest 逐一相符）。`build-installer.ps1` Step 1 会在构建时全量校验。

另外构建机需要可用的 Python：electron-builder 重建 better-sqlite3 原生模块时 node-gyp 需要。优先设置 `PYTHON` 环境变量指向解释器（如 `C:\Users\<you>\.conda\envs\inkcube\python.exe`），否则须 PATH 中存在 python.exe（WindowsApps 的 Microsoft Store 别名桩不算）。缺失时 Step 1 直接报错终止，不再拖到 Step 4 才暴露。

### 2. 装配 Python 后端（代码 + site-packages）

不使用 PyInstaller，改为拷贝后端代码并用 uv 按 `requirements.txt` 装配干净依赖到 `resources/python-backend/site-packages/`（决策详见 [0.2 §3](0.2packaging-design.md)，运行时布局见 [0.2 §9](0.2packaging-design.md)）：

```powershell
robocopy python resources\python-backend /E /XD __pycache__ tests data /XF *.pyc
resources\tools\uv.exe pip install --python resources\tools\python-build-standalone\python.exe --target resources\python-backend\site-packages -r python\requirements.txt
```

> 以上步骤已包含在 `build-installer.ps1` Step 2 中，单独执行时可手动运行。Step 2 还会在 site-packages 顶层生成 `sitecustomize.py`（pywin32 生产布局适配：PYTHONPATH 注入下 .pth 不生效，由 sitecustomize 复刻 pywin32.pth 的路径追加与 DLL 目录注册，机制见 [0.2 §9.2](0.2packaging-design.md)）。手动装配时若用到 pywin32 相关功能（Office COM 转换）需同样补齐。

### 3. 打包 Electron 应用

```bash
npm run pack
```

该命令先执行 `vite build` 构建前端，再调用 `electron-builder` 生成当前平台的安装包。**它不装配后端**：`python-backend/` 直接取 `resources/` 下的现有快照——后端代码改动后单独跑 pack，改动不会进安装包（实测陷阱：2026-10-16 验证 transfer 模块随包时发现快照停在上次装配）。含后端变更的构建必须先装配（§11.2）或直接用一键脚本 `powershell -ExecutionPolicy Bypass -File .\scripts\build-installer.ps1`（工具链校验 + 依赖装配 + electron-builder 全流程）。

> 判断后端是否需要重新装配：对比 `python/` 与 `resources/python-backend/` 的目录修改时间，或直接跑一键脚本（每次全量重装配，无此心智负担）。

electron-builder 支持指定目标平台：

| 命令 | 目标平台 |
|---|---|
| `npx electron-builder --win` | Windows `.exe` (NSIS) |
| `npx electron-builder --mac` | macOS `.dmg` |
| `npx electron-builder --linux` | Linux `.AppImage` |

> 注意：虽然 electron-builder 可以交叉打包前端，但 `python-backend/site-packages/` 与 `resources/tools/`（python-build-standalone、uv 等二进制）必须与目标平台匹配，需在目标平台上执行装配步骤后再打包。

打包产物位于 `dist/` 目录。

## 13. 数据存储

| 数据 | 位置 |
|---|---|
| SQLite 数据库 | 开发：`python/data/inkcube.db`；生产：`%APPDATA%/InkCube/data/inkcube.db`（Windows）|

## 16. 列表分页统一约定

所有列表型端点统一支持分页（2026-10 全量改造，20 端点；2026-10-20 审计补齐漏网的第 20 个 `GET /projects/{id}/suggestions`——此前宣称全量改造但实际未覆盖，本轮补 limit/offset/has_more/total 契约；回归测试 `python/tests/test_*_pagination.py`，前端基建 `src/hooks/usePagedList.ts`）。

### 1. 后端契约

| 参数/响应键 | 语义 |
|---|---|
| `limit` 查询参数 | 页大小，默认 50；**`limit=0` = 全量**（沿用 `GET /tasks` 先例，选择器/日历等既有调用方零改动） |
| `offset` 查询参数 | 偏移量，默认 0 |
| `has_more` | 是否还有更多（`limit+1` 探测） |
| `total` | 筛选后全量行数（单表 COUNT，不随分页变化） |

- 响应保持原有键不变，只追加 `has_more`/`total`（向后兼容）。
- enrichment/归一化（usage 聚合、行级字段加工）只作用于当前页行。
- 例外：`GET /projects/{id}/ledger/entries` 保留 `1≤limit≤100` 校验（无 limit=0 语义，422 拒绝）；`GET /schedules/runs/inbox` limit≥1；`GET /ppt-templates/jobs` 分段契约——活跃段（running/awaiting_input）恒全量 + 终态段 limit/offset，`has_more` 只看终态段；knowledge 文件列表（`/projects/{id}/files`、`/base-libs/{id}/files`）`Query(20, ge=1, le=100)`——默认 20 非 50，无 limit=0 语义（页码组形态，前端恒传 20/页）。
- 特殊口径：wiki pages 的 `missing_pages` 恒基于全量 page_key 集计算（不随分页截断）；wiki reviews 响应追加 `counts`（全表分型计数，供徽章，不随 resolved 筛选/分页变化），其 `total` 亦为全表口径（不随 resolved 筛选变化，与通用「筛选后行数」条款不同，消费方勿用 total 做分页器）；usage rounds 的 `total = COUNT(DISTINCT round_id)`。
- DB 层 `list_*` 系列统一补 limit/offset/total；SQL 用 `LIMIT ?/OFFSET ?` 占位符序（参数 append 顺序必须一致，有绑定顺序回归测试）。

### 2. 前端形态（混合）

| 形态 | 适用 | 范式 |
|---|---|---|
| 页码组 | 有搜索/筛选的管理页 | 筛选参数（q/status 等）服务端下沉 + 页码控件 + total（对齐 KnowledgePage 文件列表范式） |
| 加载更多 | 流式列表（看板/时间轴/侧栏/面板） | `src/hooks/usePagedList.ts`（items/hasMore/total/loadMore/reload），pageSize=50 |

- **轮询纪律**：轮询/边沿重拉按当前已加载量重拉（`reload()`，useTasks limitsRef 模式），不退回第一页。
- **选择器**：创建弹窗/向导下拉传 `limit=0` 全量拉取（行为与改造前一致）。
- **豁免**：静态注册表/天然有界列表不分页（`skills:builtinTools`、`wiki:getSchemas`、`ppt-template:list`、`taskTemplates:list`）。
- **测试**：后端每 router 一文件（`test_*_pagination.py`：limit 切片/offset 跨页无重叠/has_more/limit=0 全量/筛选组合）；前端 `usePagedList.test.ts`。直调 router 函数的测试必须显式传全部 Query 参数（FastAPI Query 默认值在直调时不解析）。

## 17. 前端错误反馈统一约定

全仓 catch 块按「失败是否影响用户决策」分级（2026-10-24 全仓静默 catch 排查确立，162 文件 296 处逐一定级；后续新增 catch 按同口径）。

### 1. 三级口径

| 级别 | 判定 | 处理 |
|---|---|---|
| 动作类必须反馈 | 用户点击触发的 invoke（删除/暂停/确认/导出/批量等） | catch → toast（`apiErrorText` 包装错误码，无码回退固定文案），禁止静默或仅 console.error |
| 引导类失败 ≠ 空态 | 首拉失败且列表空，组件存在「空态引导/暂无 X」分支 | 失败态标记（`loadFailed/fetchFailed`）→ 错误+重试分支；禁止与真实空态同路渲染（误导用户创建重复数据或误判无数据） |
| 展示类可降级 | 增强信息（徽章/KPI/详情字段）、有内容可保留的重拉失败、后台轮询（usePolling 退避自愈）、清理/卸载场景 | 静默或 console.error 可接受，但须注释说明降级理由与自愈路径 |

### 2. 实施细则

- 失败态复位点必须覆盖所有成功路径：组件若有静默刷新函数（如 `refreshImages`），其成功回调同样复位失败标记，否则重试成功后错误态不消失。
- rethrow 约定（0.4 §5.8 usePolling）：task 抛错 = 本次失败触发退避；task 内部自行 catch 且不抛出 = 视为成功。rethrow 时必须核对该函数**全部调用点**都有 catch（effect 初次加载侧是最常见遗漏——TaskLogViewer 2026-10-24 实例）。
- 空态/加载态/失败态三分支用 data-testid 区分（如 `intel-feed-empty`/`intel-feed-loading`/`intel-feed-error`/`intel-feed-fetch-error`），回归测试逐态断言互斥。
- 2026-10-24 排查修复清单：IntelFeed inbox 首拉失败、LeadPool 首拉失败、ImageGallery 首拉失败、ImportTargetDialog 列表失败（以上四者空态伪装）；useTaskChat pause/shell 确认/skill 确认/resume 四动作静默、TaskLogViewer 手动刷新与初次加载静默（动作无反馈）；其余约 60 处静默 catch 按展示类口径保留并核对注释。
