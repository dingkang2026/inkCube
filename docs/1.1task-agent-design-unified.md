
> **概述**：本文档是 InkCube 任务子系统（通用编程智能体）的设计权威，覆盖任务全生命周期：创建（每任务独立 workspace + venv）→ 执行（Planner/Editor 双模型 Function Calling 循环）→ 中断与恢复（断点自动保存 + 暂停 + 续跑）→ 归档/导出/删除。核心机制：
> 1. **双模型架构**——可配置独立 Planner（架构师规划）+ Editor（执行者工具调用），Planner 未配置或失败时自动回退单模型（§5.1）；
> 2. **断点续跑**——每轮迭代完成后自动保存完整 LLM messages（含 tool_calls 配对）到 `task_agent_state`，崩溃/暂停后从断点续跑（§5.3）；
> 3. **上下文治理**——token 精确计数（tiktoken）+ 两级压缩（Snip 截断单条输出 / Collapse 折叠历史），128K 预算下长任务不爆上下文（§6）；
> 4. **安全确认**——shell 命令三档确认模式（strict/smart/auto）+ 域名白名单 + 会话级放行；高危 Skill 执行前独立确认（§7）；
> 5. **工具生态**——16 个内置工具 + Agent Skills 行业标准（SKILL.md）第三方扩展，本地路径 / git 仓库两种安装来源（§3 / §4）。
>
> **结构**：§1 概述 → §2 系统架构 → §3 工具系统 → §4 Skill 框架 → §5 Agent 执行循环 → §6 上下文管理 → §7 安全与确认 → §8 系统提示 → §9 前端交互 → §10 数据存储与 API → §11 日志 → §12 差异与下一步优化建议。进程模型与端口分配见 [0.0architecture](0.0architecture.md)；长时活动的全局反馈 / 恢复规则见 [0.4lifecycle-design](0.4lifecycle-design.md)（本文档只展开任务模块特有部分）；流式思维展示的 UI 细节见 [1.2streaming-thought-display](1.2streaming-thought-display.md)；任务韧性（崩溃恢复语义）见 [1.3task-resilience-design](1.3task-resilience-design.md)。

## 1. 概述

### 1.1 核心定位

任务模块提供通用编程智能体能力：能写代码、跑代码、迭代调试，面向开发任务；同时提供 general 模式（通用助手，隐藏编码专用工具）覆盖非编程场景。

- **通用编程智能体**：Function Calling 驱动的多轮工具调用循环，最多 25 轮迭代，支持卡死检测与自动纠错
- **每任务隔离**：独立 workspace 目录 + 独立 Python venv，任务间依赖互不污染
- **可扩展**：支持第三方 Agent Skills（行业标准 SKILL.md 格式）安装，与内置工具统一注册、统一调用协议
- **跨平台**：Windows / macOS / Linux 一致体验（工具二进制与 Python 发行版均随应用分发）

### 1.2 技术选型

| 组件 | 选型 | 说明 |
|------|------|------|
| 后端集成 | 扩展现有 FastAPI 主进程 | 与其他路由同进程，动态端口（见 [0.0 §3](0.0architecture.md)） |
| Python 发行版 | python-build-standalone | 随安装包分发，仅作为任务 venv 的基底，不直接执行用户代码 |
| 依赖管理 | uv（回退 stdlib venv + pip） | 捆绑分发；创建快、全局缓存加速重复安装 |
| 代码搜索 | ripgrep (rg) | 捆绑分发，`code_search` 工具底层 |
| 代码检查/格式化 | ruff | 捆绑分发，`code_lint` / `code_format` 工具底层 |
| 文档转换 | pandoc | 捆绑分发（见 [0.2 §7](0.2packaging-design.md)），`doc_generator` 工具底层 |
| 执行隔离 | 每任务独立 venv | 基于 python-build-standalone 副本创建（§2.3） |
| 记忆 | 会话级 + 自动压缩 | 不做跨会话长期记忆与隐式记忆提取 |

### 1.3 与其他模块的关系

| 关系 | 说明 |
|------|------|
| 长时活动模型 | 任务是六大长时活动之一：活跃状态经注册表接入 `useActivity('task')`，终态事件经 activity_events 统一通知（[0.4 §1.4](0.4lifecycle-design.md)） |
| 知识库 | `knowledge_search` 工具可检索知识库项目文档（list_projects / search 两步），复用知识库检索层（[2.2](2.2knowledge-base-design.md)） |
| 设置 | 9 项任务专属设置（模型/超时/确认模式/配额等，§9.8） |
| 准入 | `ensure_ready("task")` 要求 LLM 已配置；前端入口经 `useFeatureGuard` 弹层引导（[0.4 §7](0.4lifecycle-design.md)） |

## 2. 系统架构

### 2.1 运行时架构

```
React 前端（src/features/task/）
  │  IPC：tasks:chat / tasks:pause / tasks:confirmShell ...（§10.2）
  │  事件：task:stream（SSE 流式事件，§10.3）
  ▼
Electron ipc-handlers.js
  │  fetch 转发至 Python 后端（SSE 流转发豁免超时）
  ▼
FastAPI 后端主进程（routers/tasks.py + routers/skills.py）
  ├── TaskAgent（python/agent/task_agent.py，单实例）
  │     ├── Planner/Editor 双模型循环（§5）
  │     ├── 16 内置工具（python/tools/，§3.2）
  │     ├── SkillRegistry（python/skills/，§4）
  │     └── ContextManager（python/agent/context_manager.py，§6）
  │
  │  工具执行：subprocess 调用任务 venv 的 Python / 捆绑二进制
  ▼
数据目录（data_dir；开发环境 python/data，生产环境 Electron userData）
├── inkcube.db                    ← tasks / task_messages / task_agent_state / skills 表
└── tasks/
    └── {task_id}/
        ├── workspace/            ← 任务工作目录（文件树 / 上传 / 导出）
        ├── .venv/                ← 任务专属 venv（仅应用托管目录创建，§2.3）
        └── execution.log         ← 用户可见执行日志（§11）
```

### 2.2 执行流程

```
用户输入任务描述
  → ensure_ready("task") 准入校验（缺 LLM 配置时结构化报错）
  → try_acquire_task 原子占用（并发闸门 + 同任务重入拒绝，§7.4）
  → Planner（若配置）生成执行计划 → 结构化 plan 事件推给前端
  → Editor 进入 FC 迭代循环（最多 25 轮）：
      每轮：上下文压缩检查 → LLM 决策 → 工具调用（含确认拦截）→ 观察结果
      每轮完成：断点自动保存（§5.3）
  → done / error 终态 → 清除断点（暂停除外）→ 终态通知（activity_events）
```

### 2.3 预装 Python 与任务 venv

预装 Python（python-build-standalone）**只作为发行版基底**：创建任务 venv 时作为 `--python` 参数，不直接执行用户代码。注意它与后端自身的运行时是两个东西——后端由 `resources/python-backend` 的完整环境运行（[0.2 §9](0.2packaging-design.md)）；任务 venv 用的副本由 tool-initializer 解压到 userData（`resolve_python()` 解析，环境变量 `INKCUBE_PYTHON_PATH` 优先）。

venv 创建策略（`db.create_task` → `tools/venv_manager.py`）：

| 规则 | 内容 |
|------|------|
| 创建时机 | 任务创建时同步创建（仅应用托管目录） |
| 托管判定 | `task_dir.startswith(data_dir)`——用户自选 workspace **不建 venv**（避免污染用户目录） |
| 创建方式 | `uv venv --python <预装python>`（timeout 60s）→ 失败回退 `python -m venv`（timeout 300s，子进程执行防 ensurepip 挂死阻塞事件循环） |
| 预装包 | 新建 venv 后台 daemon 线程安装 6 个常用包：requests、httpx、pyyaml、beautifulsoup4、openpyxl、pillow（uv pip install，timeout 120s，best-effort 不阻塞任务创建；uv/pip 全局缓存使重复安装很快） |
| 幂等 | venv 已存在则跳过创建与预装 |

好处：预装 Python 保持干净不被任何 `pip install` 污染；任务间依赖完全隔离；预装包覆盖常见 Skill 依赖，多数 Skill 免安装直接运行。

### 2.4 记忆模型

- **工作记忆**：当前执行轮次的完整 LLM messages（含 tool_calls/tool_call_id 配对），存 TaskAgent 内存（`_task_messages`），暂停/断点时序列化落库
- **会话记忆**：跨轮对话历史存 `task_messages` 表（§10.1），任务重新打开时重建上下文
- **自动压缩**：长对话达阈值时 Snip/Collapse 两级压缩（§6），避免 context overflow
- 不做跨会话长期记忆，不做隐式记忆提取

## 3. 工具系统

### 3.1 Tool 与 Skill 概念

Skill 是工作流驱动的复合能力（编排 + 领域知识 + 脚本），Tool 是原子函数调用。内置工具大部分封装现成底层能力（subprocess / 标准库 / 捆绑二进制），提供统一 BaseTool 接口让 agent 调用；第三方 Agent Skills 经 AgentSkillAdapter 包装后与内置工具在同一注册表中无差别调用。

### 3.2 内置工具清单（16 个）

TaskAgent 初始化时实例化全部 16 个工具（`python/agent/task_agent.py`），按名称注册：

| 工具 | 能力 | 底层实现 | 依赖捆绑二进制 |
|------|------|---------|----------------|
| **code_executor** | 执行 Python 代码，捕获 stdout/stderr/返回值/耗时 | subprocess 调用任务 venv 的 Python | 否 |
| **shell** | 在 workspace 执行 shell 命令，带确认拦截（§7.1） | subprocess | 否 |
| **file_ops** | 文件读写/创建/删除/移动/search_replace/apply_diff | pathlib / shutil | 否 |
| **code_search** | 代码库搜索（grep/正则/符号） | ripgrep | rg |
| **code_lint** | 静态检查（ruff） | ruff | ruff |
| **code_format** | 代码格式化 | ruff format | ruff |
| **package_manager** | 依赖管理（uv pip install / requirements 生成） | uv | uv |
| **project_scaffold** | 项目脚手架（目录结构/配置文件生成） | 模板 + 文件生成 | 否 |
| **web_search** | 网络搜索 | Tavily API | 否 |
| **web_fetch** | 抓取网页，HTML→Markdown | httpx + html2text | 否 |
| **knowledge_search** | 知识库检索（list_projects / search） | TaskKnowledgeSearchTool，复用知识库检索层 | 否 |
| **doc_generator** | 文档生成（md_to_docx / md_to_pdf，Mermaid 预处理 SVG） | pandoc（bundled > PATH 统一解析）+ LibreOffice/MS Office（PDF 第二段） | pandoc |
| **repo_map** | 代码库结构感知 | tree-sitter AST | 否 |
| **skill_runner** | Agent Skill 执行器（§4.4） | subprocess 调用任务 venv | 否 |
| **git_ops** | Git 版本控制操作 | subprocess 调用 git | 否 |
| **lsp_client** | LSP 集成（pyright/tsc + ripgrep 兜底） | subprocess + regex | 否 |

### 3.3 模式差异：coding vs general

任务有两种模式（`tasks.mode` 列，创建时指定，可切换）：

| 模式 | 工具集 | 身份提示 |
|------|--------|----------|
| **coding**（默认） | 全部 16 个工具 | 编程智能体身份 |
| **general** | 10 个：file_ops / shell / web_fetch / web_search / knowledge_search / doc_generator / repo_map / skill_runner / git_ops / lsp_client | 通用助手身份 |

general 模式隐藏 6 个编码专用工具（code_executor / code_search / code_lint / code_format / package_manager / project_scaffold），降低无关工具对决策的干扰。

### 3.4 捆绑工具统一解析（tool_resolver）

`python/tools/tool_resolver.py` 为 uv / rg / ruff / pandoc 提供统一三级查找：

1. 环境变量覆盖：`INKCUBE_UV_PATH` / `INKCUBE_RG_PATH` / `INKCUBE_RUFF_PATH` / `INKCUBE_PANDOC_PATH`（开发测试用）
2. 捆绑目录：`resources/tools/`（开发环境与 exe 同级）→ `%APPDATA%/InkCube/tools/`（生产解压位置，跨平台对应目录）
3. 系统 PATH：`shutil.which` 兜底

`resolve_python()` 同样三级：`INKCUBE_PYTHON_PATH`（生产由 python-manager.js 注入）→ userData 解压副本 → 开发环境 resources → `sys.executable` 兜底。捆绑清单与体积预算见 [0.2 §7](0.2packaging-design.md)。

## 4. Skill 框架

### 4.1 Agent Skills 标准

第三方 Skill 采用行业标准 SKILL.md 格式（agentskills.io 规范：frontmatter 元数据 + 正文使用指南 + 可选 scripts / references / assets），生态内 60,000+ Skill 可直接安装。一个 Skill 的目录结构：

```
skills/color-conv/            # dev/demo-skills/color-conv 为标准参照实现（测试夹具）
├── SKILL.md                  # frontmatter（name/description/license/compatibility…多余字段容忍）+ 使用说明正文
├── scripts/                  # 可执行脚本（可选）
└── references/               # 详细参考文档（可选，按需读取，不预加载）
```

解析与校验（`python/skills/parser.py`）：安装时解析 frontmatter 落库；运行时按需解析正文生成 prompt 描述，并用 mtime 缓存避免重复解析未变更的 SKILL.md（TaskAgent `_skill_scan_cache`）。

### 4.2 协议与注册表

```python
# python/skills/protocol.py（节选）
@dataclass
class SkillContext:
    workspace_path: str           # 任务工作目录
    venv_python: str = ""         # 任务 venv 的 python 路径
    task_id: str = ""
    settings: dict = field(default_factory=dict)
    cancel_event: Any = None      # asyncio.Event，用于取消

class BaseSkill:
    name: str = ""
    description: str = ""
    input_schema: dict = {}
    permissions: list[str] = []
    async def execute(self, params: dict, context: SkillContext) -> str: ...
    async def pre_execute(self, params: dict, context: SkillContext) -> dict | None: ...
    async def post_execute(self, result: str, params: dict, context: SkillContext) -> str: ...
```

`SkillRegistry`（`python/skills/registry.py`）是唯一入口：内置工具经适配包装与 Agent Skills 统一注册，自动生成 Function Calling tools 列表，统一 pre_execute → execute → post_execute 执行协议。Agent Skills 在每次任务启动时从 DB 安装清单动态注册（`TaskAgent._register_external_skills`）：列出 enabled Skill → 发现类型（SKILL.md 存在即 agent_skill）→ 解析校验（frontmatter 完整性）→ AgentSkillAdapter 包装注册。

### 4.3 安装管理（routers/skills.py，6 条路由）

| 路由 | 能力 |
|------|------|
| GET /skills | 列出已安装 Skill（含启用状态 / needs_confirm） |
| POST /skills/install | 安装：`source_type=local`（本地目录）或 `git`（git 仓库 URL），两种来源 |
| DELETE /skills/{id} | 卸载（删除安装目录 + DB 记录） |
| POST /skills/{id}/toggle | 启用 / 禁用（禁用后不注册进任务） |
| POST /skills/{id}/confirm | 高危 Skill 首次运行确认（needs_confirm 标记，§7.2） |
| GET /skills/builtin-tools | 内置工具清单（前端设置页展示） |

本地安装支持「集合目录」检测：所选目录本身无 SKILL.md 但子目录有多个 Skill 时，返回建议列表引导用户单装子目录，避免误装集合。安装位置为数据目录 `skills/`。

### 4.4 Skill 执行（双入口）

Agent Skills **没有独立 venv**，统一使用当前任务的 venv（与内置工具同环境，依赖 §2.3 预装包覆盖）。安装的 Skill 对 LLM 有两个等价入口，最终都收敛到 AgentSkillAdapter：

| 入口 | LLM 调用形态 | 代码路径 | 确认门 |
|------|-------------|---------|--------|
| ① Skill 专属函数 | `{skill-name}(command="CLI参数")` | FC 循环 `skill_registry.execute()` → AgentSkillAdapter | needs_confirm（§7.2，经 skill_runner 实时缓存判定） |
| ② skill_runner 工具 | `skill_runner(skill="{name}", input={"command": …})` | FC 循环 `tools.get("skill_runner")` → 内部实例化 AgentSkillAdapter | needs_confirm（§7.2） |

```
两入口共同尾部（AgentSkillAdapter.execute）：
  定位 install_path/scripts/ 脚本
  → subprocess：[任务 venv python, 脚本, ...shlex(command)]，捕获 stdout/stderr/退出码
  → 无脚本或无 venv 时返回 SKILL.md 指令正文（LLM 按指南自行执行）
  → 首次执行结果附 SKILL.md 指南（≤4000 字符）+ references/ 注记，之后精简（slash 场景 hint 已带指南则不再附，mark_guide_sent 联动）
```

上下文按官方三级渐进式披露（progressive disclosure）加载，常驻开销不随 Skill 数量膨胀：

| 层级 | 内容 | 加载时机 |
|------|------|--------|
| **L1 Metadata** | name + description + command schema | 函数定义常驻（每 Skill ~100-150 tokens） |
| **L2 Instructions** | SKILL.md 正文（≤4000 字符） | 激活时一次：slash 随 hint 注入；自然语言随首次执行结果附带（同一 run 不重复，每次 run 重置——tool result 不进重建的历史） |
| **L3 Resources** | references/ 参考文件 | 按需：TaskAgent 注册 Skill 时把 install_path 登记为 file_ops 只读根（`add_readonly_root`），LLM 依注记用 read/list 读取；写操作仍被沙箱拒绝 |

`compatibility` 字段为自由文本环境说明（规范语义，非 pip 依赖清单，≤500 字符），展示于 prompt_description；真实依赖由 LLM 按 SKILL.md 指引经 shell/pip 自助安装（历史教训：曾把它解析成包名清单自动 pip install，标准写法 "Requires Python 3.10+; uses only the standard library" 会被解析出 uses/only/standard/library… 整串误装，外部标准 Skill 拷来即挂，已删除自动安装逻辑——parse_compatibility 与 _ensure_dependencies 一并移除）。

规范**没有**依赖清单机制：规范不定义 requirements.txt，目录内任意附加文件不被解析（社区惯例的 requirements.txt 属于附加文件，平台不自动读取）；规范对脚本的依赖要求是「自包含或在 SKILL.md 中写明依赖」，配合 compatibility 声明环境需求，由 LLM 执行时经 package_manager / shell 安装（任务 venv 预装包覆盖常见需求，§2.3）。

`command` 参数承载 CLI 参数：参数描述明确要求 CLI 形态并附示例（历史教训：曾写 "natural language" 引导 LLM 直传自然语言，argparse 报错，已修正），由 LLM 根据 SKILL.md 使用指南翻译——静态代码不做 CLI/NL 区分（另一教训：曾用「SKILL.md 正文行首匹配」启发式区分，被「何时使用」清单行误命中，已删除）。

### 4.5 斜杠命令

输入框 `/` 触发自动补全（`/help` + 已安装 Skill 名，§9.7）。发送后路由（`TaskAgent._slash_routing`）：

| 输入形态 | 路由 | 理由 |
|---------|------|------|
| `/help` | 直调：生成帮助清单，不进 LLM | 纯静态信息，无需消耗模型调用 |
| `/name …`（name 未安装） | 直调：报「未找到 Skill」+ 可用清单 | 即时纠错反馈，避免 LLM 幻觉 |
| 无 skill_runner 工具 | 直调：报「当前模式不支持 Skill 调用」 | 能力缺失的确定性提示 |
| `/name [params]`（name 已安装） | **一律 fallthrough 进 FC 循环**：注入系统提示 + 附 SKILL.md 使用指南（≤4000 字符，取 adapter 的 usage_instructions）+ references/ 指引（存在时），引导 Editor 翻译 params 为 CLI 后调工具（优先 Skill 专属函数，备选 skill_runner） | 参数形态（自然语言 / CLI / 空）无法静态可靠区分，LLM 需完整指南才能正确翻译；指南前置使首次调用即可构造正确参数，免「猜错→自纠」一轮；直调会把自然语言原样传给脚本导致 argparse 报错 |

历史：早期版本对已安装 Skill 的 params 做 CLI/NL 启发式预检（取首 token 匹配 SKILL.md 行首），误判率高（如「回声测试」命中「何时使用」清单行被判 CLI 直调报错），已删除——路由只区分「是否已安装」，参数语义一律交 LLM。

## 5. Agent 执行循环

### 5.1 Planner / Editor 双模型

任务可配置两个模型（设置项见 §9.8）：

| 角色 | 设置项 | 职责 |
|------|--------|------|
| **Planner（架构师）** | `task_planner_model`（空 = 不启用） | 分析需求生成执行计划；计划解析为结构化步骤（`_parse_plan_steps`）经 `plan` 事件推给前端渲染 PlanProgressCard；计划文本注入 Editor 上下文 |
| **Editor（执行者）** | `task_model`（空 = 全局模型） | 主循环：工具调用、结果分析、迭代 |

Planner 调用细节（`_run_planner`）：输入 = 架构师系统提示 + Editor 近 6 条非 system 消息 + 用户消息；失败时回退单模型模式（流内发 thought 提示「回退到单模型」）。**断点恢复时不重跑 Planner**（保存的 messages 已含计划上下文）。

### 5.2 FC 迭代主循环

```
for iteration in range(start_iteration, max_iter):        # max_iter 默认 25（§5.6）
    if cancel_event.is_set(): break
    messages = await ctx_mgr.compress(messages, llm, settings)   # 上下文压缩（§6）
    async for event in _handle_fc_iteration(...):                 # 单轮 FC
        yield event                                               # SSE 透传前端
        if event.type == "_fc_done": fc_status = event.status
    if fc_status == "continue":
        save_agent_state(task_id, {messages, iteration+1, recent_errors})  # 断点保存
    elif fc_status in ("done", "error"):
        if done 或非暂停退出: delete_agent_state(task_id)          # 清断点（暂停保留）
        _run_outcomes[task_id] = completed/failed                  # 终态通知用
        yield done; return
# 循环耗尽或取消：保存 fallback 消息后 yield done
```

单轮 FC（`_handle_fc_iteration`）内部：LLM 流式响应（reasoning / answer_chunk 事件透传）→ 解析 tool_calls → 逐个执行工具（含确认拦截 §7、edit-verify 增强 §5.5）→ observation 事件（含 diff / file_path）→ tool result 回填 messages → 返回 `_fc_done{status}`（continue = 继续下轮；done = 任务完成；error = 异常退出）。每轮开始与工具调用均记入 app.log 与 execution.log（§11）。

### 5.3 断点保存 / 暂停 / 恢复 / 取消

| 操作 | 机制 | 用户感知 |
|------|------|----------|
| **断点自动保存** | 每轮 iteration 完成后保存完整 messages（含 tool_calls/tool_call_id 配对，保证恢复后 LLM 能正确配对）+ iteration 序号 + recent_errors 到 `task_agent_state` | 无感；崩溃后任务列表可「继续执行」 |
| **暂停**（POST pause） | 取内存中的完整 messages（优先，含工具调用配对；DB 消息兜底）→ pause_task 保存状态并置 cancel | 任务停止，「继续执行」按钮出现 |
| **恢复**（POST chat + `resume=true`） | 读取保存状态 → 从 start_iteration 续跑，跳过 Planner，recent_errors 一并恢复；恢复时**不保存用户消息** | 流内提示「从第 N 轮恢复执行」 |
| **取消**（POST chat/cancel） | 置 cancel_event，循环在轮次边界退出 | 流内 fallback「已停止生成」 |
| **同任务重入** | 新消息发送时先 delete_agent_state，从完整历史重建上下文 | — |

崩溃恢复的完整语义（启动扫描、状态判定、与 0.4 统一规则的关系）见 [1.3task-resilience-design](1.3task-resilience-design.md)。

### 5.4 卡死检测

维护 recent_errors 队列（错误签名去重）：同一错误签名连续出现 ≥ 3 次（STUCK_THRESHOLD）时，向 LLM 注入警告提示引导换思路；跨轮保持（随断点保存/恢复）。

### 5.5 Edit-Verify 循环

文件编辑类工具结果经 lint 增强（`_edit_verify_loop`）：file_ops 编辑后若 lint 报错，自动将错误 + 文件内容反馈给 LLM 生成修复，重新应用 + 复检，最多重试 N 次；修复成功后 observation 携带修复说明，失败则保留 lint 提示供下轮决策。目的：编辑→验证→修复闭环，避免一轮编辑留下一堆静态错误到下轮才暴露。

### 5.6 迭代上限与并发控制

| 参数 | 值 | 说明 |
|------|-----|------|
| max_iter | 默认 25 | 读 `settings.task_max_iterations`；该键不在设置默认表与设置界面，属隐藏配置（§12） |
| MAX_CONCURRENT | 3 | 全局同时运行任务数上限（TaskAgent 类常量） |

并发闸门见 §7.4；超出上限或同任务重入的拒绝语义见 §10.2（409 / 429）。

## 6. 上下文管理

### 6.1 Token 计数

`python/agent/context_manager.py`：优先 tiktoken（gpt-4o cl100k 编码）精确计数；未安装时回退启发式（CJK ≈ 1.5 字符/token，Latin ≈ 3 字符/token）。

### 6.2 两级压缩：Snip 与 Collapse

| 级别 | 触发 | 动作 | 参数 |
|------|------|------|------|
| **Snip** | 单条工具输出 > snip_threshold | 截断该条输出保留头部 | 32000 字符（约 8K token，128K 上下文的约 6%） |
| **Collapse** | 估算总量超预算（max_tokens × 压缩比，扣除响应与系统提示预留） | 压缩历史消息，保留最近 KEEP_RECENT 条完整 | max_tokens 128000 / compress_ratio 0.85 / KEEP_RECENT 10 |

压缩时机：每轮迭代开始时（`ctx_mgr.compress`）。system 提示不参与压缩（另行受 §8 预算约束）。

### 6.3 设计意图

- 单条限长（Snip）解决「一次搜索返回巨量文本」；整体限量（Collapse）解决「长任务多轮累积」
- 压缩发生在 LLM 调用前，保证每次请求都在预算内；压缩后消息仍是合法 OpenAI 消息序列

## 7. 安全与确认

### 7.1 Shell 命令确认（三档模式）

`task_shell_confirm_mode` 控制确认策略（shell 工具执行前拦截，TaskAgent 确认状态机）：

| 模式 | 行为 |
|------|------|
| **strict** | 所有 shell 命令逐条弹窗确认 |
| **smart**（默认） | 按风险分级：高危命令（删除/系统修改等）弹窗；安全命令（只读查询等）放行；`task_shell_domain_whitelist` 中的域名相关命令自动批准（每行一个域名） |
| **auto** | 全部自动执行（信任环境使用） |

弹窗三选：允许 / 允许且本会话不再询问（`_session_auto_allow`，任务粒度）/ 拒绝。确认交互：后端 yield `confirm_shell` 事件 → 前端弹窗 → POST confirm-shell 回传 → asyncio.Event 放行或拒绝。历史兼容：`task_auto_confirm_shell` 布尔为旧版设置，仅向后兼容保留，无 UI。

### 7.2 Skill 执行确认

Skill 安装即带 `needs_confirm=1`（skills 表迁移列，DEFAULT 1）：任务内首次执行前 yield `confirm_skill` 事件弹窗确认（POST confirm-skill 回传）。用于第三方 Skill（任意代码执行）的首运行门槛。

确认门覆盖 §4.4 的两个执行入口：skill_runner 工具路径与 Skill 专属函数路径均在执行前经 skill_runner 实时缓存查 DB `needs_confirm` 判定（不用 adapter 的启动快照，保证任务运行中在设置页操作能即时生效）。

确认语义（2026-10 修复：此前任务内确认不落库，needs_confirm 恒为 1，每个任务重复弹窗）：

- **任务内点「允许」= 永久信任**：后端 respond_skill_confirm 按 skill_name 落库置 0（`confirm_skill_by_name`），与设置页 POST /skills/{id}/confirm 等效——弹窗即首次使用确认点，此后不再询问（落库失败降级为仅本次放行并 warning 留痕）；
- **「拒绝」仅本次**：不清标记，下次仍询问；
- **超时 fail-safe 默认拒绝**（不自动同意——确认框防的是任意代码执行，fail-open 会架空确认机制）：skill 180s / shell 与 git commit 120s，超时后 yield `confirm_expired` 事件关前端残留弹窗，跳过原因经该 action 的 observation 留痕（「确认超时，已跳过…」，与用户主动拒绝文案区分）；
- **失效点击反馈**：确认已超时后 confirm-skill 返回 `found=false`，前端提示「该确认已超时失效」而非静默落空。

### 7.3 路径与文件安全

| 防线 | 实现 |
|------|------|
| workspace 越界防护 | 文件读取（files/content）与上传均做 `resolve()` 后前缀校验，拒绝 workspace 之外的路径 |
| 上传限制 | 单文件 50MB；文件名取 basename 防路径注入 |
| 删除范围限制 | 删除任务仅对应用托管目录（data_dir/tasks/{id}）rmtree；用户自选 workspace 只删 DB 记录不动文件 |
| 删除前取消 | 运行中任务先 request_cancel，最多等 10s 让循环退出，避免删目录与写入竞态 |
| 二进制识别 | 文件预览按扩展名三类（image/text/binary）+ 未知扩展读前 8KB 检测空字节，避免误读二进制 |

### 7.4 配额与并发闸门

| 闸门 | 规则 | 拒绝语义 |
|------|------|----------|
| 任务数配额 | 创建时检查非 deleted 任务数 ≥ `task_max_count`（默认 50，0 = 不限） | 返回 error 文案（引导删除/归档） |
| 全局并发 | `try_acquire_task` 原子占用（check-then-act 单步化，防竞态双开）；运行数 < MAX_CONCURRENT(3) | 429 `TASK_LIMIT_REACHED` |
| 同任务重入 | 已运行任务拒绝第二次 chat（会破坏消息历史配对） | 409 `TASK_RUNNING` |

准入校验（`ensure_ready("task")`，要求 LLM 已配置）在占用闸门之前，缺配置时结构化报错而非运行中途失败（[0.4 §7](0.4lifecycle-design.md)）。

## 8. 系统提示

### 8.1 组装

`_build_system_prompt` 模块化拼接：身份（按 mode 二选一）→ 当前日期时间（含星期，让 agent 理解「今天/昨天」）→ 可用工具描述（各工具 prompt_description，按 mode 过滤 §3.3）→ 项目配置 / 项目上下文 / git 上下文（按可用性）。用户全局 `system_prompt` 设置存在时前置拼接。

### 8.2 提示预算

PROMPT_BUDGET = 4000 tokens：超出时按优先级丢弃低优先级段（项目配置 → 项目上下文 → git 上下文），身份与工具描述永不丢。

### 8.3 构建线程化

提示构建涉及 git 命令（3×5s 超时）、workspace 扫描、repo-map 生成，整体经 `asyncio.to_thread` 移出事件循环，避免阻塞其他任务的 SSE 流。工具描述仅生成一次（TaskAgent 持久实例）。

### 8.4 富文本契约（_PROMPT_RICH_TEXT × Markdown.tsx）

系统提示注入 `_PROMPT_RICH_TEXT`，承诺的渲染能力与前端渲染管线严格对齐（prompt 承诺什么，前端就支持什么）：

| 能力 | LLM 输出形态 | 前端渲染（src/components/Markdown.tsx） |
|------|-------------|----------------------------------------|
| Mermaid 图表 | ```mermaid 代码块 | splitSegments 提取 → Mermaid 组件渲染 |
| SVG 图形（块级） | `<svg>` 标签（仅图形元素 rect/circle/text/path/g 等） | splitSvgSegments 提取 → DOMParser 白名单清洗（元素/属性白名单，剥 script/foreignObject/事件属性/外链 href）→ dangerouslySetInnerHTML |
| 行内样式 | `<span style="color:#663399">`（style 仅视觉属性：color/background/font-weight/font-size/padding/border-radius 等） | 行级白名单标签管线：受控 React 元素 + style 声明级白名单（position/z-index/float 等 layout 属性剥除、url() 注入拒绝）；b/strong/i/em/code/mark/u/sub/sup/br 同通道 |
| 标准 Markdown | 表格/列表/代码块/加粗等 | ReactMarkdown + remark-gfm |

安全边界：文本节点永远经 React 转义（不拼接 HTML 字符串），HTML 唯一注入点是清洗后的 SVG；未闭合标签（流式中间帧）整行降级 ReactMarkdown（未闭合 SVG 降级显示源码），不 crash；`x < y` 类数学式因无成对闭合标签不走行内管线，行为不变。约束：表格单元格内不支持 HTML（prompt 明确告知 LLM）。测试 tests/Markdown.test.tsx（14 用例：清洗/上风/降级/回归）。

历史教训（2026-10）：曾出现承诺与实现脱节——prompt 承诺「直接嵌入 <svg>」但前端 react-markdown 默认不解析原始 HTML，SVG/span 以源码文本显示（用户实测 rebecca purple 色卡暴露）；修复时行内标签一并纳入白名单管线。

UI 细节（迭代卡片层级、流式思维展示节奏、视觉状态色）见 [1.2streaming-thought-display](1.2streaming-thought-display.md)。

### 9.2 流事件协议（task:stream，10 种）

后端 TaskAgent.run() 为 async generator，经 POST /tasks/{id}/chat 的 SSE 流转发；Electron 解析后 `sender.send('task:stream', {taskId, type, data})` 按任务分发。前端 useTaskChat 按类型处理：

| type | data | 前端行为 |
|------|------|----------|
| `reasoning` | {content} | 追加到当前轮推理块；新事件到来前归档上一轮快照 |
| `plan` | {text, steps[], total} | 渲染 PlanProgressCard |
| `thought` | {content} | 轮次边界：归档上一轮内容 → 清空流式区 → 迭代计数 +1，步骤列表仅留 action |
| `action` | {tool, input} | 追加工具步骤卡 |
| `observation` | {content, diff?, file_path?} | 回填最近一个未完成的 action；diff 渲染 DiffCard；file_ops/doc_generator 触发文件树刷新 |
| `answer_chunk` | {content} | 流式追加正文（同时归档当前推理块） |
| `confirm_shell` | {command, task_id} | 弹 shell 确认框 |
| `confirm_skill` | {skill_name, task_id} | 弹 skill 确认框 |
| `confirm_expired` | {kind, task_id} | 确认等待超时：关闭对应确认弹窗（kind: shell / skill，含前台与 bgStates 副本）；跳过原因由该 action 的 observation 回填（§7.2） |
| `done` | {} | 流式状态本地转永久消息（reasoning/thought/action/observation/assistant 按轮分组重建，**不重拉 DB**），清理状态，触发 onDone |

### 9.3 多任务并行：bgStates 后台状态缓存

多任务可同时运行（MAX_CONCURRENT=3），但同一时刻只有一个任务在前台。useTaskChat 维护 bgStates（Map<taskId, 流式状态>）：

- 切走：当前任务全部流式状态（content/reasoning/steps/iteration/planData/待确认弹窗）存入 bgStates；后台任务事件继续经 task:stream 到达，直接更新 bgStates 条目（不入 React state，零渲染开销）
- 切回：bgStates 恢复到前台 state，进度无缝衔接
- done：后台任务完成直接清 bgStates（DB 已有消息，切回时拉取）

### 9.4 确认弹窗与恢复入口

- **shell 确认**：允许 / 允许且本会话不再询问 / 拒绝；后台任务的确认请求存 bgStates，切回时弹出；等待 120s，超时后端发 `confirm_expired` 关弹窗并在 action 卡留痕「确认超时」
- **skill 确认**：允许（= 永久信任，needs_confirm 落库置 0，此后不再询问，§7.2）/ 拒绝（仅本次）；等待 180s，超时发 `confirm_expired` 关弹窗（含 bgStates 副本）并留痕；对已失效弹窗点击时 confirm-skill 返回 found=false，会话内提示「该确认已超时失效」；done/clearStreamState 兜底清残留弹窗（终态不挂死弹窗）
- **恢复（resume）**：canResume 由 GET /tasks/{id}/has-state 驱动；点击后 POST chat（message='' + resume=true），任务从断点续跑
- **崩溃重置**：Python 进程重启后前端可能残留 isGenerating，resetGeneratingState 兜底复位

### 9.5 文件交互

- 拖拽/点击上传 → tasks:uploadFiles → 后端存 workspace + 注入系统消息（「用户上传了文件…」）通知 agent
- 文件树点击 → files/content 预览（文本高亮/图片 base64/二进制提示）；宽度可拖拽调整

## 10. 数据存储与 API

### 10.1 表结构（DDL，python/db/database.py）

```sql
-- 任务主表（venv_path / mode 为迁移列，初始建表后新增）
CREATE TABLE tasks (
    id TEXT PRIMARY KEY,
    title TEXT,
    status TEXT DEFAULT 'active',     -- active | archived | deleted
    workspace_path TEXT,
    venv_path TEXT,                    -- 迁移列；用户自选 workspace 时为空
    mode TEXT DEFAULT 'coding',        -- 迁移列：coding | general
    created_at TEXT,
    updated_at TEXT                    -- 每条新消息时刷新（auto_archive 依据）
);

-- 消息表（role 六种；工具调用细节全部在 metadata JSON）
CREATE TABLE task_messages (
    id TEXT PRIMARY KEY,
    task_id TEXT REFERENCES tasks(id) ON DELETE CASCADE,
    role TEXT,                         -- user | assistant | reasoning | thought | action | observation
    content TEXT,
    metadata TEXT,                     -- JSON：action/observation 携带
                                       --   {tool_name, tool_input, tool_output?, diff?, file_path?, action_id?}
    created_at TEXT
);
CREATE INDEX idx_task_messages_task ON task_messages(task_id);

-- 断点状态（崩溃/暂停恢复）
CREATE TABLE task_agent_state (
    task_id TEXT PRIMARY KEY REFERENCES tasks(id) ON DELETE CASCADE,
    state_json TEXT,                   -- {messages(含 tool_calls 配对), iteration, recent_errors, auto_saved}
    paused_at TEXT
);

-- 第三方 Skill（needs_confirm 为迁移列，DEFAULT 1：建表语句无此列，经 ALTER TABLE 添加；
--   迁移必须位于建表之后 —— _migrate_add_column 对不存在的表静默跳过，
--   2026-10 曾因迁移写在建表前导致全新库缺列，confirm 时报 no such column）
CREATE TABLE skills (
    id TEXT PRIMARY KEY, name TEXT NOT NULL UNIQUE, description TEXT,
    source_type TEXT NOT NULL DEFAULT 'builtin', source_path TEXT,
    install_path TEXT NOT NULL, enabled INTEGER NOT NULL DEFAULT 1,
    created_at TEXT
);
ALTER TABLE skills ADD COLUMN needs_confirm INTEGER DEFAULT 1;  -- 迁移（建表后执行）
```

读写定位：tasks 为列表/过滤/归档的唯一事实（message_count 联表聚合）；task_messages 是会话回放源（重启后重建上下文只取 user/assistant）；task_agent_state 仅供断点续跑，done/error 后清除（暂停保留）；skills 与安装目录双源（DB 记录 + install_path 文件），注册时以 DB 为清单、文件存在性为准。

### 10.3 端到端数据流

**执行链（写）**：
```
输入框 → guardSend（useFeatureGuard） → IPC tasks:chat → Electron fetch 转发（SSE 豁免超时）
  → POST /tasks/{id}/chat（准入+闸门） → TaskAgent.run 异步生成器
  → SSE event 流 → Electron 解析 → task:stream → useTaskChat（活跃任务 / bgStates 后台任务）
  终态：activity_events.complete_task/fail_task → notifications + activity:stream（[0.4 §6.4](0.4lifecycle-design.md)）
```

**回放链（读）**：任务切回/重启 → GET /tasks/{id}/messages → enrichMessages → 按轮分组渲染。

### 10.4 与长时活动模型的联动

任务接入统一活动模型（[0.4](0.4lifecycle-design.md)）：活跃状态源 = GET /tasks/status 包装；终态 = activity_events（done→completed / error→failed）；前端消费 = useActivity('task')（TaskStatusMonitor、导航角标）；准入 = ensure_ready("task") + useFeatureGuard。本文档不重复展开全局反馈面。

### 12.2 设计层面的优化建议

| # | 方向 | 说明 |
|---|------|------|
| 1 | 迭代上限自适应 | 固定 25 轮对简单任务冗余（多轮空转耗 token）、对复杂任务不足；可按任务类型/历史长度自适应，或在接近上限时主动提示 |
| 2 | edit-verify 重试上限显式化 | 重试次数为函数内常量，建议与 task_timeout 一致地纳入设置而非常量 |
| 3 | bgStates 无上限 | 多任务后台流式状态常驻内存（steps 全量累积），长任务多开时内存增长；可对非活跃任务仅保留摘要 |
| 4 | planner 上下文窗口 | 取近 6 条非 system 消息，长对话后早期约束可能遗失；可升级为压缩摘要 + 近期消息的混合 |
| 5 | Skill 依赖声明 | 预装包外依赖靠 agent 运行时发现缺包后 pip install；若 SKILL.md 支持依赖声明可在安装时预装 |
| 6 | 断点状态清理时机 | 应用崩溃后 task_agent_state 残留属预期（可恢复）；但用户主动「新消息重入」会静默丢弃断点，可考虑提示未完成的上次执行 |
