# 填表系统设计（Word 表单智能填写）

> **概述**：填表系统是项目的**第二种产出形式**，与报告系统并列——报告输出自由文本长文，填表输出结构化 Word 表单（从项目知识库提取字段值填充 docx 表格）。本文档为实施设计，核心机制移植自已验证的 form_fill_v2 实现（模板两阶段分析 + TemplateSchema 落盘 + 批次化填表），并适配 InkCube 的 SQLite / 统一活动模型 / IPC 架构。**已按 §7 六步路径落地（2026-10）**：`python/form_fill/` 移植包 + `routers/forms.py` 11 端点 + Electron IPC 11 通道 + 前端 `FormsTab` / `FormSchemaForm` / `FormTemplatePanel`（原 mock 原型已全部清除，见 §5.4 不变量 7）；实现与设计的一致性由 [2.1 §10](2.1project-design.md) 概要登记，本文档即现状文档。

**已确认决策**（2026-10-14）：

| 决策点 | 结论 |
|--------|------|
| 表单范围 | 仅 Word（.docx）表单，不含 XLSX |
| 模板入口 | 预置模板 3 张：《投资推荐项目情况表》《招商引资项目信息表》《项目立项审批表》（`resources/templates/forms/`，文件名纯 ASCII，随包配出厂预解析产物 `{stem}.schema.json`，新用户 seed 即 success 开箱即用）+ 用户上传自定义模板，共用同一分析管线 |
| 检索范围 | 项目知识库 + 关联基础库；**不含互联网** |
| LLM | 用户 settings 标准档模型（与报告一致，`LLMClient`），可经 `form_analyze_model`/`form_fill_model` 管线路由选档覆盖（llm/routing.py 档位制，空按标准档解析、槽位互为回退；2.6 §12.2.13）；不硬编码厂商 |
| doc_section 写作 | **保留**（Word 表单模板普遍含写作区，砍掉大幅降低可用性） |

## 1. 定位：与报告系统的对比

| 维度 | 报告系统 | 填表系统 |
|------|---------|---------|
| 产出形式 | 自由文本（长文） | 结构化 Word 表单（表格内填值 + 写作区） |
| 内容特征 | 分析性、论述性 | 数据性、清单性为主，少量写作区 |
| 输出格式 | docx / pdf（[2.5](2.5report-design.md)） | docx（python-docx，已在依赖内） |
| 生成方式 | LLM 按章节生成 | 按模板 Schema 批次化提取 + 写入原语回填 |
| 模板形态 | JSON 模板（章节大纲） | docx 模板 + 分析产出的 TemplateSchema（JSON） |

## 2. 核心机制（移植自 form_fill_v2）

核心思想：把硬编码的「格子知识」变成可落盘、可复用的 **TemplateSchema**。分析是为模板建索引，填表是按索引驱动。

### 2.1 模板分析（两阶段）

```
模板 docx（预置 seed 或用户上传）
   ↓ 建记录 (status=pending)
后台分析任务 (status=analyzing)
   ├─ 阶段一：结构提取（确定性规则，python-docx + OOXML，可单测）
   │    递归遍历表格 → 8 级决策树逐格分类 → 候选字段清单（含上下文线索）
   ├─ 阶段二：语义映射（LLM 一次调用）
   │    field_key 命名 / fill_type 确认 / kb_query 生成 / 批次规划 / 置信度
   ├─ 校验（路径存在性 / key 唯一性 / 类型一致性 / 批次 DAG）
   ↓ 写 template_schema (status=success)；失败 status=failed（异常）/ invalid（格式不符）
```

**定位模型**：XML 路径 `top{i}/r{ri}c{ci}/nested{j}/r{ri}c{ci}`（同层 findall 顺序索引，0 起）。不使用 `(row, col)` 逻辑坐标——vMerge/gridSpan 导致 python-docx `cell(r,c)` 映射歧义（参考实现实测结论）。分析器输出与填充器输入使用同一套路径，**Schema 即接口**。

**六种 fill_type**：

| fill_type | 结构特征 | 填充方式 |
|-----------|---------|---------|
| text | 值格（左标签 / 下划线 `___` / 【】占位） | 清格写入，保留首 run 字体 |
| choice / checkbox | □☐○ 勾选符（≥2 选项 / 单选项） | □→☑ 跨 run 替换（3 种分布 + 引号归一），支持多选；「□租赁：___平方米」复合格拆出 blank 子字段 |
| label_group | 同格多段落「短标签：」堆叠 | 逐锚点定位段落，「标签：」后整段替换 |
| table_rows | 首行为表头的数据表 | 从 header_rows 起逐行写入，不足时 deepcopy 末数据行追加 |
| doc_section | 长文本含指令动词（说明/分析/总结…） | 写作式生成，按预解析子节（「一、二、…」）循环成文 |

**两种 fill_mode**：`kb_fill`（默认，运行时检索决定是否留白——禁止分析阶段预判「知识库没有」而跳过，知识库内容是动态的）；`rule_fill`（仅规则可定字段，如申请日期 `rule_hint=today`）。

**批次规划固化于 Schema**（`batches`）：分析阶段由 LLM 在语义映射同一次调用中产出草案（章节为批边界、单批 ≤12 字段、批内 kb_query 去重合并为 2~4 条、仅「总结/估值」类章节声明 `depends_on`），代码校验（覆盖性 / 无环 / 体量）不过则回退默认分批。**填表执行时零批次决策，只按拓扑序执行**。

**阶段一决策树摘要**（完整实现见移植代码）：含嵌套表 → container 递归；勾选符 → choice/checkbox（选项内嵌「标签：___单位」拆独立 blank 字段）；≥2 段「短标签：」→ label_group；下划线/【】占位 → text；空格 → 查左标签上下文；短文本 → label（仅上下文）；长文本含指令动词 → doc_section；兜底 label 交 LLM 二次判断。**结构锁定**：choice/checkbox/table_rows/label_group 为结构锁定类型，LLM 不得改判；text/doc_section 保留修正权。

**模板制作惯例（写作区自描述，2026-10-18）**：写作区大格内应放「请说明/介绍/阐述…」指引文字（≥20 字含指令动词，命中决策树规则 7 → doc_section + instruction 作写作指引）——纯空白大格走「空格查左标签」只会产 text 候选，AI 初填退化为单行值而非成段写作。预置模板已按此惯例制作（dev/_gen_form_templates.py）；用户自制模板同样建议在写作区印填写要求（真实政务表普遍如此）。

### 2.2 填表执行（批次循环）

```
读 Schema.batches（拓扑排序）
for batch in batches:
  (1) rule_fill 直填（项目基础信息 / rule_hint）
  (2) 检索：各字段（含 label_group 子锚点）kb_query 按字段轮转交错去重（≤8 条/批，
      轮转保证截断后每字段至少保留首条；merged_kb_queries 预合并层已删除 2026-10-15）
      → KnowledgeSearchTool（项目知识库 + 关联基础库联合检索，口径同报告 knowledge 通道；
      同一资料块跨检索词先到先得去重，不重复占 kb_context 预算）
      资料块带来源标注（「—— 来源：{filename}」；无 metadata 时省略）
  (3) 生成：批内字段一次 LLM 调用输出严格 JSON 值集
      上下文 = 检索片段 + 项目主体锚定段 + 项目基础信息 + 前序批次产出摘要
      资料块预算（2026-10-15）：kb_context 总长经 derive_kb_chars_budget(llm_settings)
      动态计算——(budget.context_window − budget.output_tokens − 8192 结构余量)
      × CHARS_PER_TOKEN(1.5) × 0.7 安全垫，clamp [24k, 120k] chars，默认配置
      ≈94,600 chars（旧硬截 24,000 严重低用窗口，80k chars 检索入口不再触发截断）；
      tokens 判断经 llm/budget.py 唯一入口（口径纪律：判断 token、切片 chars）。
      主体锚定（2026-10-15）：「## 项目主体」段注入 company_name/credit_code +
      归属甄别指令——资料归属与主体不符或无法确认的（他企执照/证书、关联方
      与客户供应商文件、个人材料等）不得作为字段依据；基础信息未登记时降级
      为通用甄别指令。系统 prompt 资料纪律含同款主体纪律。
      严禁编造：资料不足的字段输出 null
  (4) 归一化 + 写入：_normalize_value 严校验（选项白名单/数值提取/多选收敛）
      → docx_filler.apply_field 按 fill_type 分发写入 → 逐批更新 progress（单调递增）
导出：产物 docx 落盘 + 值集/报告落库
```

**填表报告**：每字段一行 `{field_key, label, fill_type, status: filled|no_data|failed, value_preview, missed}`。no_data（查无资料）一律**留空不写占位文字**，仅在报告中说明，供人工补填；勾选类 no_data = 不勾选任何项，报告中与漏填区分。

**人工修订通道**（不走 LLM）：前端抽屉改值提交 → 值集经 `_normalize_value`（对自身输出幂等，参考实现双模板 55 字段实测）→ `apply_field` 重写模板 → 秒级重新生成产物。AI 初填与人工修订共用同一值集形状与落库通道。

### 2.3 重解析（修正 Schema）

分析结果不准（字段判错 / 选项拆分错 / 子字段遗漏）→ 用户补充说明（必填）→ 携带上次 `llm_mapping` 原始输出作基线整体送 LLM 局部修正：未提及部分原样保留、`field_key` 保持稳定（下游按其落库与回显）、输出完整 JSON 覆盖原 schema。

### 2.4 边界与拒绝策略

| 情形 | 处理 |
|------|------|
| .doc 老格式 / 文档损坏 | status=invalid，提示另存为 .docx |
| 无任何规则表格（纯段落文档） | status=invalid |
| Wingdings 类符号字体勾选符 | 该格降级 unmapped，其余照常 |
| 嵌套超过 3 层 | 第 4 层起整表 unmapped（防失控） |
| 图片 / SDT 内容控件 | 忽略，不入 Schema |
| LLM / 嵌入模型未配置 | 发起前 `ensure_ready` 结构化报错（对齐 [0.4 §7.3](0.4lifecycle-design.md) 准入） |
| 应用重启时 analyzing/filling 残留 | 启动恢复：重置为 pending 由后台重新拾取（对齐 task_queue 中断恢复模式） |
| 模板文件内容变更（分析成功后被替换/修改） | 列表/详情响应时动态比对 file_hash 标记 `file_changed`（行内橙字提示）；发起填表 409 `FORM_TEMPLATE_CHANGED`（旧 schema 的格子索引填新文件会错位），重解析后自动解除 |

## 3. 表结构（SQLite DDL）

### 3.1 form_templates — 模板表（全局共享，模板不可变）

```sql
CREATE TABLE form_templates (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,                  -- 中文模板名（预置：如《投资推荐项目情况表》）
    source TEXT NOT NULL DEFAULT 'upload',   -- preset / upload
    file_path TEXT NOT NULL,             -- preset 指向 resources/templates/forms/；upload 存 data/form_templates/
    template_schema TEXT,                -- JSON：TemplateSchema（§3.3）
    llm_mapping TEXT,                    -- JSON：上次语义映射原始输出（重解析基线）
    user_hint TEXT,                      -- 用户补充说明（重解析时必填）
    status TEXT NOT NULL DEFAULT 'pending',  -- pending/analyzing/success/failed/invalid
    error TEXT,
    field_count INTEGER,                 -- 冗余字段数（列表页展示）
    file_hash TEXT,                      -- SHA-256（分析成功时写入，含出厂预置 seed；NULL=存量不参与比对）
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE INDEX idx_form_templates_status ON form_templates(status);
```

- **预置模板 seed**：对齐 `seed_wiki_schemas` 幂等模式（按固定 id 逐条 INSERT，清单 `PRESET_FORM_TEMPLATES` 见 forms.py，固定 id 如 `form_tpl_investment_recommend`），启动时不存在则插入。**出厂预解析产物随包**（2026-10-18）：每张 docx 配 `{stem}.schema.json`（含 template_schema/llm_mapping/file_hash/field_count，由 `dev/_preset_form_schemas.py` 跑真实分析管线生成），seed 时读产物直接落 `status=success`——新用户首次启动零 LLM 调用、零等待开箱即用；`preset_form_templates()` 逐张校验产物 `file_hash` 与 docx 配对（schema 的 target 是文件格子索引，错位会填错格），缺失/损坏/不配对回退 `status=pending` 由运行时分析兜住。已存在记录仅对齐 `file_path`（预置文件随版本移动/改名时迁移路径，分析产物保留不重分析）；分析产物（schema/mapping）落库，**模板 docx 本身不复制**，`file_path` 直接指向 resources（打包兼容同 `paths.py::get_templates_dir()` 单一来源链路，2026-10-21 自报告模块 loader.py 收敛）。
- **模板不可变**：上传模板修改 = 重新上传 = 新记录；预置模板仅支持重解析（reanalyze 覆盖 schema 与 mapping，不动文件）。
- **读**：列表页（轻量视图：不含 schema/mapping 大列；含 file_path/file_hash 供路由层动态比对 `file_changed`，比对列不出路由层）、详情页（schema/unmapped/user_hint）；**写**：seed、上传、状态流转（仅后台任务）、reanalyze、物理删除（引用容错：模板随时可删，实例侧悬空提示，见 §3.2 与 §5.4 不变量 11；原 FK RESTRICT 409 拦截已于 2026-10-16 摘除落地）。
- **文件变更检测（零状态同步）**：分析成功时计算文件 SHA-256 落 `file_hash`；列表/详情响应时实时重算比对得 `file_changed` bool（不落标记列），重解析成功写入新 hash 后提示自动消失；存量 `file_hash` 为 NULL（升级前已分析的记录）不提示，下次重解析后自然生效。

### 3.2 form_fills — 填表实例表（项目作用域）

```sql
CREATE TABLE form_fills (
    id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    template_id TEXT NOT NULL,           -- 生成时模板 id；无外键（2026-10-15 摘除，
                                         --   模板随时可删，悬空容错见 §5.4 不变量 11）
    title TEXT NOT NULL,                 -- 默认「{模板名} {YYYY-MM-DD}」，可改
    output_path TEXT,                    -- 产物 data/form_fills/{id}.docx
    report TEXT,                         -- JSON：填表报告（§2.2 字段行清单）
    filled_values TEXT,                  -- JSON：完整值集（形状与 LLM 值集同构）
    status TEXT NOT NULL DEFAULT 'pending',  -- pending/filling/success/failed
    progress INTEGER NOT NULL DEFAULT 0, -- 0-100，逐批单调递增（封顶 95，完成 100）
    error TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE INDEX idx_form_fills_project ON form_fills(project_id);
```

- **读**：项目实例列表（`LEFT JOIN form_templates` 附模板名，悬空实例可见且 `template_name` 为 NULL）、详情（schema + 值集 + 报告，动态表单回填所需；模板缺失时 schema 为 null）；**写**：create（发起）、后台任务状态/进度流转、update（人工修订重新生成）、删除（级联删产物文件）。
- **摘除外键（2026-10-16）**：`template_id` 摘除 `REFERENCES form_templates(id)`（NOT NULL 保留）。项目未上线、无存量库负担：直接修改 DDL，不提供迁移；开发机旧结构库删除本地 .db 重新初始化即可。

### 4.2 端到端路径

**写路径 A — 模板分析**：
`全局模板管理页上传` → IPC `form-template:upload`（multipart，120s 超时）→ `POST /forms/templates/upload` → 存 `data/form_templates/{id}.docx` + INSERT(status=pending) → 立即返回 `{id}` → `background_tasks.add_task(_run_template_analysis)`：结构提取 → LLMClient 语义映射（usage 落 app.log）→ 校验组装 → UPDATE status/template_schema/field_count（失败：failed/invalid + error）→ 终态 `complete/fail_form_template` → notifications + SSE。预置模板走启动 seed：带出厂预解析产物（§3.1）直接 `status=success` 开箱即用；产物缺失/不配对才回退 pending 走同一分析管线（均无 upload 步骤）。

**写路径 B — 填表执行**：
`FormsTab 选模板发起` → IPC `form-fill:create` → `POST /forms/fills`（project_id + template_id + title）→ INSERT(status=pending) → 返回 `{id}` → 后台：读 schema + 模板 docx → 批次循环（§2.2，逐批 UPDATE progress）→ 产物写 `data/form_fills/{id}.docx` + report/filled_values 落库 + status=success → `complete_form_fill`。并发上限 `form_fill_max_concurrent`（settings，默认 2），超限 429（对齐报告模式）；模板文件已变更（§2.4，file_hash 比对不符）时 409 `FORM_TEMPLATE_CHANGED` 阻断——防旧 schema 填错位。

**写路径 C — 人工修订**（同步，无 LLM）：
`FormSchemaForm 改值提交` → IPC `form-fill:update` → `POST /forms/fills/{id}/update`（值集）→ 值集归一化落库 → 读模板 docx 逐字段 `apply_field` 重写产物 → 返回最新值集与报告。

**读路径**：
实例列表 `form-fill:list` → `GET /forms/fills?project_id=`（limit/offset 分页 + has_more/total，limit=0 全量）；详情 `form-fill:detail` → `GET /forms/fills/{id}`（模板列表同构）；模板管理页列表 `GET /forms/templates`（q/status 服务端筛选下沉 + limit/offset 分页 + total）；产物下载 `form-fill:download` → `GET /forms/fills/{id}/download`（文件流）→ Electron dialog.showSaveDialog 写出。模板分析中/填表中的明细刷新由 `usePolling` 驱动同一批 GET 端点（enabled 从 `useActivity(kind).isActive` 派生，[0.4 §5.8](0.4lifecycle-design.md)）；列表轮询按已加载量重拉（usePagedList reload，不退回第一页，列表分页统一约定见 [0.1 §16](0.1dev-guide.md)）。

### 5.4 关键交互规则与不变量

1. **填表执行零批次决策**：批次固化于 schema.batches，执行层只按拓扑序消费。
2. **no_data 不写占位文字进 docx**：留空 + 报告说明；前端以待补填徽标引导，与漏填/失败区分。
3. **值集形状同构**：AI 初填与人工修订共用 `filled_values` 通道；`_normalize_value` 对自身输出幂等，修订不走 LLM。
4. **进度单调递增**：批次完成推进（封顶 95%），收尾 100%；不因批次失败回退。
5. **模板不可变**：预置模板仅 reanalyze；上传模板重传 = 新记录。
6. **模板管理入口全局唯一**：模板 CRUD 与 schema 查看只出现在全局模板管理页；项目页只消费（发起弹窗选模板），不做管理动作——避免跨项目语义混乱（在 A 项目删模板影响 B 项目）。
7. **mock 全部清除（已落地）**：原 `FormsTab.tsx` 的 `MOCK_FORM_TEMPLATES` / `MOCK_FORMS` / `MOCK_FIELDS`、200ms×10 假进度动画、`alert` 导出动作已随重构删除（2.1 §13.2 登记项已核销）；填表链路禁止再引入 mock 数据。
8. **轮询谓词纪律**：页面明细轮询 enabled 一律从 `useActivity(kind)` 派生，不自建布尔（[0.4 §5.8](0.4lifecycle-design.md)）。
9. **i18n 双语**：新增 UI 文案全部走 `project.forms.*` / `activity.form_*` 键（中英）。
10. **文件变更检测零状态同步**：`file_changed` 响应时动态比对 file_hash 得出（不落标记列、不参与模板状态机），重解析写入新 hash 后自动解除；后端 create 同步准入拦截（409 `FORM_TEMPLATE_CHANGED`）与前端置灰为双层防御。
11. **模板引用解耦（2026-10-15）**：`form_fills.template_id` 无外键，模板随时可删；悬空实例走容错链——查看（详情 schema=null 降级）、人工修订（409 `FORM_TEMPLATE_MISSING`）、发起填表（404）、后台填表/重启拾取（failed「模板不存在」）、下载（不受影响）；实例列表 `LEFT JOIN` 模板名，悬空行可见。与 playbook_templates「已生成实例与模板解耦」语义对齐（3.0 §4.1）。
