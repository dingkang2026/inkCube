## 四、设计说明

### 4.1 轮询 vs 事件推送

当前所有轮询均为前端主动拉取（pull），未使用 WebSocket 或 SSE 推送。原因：

- 任务对话（Task Chat）已使用 SSE（`StreamingResponse`）实现流式输出，但状态查询仍用轮询，因为状态变化频率低、逻辑简单，轮询足够且实现成本低。
- 后端 Python 侧的异步任务（文件解析、Wiki 编译、模型下载）没有主动推送通道，前端只能通过轮询获取进度。

### 4.2 常驻轮询 vs 条件触发

- **常驻轮询**（#1、#4）：无论用户操作如何都会运行，但 #4 采用自适应频率降低空闲时的开销。
- **条件触发轮询**（其余）：仅在特定操作进行时启动，操作结束或页面离开后自动停止，避免不必要的网络请求。

### 4.3 防重叠机制

- WikiTab 编译进度轮询（#3）使用 `polling` 标志位防止请求重叠（上一次请求未完成时跳过下一次）。
- 其他轮询依赖 `setInterval` 的自然间隔，通常后端响应时间远小于轮询间隔，不会重叠。

## 五、优化建议

### 5.1 [P0] Wiki 编译状态重复轮询（#3 + #4）

**问题**：#3（WikiTab）和 #4（ProjectDetailPage）调用**同一个后端接口** `GET /wiki/projects/{id}/compile-status`。当编译对话框打开时，两个轮询同时运行——#3 每 2 秒、#4 每 5 秒，等于同一接口 2 秒内被请求 1.4 次，返回数据高度重叠。

**方案**：将 `wikiCompileState` 状态统一由 #4（ProjectDetailPage）管理，WikiTab 通过 props 消费该状态，删除 #3 的独立轮询。当 WikiTab 编译对话框打开且需要更高频率时，可在 #4 基础上临时将间隔降至 2s，关闭后恢复自适应。

**预期收益**：编译期间该接口请求量减少 50%+，且消除两个 useEffect 竞争同一数据源的一致性问题。

---

### 5.2 [P0] 缺少窗口可见性感知

**问题**：所有轮询在窗口最小化或被遮挡时仍全速运行。Electron 桌面应用中，用户切到其他应用工作时，InkCube 仍在后台持续请求 Python 后端（#1 每 5s + #4 空闲态每 30s = 每分钟约 14 次无效请求）。

**方案**：

1. Electron 层（`electron/main.js`）监听 `mainWindow.on('focus')` / `mainWindow.on('blur')`，通过 IPC 广播 `window:visibility` 事件（`{ focused: boolean }`）。
2. 前端封装 `useWindowVisibility()` hook，全局可消费。
3. 常驻轮询（#1、#4）在 `blur` 时降频至 1/3（#1: 5s → 15s，#4 空闲态: 30s → 90s）。
4. `focus` 时立即恢复频率并做一次即时刷新，确保数据无延迟。

**预期收益**：后台时常驻轮询请求量减少约 70%。

---

### 5.3 [P1] 审阅状态检测功能重叠（#1 + #4）

**问题**：

- #1（WikiReviewMonitor）每 5s 调用 `GET /wiki/review-status`，检测全局 `waiting_review` 并弹 Toast。
- #4（ProjectDetailPage）每 10s 调用 `GET /wiki/projects/{id}/compile-status`，也检测 `waiting_review` 并显示 Tab 角标。

两者都在检测"等待审阅"状态，只是粒度不同（全局 vs 单项目）。

**方案**：#4 的 Tab 角标复用 #1 的全局数据（通过 props 传递 `waitingReviewCount` 并按 `project_id` 匹配当前项目），而不是独立发请求。这样 #4 在 `waiting_review` 态的 10s 轮询可以省掉，仅保留 `idle` 和 `compiling` 两种状态的自适应轮询。

**预期收益**：等待审阅态下减少 1 个轮询源的请求。

---

### 5.4 [P1] 缺少错误退避机制

**问题**：所有轮询在请求失败时（Python 后端未启动、网络异常等）仍以固定频率持续重试。以后端未启动为例，#1 每 5 秒发一次必定失败的请求，日志中充满错误。

**方案**：引入指数退避——连续失败时逐步拉长间隔，成功后恢复正常。封装到通用 hook 中：

```typescript
// 退避策略示例
const baseInterval = 5000
const maxInterval = 30000
const interval = Math.min(baseInterval * Math.pow(2, failCount), maxInterval)
// failCount: 连续失败次数，成功时重置为 0
```

**预期收益**：后端异常时避免请求风暴，减少无意义的错误日志。

---

### 5.5 [P1] 缺少请求防重叠保护

**问题**：仅 #3（WikiTab 编译进度）使用 `polling` 标志位防止请求重叠。其余轮询在后端响应慢于轮询间隔时，会出现多个请求同时在途。

**方案**：所有轮询统一加 `inFlight` 保护，推荐封装 `usePolling` hook：

```typescript
function usePolling(fn: () => Promise<void>, interval: number, enabled: boolean) {
  const inFlight = useRef(false)
  useEffect(() => {
    if (!enabled) return
    const timer = setInterval(async () => {
      if (inFlight.current) return
      inFlight.current = true
      try { await fn() } finally { inFlight.current = false }
    }, interval)
    return () => clearInterval(timer)
  }, [fn, interval, enabled])
}
```

**预期收益**：防止后端负载高时请求堆积，保证系统稳定性。

---

### 5.6 [P2] 报告生成期间双重轮询可合并（#7 + #8）

**问题**：#7（ReportWizard）和 #8（ReportPreview）在报告生成期间同时运行：

- #7 每 2s 查 `GET /reports/{id}` 获取进度
- #8 每 2s 查 `GET /reports/{id}/logs` 获取日志

两者触发条件完全一致（`report.status === 'generating'`），合计每 2 秒 2 个请求。

**方案**：

- 方案 A：后端新增组合端点 `GET /reports/{id}/progress`，一次返回 `{ status, progress, recent_logs }`，前端只需一个轮询。
- 方案 B（轻量）：保持两个端点，但将 #8 日志刷新频率从 2s 降至 5s（日志不需要 2 秒级实时性），减少 60% 的日志请求。

**预期收益**：报告生成期间请求量减少 30%-50%。

---

### 5.7 [P2] #1 间隔对于通知场景偏激进

**问题**：#1（WikiReviewMonitor）每 5 秒轮询一次，目的是检测"新的待审阅任务"并弹 Toast。Wiki 编译本身耗时较长（分钟级），从"编译完成"到"用户看到通知"延迟 10-15 秒完全可以接受。

**方案**：将 #1 的间隔从 5s 调整为 15s，配合 5.2 的窗口可见性感知（失焦时 30s），足以满足通知时效性。

**预期收益**：常驻请求量减少 66%（从 12 次/分钟降至 4 次/分钟）。

---

### 5.8 [P3] 统一轮询管理架构

**问题**：12 个轮询分散在 8 个组件中，各自独立管理 `setInterval`/`setTimeout`，没有统一的生命周期控制。

- 无法全局暂停/恢复（如窗口失焦时批量降频）
- 无法监控当前有多少轮询在运行
- 调试时难以追踪请求来源
- 新增轮询需要重复编写 `useEffect` + `setInterval` 样板代码

**方案**：创建 `PollingManager` 单例或 React Context：

```typescript
class PollingManager {
  register(id: string, fn: () => Promise<void>, interval: number, options?: PollingOptions): string
  unregister(id: string): void
  pause(id: string): void
  resume(id: string): void
  pauseAll(): void       // 窗口失焦时调用
  resumeAll(): void      // 窗口获焦时调用
  setFrequency(id: string, interval: number): void
  status(): Record<string, PollingState>  // 调试用
}
```
