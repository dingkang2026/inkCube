# PPT 导出设计

> **概述**：PPT 导出是报告系统的**下游渲染能力**——将报告引擎已生成的 Markdown/Word 内容适配幻灯片版式输出 `.pptx`，不做二次内容生成。该功能**尚未实施**：报告导出现状仅有 docx / pdf 两条链路（[2.5 §渲染](2.5report-design.md)），代码中无 PPT 生成实现（无 python-pptx 依赖、无路由 / IPC / 前端入口）。本文档承载实施前需确定的设计决策，作为后续立项依据。「本阶段不做 PPT」的决策见 [2.1 §12](2.1project-design.md)（决策 10）与 [0.0 §6](0.0architecture.md) 功能矩阵。

## 1. 定位与设计原则

PPT 导出是墨方报告系统的下游渲染，不是独立的生成管线：

```
模板 → 报告引擎生成 Word 内容 → 渲染为 PPT
```

| 原则 | 说明 |
|------|------|
| 不单独定义 PPT 内容模板 | 复用报告模板生成的内容（章节结构、表格、引用），PPT 侧只定义视觉版式 |
| 不做二次生成 | 不调用 LLM 重新生成内容，只做格式转换与版式适配 |
| 排版优先 | 长文内容适配幻灯片布局的核心问题是信息密度控制，而非内容再加工 |

## 2. 依托现状

实施 PPT 导出可依托的报告导出既有链路：

| 链路 | 实现 | 说明 |
|------|------|------|
| Markdown → docx | `report_generator/renderer.py`（python-docx） | 报告引擎内置渲染，标题三层分离、引用转上标、尾注列表 |
| Markdown → PDF / docx → PDF | `tools/doc_generator.py`（Agent 工具） | md_to_pdf 走 pandoc；docx/pptx/xlsx → PDF 走 MS Office COM 或 LibreOffice headless |

注：`doc_generator` 的 `docx_to_pdf` 可接受 `.pptx` 输入，但那是「PPTX 文件 → PDF」的格式转换（Office COM 能力），与「报告内容 → PPT」的生成无关。

## 3. 实施前需确定的设计点

以下四项是立项时必须先回答的设计问题：

1. **内容映射策略**：Word 长文（章节 / 段落 / 表格 / 引用列表）如何映射到幻灯片页面——按章节切页、按信息单元切页，还是混合策略；单页信息密度上限。
2. **幻灯片布局类型**：至少需要封面页、章节分隔页、正文内容页、表格页、来源页、结束页六类版式，各类版式的占位符结构。
3. **PPT 模板系统**：视觉样式（配色 / 字体 / 版式）与报告模板分离，用户可在应用内选择主题；模板的存储与分发方式。
4. **渲染流程与选型**：`Markdown → 内容分片 → 布局映射 → 样式渲染 → .pptx`。生成库选型（如 python-pptx）需先通过依赖评估（electron-builder / PyInstaller 打包兼容性、安装便利性、包体积，见开发规范 §三）。

## 4. 差异与下一步建议

### 4.1 文档与代码差异

无——功能未实施，本文档全部内容为前瞻设计，不存在与代码的对齐差异。

### 4.2 实施路径建议

按能力递进分四步，每步可独立交付：

1. **基础渲染**：封面 + 正文内容页 + 结束页，覆盖纯文字报告的最小可用导出。
2. **结构版式**：章节分隔页 + 表格页，覆盖带结构化内容的报告。
3. **PPT 模板系统**：主题切换（配色 / 字体 / 版式预设），与报告模板解耦。
4. **信息密度优化**：长段落压缩。注意与「不做二次生成」原则的边界——规则式压缩（要点抽取 / 截断）符合原则；若引入 LLM 摘要则构成内容再生成，需重新评估定位。
