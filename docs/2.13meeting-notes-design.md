# 拜访/会议纪要（Meeting Notes）设计

> 项目内「结构化素材创建器」：粘贴转写稿/手记 + 现场图片 → LLM 结构化（纪要正文 + 行动项）→ 人工确认 → 行动项建事务、正文归项目素材。
> 与便签（[2.12](2.12sticky-notes-design.md)）为两个独立功能。定位为项目管理级动线，**不新增 Tab、不新增列表页**。
> 三要素见 §2/§3/§4；活动体系见 [0.4](0.4lifecycle-design.md)，事务体系见 [3.0](3.0project-lifecycle-design.md)。

---

## 1. 决策记录（2026-10-27 brainstorm 收敛）

| 决策点 | 结论 | 落选方案与理由 |
|---|---|---|
| 功能定位 | **结构化素材创建器**：确认后的纪要就是素材列表里的一份 md 文件，行动项是事务条目（**2.14 演进**：迁出为项目详情页独立「纪要」Tab，正文留存归档行——独立列表的落选理由被验收实证推翻，见 [2.14](2.14meeting-notes-hub-design.md) 偏差 18） | 独立纪要列表/新 Tab：产物与素材分离，动线断裂；output Tab 新分区：纪要是过程记录非交付物 |
| 输入形态 | **文本（含外部转写稿粘贴）+ 图片** | 现场收音 + 本地转写模型（faster-whisper ~1.5GB）：2026-10-27 裁决不做——转写是讯飞/通义/飞书等成熟工具的主业，InkCube 自建成本高且质量不如专业工具；**转写外包，InkCube 吃转写结果**（差异化在「记录 → 行动项入事务 → 知识入项目」闭环，非转写） |
| 确认模式 | **智能体优先**：AI 预填（结构化产物），人工确认修改（正文/行动项均可编辑，行动项逐条勾选是否建事务） | 直接保存 AI 产物：违背「AI 预填人工确认」原则 |
| 异步承载 | **统一 Activity 模型**（kind=`note_structuring`，FunctionSource 注册），禁止自建轮询 | §2.7 硬约束 |
| 行生命周期 | **表行 = 进行中的向导中间态，终态即删行**（产物在素材与事务，行无长期价值）；自清理设计见 §2（**2.14 演进**：终态由删行改置 archived，行长期留存于纪要中心——「集中查看纪要」缺口实证，偏差 18） | confirmed 行长期留存：无 UI 消费即死数据，违反生命周期闭环（2.14 落地纪要中心后该落选理由消除） |
| 图片归属 | 纪要图片经现有素材上传通道成为**正式素材文件**，`image_file_ids` 仅记录引用 | 图片独立暂存区：多一套存储与清理，且图片本是项目资料应沉淀 |

## 2. 表结构

```sql
CREATE TABLE IF NOT EXISTS meeting_notes (
    id             TEXT PRIMARY KEY,   -- 裸 _uuid()（同 sticky 现状无前缀；初稿 'mnote_<uuid>' 示意未落地）
    project_id     TEXT NOT NULL,
    title          TEXT NOT NULL,      -- 默认「拜访-YYYYMMDD」可改
    occurred_at    TEXT,               -- 拜访/会议日期（ISO），NULL = 今天
    raw_text       TEXT,               -- 原始文本输入（含粘贴的转写稿），重试期间零丢失的保底
    image_file_ids TEXT,               -- JSON 数组，引用 files 表（素材文件）
    draft_md       TEXT,               -- LLM 结构化产物 JSON：{content_md, action_items:[{title}]}
    saved_refs     TEXT,               -- JSON：{file_id, task_ids[]}——confirm 分步落引用，重试幂等键
    last_error     TEXT,               -- 最近一次结构化失败原因（i18n 错误码），NULL = 无
    status         TEXT NOT NULL,      -- draft → structuring → structured → archived（confirm 成功置 archived，2.14 原删行）
    created_at     TEXT NOT NULL,
    updated_at     TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_meeting_notes_project ON meeting_notes(project_id, status);
```

读写行为与生命周期闭环：

| 操作 | 行为 |
|---|---|
| 创建草稿 | INSERT（status=draft）；title/raw_text/image_file_ids 可经 PATCH 随时改 |
| 发起结构化 | 前置校验（status∈{draft, structured}，structured 重发=回 draft 重走生成新产物，偏差 19；raw_text 与 image_file_ids 至少其一非空）→ status=structuring → 异步 LLM → 成功 status=structured + draft_md 落库；失败 status 回 draft + last_error 记录。受理时附图未解析的先入解析队列（pending 即时入队 / error 清残留重置重入队 / done 文件的 error 图强制重描述），附图就绪前 LLM 等待（见 §3 结构化路径） |
| 确认保存 | status 必须 structured → 正文与同步态对齐（见 §3 步骤 2，勾选框=同步目标态：勾选且内容变删旧传新 / 不勾且已入一律删旧 / 勾选且 file 缺失补传；载荷不一致回写 draft_md，偏差 19/20）→ 建事务（见 §3）→ **置 archived**（2.14 原删行：行长期留存于纪要中心） |
| 正文保存 | status ∈ {structured, archived}（偏差 20 放宽）：structured = 格式化态「暂存」（人工修改存回行内、保持待确认，不入素材不建事务不归档；重试残留 file_id 行照常联动删旧传新）；archived = 确认态人工修改确认。内容比对同 confirm 步骤 2 语义（不一致且已入素材删旧传新并回写，一致幂等跳过）；行动项与输入字段不可改（PATCH 409） |
| 删除纪要 | 用户显式 DELETE（useConfirm）；**级联清理行专属产物（偏差 20 推翻 2.14「仅删行」）**：素材 md（refs.file_id 完整级联）+ 现场图片（未被同项目其他纪要行引用时一并删，共享图片保护）；已建事务保留；confirm 进行中 409 |
| 崩溃恢复 | draft/structuring 行自然留存；启动时 structuring 残留行视为中断——后端启动清扫将其重置 draft + last_error=中断提示（幂等可重入，随现有启动恢复序列） |

级联清理：项目删除时 `meeting_notes` 同项目行级联删除（级联清单条目 [2.2 §10.1](2.2knowledge-base-design.md)，含 archived 行；初稿误写 3.0——非级联清单载体）；已保存产物（素材 md、事务）走现有项目级联。

## 3. 数据流

```
[Python FastAPI]  routers/meeting_notes.py（挂 /projects/{project_id}/notes）
  POST   /projects/{p}/notes                          创建草稿
  GET    /projects/{p}/notes                         未完成列表（draft/structuring/structured 待确认；草稿提示条/向导恢复）
  PATCH  /projects/{p}/notes/{id}                     编辑输入（缺席=不改、显式 null=清除；title 空值=不改）
  DELETE /projects/{p}/notes/{id}                     删除纪要（任何状态；级联素材 md+未共享现场图片，事务保留；confirm 进行中 409，偏差 20）
  POST   /projects/{p}/notes/{id}/structure           发起 LLM 结构化（异步）
  PATCH  /projects/{p}/notes/{id}/content            正文保存（structured 暂存 / archived 确认修改，偏差 20 放宽；内容比对删旧传新联动素材）
  POST   /projects/{p}/notes/{id}/confirm             确认保存（同步）
```

**结构化路径**（`structure`，异步）：
1. status 置 structuring → 返回 202；Activity 注册表 `note_structuring` 源 fetch 返回该行（entity_title=title, project_id）
2. 后台任务：**先等附图解析就绪**（定稿驱动，偏差 17——受理时附图才入解析队列；逐图三态判定：file pending/parsing 在途、error → IMAGE_FAILED、done 后查 images 全终态；轮询 2s 上限 600s，超时 IMAGES_TIMEOUT，图仍在后台解析可稍后重试；已删图跳过）→ 取 raw_text + 各 image_file_ids 对应 file 的解析文本（复用现有解析产物；后端对缺解析文本的图片跳过并随返回体 warning 提示）→ LLM 单次调用（`llm/routing.get_task_settings("meeting_note")` → 档位键 `meeting_note_model`，未配置按 standard 走全局默认槽；usage 落 llm_usage，source=`meeting_note`）→ 输出 schema JSON：`{content_md, action_items:[{title}]}`，反幻觉纪律写入 prompt（仅基于输入材料，无材料支撑的推断标「待确认」）
3. 成功：draft_md + status=structured（心跳快照可见，终态停轮）；失败：status 回 draft + last_error（i18n 错误码，前端 errorCodes 翻译）

**确认保存路径**（`confirm`，body: `{content_md, action_items:[{title, selected, due_date?}], save_to_materials?}`，同步；**分步落引用，重试幂等**）：
1. status=structured 守卫（并发双击后到者 409）
2. **正文与同步态对齐（勾选框 = 同步目标态，偏差 20）**：`save_to_materials=True`（目标「在素材」）——载荷 content_md 与行内 strip 不一致且已有 file_id → 先级联删旧素材文件（cleanup 完整级联：向量/图片索引/磁盘）再写新 md「纪要-YYYYMMD D-标题.md」重传（**函数级复用 upload 落盘 + 建 file 行 + 解析入队**，同 [2.12 §3](2.12sticky-notes-design.md)；`_upload_core` 无同名覆盖语义，重传即新 file_id 新档+重新解析刷新 RAG）；file_id 缺失（上传失败后重试，内容未变）→ 补传（偏差 20 修复原 content_changed 门控漏补传致「重试保存」死循环）。`save_to_materials=False`（目标「不在素材」）——已有素材一律删旧置 file_id=null（**内容未变也删**，偏差 20 修复原实现漏删）。载荷与行内不一致（正文或行动项）→ **回写 draft_md**（正文快照随行对齐载荷；偏差 19 修复原「只落 refs 不回写」——materialize/详情读 draft_md，不回写则移出再入回退 LLM 原稿）
3. 选中行动项逐个 `db.create_phase_task`（task_type='material'）→ 每成功一条即将条目 title 追加进 `saved_refs.task_ids`——单条失败不阻断其余，收集 failed 列表；重试时 saved_refs 已有的 task 跳过不重建（**幂等键 = 条目 title，偏差 21：改清单重试不再按下标误跳致漏建静默归档；存量 int 元素（旧格式）按下标跳过，双格式同表达式兼容免迁移；同名条目视为同一条待办**）
4. saved_refs 完整（file_id 或 save_to_materials=false + 全部选中项 title 已记，含全不选合法态）→ **置 archived**（2.14 原删行：行长期留存于纪要中心，正文副本随行）；返回 `{file, created_tasks, failed_tasks, archived: 实际状态}`（偏差 21 修正原恒 true 契约污染）前端逐项明示；未完整则行留存，前端「重试保存」按钮只补未完成步骤

**图片路径**（定稿驱动，偏差 17）：向导内选图仅本地 blob 预览（零服务端痕迹，未定稿放弃即无残留）；点「生成纪要草稿」定稿时才逐图走现有 `POST /projects/{id}/upload`（multipart，成正式素材文件）→ create/update 补全 image_file_ids → structure 受理入解析队列（§3 结构化路径等待就绪）。生成钮门控：新选图恒就绪；恢复草稿的已传图仍以 files Activity 判定 busy（未就绪禁用 +「图片理解中 n/m」）。**附图描述注入纪要上下文**：images.context_text 为空时（纪要附图无文档前后文）描述执行时查引用该 file 的纪要行，以「纪要《标题》+正文」为上下文（定稿后行必已落库，竞态消除即本设计动机）。

**转写稿检测**（免培训，§2.10）：前端对粘贴文本做轻量模式匹配（`发言人/说话人N/姓名：` 行首模式或 `[MM:SS` 时间戳，命中 ≥2 行）→ 输入区下提示「检测到转写稿，将按对话结构提取行动项」，不阻断不强制。

**IPC 通道**（与端点一一对应）：`meetingNotes:create` / `meetingNotes:listPending` / `meetingNotes:update` / `meetingNotes:delete` / `meetingNotes:structure` / `meetingNotes:confirm`。同变更内全部落地前端消费（§2.9 孤儿通道零容忍）。**2.14 增四通道**：`meetingNotes:listArchived` / `meetingNotes:materialize` / `meetingNotes:dematerialize` / `meetingNotes:updateContent`（见 [2.14 §3](2.14meeting-notes-hub-design.md)）。

**关键交互规则与不变量**：
- 产物归宿唯一：正文 → 素材 md，行动项 → material 事务；`meeting_notes` 行不承载任何长期数据。
- 正文与行动项在确认步完全可编辑，AI 产物仅为预填（智能体优先）。
- confirm 后不可重入（行已置 archived，2.14 原删行）；「重新生成」在 draft/structured 均可发起（structured 重发=回 draft 重走，偏差 19）；正文保存走 updateContent（structured 暂存保持待确认 / archived 确认修改终态，仅正文，内容比对联动素材，偏差 20）。
- 删除纪要级联行专属产物（素材 md + 未共享现场图片），已建事务保留（偏差 20 推翻「仅删行」）；confirm 的同步素材勾选是目标态：不勾即移出（含内容未变）、勾选且文件缺失则补传。
- 双语 i18n 全套（`meetingNotes.*`），zh-CN 与 en-US 同步。
