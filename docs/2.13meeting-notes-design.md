# 拜访/会议纪要（Meeting Notes）设计

> 项目内「结构化素材创建器」：粘贴转写稿/手记 + 现场图片 → LLM 结构化（纪要正文 + 行动项）→ 人工确认 → 行动项建事务、正文归项目素材。
> 与便签（[2.12](2.12sticky-notes-design.md)）为两个独立功能。定位为项目管理级动线，**不新增 Tab、不新增列表页**。
> 三要素见 §2/§3/§4；活动体系见 [0.4](0.4lifecycle-design.md)，事务体系见 [3.0](3.0project-lifecycle-design.md)。

---

## 1. 决策记录（2026-10-27 brainstorm 收敛）

| 决策点 | 结论 | 落选方案与理由 |
|---|---|---|
| 功能定位 | **结构化素材创建器**：确认后的纪要就是素材列表里的一份 md 文件，行动项是事务条目 | 独立纪要列表/新 Tab：产物与素材分离，动线断裂；output Tab 新分区：纪要是过程记录非交付物 |
| 输入形态 | **文本（含外部转写稿粘贴）+ 图片** | 现场收音 + 本地转写模型（faster-whisper ~1.5GB）：2026-10-27 裁决不做——转写是讯飞/通义/飞书等成熟工具的主业，InkCube 自建成本高且质量不如专业工具；**转写外包，InkCube 吃转写结果**（差异化在「记录 → 行动项入事务 → 知识入项目」闭环，非转写） |
| 确认模式 | **智能体优先**：AI 预填（结构化产物），人工确认修改（正文/行动项均可编辑，行动项逐条勾选是否建事务） | 直接保存 AI 产物：违背「AI 预填人工确认」原则 |
| 异步承载 | **统一 Activity 模型**（kind=`note_structuring`，FunctionSource 注册），禁止自建轮询 | §2.7 硬约束 |
| 行生命周期 | **表行 = 进行中的向导中间态，终态即删行**（产物在素材与事务，行无长期价值）；自清理设计见 §2 | confirmed 行长期留存：无 UI 消费即死数据，违反生命周期闭环 |
| 图片归属 | 纪要图片经现有素材上传通道成为**正式素材文件**，`image_file_ids` 仅记录引用 | 图片独立暂存区：多一套存储与清理，且图片本是项目资料应沉淀 |

## 2. 表结构

```sql
CREATE TABLE IF NOT EXISTS meeting_notes (
    id             TEXT PRIMARY KEY,   -- 'mnote_<uuid>'
    project_id     TEXT NOT NULL,
    title          TEXT NOT NULL,      -- 默认「拜访-YYYYMMDD」可改
    occurred_at    TEXT,               -- 拜访/会议日期（ISO），NULL = 今天
    raw_text       TEXT,               -- 原始文本输入（含粘贴的转写稿），重试期间零丢失的保底
    image_file_ids TEXT,               -- JSON 数组，引用 files 表（素材文件）
    draft_md       TEXT,               -- LLM 结构化产物 JSON：{content_md, action_items:[{title}]}
    saved_refs     TEXT,               -- JSON：{file_id, task_ids[]}——confirm 分步落引用，重试幂等键
    last_error     TEXT,               -- 最近一次结构化失败原因（i18n 错误码），NULL = 无
    status         TEXT NOT NULL,      -- draft → structuring → structured（confirm 成功即删行）
    created_at     TEXT NOT NULL,
    updated_at     TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_meeting_notes_project ON meeting_notes(project_id, status);
```

读写行为与生命周期闭环：

| 操作 | 行为 |
|---|---|
| 创建草稿 | INSERT（status=draft）；title/raw_text/image_file_ids 可经 PATCH 随时改 |
| 发起结构化 | 前置校验（status=draft；raw_text 与就绪图片至少其一非空）→ status=structuring → 异步 LLM → 成功 status=structured + draft_md 落库；失败 status 回 draft + last_error 记录 |
| 确认保存 | status 必须 structured → 写素材 md + 建事务（见 §3）→ **删行**（终态即清理） |
| 放弃草稿 | 用户显式 DELETE（useConfirm） |
| 崩溃恢复 | draft/structuring 行自然留存；启动时 structuring 残留行视为中断——后端启动清扫将其重置 draft + last_error=中断提示（幂等可重入，随现有启动恢复序列） |

级联清理：项目删除时 `meeting_notes` 同项目行级联删除（级联清单新增条目，[3.0](3.0project-lifecycle-design.md) 同步）；已保存产物（素材 md、事务）走现有项目级联。

## 3. 数据流

```
[Python FastAPI]  routers/meeting_notes.py（挂 /projects/{project_id}/notes）
  POST   /projects/{p}/notes                          创建草稿
  GET    /projects/{p}/notes?status=draft,structuring 未完成列表（草稿提示条/向导恢复）
  PATCH  /projects/{p}/notes/{id}                     编辑输入
  DELETE /projects/{p}/notes/{id}                     放弃草稿
  POST   /projects/{p}/notes/{id}/structure           发起 LLM 结构化（异步）
  POST   /projects/{p}/notes/{id}/confirm             确认保存（同步）
```

**结构化路径**（`structure`，异步）：
1. status 置 structuring → 返回 202；Activity 注册表 `note_structuring` 源 fetch 返回该行（entity_title=title, project_id）
2. 后台任务：取 raw_text + 各 image_file_ids 对应 file 的解析文本（复用现有解析产物；前端门控保证发起时图片已全部就绪，后端对缺解析文本的图片跳过并随返回体 warning 提示）→ LLM 单次调用（现有 llm service，usage 落 llm_usage，source=`meeting_note`）→ 输出 schema JSON：`{content_md, action_items:[{title}]}`，反幻觉纪律写入 prompt（仅基于输入材料，无材料支撑的推断标「待确认」）
3. 成功：draft_md + status=structured（心跳快照可见，终态停轮）；失败：status 回 draft + last_error（i18n 错误码，前端 errorCodes 翻译）

**确认保存路径**（`confirm`，body: `{content_md, action_items:[{title, selected, due_date?}]}`，同步；**分步落引用，重试幂等**）：
1. status=structured 守卫（并发双击后到者 409）
2. 正文写 md 文件「纪要-YYYYMMDD-标题.md」→ **函数级复用 upload 落盘 + 建 file 行 + 解析入队逻辑**（同 [2.12 §3](2.12sticky-notes-design.md) 归档路径）→ `saved_refs.file_id` 落库（已有 file_id 则跳过重写，同名覆盖语义不变）
3. 选中行动项逐个 `db.create_phase_task`（task_type='material'）→ 每成功一条即将 task_id 追加进 `saved_refs.task_ids`——单条失败不阻断其余，收集 failed 列表；重试时 saved_refs 已有的 task 跳过不重建（**杜绝部分失败后重试导致事务重复**）
4. saved_refs 完整（file_id + 全部选中项 task_id）→ **删行**（终态即清理）；返回 `{file, created_tasks, failed_tasks}` 前端逐项明示；未完整则行留存，前端「重试保存」按钮只补未完成步骤

**图片路径**：向导内图片上传走现有 `POST /projects/{id}/upload`（multipart，成正式素材文件）；前端以 files Activity 判定各图解析就绪态，**未就绪时生成按钮禁用**（附「图片理解中 n/m」提示）。

**转写稿检测**（免培训，§2.10）：前端对粘贴文本做轻量模式匹配（`发言人/说话人N/姓名：` 行首模式或 `[MM:SS` 时间戳，命中 ≥2 行）→ 输入区下提示「检测到转写稿，将按对话结构提取行动项」，不阻断不强制。

**IPC 通道**（与端点一一对应）：`meetingNotes:create` / `meetingNotes:listPending` / `meetingNotes:update` / `meetingNotes:delete` / `meetingNotes:structure` / `meetingNotes:confirm`。同变更内全部落地前端消费（§2.9 孤儿通道零容忍）。

## 4. 前端交互

**呈现线框**（向导抽屉，右推 60% 可拖动）：

```
第一步：输入                                  第二步：确认
┌─────────────────────────────────────┐  ┌─────────────────────────────────────┐
│  新建纪要                        ✕  │  │  新建纪要                        ✕  │
│  ① 输入 ─── ② 确认                  │  │  ① 输入 ━━━ ② 确认                  │ ← 步进条
├─────────────────────────────────────┤  ├─────────────────────────────────────┤
│  标题  [拜访-20261027       ]       │  │  纪要正文（可直接修改）              │
│  日期  [2026-10-27 ▾]               │  │  ┌─────────────────────────────┐  │
│  ┌─────────────────────────────┐  │  │  │ ## 拜访纪要：XX电子 王总      │  │
│  │ 粘贴转写稿或手写记录…        │  │  │  │ **时间**：2026-10-27 …       │  │
│  │ （大文本区，12 行高）        │  │  │  └─────────────────────────────┘  │
│  └─────────────────────────────┘  │  │                                     │
│  💡 检测到转写稿，将按对话结构提取  │  │  行动项（勾选保存后建为待办事务）      │
│                                    │  │  [☑] 准备园区产业政策包→王总 截止[▾] │
│  现场图片  [＋上传]                 │  │  [☑] 安排下月考察接待    截止[  —  ] │
│  ┌────┐ ┌────┐                    │  │  [☐] 待确认：扩产投资规模            │ ← 默认不勾
│  │img✓│ │img⟳│ ← 解析状态角标      │  │                                     │
│  └────┘ └────┘                    │  │  [← 上一步]     [ 保存并创建待办 ]   │

│  将生成纪要正文+行动项清单，        │  │  （保存成功 toast 附查看链；           │
│  保存时可修改                       │  │   部分失败红字逐项列出+重试保存）      │
└─────────────────────────────────────┘  └─────────────────────────────────────┘
```

生成中为进度态（转圈 +「正在整理纪要…」，Activity 心跳驱动；失败显示 last_error + 重试钮）。保存后落位：素材 Tab 列表顶部出现「纪要-…md」（解析入队），事务 Tab 出现 material 待办。

**组件清单**（组件 × 数据 × 呈现）：

| 组件 | 数据 | 呈现 | 状态 |
|---|---|---|---|
| 素材 Tab「新建纪要」按钮 | — | KnowledgePage compact 容器层（ProjectDetailPage materials 分支），StickyNote 旁独立钮（ClipboardList 图标） | 恒渲染 |
| 草稿提示条 | meetingNotes:listPending | 「有 N 份纪要草稿 → 继续」（点击恢复向导至对应步骤） | N=0 不渲染 |
| `NoteWizardDrawer`（App 级复用抽屉规范，右推 60% 可拖动） | 行数据 + useActivity('note_structuring') | 两步向导（输入 → 确认），步进条 | open/close；草稿恢复按 status 落步骤 |
| 输入步 | — | 标题/日期（默认今天）/文本区（placeholder「粘贴转写稿或手写记录…」）/图片上传（缩略图 + 解析状态角标）/转写稿检测提示 | 生成钮门控：图片全就绪且（文本或图片非空） |
| 确认步 | draft_md | 正文 textarea 可编辑 + 行动项清单（勾选建事务 / title 可编辑 / 可选截止日）+「全部不建事务也保存」合法 | 保存中禁用 |
| 完成/失败反馈 | confirm 返回 | toast：保存成功（附「查看素材/查看事务」链）；部分失败逐项列出；结构化失败显示 last_error + 重试钮 | — |

**状态-界面映射**：

| 状态 | 用户看到 |
|---|---|
| 素材 Tab 点「新建纪要」 | 抽屉输入步，标题已预填「拜访-今天日期」 |
| 粘贴长文本命中转写稿模式 | 提示「检测到转写稿，将按对话结构提取行动项」 |
| 图片解析中 | 生成钮禁用 +「图片理解中 n/m」；全部就绪自动恢复 |
| 生成中（structuring） | 进度态（Activity 心跳驱动），抽屉内不可关闭输入区，可「取消」（status 回 draft） |
| 结构化完成 | 自动进确认步：正文 + 行动项清单全部可编辑 |
| 点保存 | 素材列表出现「纪要-…md」（解析入队，现有文件活动），事务出现在 affairs Tab；抽屉关闭 toast |
| 中途关闭抽屉 | 草稿留存；素材 Tab 顶部草稿提示条计数 +1 |

**关键交互规则与不变量**：
- 产物归宿唯一：正文 → 素材 md，行动项 → material 事务；`meeting_notes` 行不承载任何长期数据。
- 正文与行动项在确认步完全可编辑，AI 产物仅为预填（智能体优先）。
- confirm 后不可重入（行已删）；「重新生成」仅在 structured 前可发起（回 draft 重走）。
- 双语 i18n 全套（`meetingNotes.*`），zh-CN 与 en-US 同步。

## 5. 验收标准

1. `node scripts/orphan_channel_audit.js` 四组为 0（六通道 + 六端点全链消费）
2. `pytest python/tests/ -v`（含 `test_meeting_notes.py`：草稿 CRUD/结构化状态机（202 前置校验、失败回 draft+last_error）/confirm 守卫与部分失败/启动清扫幂等/项目级联删除）+ `npx vitest run`（含 `NoteWizardDrawer.test.tsx`：转写稿检测/生成门控/确认编辑/保存反馈）+ `npx tsc --noEmit` + `npm run build` 全绿
3. `npm run dev` 运行验证：全动线走通（粘贴转写稿 → 生成 → 改两笔 → 保存 → 素材与事务双落位）、草稿恢复、崩溃恢复（重启后 structuring 残留回 draft）
4. 双语齐全，无硬编码文案；usage 面板可见 meeting_note 来源调用
