## 1. 背景与目标

### 1.1 现状

基础库（招商基础库 / 投资基础库 / 自定义基础库）当前完全是前端 mock 数据：
- 前端 `BaseLibDetailPage.tsx` 硬编码文件列表，无后端交互
- 后端 `projects` 表无基础库记录，无文件上传/解析/检索能力
- 报告引擎虽预留 `base_project_ids` 参数，但无实际数据可注入

### 1.2 目标

让基础库具备与项目相同的 RAG 能力：**文件上传 → 文档解析 → 向量索引 → 知识检索**。

### 1.3 设计原则：最大化复用

基础库与项目在数据层面高度同构——都是"一个容器 + 若干文件 + 向量索引"。因此采用**统一数据模型 + kind 字段区分**的方案，而非独立建表。

| 维度 | 项目 | 基础库 | 是否相同 |
|------|------|--------|---------|
| 文件存储 | `data/files/{project_id}/` | 同 | ✅ |
| 向量索引 | ChromaDB collection by project_id | 同 | ✅ |
| FTS 索引 | chunks_fts by project_id | 同 | ✅ |
| 文件解析 | ProcessingPipeline | 同 | ✅ |
| 异步队列 | KnowledgeWorker | 同 | ✅ |
| 知识检索 | KnowledgeSearchTool | 同 | ✅ |
| UI 结构 | 四 Tab（资料/Wiki/报告/填表） | 两 Tab（资料/Wiki） | ❌ 前端差异 |
| 生命周期 | 用户创建/删除 | 预置 + 用户自建 | ⚠️ 略有差异 |

## 2. 数据模型变更

### 2.1 projects 表扩展

在现有 `projects` 表新增 `kind` 字段，区分项目和基础库：

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `kind` | TEXT | `'project'` | `project` = 普通项目, `base_lib` = 基础库 |
| `lib_type` | TEXT | `NULL` | 基础库子类型：`preset_recruitment` / `preset_investment` / `custom`（仅 kind=base_lib 时有值） |

**迁移 SQL**：

```sql
ALTER TABLE projects ADD COLUMN kind TEXT DEFAULT 'project';
ALTER TABLE projects ADD COLUMN lib_type TEXT DEFAULT NULL;
```

**查询区分**：
- 项目列表：`SELECT ... WHERE kind = 'project'`
- 基础库列表：`SELECT ... WHERE kind = 'base_lib'`

**受影响查询清单**（加 `kind` 列后必须同步修改）：

| 位置 | 现有查询 | 需加过滤 |
|------|---------|----------|
| `database.py` `list_projects()` | `SELECT ... FROM projects p` | `WHERE p.kind = 'project'` |
| `knowledge.py` `list_projects` 路由 | `FROM projects p LEFT JOIN files f` | `WHERE p.kind = 'project'` |
| `knowledge_search.py` `list_projects()` | `FROM projects p LEFT JOIN files f` | `WHERE p.kind = 'project'` |
| `knowledge.py` `delete_project` 路由 | `DELETE FROM projects WHERE id = ?` | 加 `AND kind = 'project'` 防止误删基础库 |
| `task_knowledge_search.py` fallback 查询 | `FROM projects p LEFT JOIN files f` | `WHERE p.kind = 'project'` |
| `system.py` 清理知识库 `DELETE FROM projects` | 无 WHERE（全删） | 见 §2.4 清理策略 |

### 2.2 系统数据清理策略

`system.py` 的“清理知识库数据”端点当前执行 `DELETE FROM projects`（无 WHERE），会同时删除基础库记录。需明确策略：

| 方案 | 行为 | 推荐 |
|------|------|:----:|
| A: 全部清除 | 项目和基础库记录全部删除，预置基础库下次启动时重建 | ✅ |
| B: 保留基础库 | 仅删除 `kind='project'` 的记录，基础库保留 | 可选 |

推荐**方案 A**（简单一致）：清理 = 全部清除，预置基础库由 `ensure_preset_base_libs()` 在下次启动时自动重建。

### 2.3 项目-基础库关联表

新增关联表，记录项目与基础库的关联关系：

```sql
CREATE TABLE IF NOT EXISTS project_base_libs (
    project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    base_lib_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    auto_linked INTEGER NOT NULL DEFAULT 0,  -- 1=系统自动关联, 0=用户手动关联
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (project_id, base_lib_id)
);
```

**自动关联规则**：
- 招商引资类项目 → 自动关联招商基础库
- 投资分析类项目 → 自动关联投资基础库
- 通用类项目 → 不自动关联
- 用户可在报告生成时手动勾选额外基础库

### 2.4 预置基础库初始化

应用首次启动时，自动创建预置基础库记录：

```python
PRESET_BASE_LIBS = [
    {
        "id": "bl-recruitment",
        "name": "招商基础库",
        "description": "政策、园区、产业扶持等基础资料",
        "kind": "base_lib",
        "lib_type": "preset_recruitment",
    },
    {
        "id": "bl-investment",
        "name": "投资基础库",
        "description": "估值基准、法规、行业数据等",
        "kind": "base_lib",
        "lib_type": "preset_investment",
    },
]
```

**预置基础库特性**：
- 不可删除、不可重命名（系统内置）
- 用户可上传/删除文件
- 自定义基础库可创建、重命名、删除

### 5.4 项目创建时自动关联（后端处理）

项目创建时，由**后端** `create_project` 方法根据 `project_type` 自动建立关联（比前端调用更可靠）：

```python
# database.py create_project() 末尾
def create_project(self, name, description, project_type, ...):
    # ... 现有创建逻辑 ...
    # 自动关联基础库
    auto_libs = self.get_auto_linked_base_libs(project_type)
    for lib_id in auto_libs:
        self.link_project_to_base_lib(proj_id, lib_id, auto=True)
    return ...
```

| 项目类型 | 自动关联基础库 |
|---------|-------------|
| 招商引资 (`recruitment`) | `bl-recruitment` |
| 投资分析 (`investment`) | `bl-investment` |
| 通用 (`general`) | 不自动关联 |

用户可在报告生成时手动勾选额外基础库。

### 5.5 报告向导知识来源（已实现）

报告向导的“知识来源”步骤，从 API 获取基础库列表，替换 mock 的 `KNOWLEDGE_SOURCES`。

**当前实现**（`ReportWizard.tsx`）：
- ✅ 自定义基础库已从 `baseLib:list` 动态加载（`loadCustomLibs`），不再是 mock
- ✅ 生成时将勾选的基础库 ID 收集为 `baseProjectIds` 传入后端
- ✅ 初始勾选改为调用 `project:getBaseLibs` 读项目**真实关联**（预置库按 baseLibId 命中、已关联的自定义库也预勾选），替代原 projectType 硬匹配；API 失败时兜底仅勾项目知识库。`STATIC_SOURCE_ENTRIES` 的 `autoMatched/matchType` 仅保留用于“自动匹配”标签展示

**关联同步**：生成启动后，向导将用户勾选 diff 同步回 `project_base_libs`（新增勾选 → `project:linkBaseLib`，取消勾选含自动关联 → `project:unlinkBaseLib`），勾选持久化为下次向导的默认值；同步失败不影响已启动的生成。独立的关联管理 UI（在向导之外增删关联）按当前设计不需要。

### 5.6 报告生成自动填充（已实现）

报告生成时 `base_project_ids` 的填充策略：

| 方案 | 行为 | 状态 |
|------|------|:----:|
| A: 前端传入 | 前端从勾选源收集基础库 ID，传入 `baseProjectIds` | ✅ 已采用 |
| B: 后端自动查询 | 后端 `generate_report` 中自动查询 `project_base_libs` 表 | 未采用 |

## 8. 与 Wiki 的衔接（可选，延后）

> ⚠️ 本节为可选扩展。当前方案：基础库通过 RAG 直达服务报告生成和项目 Wiki 编译，不额外做 Wiki 编译。
>
> 详见 [2.6wiki-design.md](2.6wiki-design.md) v0.5.0 方案调整。

如果未来基础库文件量大到 RAG 质量下降，或多个项目反复引用相同基础库结论，可在现有 RAG 基础上增加 Wiki 编译层：

```
文件上传 → RAG 解析完成（现有 pipeline）→ 触发 Wiki 编译（新增）
                                              ↓
                                     读取 RAG chunks（Raw 层）
                                              ↓
                                     LLM 编译 → Wiki 页面
```

Wiki 编译在 KnowledgeWorker 中新增**第三种 worker**（`_wiki_queue` + `_wiki_worker`），独立于文件解析 worker 和图片描述 worker，独立并发控制。文件解析完成后触发 Wiki 编译入队：

```
文件解析完成 → 入队 _wiki_queue → _wiki_worker 执行编译（LLM 调用）
```

不引入新的基础设施，复用 KnowledgeWorker 的异步队列模式。
