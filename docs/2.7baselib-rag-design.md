# 基础库 RAG 设计文档

> 基础库（招商 / 投资 / 自定义）是与项目同构的知识容器：同一套 `projects` 表、文件解析管线、向量与 FTS 索引、检索与 RAG 对话，通过 `kind='base_lib'` 区分并以关联表服务于项目报告生成。
>
> 关联文档：架构总览 [0.0](0.0architecture.md)、项目与页面归属 [2.1](2.1project-design.md)、知识库管线 [2.2](2.2knowledge-base-design.md)、报告引擎 [2.5](2.5report-design.md)、Wiki [2.6](2.6wiki-design.md)、打包（预置库不捆绑种子资料）[0.2](0.2packaging-design.md)、活动通知（baselib 容器）[0.4](0.4lifecycle-design.md)。

---

## 1. 背景与设计原则

### 1.1 基础库定位

基础库是**跨项目共享的知识容器**：预置的招商基础库、投资基础库由系统内置，用户可上传文件（2.9 D3 收敛后无自定义库）。它的价值不在于独立浏览，而在于两点：

1. **独立 RAG 容器**——上传 → 解析 → 向量索引 → 检索/对话，与项目知识库完全同构；
2. **报告检索的外部知识源**——项目生成报告时，将关联基础库的 chunks 一并纳入检索范围（§5.5/§5.6）。

### 1.2 设计原则：最大化复用

基础库与项目在数据层面高度同构——都是"一个容器 + 若干文件 + 向量索引"。因此采用**统一数据模型 + `kind` 字段区分**，而非独立建表：

| 维度 | 项目 | 基础库 | 是否相同 |
|------|------|--------|---------|
| 数据行 | `projects` 表，`kind='project'` | `projects` 表，`kind='base_lib'` | 同表 |
| 文件存储 | `data/files/{id}/` | 同（id 即基础库 ID） | 相同 |
| 向量索引 | ChromaDB collection by project_id | 同 | 相同 |
| FTS 索引 | chunks_fts by project_id | 同 | 相同 |
| 文件解析 | ProcessingPipeline + KnowledgeWorker | 同（按 file_id 入队） | 相同 |
| 知识检索 | KnowledgeSearchTool / KnowledgeRAG | 同 | 相同 |
| 前端资料页 | KnowledgePage | 同组件 + IPC 通道映射（§5.2） | 复用 |
| 页面布局 | 四 Tab（资料/Wiki/报告/填表） | 资料 + Chat 并排单页 | 前端差异 |
| 生命周期 | 用户创建/删除 | 预置内置（仅 2 个，不可创建/删除） | 略有差异 |

带来的直接收益：管线、索引、检索、图片描述、活动通知等基础设施**零修改**即可覆盖基础库；新增的只有数据模型字段、关联表、基础库路由与 IPC、前端通道映射。

### 1.3 与其他文档的分工

- 文件解析管线、检索引擎、图片描述的内部设计见 [2.2](2.2knowledge-base-design.md)，本文只描述基础库如何接入；
- 报告生成的整体流程见 [2.5](2.5report-design.md)，本文只覆盖"基础库作为知识源"的注入链路（§5.5/§5.6）；
- Wiki 编译如何利用基础库（`base_lib_search_hints`）见 [2.6 §4.5](2.6wiki-design.md)，基础库自身不编译 Wiki（§8）。

## 2. 数据模型

### 2.1 projects 表扩展

`projects` 表新增两列（`database.py` 启动迁移，`_migrate_add_column` 幂等）：

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `kind` | TEXT | `'project'` | `project` = 普通项目，`base_lib` = 基础库 |
| `lib_type` | TEXT | `NULL` | 基础库子类型：`preset_recruitment` / `preset_investment`（仅 kind=base_lib 时有值；2.9 D3 收敛后仅预置） |

**kind 过滤全景**——所有"项目列表/项目删除"语义的查询必须过滤，防止基础库混入或被误删：

| 位置 | 查询 | 行为 |
|------|------|------|
| `database.py` `list_projects()` | `WHERE p.kind = 'project'` | 项目列表不含基础库 |
| `database.py` `delete_project()` | `DELETE ... AND kind = 'project'` | 按项目 ID 删除时不会误删同 ID 基础库 |
| `database.py` `_notify_schema_change()` | `WHERE type = ? AND kind = 'project'` | Wiki 结构变更的 pending 提醒只通知项目 |
| `routers/knowledge.py` `list_projects` 路由 | `WHERE p.kind = 'project'` | REST 项目列表 |
| `knowledge/knowledge_search.py` `list_projects()` | `WHERE p.kind = 'project'` | 检索工具的项目清单 |
| `tools/task_knowledge_search.py` fallback 查询 | `WHERE p.kind = 'project'` | Agent 工具列项目（工具路径走 knowledge_search，fallback 直查同过滤） |
| `db/database.py` `list_base_libs()` | `WHERE p.kind = 'base_lib'` | 基础库列表（反向过滤） |

### 2.2 系统数据清理策略

`routers/system.py` 的"清理知识库数据"（`DELETE /system/data/knowledge`）执行 `DELETE FROM projects`（无 kind 过滤），即**全部清除**：项目与基础库记录、files、images、chunks_fts、磁盘 `files/` 与 `chroma/` 一并删除。

预置基础库在同一事务内经 `ensure_preset_base_libs()` 即刻补种（2026-10-20 修复：原先只在启动播种，清理后不重启则侧栏基础库消失）。「真·全清」（`POST /system/data/reset-all`，清空全部用户表）同样在清空 `projects` 后补种——预置库是系统内置空容器而非用户数据，「恢复初始状态」的目标态含两个预置库。两条清理链路均有回归用例（`tests/test_system_data_api.py`）。

### 2.3 project_base_libs 关联表

```sql
CREATE TABLE IF NOT EXISTS project_base_libs (
    project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    base_lib_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    auto_linked INTEGER NOT NULL DEFAULT 0,  -- 1=项目创建时自动关联, 0=用户经向导勾选
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (project_id, base_lib_id)
);
```

- 数据库连接开启 `PRAGMA foreign_keys=ON`，项目或基础库删除时关联行级联清除；
- `auto_linked` 只标记关联来源，勾选同步（§5.5）建立的用户关联为 0；
- 关联关系是报告向导初始勾选与持久化的数据基础。

### 2.4 预置基础库

`database.py` 内置两个预置库定义，`ensure_preset_base_libs()` 启动时按固定 ID 幂等插入：

| ID | 名称 | lib_type | 描述 |
|----|------|----------|------|
| `bl-recruitment` | 招商基础库 | `preset_recruitment` | 政策、园区、产业扶持等基础资料 |
| `bl-investment` | 投资基础库 | `preset_investment` | 估值基准、法规、行业数据等 |

**预置库保护规则**：`lib_type` 以 `preset_` 为前缀的库不可删除、不可改名/改描述——实现方式为**方法级缺席**（2.9 D4 收敛后 `create_base_lib`/`update_base_lib`/`delete_base_lib` 及对应路由已全链移除，无入口即无绕过）；用户可正常上传/删除其中的文件。预置库初始为空容器，不捆绑种子资料（打包设计见 [0.2](0.2packaging-design.md)）。

## 3. 后端 API 设计

全部路由位于 `routers/knowledge.py`，前缀 `/knowledge`。文件/检索/对话/图片路由与项目侧同构，仅路径参数为库 ID 并前置 `_validate_base_lib_exists` 校验（404）。

### 3.1 基础库读取

2.9 D3 收敛后仅剩读取（创建/改名/删除路由已退场）：

| 路由 | 方法 | 说明 |
|------|------|------|
| `/knowledge/base-libs` | GET | 列出所有基础库（含 file_count 聚合，恒为两个预置库） |

### 3.2 文件管理

| 路由 | 方法 | 说明 |
|------|------|------|
| `/knowledge/base-libs/{id}/files` | GET | 文件列表（游标分页 + 类型过滤 + 文件名搜索） |
| `/knowledge/base-libs/{id}/upload` | POST | 上传文件（核心逻辑与安全检查见 §4.3） |
| `/knowledge/base-libs/{id}/files/active` | GET | 活跃文件轮询（pending/parsing 或图片描述中） |
| `/knowledge/base-libs/{id}/files/{fid}` | DELETE | 删除文件（cleanup_file_data 级联） |
| `/knowledge/base-libs/{id}/files/{fid}/retry` | POST | 重试失败文件（清理后重置重入队） |
| `/knowledge/base-libs/{id}/files/retry-failed` | POST | 批量重试全部失败文件 |
| `/knowledge/base-libs/{id}/files/batch-delete` | POST | 批量删除 |
| `/knowledge/base-libs/{id}/files/batch-reprocess` | POST | 批量重新解析 |
| `/knowledge/base-libs/{id}/recent-chunks` | GET | 最近 chunks（可按 file_id 过滤） |

### 3.3 检索、对话与图片

| 路由 | 方法 | 说明 |
|------|------|------|
| `/knowledge/base-libs/{id}/search` | POST | 知识检索（KnowledgeSearchTool，project_id=lib_id） |
| `/knowledge/base-libs/{id}/chat` | POST | RAG 问答（KnowledgeRAG.ask，读取全局 settings；模型经 `rag_model` 路由选档，llm/routing.py 档位制，空按标准档解析、槽位互为回退） |
| `/knowledge/base-libs/{id}/images` | GET | 图片列表（服务端状态/类别/尺寸过滤 + 计数聚合） |

### 3.4 关联管理

| 路由 | 方法 | 说明 |
|------|------|------|
| `/knowledge/projects/{pid}/base-libs` | GET | 获取项目关联的基础库列表 |
| `/knowledge/projects/{pid}/base-libs` | POST | 添加关联（body: base_lib_id） |
| `/knowledge/projects/{pid}/base-libs/{blid}` | DELETE | 移除关联 |

### 3.5 报告引擎适配

报告生成的知识检索入口 `retrieval.py` 提供 `base_project_ids` 参数：检索时 `search_project_ids = [project_id] + base_project_ids`，将基础库 chunks 纳入同一轮检索。变量解析（`variable_resolver.py`）同样接受该参数。

填充方式为**前端传入**：ReportWizard 收集勾选的基础库 ID → `reports:generateReport` → `reports.py` 持久化到 `reports.base_project_ids`（JSON）→ 恢复/重试时读回并传给 runner。后端不做自动关联查询，链路细节见 §5.6。

## 4. 后端实现细节

### 4.1 代码组织

不新建基础设施模块，扩展点集中：

| 文件 | 职责 |
|------|------|
| `python/db/database.py` | kind/lib_type 迁移、project_base_libs 建表、基础库读取与关联方法、预置库初始化 |
| `python/routers/knowledge.py` | 16 条基础库/关联路由（§3；2.9 D3 收敛后 CRUD 仅剩 GET）、`_validate_base_lib_exists`、`_base_lib_upload_core` |
| `python/main.py` | 启动时调用 `ensure_preset_base_libs()` |
| `python/knowledge/*`（pipeline/task_queue/knowledge_search/vector_store/fts_store） | 零修改——已按 project_id/file_id 参数化 |
| `python/report_generator/retrieval.py` | `base_project_ids` 检索扩围 |

### 4.2 Database 层方法

```
# ── Base Library（2.9 D4 后仅剩读取与 seed） ──
ensure_preset_base_libs()                      # 幂等创建预置库（按固定 ID）
list_base_libs()                               # kind='base_lib' + file_count 聚合
get_base_lib(lib_id)                           # 含 kind 校验

# ── Project-BaseLib Association ──
link_project_to_base_lib(project_id, base_lib_id, auto=False)   # INSERT OR IGNORE 幂等
unlink_project_from_base_lib(project_id, base_lib_id)
get_project_base_libs(project_id)               # JOIN projects，含 auto_linked/linked_at
get_auto_linked_base_libs(project_type)         # _AUTO_LINK_MAP 查表
```

自动关联映射 `_AUTO_LINK_MAP`：`recruitment → ['bl-recruitment']`、`investment → ['bl-investment']`、其他类型为空。

### 4.3 上传核心与安全检查

`_base_lib_upload_core` 与项目上传共用一套约束：

1. **体积预检**：base64 解码前估算（payload × 3/4），超过 200MB 直接 413，不物化到内存；
2. **文件名安全**：`_safe_filename` 剥离路径分量，阻断路径穿越（`../../evil.txt`）；
3. **解码落盘**：`asyncio.to_thread` 执行 base64 解码 + MD5 哈希 + 写盘，不阻塞事件循环；
4. **重复检测**：同库内 file_hash 命中即删除临时目录并返回 `duplicate: true` 与既有 file_id；
5. **入队解析**：`worker.enqueue_file(file_id)` 走与项目一致的 KnowledgeWorker 管线；worker 不可用时由队列扫描器兜底。

## 5. 前端设计

### 5.1 详情页布局（BaseLibDetailPage）

`BaseLibDetailPage.tsx` 以 `baseLibId` 为入参：

- **头部**：`baseLib:list` 查找库信息（名称/描述/图标）；预置库按 ID 映射图标（bl-recruitment=Factory、bl-investment=DollarSign），其余为 Library；找不到时显示 notFound 空态；
- **主体**：左侧嵌入 `KnowledgePage`（compact 模式 + IPC 通道映射 §5.2），右侧为 `ProjectChatPanel`（`chatIpcChannel="baseLib:chat"`），二者以 `onFileSelect` 联动——在文件列表选中文件后，Chat 自动限定该文件范围。

基础库无 Wiki/报告/填表 Tab，是"资料 + 对话"的并排单页。

### 5.2 KnowledgePage 复用机制（ipcChannels）

`KnowledgePage` 及其子组件（FileUploader / ImageGallery / ImageList）均接受可选 prop：

```typescript
ipcChannels?: Partial<KnowledgeIpcChannels>
```

组件内部以 `{ ...DEFAULT_KNOWLEDGE_IPC_CHANNELS, ...ipcChannels }` 合并——项目场景不传走 `knowledge:*` 默认通道；基础库场景由 `BaseLibDetailPage` 传入 `BASE_LIB_IPC_CHANNELS` 覆盖 12 项为 `baseLib:*` 通道（getFiles/getActiveFiles/uploadFile/deleteFile/retryFile/retryFailedFiles/batchDeleteFiles/batchReprocessFiles/search/recentChunks/getProjectImages/getImages）。

图片级操作（retryImage / updateImageCategory / archiveImage / retryFailedImages）**保留 `knowledge:*` 默认通道**：这些操作按 file_id 全局定位，无需库 ID 区分后端。

由于 KnowledgePage 以 `selectedProject.id` 作为容器 ID 传递，基础库场景构造 `fakeProject`（id=库 ID）即可整体复用，包括上传 guard（缺解析/embedding 模型时引导）、活跃文件轮询（谓词 `useActivity('file')` 按 project_id 匹配，基础库行同样生效）与终态边沿补拉。

### 5.3 侧边栏基础库列表（BaseLibFooter）

`BaseLibFooter.tsx` 位于项目列表下方：

| 能力 | 实现 |
|------|------|
| 列表 | `baseLib:list` 动态加载（含 file_count），无硬编码常量 |
| 预置标识 | `lib_type` 以 `preset_` 开头显示“预置”徽章（2.9 D3 后恒显示，无自定义库） |
| 活跃点 | `useActivity` 的 byProject 派生，`container='baselib'` 的行显示心跳/待审阅圆点与 tooltip（[0.4 §5.7](0.4lifecycle-design.md)） |
| 模板管理入口 | 可选渲染“模板管理”导航行（与基础库列表并列的独立页面入口） |

### 5.4 项目创建时自动关联

`database.py` `create_project()` 末尾按项目类型查 `_AUTO_LINK_MAP`，命中即 `link_project_to_base_lib(proj_id, lib_id, auto=True)`：

| 项目类型 | 自动关联 |
|---------|---------|
| 招商引资（recruitment） | `bl-recruitment` |
| 投资分析（investment） | `bl-investment` |
| 通用（general） | 不自动关联 |

自动关联只决定**初始关联集**；用户在报告向导中的勾选会改写该集合（§5.5）。

### 5.5 报告向导知识来源与关联同步

报告向导（`ReportWizard.tsx`）第 2 步的“知识来源”区由两部分构成：

1. **静态条目** `STATIC_SOURCE_ENTRIES`：项目知识库（`alwaysChecked`，复选框禁用 + “自动包含”标签）+ 招商/投资两个预置库（携带 `baseLibId` 与 `matchType`）；2.9 D3 收敛后知识源恒为该静态表，无动态追加条目；
2. **初始勾选**：`project:getBaseLibs` 读取项目**真实关联集**——预置库按 baseLibId 命中则预勾选；API 失败时兜底仅勾项目知识库。项目知识库恒勾。

`autoMatched/matchType` 字段仅用于在项目类型匹配时展示"自动匹配"标签，不参与勾选逻辑。

**勾选同步**：生成启动成功后执行 `syncBaseLibAssociations(projectId, targetLibIds)`——先读当前关联集，diff 出 toLink/toUnlink，并行调用 `project:linkBaseLib` / `project:unlinkBaseLib` 将**向导勾选集持久化为项目的关联集**（含取消自动关联的库）。同步失败不影响已启动的生成，下次向导回退到当前关联集。独立于向导的关联管理 UI 不存在——关联集的唯一编辑入口就是向导勾选。

### 5.6 报告生成 base_project_ids 填充

`base_project_ids` 的填充采用**前端传入**方案：

```
ReportWizard.doStartGenerate
  ├─ 遍历勾选条目收集 targetLibIds（跳过 ks-project）
  ├─ baseProjectIds = [...targetLibIds]
  └─ invoke('reports:generateReport', { ..., baseProjectIds, ... })
        ↓
reports.py：JSON 序列化存入 reports.base_project_ids（生成/恢复/重试均读回）
        ↓
runner.py → retrieval.py（search_project_ids 扩围）+ variable_resolver.py
```

未采用"后端在 generate_report 内自动查询 project_base_libs"的替代方案——勾选集在向导中已实时同步为关联表内容（§5.5），前端传入与后端自动查询等价，且让"本次生成用了哪些库"在发起时刻即确定并随报告持久化。

## 6. Electron IPC 层

### 6.1 IPC 通道清单

`electron/ipc-handlers.js` 注册 16 个通道，全部转发到 §3 的 REST 路由：

| IPC 通道 | 说明 |
|----------|------|
| `baseLib:list` | 基础库列表（2.9 D3 后 CRUD 通道仅剩 list） |
| `baseLib:getFiles` / `getActiveFiles` / `upload` / `deleteFile` / `retryFile` | 文件管理 |
| `baseLib:retryFailedFiles` / `batchDeleteFiles` / `batchReprocessFiles` | 批量操作 |
| `baseLib:search` / `recentChunks` / `chat` / `getImages` | 检索/对话/图片 |
| `project:getBaseLibs` / `linkBaseLib` / `unlinkBaseLib` | 关联管理（§5.5） |

**参数双命名兼容**：KnowledgePage 及子组件以 `projectId` 字段名传容器 ID，基础库语义下实为库 ID。各 handler 统一 `const id = libId || projectId` 兼容两种字段名，前端组件无需感知差异。

### 6.2 preload 代理模式

`preload.js` 采用通用 invoke 代理（仅暴露 `invoke`/`send`/`on`），不逐通道注册——新增基础库通道只改 `ipc-handlers.js`，preload 与渲染进程桥接层零修改。前端以 `window.electronAPI.invoke('baseLib:list', ...)` 调用。

## 7. 活动与通知集成

基础库不是独立的一套活动体系，而是以 `container='baselib'` 标记复用项目的活动基础设施（[0.4](0.4lifecycle-design.md)）：

- **通知路由**：notifications 表的 `container` 列区分 project/baselib，文件解析完成/失败等终态通知在基础库容器内定向展示；
- **活跃点**：BaseLibFooter 的库行与项目行共享同一 `byProject` 心跳派生，仅 `container='baselib'` 的行点亮；
- **轮询谓词**：KnowledgePage 的活跃文件轮询以 `useActivity('file')` 的 project_id 匹配当前容器（基础库场景即库 ID），基础库与项目同源同逻辑；
- **入口 guard**：上传（file_parsing）、检索（knowledge_search）的模型缺失弹层对基础库场景同样生效（组件级复用自带）。

系统清理（§2.2）会连带清除基础库的活动数据，与项目数据同周期。

---

## 8. 与 Wiki 的衔接

当前方案：**基础库不做 Wiki 编译**，无编译入口、无 Wiki Tab。基础库参与 Wiki 的方式是作为**检索源**——项目 Wiki 摄入时，`wiki_schemas.base_lib_search_hints`（结构页种子携带）指导引擎从关联基础库检索补充资料，链路见 [2.6 §4.5](2.6wiki-design.md)。

早期设想中的可选扩展（基础库文件解析完成后触发 Wiki 编译、在 KnowledgeWorker 中新增第三种 worker 独立并发）未实施：在现行“RAG 直达 + 结构页 hint 检索”方案下，只有当基础库文件量大到检索质量下降、或多项目反复引用相同基础库结论时，才需要重新评估编译层。

另一处交叉点：基础库详情页右侧的 ProjectChatPanel 与项目共用，其中「归档为 Wiki 页面」按钮（`wiki:archive`）在基础库上下文中可用——归档页面会写入挂靠在该库 ID 下的 wiki_pages，但基础库前端无 Wiki 浏览入口，页面不可见。差异登记见 §9.1。

## 9. 差异与下一步建议

### 9.1 现状差异登记

| # | 差异 | 现状说明 | 处置建议 |
|---|------|---------|---------|
| 1 | 重命名/改描述无前端入口（**已闭环：能力移除，2026-10-16 孤儿治理**） | `baseLib:update` IPC 与 PATCH 路由长期零消费，已全链移除（含 update_base_lib 服务函数）；如未来需要重命名/改描述需重建端点 + IPC + UI | 不再建议接线；需求成立时按全链方式重建 |
| 2 | 基础库 Chat 的 Wiki 归档不可见 | ProjectChatPanel 共用导致基础库上下文可“归档为 Wiki 页面”，写入成功但无浏览入口 | 短期隐藏该按钮，或在详情页提供只读页面列表 |
| 3 | Agent 工具不可检索基础库 | `task_knowledge_search` 的项目清单过滤 `kind='project'`，任务智能体无法把基础库作为检索范围；报告链路不受限（§5.6） | 如有需求可增加带白名单的基础库范围参数 |
| 4 | 预置库描述不可修改 | 无任何更新端点（原 update_base_lib 的 preset_ 前缀拒绝逻辑已随孤儿治理移除），名称与描述均锁定 | 与“系统内置不可变”定位一致，维持现状 |

### 9.2 优化建议

1. **归档按钮按容器裁剪**：ProjectChatPanel 已有 `chatIpcChannel` 区分场景，可同样以 prop 控制归档按钮可见性，避免基础库写入不可见页面；
2. **基础库检索范围开放（可选）**：若任务智能体需要引用公共资料，可在 `task_knowledge_search` 中增加 `search_base_lib` 动作或 project_id 直接传库 ID 的白名单校验，与报告链路的安全模型对齐。
