
# 任务韧性设计：切换、并行、崩溃恢复

> **概述**：本文档定义任务子系统的韧性机制，覆盖三类中断场景的语义与实现：
> 1. **多任务并行**——MAX_CONCURRENT=3 个任务同时运行，切走任务不丢流式状态（bgStates ref 架构），列表实时显示运行指示（§3）；
> 2. **崩溃恢复**——每轮迭代自动保存完整 agent state（含 tool_calls 配对），Python 崩溃/重启后任务可从断点续跑，前端生成状态自动复位（§2）；
> 3. **暂停/恢复**——用户主动暂停保存完整内存态，恢复时跳过 Planner 从断点续跑；恢复入口是 chat 的 resume 参数（§4）。
>
> 三层机制的关系：断点保存（数据层）是崩溃恢复与暂停恢复的共同基础；bgStates（前端层）解决「看哪个任务」的切换连续性；恢复 UI（交互层）把可恢复状态暴露给用户。任务执行循环与断点保存时机详见 [1.1 §5](1.1task-agent-design-unified.md)；全局崩溃恢复规则（六活动分级自愈）见 [0.4 §2.4](0.4lifecycle-design.md)。

## 1. 设计目标与总体结构

```
┌──────────────────────────────────────────────────────────────┐
│  数据层：崩溃检测 + 自动保存（后端）                            │
│    ├─ 每个 iteration 完成时自动保存完整 agent state            │
│    ├─ Python 启动时检测残留 state → 写中断提示（保留 state）    │
│    └─ 前端收到 process-exit 时重置 isGenerating               │
│                                                              │
│  前端层：per-task 流式状态 + 运行状态指示                      │
│    ├─ bgStates: useRef<Map<taskId, 流式快照>>                 │
│    ├─ 后台任务事件按 taskId 累积，不丢弃、不触发渲染           │
│    └─ 任务列表显示运行中指示器（全局心跳驱动）                  │
│                                                              │
│  交互层：暂停/恢复 UI                                         │
│    ├─ resume 经 tasks:chat(resume=true) 触发续跑              │
│    ├─ 任务会话显示「继续执行」入口（has-state 驱动）           │
│    └─ pause 保存完整内存 messages（含 tool_calls）             │
└──────────────────────────────────────────────────────────────┘
```

## 2. 崩溃检测与恢复

### 2.1 自动保存 agent state

`TaskAgent` 主循环每轮 iteration 完成且状态为 continue 时，保存完整状态到 `task_agent_state` 表：

```python
for iteration in range(start_iteration, max_iter):
    # ... 执行单轮 FC ...
    if fc_status == "continue":
        self.db.save_agent_state(task_id, {
            "messages": messages,       # 完整列表，含 system/user/assistant(tool_calls)/tool
            "iteration": iteration + 1,
            "recent_errors": list(recent_errors),
            "auto_saved": True,         # 标记：可恢复；启动检测依赖此标记
        })
    elif fc_status in ("done", "error"):
        if fc_status == "done" or task_id not in self._paused_tasks:
            self.db.delete_agent_state(task_id)   # 清除断点（用户暂停除外）
        ...
```

**关键**：保存完整 `messages`（含 `tool_calls` / `tool_call_id`），而非仅 `role`+`content`——否则恢复后 LLM 无法配对 tool call 与 tool result。保存失败只记 warning 不中断任务（best-effort）。

终态清理规则：done / error 清除断点；**因用户暂停而退出的 error 保留断点**（`_paused_tasks` 集合判定），供「继续执行」使用。

### 2.2 Python 启动时检测残留状态

`main.py` lifespan 启动序列中（通知清理之后）：

```python
_interrupted = deps.db.list_tasks_with_saved_state()   # 全部有断点的任务
for _tid in _interrupted:
    _state = deps.db.load_agent_state(_tid)
    if _state and _state.get("auto_saved"):
        if not deps.db.has_interrupt_marker(_tid):     # 防重复：反复重启不叠加提示
            deps.db.save_task_message(_tid, "assistant",
                "⚠️ 此任务在上次程序关闭时被中断。点击「恢复」可从上次中断处继续，或发送新消息重新开始。")
    # 注意：不调用 delete_agent_state——保留 state 供 has-state API 检测与恢复
```

配套 DB 方法（`database.py`）：`list_tasks_with_saved_state()`（列全部断点任务）、`has_interrupt_marker()`（最后一条消息是否已是中断提示）。

### 2.3 前端崩溃复位

`App.tsx` 监听 `python:process-exit`：显示进程退出 banner（带「查看日志」入口），同时调用 `resetTaskGeneratingState()`（useTaskChat 暴露）强制重置 isGenerating 与全部流式状态——否则 Python 进程已死、SSE 永不再来，UI 会永远卡在「生成中」。

Python 重启后，用户打开被中断的任务 → `GET /tasks/{id}/has-state` 返回 true → canResume=true → 会话显示恢复入口 → 点击续跑（§4.1）。

### 2.4 崩溃恢复链全貌

```
任务运行中 → Python 进程崩溃
  → SSE reader done（无 done 事件）
  → python-manager: process.on('exit') → python:process-exit
  → 前端: isGenerating=false + 退出 banner

Python 重启（Electron 自动拉起）:
  → lifespan: 检测 task_agent_state 残留（auto_saved）
  → 写中断提示消息（保留 state，防重复）
  → 前端: has-state → canResume=true → 恢复入口
  → 用户点击 → tasks:chat(resume=true) → 从保存的 iteration 续跑
```

## 3. 多任务并行

### 3.1 各层并发支持

| 层 | 并发支持 | 实现 |
|---|---|---|
| **Python 后端** | 完整 | `MAX_CONCURRENT=3`；per-task `cancel_events` / `_task_iterations` / `_task_messages` / 工具实例 / LLM client |
| **Electron IPC** | 完整 | 每个任务独立 SSE 连接，事件携带 `taskId` 路由（[1.1 §10.3](1.1task-agent-design-unified.md)） |
| **前端 useTaskChat** | 完整 | bgStates ref + React state 混合架构（§3.2） |
| **前端事件分发** | 完整 | 按 taskId 路由到活跃 handler / 后台 handler |
| **任务列表指示** | 完整 | runningTaskIds 全局心跳驱动（§3.4） |

### 3.2 bgStates 混合架构（useTaskChat）

活跃任务使用 React state（驱动 UI 渲染），后台任务使用 `useRef<Map>` 存储（不触发渲染）：

```typescript
interface BgTaskState {
  content: string; reasoning: string; steps: StreamStep[]; iteration: number;
  isGenerating: boolean; planData: PlanData | null;
  iterationReasoning: Map<number, string>; iterationThoughts: Map<number, string>;
  pendingShellConfirm: ShellConfirmData | null; pendingSkillConfirm: SkillConfirmData | null;
}
const bgStates = useRef<Map<string, BgTaskState>>(new Map())
```

**设计决策**：不用 `useState<Map>` 存所有任务状态。后台任务每秒可能收到多个流式事件，每次事件触发 React 渲染是不必要的性能开销；ref 存后台状态，仅在切换任务时经 save/restore 同步到 React state。切换逻辑见 [1.1 §9.3](1.1task-agent-design-unified.md)。

### 3.3 事件路由

`task:stream` 监听器按 taskId 分发，两类 handler 逻辑对称：

```
taskId === activeTaskId → handleStreamEvent    → React state（驱动渲染）
taskId !== activeTaskId → handleBgStreamEvent  → bgStates ref（静默累积）
```

`handleBgStreamEvent` 同样处理 `confirm_shell` / `confirm_skill`——存入该任务的 bgState，用户切换过去时恢复为 React state 并弹出确认卡片；确认后经 IPC 正常回传（确认是 per-task 的，不依赖任务在前台）。

### 3.4 运行状态指示

后端 `GET /tasks/status` 返回 `running_task_ids`；前端经 **TaskStatusMonitor**（App 层、Provider 内常驻）消费——轮询谓词从全局活动心跳派生（`useActivity('task')`），App 只持有回调上抛的派生结果（`canStartTask` + `runningTaskIds`）供 TaskList 消费。该轮询已收编进全局轮询台账（[0.4 §8.1](0.4lifecycle-design.md)），页面不自建。

TaskList UI：`TaskItem` 按 `runningTaskIds` 包含关系显示绿色脉动指示器（pulse 动画）；3 个任务并行时列表同时显示 3 个指示器。

## 4. 暂停与恢复

### 4.1 恢复流程（resume = chat 参数）

恢复不是独立端点，是 `POST /tasks/{id}/chat` 请求体的 `resume: true`：

```python
if req.resume:
    state = deps.db.load_agent_state(task_id)
    if not state:
        return {"error": "没有可恢复的任务状态"}
    # 不保存 user 消息，直接触发 agent 续跑
else:
    deps.db.delete_agent_state(task_id)          # 新消息 = 放弃断点重新开始
    deps.db.save_task_message(task_id, "user", req.message)
    deps.db.update_task_title_from_message(task_id, req.message)
```

「放弃断点重新开始」无需独立按钮：用户直接发送新消息即隐含重开。恢复执行时跳过 Planner（保存的 messages 已含计划上下文），从 `start_iteration` 续跑并在流内提示「从第 N 轮恢复执行」。

### 4.2 暂停流程（pause 保存完整内存态）

`POST /tasks/{id}/pause`：优先取 TaskAgent 内存中的完整 messages（`_task_messages[task_id]`，含 `tool_calls` / `tool_call_id` 配对）；仅运行时内存缺失时才回退 DB 消息（此时只有 user/assistant 文本，恢复后 LLM 上下文弱化但可用）。保存后置 cancel 事件，循环在轮次边界退出。

`pause_task()` 保存的 state 与自动保存格式一致（`auto_saved: True` 标记），因此：
- 启动检测能把「暂停后程序关闭」的任务同样识别为可恢复
- 恢复路径与崩溃恢复完全复用（同一 state 结构、同一 resume 入口）

### 4.3 恢复 UI

`canResume` 由 `GET /tasks/{id}/has-state` 驱动（loadMessages 时查询）：任务不在生成中且存在断点 → 会话顶部显示恢复入口（▶ 继续）；点击后 `tasks:chat(message='', resume=true)`。

## 5. 边界情况

| 场景 | 处理方式 |
|------|---------|
| 恢复时模型已更换 | 正常。state 只保存 messages，不保存模型配置 |
| 恢复时工作区文件已修改 | 正常。工具读取当前文件状态 |
| 恢复时工具清单已变更 | LLM 根据当前工具列表重新决策 |
| 自动保存失败 | 只记 warning，不中断任务 |
| 多个任务同时崩溃 | 各自独立恢复，按 task_id 隔离 |
| 恢复过程中再次崩溃 | 下次启动再次检测、再次提示（has_interrupt_marker 防提示叠加） |
| 暂停后删除任务 | `delete_task` 同步清理 `task_agent_state`（防残留 state 干扰 has-state） |
| 3 个任务都在运行，用户只看一个 | per-task state 各自累积，列表显示 3 个运行指示器 |
| 后台任务需要 shell 确认 | 确认事件存入该任务 bgState，切回时弹出；确认 IPC 按 taskId 直达，不依赖前台 |
| context collapse 在自动保存后触发 | 恢复后首轮 iteration 再次检查压缩 |
| SSE 断流导致生成器 GC（GeneratorExit） | GeneratorExit 为 BaseException 不走 `except Exception`，经 finally 收尾；极端时序下可能多发一条终态通知（仅多一条 Toast，不影响 DB 状态机正确性）。已知限制，接受 |
| 任务终态通知 | 用户取消/暂停静默；自然完成/异常终止经 activity_events 写全局通知（[0.4 §6.4](0.4lifecycle-design.md)），后台任务完成全局可见 |
| 崩溃后并发槽 | `_running_task_ids` 为内存态，重启即空 → 并发槽自动释放 |

## 6. 与其他机制的关系

| 机制 | 关系 |
|------|------|
| LLM 超时重试（task_agent 内置） | 独立功能，瞬时网络错误在单轮内重试，不触发断点；重试耗尽才 error 终态 |
| 上下文压缩（[1.1 §6](1.1task-agent-design-unified.md)） | 自动保存的 state 含压缩后 messages，恢复后再次检查压缩 |
| 任务并发限制（MAX_CONCURRENT=3，[1.1 §7.4](1.1task-agent-design-unified.md)） | `try_acquire_task` 原子占用；崩溃后槽随进程消失自动释放 |
| 长时活动模型（[0.4](0.4lifecycle-design.md)） | 任务的崩溃恢复遵循全局「重启即中断判定 + 按资源代价分级自愈」规则——任务属消耗 token 类，标中断 + 等用户，不自动续跑 |
| 准入校验（[0.4 §7](0.4lifecycle-design.md)） | chat 入口 `ensure_ready("task")`；与恢复无交集（恢复时配置已就绪） |
| Python 看门狗（[0.0 §5](0.0architecture.md)） | watchdog 管进程级健康与重启；本机制管数据层断点，重启后由 lifespan 检测衔接 |

| # | 方向 | 说明 |

| 1 | 崩溃时正在执行的工具无断点 | 自动保存在轮次边界，崩溃点若在某工具执行中，该轮已完成的工具调用结果丢失（恢复从上轮末尾重跑该轮）；可在工具执行后增量追加 messages 快照 |
