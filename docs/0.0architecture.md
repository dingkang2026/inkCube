## 1. 项目概述

墨方 InkCube 是一款桌面端智能助手客户端，面向**招商经理 / 投资经理**，提供本地知识库管理、LLM Wiki 知识编译、专业报告生成、通用任务智能体等能力。除大模型推理外，所有功能均在本地运行，保障数据隐私。

### 1.1 核心能力

| 能力 | 说明 | 对应模块 |
|------|------|----------|
| **任务智能体** | 基于 Function Calling 的双模式 Agent（编程 / 通用），支持多轮推理、工具调用、Skill 扩展、多任务并行、暂停/恢复/崩溃续跑 | `python/agent/`、`src/features/task/` |
| **项目工作空间** | 资料 → Wiki → 报告 → 填表 四 Tab 闭环；基础库跨项目复用 | `python/routers/knowledge.py`、`src/features/project/` |
| **本地知识库（RAG）** | 文档解析（Docling）→ 分块 → 向量化（bge-m3 / ChromaDB）+ 全文索引（SQLite FTS5）→ 混合检索（向量 + BM25 + RRF） | `python/knowledge/` |
| **LLM Wiki** | 逐文件增量摄入，将碎片文档编译为结构化、互链的 Markdown 知识页面（Karpathy LLM Wiki 范式） | `python/wiki/` |
| **报告生成引擎** | 模板驱动 + 多通道检索（知识库 / 互联网）+ 知识卡片 + 两遍执行 + 校验重试 + 断点恢复，输出 Word/PDF | `python/report_generator/` |
| **完全本地** | 除 LLM / VLM / Tavily API 外，无外部网络依赖，无遥测 | — |

### 1.2 开源协议

本项目采用 **AGPL-3.0** 协议。所有修改和衍生作品必须以相同协议开源，网络服务亦视为分发。

## 2. 系统架构

三层进程模型：Electron 主进程（Node.js）负责窗口与子进程管理，React 渲染进程负责 UI，Python FastAPI 后端负责全部业务逻辑。渲染进程不直连 Python，统一经 Electron IPC 代理。

## 5. 关键设计决策

### 5.1 Python 进程管理

Python Agent 作为独立子进程运行，由 Electron 主进程管理生命周期。

**启动流程：**

```
Electron app.whenReady()
    ├── 首次启动：解压工具链到 %APPDATA%/InkCube/（tool-initializer.js）
    ├── 分配空闲端口
    ├── spawn Python 进程（开发: uvicorn --reload；生产: python-build-standalone/python.exe main.py）
    ├── 轮询 GET /health（超时判定）
    └── 健康检查通过 → 创建 BrowserWindow
```

> 开发模式下，若检测到已有 Python 实例（如 PyCharm 手动启动的 8765），Electron 直接复用而不重复启动。

**退出处理：** `before-quit → POST /shutdown（优雅关闭）→ 等待 → SIGTERM/SIGKILL 兜底`。`watchdog.py` 监控父进程，父进程消失时后端自杀，避免孤儿进程。

### 5.2 通信协议与 API 路由

**Electron ↔ Renderer：** contextBridge + 通用 `invoke/send/on` 代理（不逐个注册通道）。前端通过 `window.electronAPI.invoke('<namespace>:<action>', ...)` 调用。

**Electron ↔ Python：** HTTP + SSE。任务对话使用 SSE 流式推送，事件携带 `taskId` 以支持多任务并行路由。

后端共 **10 个路由模块**：

| 路由模块 | 前缀 | 职责（代表性端点） |
|----------|------|-------------------|
| `health.py` | `/health` | 健康检查 + 功能就绪度 features 段（Readiness） |
| `settings.py` | `/settings` | 应用配置读写、连通性与模型能力探测（personal_test：FC / 思考深度 / 思考开关）、首启向导标记 `/onboarding` |
| `models.py` | `/models` | 本地模型下载状态、GPU 模型、LibreOffice 检测 |
| `system.py` | `/system` | 数据用量、数据清理、外部依赖检测、工具链状态 |
| `skills.py` | `/skills` | Skill 列表 / 安装 / 删除 / 启停 / 确认、内置工具清单 |
| `tasks.py` | `/tasks` | 任务 CRUD、`/chat`（SSE）、pause/cancel、confirm-shell/skill、文件、日志、状态、has-state |
| `knowledge.py` | `/knowledge` | 项目 CRUD、文件上传/解析/重试、图片管理、检索 `/search`、RAG 问答 `/chat`、基础库 `/base-libs`、项目-基础库关联 |
| `wiki.py` | `/wiki` | 页面 CRUD、编译 `/compile`（+stop/continue/status）、全局审阅状态、Lint、sweep-reviews、图谱、搜索、Schema、变更日志、反链 |
| `reports.py` | `/reports` | 模板 CRUD/复制/升级/样例提取、报告生成 `/generate`、导出、内容、重试、进展日志 |
| `activities.py` | `/activities` | Activity Hub：`/status` 全局活动聚合（活跃列表 + summary + 通知）、`/notifications/read` 批量已读 |

### 5.3 任务智能体设计（Function Calling）

任务智能体采用 **OpenAI Function Calling 循环**（非纯文本 ReAct），交替进行推理与工具调用。详见 [1.1](1.1task-agent-design-unified.md)。

- **双模式**：`coding`（编程模式，全工具集）/ `general`（通用模式，精简工具集），由 `tasks.mode` 持久化，System Prompt 与工具集随模式切换。
- **可选 Planner**：配置 `task_planner_model` 时，先由 Planner 模型生成结构化执行计划再进入 FC 循环。
- **并发**：`MAX_CONCURRENT = 3`，per-task 隔离（cancel_events / iterations / tools / LLM client / in-memory messages）。
- **上下文管理**：`context_manager.py` 负责 Token 预算与 Context Collapse（早期对话压缩为摘要）、超长工具输出 Disk Dump。
- **韧性**：每 iteration 自动保存完整 agent state（含 tool_calls），支持暂停/恢复/崩溃续跑。详见 [1.3](1.3task-resilience-design.md)。
- **流式渲染**：reasoning / answer_chunk / thought / action / observation / done 事件流。详见 [1.2](1.2streaming-thought-display.md)。

### 5.4 工具体系

**内置工具**（`python/tools/`，通过 Adapter 桥接为 Skill）：

| 分类 | 工具 |
|------|------|
| 文件 | `file_ops`（读写/inline diff）、`project_scaffold` |
| 代码 | `code_executor`（venv 内执行）、`code_search`（rg）、`code_lint` / `code_format`（ruff）、`repo_map`（tree-sitter + PageRank）、`lsp_client` |
| 系统 | `shell_tool`（域名白名单 + 用户确认）、`git_ops`、`venv_manager`、`package_manager`（uv） |
| 检索 | `knowledge_search` / `task_knowledge_search`（项目 RAG）、`tavily_search`（互联网）、`web_fetch` |
| 文档 | `doc_generator`（pandoc + LibreOffice/MSO 转 Word/PDF） |
| Skill | `skill_runner`（执行第三方 Agent Skill） |
| 基础 | `base`（工具基类）、`tool_resolver`（统一工具路径解析） |

**Skill 框架**（`python/skills/`）：兼容 Anthropic **Agent Skills** 标准（`SKILL.md`）。内置工具通过 Adapter 永久桥接为 Skill；第三方 Skill 支持安装、启停、首次使用确认、渐进式披露（Level 1 元数据 + Level 2 执行时注入 body）。

### 5.5 数据存储策略

**存储分层：** SQLite 存结构化元信息，ChromaDB 存向量，文件系统存原始文档/报告内容/日志。

```
开发: python/data/
生产: %APPDATA%/InkCube/data/   （platformdirs，跨平台）
```

**核心数据表（SQLite，共 23 表 + FTS5 虚拟表）：**

| 领域 | 表 |
|------|-----|
| 配置 | `settings` |
| 任务 | `tasks`、`task_messages`、`task_agent_state`、`skills` |
| 知识库 | `projects`（含 kind/lib_type/type/stage/company_name/credit_code）、`files`、`images`、`chunks_fts`(FTS5)、`project_base_libs` |
| 报告 | `reports`、`report_sections`、`templates`、`report_logs` |
| Wiki | `wiki_schemas`、`wiki_pages`、`wiki_source_pages`、`wiki_page_sources`、`wiki_page_versions`、`wiki_reviews`、`wiki_change_log`、`wiki_compile_tasks` |
| 活动通知 | `notifications`（终态通知，未读查重）、`model_downloads`（下载状态持久化，崩溃恢复） |

> 向量数据存于 ChromaDB（`data/chroma/`，按 project_id 隔离 collection）；本地模型存于 `data/models/`（bge-m3 等）。

**Schema 迁移：** `database.py` 采用幂等 `_migrate_add_column()` + `CREATE TABLE IF NOT EXISTS`，应用启动时自动补齐列/表，只迁移结构不改用户内容。

### 5.6 升级不覆盖用户数据

| 类型 | 位置 | 升级行为 |
|------|------|----------|
| 应用代码 | `C:\Program Files\InkCube\` | 覆盖更新 |
| 程序资源 | 安装包 `resources/`（模板、工具链） | 随版本覆盖（只读） |
| 用户数据 | `%APPDATA%\InkCube\`（data.db、data/、tasks/、models/、skills/） | 永久保留 |

NSIS 配置 `deleteAppDataOnUninstall: false`，卸载重装数据不丢。详见 [0.2](0.2packaging-design.md)。

### 5.7 长时操作生命周期

任务、文件解析、图片描述、Wiki 编译、报告生成五类长时操作共享统一状态机与崩溃恢复模型：**DB 是状态源，前端是只读镜像**；启动时扫描 `processing/queued` 记录，超时标记失败、未超时续跑。恢复逻辑分布在 `main.py`（任务 + 报告）与 `knowledge/task_queue.py::_reset_interrupted_items`（文件 / 图片 / Wiki 编译）。详见 [0.4](0.4lifecycle-design.md)。

前端反馈侧为**统一后台活动总线（Activity Hub，已实施）**：notifications 表持久化终态通知 + `GET /activities/status` 聚合端点 + 前端 ActivityMonitor 单一常驻轮询（已吸收原 `WikiReviewMonitor` 轮询），分发到 Toast / 侧边栏徽章 / 首页活动区 / 详情页 Tab 角标四个反馈面（见 0.4 v1.1 §3）。功能就绪度与准入引导（Readiness，已实施）见 0.4 v1.6 §10。

## 6. 功能模块架构

### 6.1 知识库 RAG（`python/knowledge/`）

```
文件上传 → ProcessingPipeline（Docling 解析 → 分块 → bge-m3 向量化 → ChromaDB + FTS5）
        → 图片抽取 → VLM 描述（异步）
检索：KnowledgeSearchTool（向量 + BM25 → RRF 融合 → 可选 rerank）
异步：KnowledgeWorker（文件解析 worker + 图片描述 worker，独立并发控制）
```

关键文件：`pipeline.py`（解析管线）、`vector_store.py`（ChromaDB + bge-m3）、`fts_store.py`（FTS5）、`hybrid_retriever.py`（RRF 融合）、`knowledge_search.py`（检索工具）、`task_queue.py`（异步 worker）、`doc_parser.py`、`vlm_client.py`、`model_manager.py`、`file_cleanup.py`。详见 [2.2](2.2knowledge-base-design.md)。

### 6.2 LLM Wiki（`python/wiki/`）

逐文件增量摄入（Per-Source Ingest）：LLM 读取完整原文 → 创建来源页 → 触碰 10-15 个相关页面（实体/概念/主题页）→ 更新 index.md / log.md。支持监督模式、Lint 健康检查、sweep-reviews、知识图谱、级联删除、页面版本。关键文件：`ingest.py`、`compiler.py`、`parser.py`、`wiki_graph.py`、`wiki_search.py`、`lint.py` / `semantic_lint.py`、`sweep_reviews.py`、`dedup.py`、`context_budget.py`、`llm_routing.py`、`detect_language.py`、`wiki_enrich.py`、`prompts.py`。详见 [2.6](2.6wiki-design.md)。

> **当前集成状态**：Wiki 通道已接入报告引擎检索主流程——项目存在已完成（compiled / user_edited）Wiki 页面时自动启用（`runner.py` 检测 → `retrieval.py` wiki 通道），采信优先级 Wiki > 知识库 > 互联网（见 2.6 §8.2）。

### 6.3 报告生成引擎（`python/report_generator/`）

独立模块（非 Tool/Skill），有状态多步流水线：

```
模板加载(loader) → 归一化(normalizer，多级大纲折叠为两级 + 变量实例化 + foreach 展开)
  → 变量解析(variable_resolver，研究 DAG 拓扑求值)
  → 逐节：检索策略(search_strategy) → 多通道检索(retrieval：knowledge + internet，通道间/内并行)
          → 知识卡片(card_builder：LLM 提取 + 归因 + 去重 + 充足性评估)
          → 引用注册(registry) → Prompt 构建(prompts) → 生成(runner，两遍执行 + checkpoint)
          → 单节校验(validator) → Token 统计(token_tracker)
  → 全局收尾(finalizer：一致性检查 + 衔接润色 + 引用重排)
  → 渲染导出(renderer：Markdown → docx/pdf)
```

详见 [2.5](2.5report-design.md)。

## 7. 安全考量

| 风险 | 措施 |
|------|------|
| XSS → 本地文件访问 | CSP 限制，禁用 nodeIntegration，contextBridge 隔离 |
| Python 端口被外部访问 | 仅绑定 `127.0.0.1` |
| Shell 命令风险 | 域名白名单 + 用户确认（30s 倒计时） |
| Skill 执行风险 | 首次使用确认（60s 倒计时） |
| 任务代码隔离 | 每任务独立 venv（基于 python-build-standalone） |
| LLM API Key 存储 | 本地 settings（DB），不外传 |
| 用户数据泄露 | 全部本地存储，无遥测 |
