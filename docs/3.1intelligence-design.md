# 3.1 四期:智能层设计(脉搏带 AI 状态句 / 台账时间轴卡 / 事件驱动任务建议 / milestone 台账提取)

> 上位文档:[3.0project-lifecycle-design.md](3.0project-lifecycle-design.md) §8 分期路线四期行。蓝图与验收信号以 3.0 为准,本文档是其四期的详细设计(表结构/数据流/前端交互三要素)。
> 状态:**✅ 已实施交付(2026-10-11,方案 A)**。设计裁决与实现一致;实施过程偏差(首页摘要行拉取点从 App.tsx 改 HomePage,因 App 在 ActivityProvider 之上不可用 useActivity)已在 3.0 §6.2 同步。

## 1. 背景与四个子项

一/二/三期交付了「结构」:知识置首、脉搏带、时期任务模型、首页工作台——系统能**记录和展示**状态,但所有判断由用户自己做。四期让 AI 读项目持续产生的内容(月报→台账追加、发现项累积),主动给出判断与建议:

| # | 子项 | 现状缺口 | 四期后 |
|---|---|---|---|
| ① | 脉搏带 AI 状态句 | 状态句是规则拼接(数字串一句话),准确但无洞察 | 轻模型读信号生成一句「懂行」的现状判断;**仅换生成逻辑,UI 结构不动**(3.0 §10 决策 9) |
| ② | 台账时间轴卡 | 台账是 wiki 页里的 Markdown 文本,机器读不懂,只有人翻 wiki 才看见 | 结构化解析端点把台账文本解析成条目;知识总览时间轴卡 + 首页卡片墙摘要(3.0 §7.1 预留位)可视化 |
| ③ | 事件驱动任务建议 | 台账新增值得跟进的事件(如行政处罚)后无人建任务 | 系统生成「是否创建跟进任务」建议卡,[采纳]→进时期看板,[忽略]→永不再提 |
| ④ | milestone 台账提取 | 同一里程碑两边记账:看板节点等打勾、台账可能已写「已投产」,靠人肉对齐 | 台账条目 vs 看板 open 节点比对,建议「标记完成」,[确认]→PATCH 打勾 |

依赖关系:②是数据地基 → ③④消费同一份结构化条目(④是③的特例:建议机制+里程碑专项比对,共用一套建议基础设施)→ ①独立支线(UI 位一期已交付)。

## 2. 架构方案(已裁决:方案 A)

核心矛盾:解析出的结构化数据和建议,存不存库、什么时候算。

| | A 编译后落库 ✅ | B 打开时即时计算 | C 混合 |
|---|---|---|---|
| 打开速度 | 毫秒级读表 ✅ | 每次等 LLM 秒级 ❌ | 部分 |
| 忽略不再提 | 持久化可记 ✅ | 无处记,反复出现 ❌ | 部分 |
| 新增轮询 | 无(挂编译完成事件) | 无 | 无 |
| 机制数 | 1 套 ✅ | 1 套 | 2 套 ❌ |

**方案 A**:编译完成时(既有事件挂点)自动触发后台解析——AI 把台账文本解析成条目存新表,建议生成好存新表;界面全部读算好的结果。与项目既有哲学同构:「编译时 AI 干重活,打开时读现成结果」(wiki 页面本身即如此)。落选理由:B 不可兑现「忽略不再提」且首页聚合场景不可行;C 两套机制并存维护成本反升(用户裁决 2026-10-11)。

## 3. 表结构

引用:台账唯一事实源 `wiki_pages`(DDL 见 [2.6wiki-design.md](2.6wiki-design.md));任务采纳落点 `phase_tasks`(DDL 见 [3.0project-lifecycle-design.md](3.0project-lifecycle-design.md) §4)。本文档新增 2 表 + 2 处扩列。

### 3.1 `ledger_entries` — 台账结构化条目(②的地基)

**定位**:台账页 content 的**结构化派生缓存**。唯一事实源永远是 `wiki_pages.content`;本表全量可重建,损坏不丢数据。

```sql
CREATE TABLE IF NOT EXISTS ledger_entries (
    id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    page_key TEXT NOT NULL,          -- 来源台账页:milestones / risk_watchlist / policy_ledger / ...
    entry_date TEXT,                 -- 条目日期,尽力规范:YYYY-MM-DD 或 YYYY-MM;解析不出为 NULL
    entry_type TEXT NOT NULL,        -- milestone / risk / policy / finance / service / ...(自由语义标注)
    content TEXT NOT NULL,           -- 条目原文(一行)
    source_file_id TEXT,             -- 来源文件(可追溯到哪份月报)
    fingerprint TEXT NOT NULL,       -- 内容指纹(规范化哈希,见 §3.5 不变量 3):幂等去重的锚
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE(project_id, page_key, fingerprint)
);
CREATE INDEX IF NOT EXISTS idx_ledger_entries_project
    ON ledger_entries(project_id, page_key, entry_date);
```

**读写行为**:
- **写**:仅在编译完成后全量重解析——按 `(project_id, page_key)` 单事务「删旧插新」;台账 content 变了条目集合必然跟着变,未变条目 fingerprint 相同,下游无感知。条目 `id = le_{project_id}_{page_key}_{fingerprint}`(含项目+页作用域,整体 review C1:纯 fp 全局主键会让跨项目同文本撞车 INSERT IGNORE → 后编译项目整页静默清空)
- **读**:时间轴卡 / 卡片墙摘要 / 建议生成 / AI 状态句,全部只读此表;**禁止任何界面直写**(事实源是 wiki 页)

### 3.2 `task_suggestions` — 任务建议(③④共用一套)

**定位**:规则产生的「要不要建任务(③)/要不要标记完成(④)」建议。持久化才能兑现验收信号「一键采纳/忽略」+「忽略过不再提」。

```sql
CREATE TABLE IF NOT EXISTS task_suggestions (
    id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    kind TEXT NOT NULL,              -- create_task(③建议新建) / complete_task(④建议标记完成)
    title TEXT NOT NULL,             -- 建议的任务标题 / 目标任务标题
    description TEXT DEFAULT '',
    rationale TEXT,                  -- 一句人话:为什么建议(引用台账条目)
    entry_fingerprint TEXT,          -- 触发条目指纹(⚠ 不存 entry id,见不变量 2)
    target_task_id TEXT,             -- kind=complete_task 时的目标任务(phase_tasks.id)
    suggested_phase TEXT,            -- create_task:建议放入的时期(before/during/after)
    suggested_task_type TEXT,        -- create_task:建议的任务类型,默认 milestone(§7 决策 4)
    status TEXT NOT NULL DEFAULT 'pending',  -- pending / accepted / dismissed
    accepted_task_id TEXT,           -- 采纳后生成的任务 id(审计可溯)
    created_at TEXT NOT NULL,
    decided_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_task_suggestions_project ON task_suggestions(project_id, status);
CREATE UNIQUE INDEX uq_task_suggestions_fp        -- 整体 review C1:幂等兑底约束,项目作用域
    ON task_suggestions(project_id, entry_fingerprint, kind);
```

存量库经启动迁移补建唯一索引(`_migrate_task_suggestions_unique`:先按 created_at 保留最新去重,再建索引,幂等跳过)。

**关键行为**:
- **采纳**(db 层单事务原子完成,整体 review W2:路由层 check-then-act 有竞态窗口——accept×dismiss 并发可产生「任务已建但建议显示 dismissed」悬挂):pending 守卫(条件 UPDATE 占位)→ `create_task` INSERT `phase_tasks`(带 suggested_phase/task_type,其余必填列取安全默认)/ `complete_task` 目标置 `done`(completed_by='manual',校验目标仍存在且 open,失效则建议同事务转 dismissed)→ 回填 accepted_task_id;已被决策 → 409
- **忽略**:`status='dismissed'` + 记 decided_at(only_pending 条件更新,不覆盖已决状态);**去重规则**:同一 `(project_id, entry_fingerprint, kind)` 已存在 dismissed/accepted 记录时不再生成新建议——「忽略过不再骚扰」(整体 review C1:必须项目作用域,否则 A 项目 dismissed 会永久沉默 B 项目同文本建议)

### 3.3 `projects` 扩 2 列 — AI 状态句(①)

状态句是项目级单值、随时覆盖、可重算——不建表,沿用 `wiki_overview` 同款列迁移先例(database.py `_migrate_add_column`):

```sql
ALTER TABLE projects ADD COLUMN pulse_ai_status TEXT DEFAULT '';  -- AI 生成的状态句
ALTER TABLE projects ADD COLUMN pulse_ai_status_at TEXT;          -- 生成时间(编译时点)
```

**定位**:AI 句是「编译时点快照」(以台账动态+发现项等相对稳定内容为主);任务类实时信号(逾期数等)仍由既有 chips 表达,两者并存不混用(§7 决策 5)。

### 3.4 `wiki_schemas` 扩 1 列 — 台账页判定(§7 决策 3)

```sql
ALTER TABLE wiki_schemas ADD COLUMN is_ledger INTEGER DEFAULT 0;  -- 1=台账页(监控页)
```

种子数据为台账式结构页标注 `is_ledger=1`(recruitment:milestones/risk_watchlist/policy_ledger/operation_monitor/service_log;investment:financial_monitor/legal_risk(动态部分)/milestone_tracker/risk_summary/exit_path/deal_terms;general:对应监控页)。解析范围 = `is_ledger=1` 的页;用户经 Schema 管理新建台账式结构页时勾选「台账页」开关。

### 3.5 设计不变量

| # | 不变量 | 理由 |
|---|---|---|
| 1 | `wiki_pages.content` 是台账唯一事实源,`ledger_entries` 可随时全量重建 | 派生缓存坏了不丢数据,重编译即可修复 |
| 2 | 建议表引用 `entry_fingerprint` 而非 `ledger_entries.id` | 全量重插会换 id,指纹才稳定——避免建议悬空 |
| 3 | 建议生成幂等:`(project_id, entry_fingerprint, kind)` 唯一(UNIQUE 索引兑底);fingerprint = NFKC 全半角归一 + lower + 去空白/标点后哈希 | 重放/重解析不产生重复建议;LLM 措辞漂移(标点/空白/全半角)不致 dismissed 复活(整体 review C1/W3)。边界:日期不归一(日期变化属内容实质变化,重新提醒符合用户利益);内容实质改写后会再提(设计预期) |
| 4 | 解析活动不建任务表,走内存活动注册表 | 崩溃恢复依赖上游编译重放(解析是编译纯下游),符合 2.7 统一模型 |

### 4.2 写路径(事件分列)

**编译完成 → 后台解析(唯一自动写入口)**,直调点=[task_queue.py L580](../python/knowledge/task_queue.py) `activity_events.complete_compile(...)` 旁(该处 `project_id` 在作用域内):

```
wiki 编译终态(complete_compile 事件声明点旁)
  → 直调 ledger_service.on_compile_complete(project_id)
     [与 on_file_parsed/on_report_completed 同款「全部直调点」惯例,3.0 §5.4]
     try/except 全包裹仅记日志——解析失败绝不影响编译主流程
     │
     ├ 守卫:该项目 ledger_parse 活动进行中 → 跳过(防手动重编译并发重复解析)
     ├ 注册活动 kind='ledger_parse' → 全局心跳自动携带进度(0.4 体系,零新增轮询)
     ├ ① 读该项目 is_ledger=1 全部台账页 content(事实源快照)
     ├ ② LLM 结构化解析 → 单事务「删旧插新」ledger_entries
     ├ ③ 建议生成(规则比对,无需 LLM):
     │    ④ milestones 条目 vs phase_tasks(open 里程碑)标题/日期匹配 → complete_task 建议
     │    ③ risk_watchlist 新增风险条目 → create_task 建议(跟进模板)
     │    幂等:(project_id, entry_fingerprint, kind) 已 dismissed/accepted → 跳过
     │    (fp = NFKC + lower + 去空白/标点后哈希,LLM 措辞漂移不复活 dismissed,整体 review W3)
     ├ ④ AI 状态句:entries 摘要 + 发现项计数 → 轻模型一句话 → UPDATE projects.pulse_ai_status(_at)
     └ 活动终态 → 既有全局心跳携带 → 前端感知
```

**采纳/忽略(用户写)**:

```
建议卡[采纳] → IPC affairs:acceptSuggestion
  → POST /projects/{id}/suggestions/{sid}/accept
     db.accept_suggestion_atomic:单事务 pending 守卫 → 动作 → 回填(整体 review W2)
     create_task    → INSERT phase_tasks(suggested_phase/task_type)→ 回填 accepted_task_id
     complete_task  → 目标置 done(completed_by='manual';校验仍存在且 open,否则建议同事务转 dismissed)
  → dispatch app:tasks-changed → 首页待办/侧栏色点/脉搏带即时同步(三期已铺,新消费方)
  → 组件 onAccepted 回调 → AffairsTab 重拉看板(看板 state 不在事件链内,整体 review W1)

建议卡[忽略] → POST .../dismiss → status='dismissed'(永不再提,靠 fingerprint 幂等)
```

### 4.3 读路径(全部毫秒级读表)

| 消费方 | IPC → 端点 | 说明 |
|---|---|---|
| 时间轴卡 | `wiki:listLedgerEntries` → `GET /projects/{id}/ledger/entries?limit=` | 按 entry_date 倒序(NULL 日期置尾),前端按日分组;limit 默认 20 |
| 卡片墙最新条目 | `ledger:listLatest` → `GET /ledger/latest` | 跨项目聚合,每项目取最新 1 条(affairs:listDue 同款模式) |
| 建议卡/脉搏带徽章 | `affairs:listSuggestions` → `GET /projects/{id}/suggestions?status=pending` | 待决策建议;脉搏带徽章只取 count |
| AI 状态句 | **零新请求** | `pulse_ai_status` 在 projects 行上,随既有 `loadProjects` 流到 `project` prop;新鲜度由 ledger_parse 活动终态驱动(前端 `useActivity('ledger_parse')` 边沿 → 既有 `onProjectDataChanged` 刷新 projects) |

### 4.4 失败与降级(纵深防御;根因是 LLM 调用固有不稳,降级保证主流程与既有功能不受影响)

| 失败点 | 行为 | 展示层 |
|---|---|---|
| LLM 解析失败 | 活动标 failed + 日志;**不删旧条目**(保持上一版) | 时间轴卡显示旧数据(事实源 wiki 页永远最新);下次编译自然重试 |
| 状态句生成失败 | 保持旧值 | PulseBar AI 句为空 → **回落既有规则句**(一期机制,天然兜底位) |
| 建议生成失败 | 跳过,不影响条目落库 | 无感知;下次编译补上 |
| 采纳时目标任务已删/已完成 | accept 端点校验失效 → 建议自动转 dismissed | Toast「任务已不存在,建议已失效」 |

### 4.5 并发守卫

| 竞态 | 守卫 |
|---|---|
| 手动重编译 × 自动编译并发触发两次解析 | 活动注册按 project_id 查重,进行中即跳过 |
| 采纳 × 目标任务同时被用户手动完成 | PATCH 幂等(已 done 再置 done 无害);accept 前置校验兜住 |
| accept × dismiss / 双击重复采纳 | db 层原子采纳(整体 review W2):单事务 pending 行级守卫,后到者 409,不产生「任务已建但建议 dismissed」悬挂 |
| 解析删旧插新 × 用户同时读条目 | 单事务替换,SQLite 串行写保证读侧只见完整旧集或完整新集 |

| AI 句为空(未生成过/生成失败) | 既有规则句(优先级:拉取失败 > 逾期 > 矛盾 > 缺口 > 报告生成中 > 一切正常,不变) |
| ledger_parse 进行中 | 保持旧 AI 句(或规则句);不显示解析进度(进度走活动监控) |
| 折叠态 | 不变(折叠行只有标题+最高优先计数,不显示 AI 句) |

**AffairsTab 建议卡**:

| 状态 | 用户看到 |
|---|---|
| pending=0 | 整卡不渲染(对齐健康卡「全 0 不渲染」惯例) |
| pending>0 | 建议列表:[③新建图标/④打勾图标] title + rationale(如「台账显示项目已于 9 月投产…」)+ [采纳][忽略] |
| 采纳中 | 该条按钮禁用;成功后条目消失 + Toast;首页待办/侧栏经 app:tasks-changed 刷新,看板经 onAccepted 重拉 |
| 采纳失败(目标失效,404) | Toast「任务已不存在,建议已失效」,条目消失(已转 dismissed) |
| 采纳失败(已被决策,409) | Toast 采纳失败(并发后到者;列表下次边沿刷新对齐) |
| 忽略 | 条目立即消失,永不再提 |
| ledger_parse 进行中且现有 pending>0 | 照常展示(新建议在解析完成后经边沿进入) |

**WikiHomePage 时间轴卡**:

| 状态 | 用户看到 |
|---|---|
| entries 为空(从未编译出条目) | 整卡不渲染 |
| 非空 | 「最近动态」卡:按日分组条目列表(最多 limit 条);每条 = 日期(YYYY-MM-DD 或 YYYY-MM,缺失显示「—」)+ 台账页标题 + 条目内容一行截断 |
| ledger_parse 进行中 | 卡头「解析中…」灰字(经 useActivity('ledger_parse') 判定),既有条目照常展示 |

**ProjectCardWall 摘要行**:

| 状态 | 用户看到 |
|---|---|
| 项目有台账条目 | 卡内新行:`09-30 风险 · 新增行政处罚记录…`;点击 → 直达该项目知识 Tab |
| 无条目(新项目/未编译) | 该行不渲染,卡高不变 |

### 5.3 交互规则与不变量

1. AI 只提议不决策:采纳/忽略/打勾永远是用户动作,建议层永不直接改任务表(3.0 §10 决策 10 精神延伸)
2. UI 文案双语(i18n 键前缀 `pulse.*` 复用 / `affairs.suggestion.*` / `home.entry.*` / `wiki.timeline.*`),AI 生成内容(状态句/建议 rationale)为中文——与 wiki 页面内容同语言策略(§7 决策 6)
3. 时间轴卡/建议卡/摘要行的空态全部「整块不渲染」,不出现空壳卡(对齐一期健康卡惯例)
4. 建议一旦 decided(accepted/dismissed)即从所有 pending 视图消失,仅在 DB 留审计
5. 零新增轮询:全部数据 = 挂载拉取 + `app:tasks-changed`/`useActivity('ledger_parse')` 边沿刷新(0.4 §3.1 验收信号)

## 7. 关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | 方案 A 编译后落库 | 打开毫秒级 + 忽略可持久 + 单机制;与「编译时干重活」哲学同构(用户裁决 2026-10-11;落选 B/C 见 §2) |
| 2 | 建议卡位置 = 事务 Tab 顶部,脉搏带加「建议」chip 作入口徽章 | 建议是任务域决策,收口在事务 Tab(3.0 §10 决策 10 同构);徽章复用 PulseBar chips 显隐模式(落盘细化) |
| 3 | 台账页判定 = `wiki_schemas.is_ledger` 标注列 | `wiki_pages.page_type` 由 LLM 摄入自由给值(ingest.py L214 默认 entity),非受控枚举不可依赖;schema 标注是单一语义源且覆盖用户自建结构页 |
| 4 | `suggested_task_type` 默认 milestone,合法值对齐 phase_tasks.task_type(material/report/milestone/recurring) | 讨论稿笔误「periodic」修正;跟进类建议多为节点,create_task 采纳时按建议值落 task_type |
| 5 | AI 状态句 = 编译时点快照,与实时 chips 并存不混用 | 句子表达「趋势+建议」,chips 表达「实时计数」;混合会互相污染新鲜度 |
| 6 | AI 生成内容(状态句/rationale)固定中文 | 与 wiki 页面内容同语言策略(compile_hint 全中文);i18n 双语约束只管 UI 文案 |
| 7 | 卡片墙顺带补「下一事务名+逾期文案」(现只有日期 MM/DD) | 数据同源(listDue 已含 title),L582 已向用户提议,随本节确认 |

## 8. 验收信号(对齐 3.0 §8)

- 建议可一键采纳/忽略;忽略过不再提(fingerprint 幂等)
- AI 仅换生成逻辑不动 UI 结构(PulseBar 结构/折叠/chips 零变化,仅状态句内容来源变化)
- 零新增轮询;解析失败不影响编译主流程;界面读表毫秒级
