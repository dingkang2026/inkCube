# 知识库设计：解析、检索与问答

> **概述**：本文档定义知识库子系统——项目「资料」能力的完整后端引擎，覆盖四条链路：
> 1. **解析管线**——上传文件经 Docling（版面分析 + OCR + 表格识别）解析、HybridChunker 分块、bge-m3 向量化后双写 ChromaDB + SQLite FTS5（§3 / §4）；
> 2. **异步任务系统**——KnowledgeWorker 三 worker 池（文件解析 / 图片描述 / Wiki 编译）+ 5s 队列扫描器 + 崩溃恢复（§5）；
> 3. **混合检索**——dense（ChromaDB HNSW cosine）与 FTS（SQLite FTS5，CJK/拉丁双路）经 RRF 融合（§6）；
> 4. **RAG 问答**——检索片段 + Wiki 页面骨架组装上下文，交 LLM 生成带来源回答（§7）。
>
> 项目结构、基础库（共享知识库）与前端页面归属见 [2.1](2.1project-design.md)；基础库 RAG 的检索范围差异见 [2.7](2.7baselib-rag-design.md)；Agent 工具 `knowledge_search`（任务内调用本引擎）见 [1.1 §3](1.1task-agent-design-unified.md)；图片描述活动、文件活动的心跳与通知集成见 [0.4](0.4lifecycle-design.md)。

## 1. 定位与核心流程

知识库是「项目」的资料层：每个项目（含基础库，projects 表统一建模）持有自己的文件、向量集合与全文索引，检索按 project_id 隔离。核心流程：

```
上传（base64 JSON 经 IPC）
  → ensure_ready("file_parsing") 前置校验
  → 200MB 上限检查 + 文件名去路径化
  → 落盘 data/files/{project_id}/{file_id}/ + MD5 去重
  → files 记录（status=pending）+ 入队
  → [file worker] pipeline 四阶段：
      ① Docling 解析（Office→PDF 预转换）→ 文本切片；
        DOCX/PPTX 图片另由原生 zip 提取（office_media，无损，§4.4）
      ② HybridChunker 分块 → ChromaDB + FTS5 双写
      ③ 图片元数据入 SQLite（status=pending）
      ④ 终态：done/error + 活动通知
  → [image worker 异步] LLM 描述 + 分类 + 小图/无用类归档
       → 描述作为 figure chunk 入 ChromaDB

检索 / 问答
  → dense（bge-m3 编码 → ChromaDB cosine top_k×2）
  → FTS（CJK LIKE bigram / 拉丁 FTS5 MATCH，top_k×2）
  → RRF 融合（dense 0.7 / fts 0.3, k=60）→ top_k
  → [问答] + Wiki 页面骨架 → 上下文组装 → LLM → 回答 + sources
```

**技术选型**：

| 组件 | 选型 | 说明 |
|------|------|------|
| 文件解析 | Docling | 统一接口处理 PDF / DOCX / PPTX / XLSX / HTML / 图片 |
| 版面分析 | docling-layout-heron | 识别文本 / 表格 / 图片 / 标题区域 |
| 表格识别 | TableFormer V2 | 表格结构还原（TableStructureV2Options） |
| OCR | RapidOCR | ONNX Runtime 推理（3 个 onnx：det/cls/rec） |
| 分块器 | HybridChunker | token-aware + contextualize + merge_peers + repeat_table_header |
| Embedding | BAAI/bge-m3 | 本地运行（FlagEmbedding，1024 维 dense；CUDA 可用时 fp16/GPU，否则 fp32/CPU 自动回退） |
| 向量库 | ChromaDB | 嵌入式 PersistentClient（进程级单例 `get_chroma_client`，统一 settings），每项目一个 collection |
| 全文索引 | SQLite FTS5 | chunks_fts 虚拟表（unicode61），BM25 排序 |
| 图片理解 | 外部 LLM API（多模态） | 与主 LLM 同一配置（standard 档，llm/vision.py，无独立配置）；无本地兜底 |
| 推理框架 | PyTorch + ONNX Runtime | PyTorch 用于 layout/TableFormer/bge-m3，ONNX 用于 RapidOCR |

## 2. 存储模型

### 2.1 SQLite 表（database.py 建表 + 迁移列）

projects 表是知识库容器（与项目/基础库统一建模，DDL 与语义见 [2.1 §3](2.1project-design.md)）。知识库自有三张表：

```sql
CREATE TABLE IF NOT EXISTS files (
    id TEXT PRIMARY KEY,                 -- file_{uuid8}
    project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    filename TEXT NOT NULL,
    file_type TEXT NOT NULL,             -- 扩展名（.pdf/.docx/...）
    file_size INTEGER NOT NULL,
    file_hash TEXT NOT NULL,             -- MD5，同项目内去重
    status TEXT DEFAULT 'pending',       -- pending / parsing / done / error
    error_message TEXT,
    chunk_count INTEGER DEFAULT 0,
    image_count INTEGER DEFAULT 0,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
-- 迁移列：image_status TEXT DEFAULT 'none'    -- none/pending/describing/done/error
--         image_described_count INTEGER DEFAULT 0
--         progress INTEGER DEFAULT 0          -- 0-100，解析阶段进度

CREATE TABLE IF NOT EXISTS images (
    id TEXT PRIMARY KEY,                 -- uuid
    file_id TEXT NOT NULL REFERENCES files(id) ON DELETE CASCADE,
    page_no INTEGER,
    caption TEXT,
    width_px INTEGER,
    height_px INTEGER,
    dpi INTEGER,
    local_path TEXT NOT NULL,            -- 图片落盘路径（在源文件目录内）
    figure_type TEXT,
    vlm_description TEXT,                -- 图片描述（LLM 异步填充；列名为历史命名，2026-10-21 VLM 链路删除，零迁移保留）
    context_text TEXT,                   -- "[上文] ...\n[下文] ..." 拼接文本
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
-- 迁移列：status TEXT DEFAULT 'pending'       -- pending/processing/done/error/archived
--         error_message TEXT
--         category TEXT DEFAULT 'uncategorized' -- LLM 分类（chart/photo/...）

CREATE VIRTUAL TABLE IF NOT EXISTS chunks_fts USING fts5(
    chunk_id,                            -- chunk_{file_id}_{idx} / img_{file_id}_*
    content,                             -- 与 ChromaDB documents 相同的纯文本
    project_id,
    filename,
    content_type,
    tokenize='unicode61'                 -- 无法分词中文 → CJK 检索走 LIKE 旁路（§6.2）
);
```

索引：`idx_files_project(files.project_id)`、`idx_images_file(images.file_id)`。

**状态机**（files）：`pending →（worker 领取）→ parsing →（管线四阶段）→ done | error`；重试经 cleanup 后回 pending。images：`pending → processing → done | error | archived`（archived 含小图自动归档与无用分类归档）。files.image_status 是文件级聚合（由 `update_file_image_status` 从属下 images 推导），供文件列表显示「描述中 x/y」。

### 2.2 ChromaDB Collection

每项目一个 collection，命名 `project_{project_id}`，HNSW 参数：`hnsw:space=cosine`、`hnsw:construction_ef=128`、`hnsw:search_ef=64`。

每条 chunk 的结构（id / documents / metadata）：

```python
{
  "id": "chunk_{file_id}_{idx}",            # 文本块；图片块为 img_{file_id}_{page_no}_{image_id}（§5.3-5）
  "documents": [contextualized 纯文本],      # 用于 embedding 的文本
  "metadata": {
    "file_id": "...", "filename": "CIM.pdf",
    "content_type": "paragraph",            # heading/paragraph/table/figure/caption/list
    "chunk_index": 0,
    "markdown_content": "| 列1 | 列2 |...",  # RAG 展示用（表格保 Markdown 结构）
    "section_path": "第三章 > 3.2 财务分析",  # 标题层级路径
    "page": 15,                              # 可选
    # 图片块额外：image_id（关联 SQLite images.id）、markdown_content=图片描述
  }
}
```

**分层原则**：ChromaDB 只存语义检索相关信息；物理属性（尺寸 / 路径 / 分类）在 SQLite images 表，配图决策与前端渲染走 SQL 查询。embedding 由 ChromaDB 的自定义 EmbeddingFunction（BgeM3EmbeddingFunction，见 §6.1）在 add 时计算。

## 4. 解析管线（doc_parser + pipeline）

### 4.1 Docling 转换器（双模块级单例）

`_get_docling_converter(models_dir, generate_picture_images)` 以模块级单例 + 双检锁加载 DocumentConverter（布局 / 表格 / OCR 模型按 options 组各加载一次）：

- **带图单例**（`generate_picture_images=True`）：`PdfPipelineOptions`：`artifacts_path=models_dir`、`do_ocr=True`、`do_table_structure=True`（TableStructureV2Options）、`generate_picture_images=True`、`generate_page_images=False`；注册 PDF + IMAGE 两种 InputFormat（IMAGE 特化为无图 options，防「图中图」碎片，见 §4.4）。服务 PDF/HTML/XLSX 等格式与独立图片输入
- **无图单例**（`generate_picture_images=False`，仅注册 PDF）：仅服务 DOCX/PPTX 转 PDF 产物——图片改由原生 zip 提取（office_media，§4.4），Docling 不再生成有损裁剪图；无 Office 文档上传时模型不加载（惰性，零开销）
- 双单例而非运行时切换共享 options 的原因：docling 2.127 的 pipeline 缓存键为 (pipeline_class, options_hash)，独立实例避免文件并发 2 下切换共享 `format_to_options[PDF]` 槽位的竞态；首次 convert 串行锁为 per-converter（`_ThreadsafeConverter`），共享 warmed 标志会使第二个 converter 的惰性初始化失去保护
- Docling 未安装时单例为 None，解析时报「converter not initialized」

### 4.2 Office→PDF 预转换

仅 `.docx` / `.pptx` 在 Docling 解析前先转 PDF（xlsx 由 Docling 直接处理；其余格式直接解析）。**转换产物仅服务文字/版面（分块），图片不走转换链路（§4.4）**——Office 导出 PDF 时图片被重采样压缩（Word/PPT 默认 ~220ppi 有损），历史版本曾从该 PDF 裁剪图片导致图片库质量明显下降。转换器检测（`ModelManager.check_office_converter`）：优先 MS Office COM（Windows 下尝试 Dispatch Word.Application，成功即可用），其次 LibreOffice（PATH → 注册表 InstallPath → 常见安装位置）。

| 转换器 | 实现 | 失败处理 |
|---|---|---|
| MS Office COM | Word SaveAs(FileFormat=17) / PowerPoint SaveAs(32)（仅 docx/pptx；xlsx 由 Docling 直接处理） | 降级：Docling 直接解析原文件 |
| LibreOffice | `soffice --headless --convert-to pdf`（120s 超时；returncode=0 也检查 stderr） | 同上 |
| 均不可用 | 不转换 | 降级 + 用户可读 warning |

降级不是静默的：warning 文案（如「未检测到 Microsoft Office 或 LibreOffice，已由内置解析器直接解析原文件，复杂版式还原度可能降低」）写入 ParseResult.metadata.warnings，随管线完成通知的 detail 呈现给用户（0.4 §7.3）。临时 PDF 在解析 finally 中删除。

MS Office COM 实现要点（doc_parser `_convert_with_ms_office`）：

- **DispatchEx 独立实例**：绝不复用用户开着的 Office 实例——批量解析结束时只 Quit 自己的实例，不误杀用户文档
- **DisplayAlerts 抑制弹窗**（Word=0 / PowerPoint=1，属性不可用时忽略）：防止密码/修复提示等模态框永久阻塞 COM 调用
- **瞬态重试**：CPU 重负载下 Office 会以 RPC_E_CALL_REJECTED / RPC_E_SERVERCALL_RETRYLATER 拒调，`_com_call` 对这两类 hresult 短退避重试（0.5/1/2s），其余错误立即上抛（2026-10-07 实测：embedding 占满 CPU 时 docx 转换被拒，人工重跑即成功）
- **finally 清理**：doc.Close(SaveChanges=0) + app.Quit() 保证失败路径不泄漏 WINWORD/POWERPNT 进程

### 4.3 分块（HybridChunker）

`_extract_chunks` 使用 Docling 原生 HybridChunker：

- tokenizer：HuggingFaceTokenizer 加载本地 bge-m3 tokenizer（`max_tokens=1024`），与 embedding 模型分词一致
- 参数：`merge_peers=True`（相邻同章节小块合并）、`repeat_table_header=True`（表格拆分重复表头）、`serializer_provider=RowMarkdownSerializerProvider()`（表格序列化见下）
- 每个 chunk 产出 ChunkInfo 五字段：
  - `text`：`chunker.contextualize(chunk)` 上下文化文本（拼接标题路径；失败回退 chunk.text）——用于 embedding 与 FTS content
  - `markdown`：从 chunk.meta.doc_items 重建的 Markdown（表格经 self_ref 查 TableItem 调 export_to_markdown；无 doc_items 回退 chunk.text）——存 metadata.markdown_content
  - `content_type`：从 doc_items 的 label 集合按优先级推导（title/section_header→heading > table > picture→figure > caption > list > 默认 paragraph）
  - `section_path`：chunk.meta.headings 以 " > " 拼接
  - `page`：从 doc_items[].prov[].page_no 提取首个非空页码

**表格序列化（RowMarkdownTableSerializer，定义于 docling_serializers.py）**：替换 docling_core 默认的 TripletTableSerializer（三元组 `行, 列 = 值.` 对 xlsx 伪表头/合并说明行会产生列头缺失与重复刷屏）。所有格式的表格统一序列化为行级 Markdown：

- **表头检测**：扫描前 5 行，取首个「非空格 ≥ 2 且非空格占总列数 ≥ 60%」的行为列头。依据：xlsx 后端的合并单元格不共享对象（col_span 恒 1），标题/说明行只能靠稀疏度判别（实测标题行 1/16、编制单位行 2/16 vs 真表头 15/16）；分母必须用总列数——若按非空格数自身算占比，只有少数非 None 格的说明行会得出 100% 而被误判；无可检测表头时全部行按纯行输出（退化但可读，不造表头/分隔行）
- **preamble 提取**：表头之上的稀疏行（表名、编制单位等）去重合并为 preamble 文本，仅出现在表格首块，不参与表头重复
- **日期序列号还原**：表头行中 ≥ 3 个纯数字格且落在 Excel 日期序列号范围（36526–73050，即 2000–2099）时，整行转为 `YYYY-MM-DD`（基准 1899-12-30）——xlsx 日期单元格被 Docling 序列化为天数整数，不还原则年份语义丢失
- **行输出**：`| 单元格 | ... |` 逐行拼接，空值格留白、竖线转义、全空行跳过；垂直合并的重复格（仅 PDF 等后端存在对象共享）去重留白
- **分块协作**：实现 `get_header_and_body_lines()`（header=列头行+分隔行，body=数据行），HybridChunker 表格路径据此按行切块、每块自动重复表头（repeat_table_header），块边界不切断行

### 4.4 图片提取（双路：Office 原生无损 / PDF 版面裁剪）

**DOCX/PPTX → 原生无损提取（office_media.py）**。根因：图片经「原始 media → Office 导出重采样（Word/PPT 默认 ~220ppi 有损）→ PDF 内嵌 → Docling 按 bbox 从页面位图裁剪」三级损伤。DOCX/PPTX 本质是 zip 容器，`word/media/`、`ppt/media/` 下的就是原始图片字节，直接提取即零损伤；文字/版面仍走 PDF 路（§4.2）。`extract_office_images` 按扩展名分发：

- **PPTX**：python-pptx 遍历 slides（页码 = slide 序号，与转换后 PDF 页天然一一对应），递归展开 group shape 取 `shape.image.blob`；图片判定用 `isinstance(shape, Picture)` 而非 `shape_type`——占位符图（`PlaceholderPicture`，模板化 PPT 极常见）的 shape_type 恒为 PLACEHOLDER 而非 PICTURE，按类型判断会整类静默漏图；上下文 = 同 slide 全部 shape/表格文本（slide 内 shape 顺序 ≠ 视觉阅读顺序，无「图前/图后」语义，整体作为页面文字上下文放 after_text）
- **DOCX**：python-docx 按 body 文档序遍历全部 `w:p`（含表格单元格内），inline 与 anchored（浮动）drawing 统一经 `//w:drawing//a:blip` 的 rId 从 `related_parts` 取字节；上下文 = 文档序前/后各 2 个非空段落（与 PDF 路 `_get_text_context` 同窗口）；页码 = None（流式文档无固定分页，前端对 null 页码显示 '?')
- **去重**：同一图片字节（MD5）在文件内多处引用（如每页页眉 logo）只登记首次出现，image_id 连续编号
- **格式门槛**：仅登记 LLM 可消费的位图格式（png/jpeg/gif/bmp/webp/tiff 白名单）；WMF/EMF 元文件、损坏字节跳过（不写盘不登记，数量记日志）
- **孤儿对账**：提取成功后按登记清单对账 `page_*_img_*` 落盘文件，清理上一轮中断遗留的孤儿（已写盘未登记，如首提中断后 retry 提取数收缩）；失败路径保守不动，留待下次成功对账
- **失败声明**：容器级异常由 doc_parser 捕获转 warning（「图片无损提取失败(异常类型)，本次解析不含图片」随完成通知 detail 呈现），images=[]、文件照常 done——原生提取是纯 zip 读字节几乎不会失败，不为此重新带图解析（避免双倍解析成本）

**PDF 等其余格式 → 版面裁剪（`_extract_images`，行为不变）**。遍历 doc.pictures：base64 uri 解码落盘 `page_{page_no}_img_{idx}.png`（与源文件同目录）→ PIL 读取尺寸 → 同页前后各 2 段文本作为上下文（`_get_text_context`，跨页截断）→ captions[0] 作为图注。产出 ImageContext（image_id=`img_{file_id}_{idx}`、before/after_text 拼接为 context_text 入库）。原生提取产物与裁剪产物共用同一落盘命名空间 `page_{n}_img_{i}.{ext}`（原生路保留原始格式扩展名，裁剪路恒 png）。

**独立图片文件**（.png/.jpg/.jpeg 直接上传，IMAGE 输入）：converter 为 IMAGE 输入配置独立 pipeline options（`generate_picture_images=False`，禁用 picture 区域裁剪）——否则版面模型会把照片内的图形元素（如证书上的国徽/公章）框成「图中图」碎片落盘，图片库出现碎片而非用户上传的整图；PDF 等文档输入不受此影响，内嵌图裁剪照常（DOCX/PPTX 的转 PDF 产物由无图单例处理，不产生裁剪图，图片走原生提取，见上）。因此 IMAGE 解析后 OCR 文字进入 chunks、`doc.pictures` 恒为空、不产生提取记录。pipeline 在阶段③补登记（`_source_image_context`）：源文件本身作为唯一图片记录入 images 表（page=1，与内嵌图共用的 img_ 命名空间靠尾部 image_id 保证向量 id 唯一，见 §5.3-5；caption=文件名；尺寸读取失败不阻断登记），使图片文件获得与内嵌图一致的下游链路（图片库 / LLM 描述 / figure chunk 检索 / 归档策略）。对应地，file_cleanup 的图片文件清理跳过源文件本身——retry 依赖源文件重跑；完整删除由目录级清理兜底。

### 4.5 管线四阶段（pipeline.process_file）

| 阶段 | 进度 | 动作 |
|---|---|---|
| ① 解析 | 2→25% | `asyncio.to_thread(parser.parse_file)`（最耗时：版面 + OCR + 表格） |
| ② 入库 | 30→75% | `_store_chunks`：构造 chunk metadata → ChromaDB add_documents（embedding 由 ChromaDB 侧计算）→ FTS 批量插入（单事务）；**0 chunks 短路**（空文件/无文本内容是成功结果：ChromaDB 拒绝空列表 add，短路跳过双写让文件正常落 done，空内容说明由 doc_parser 随 warnings 流入完成通知） |
| ③ 图片 | 80→90% | `_store_image_records`：images 表插入（status=pending，图片描述留空）；独立图片文件无提取记录时登记源文件本身（§4.4） |
| ④ 终态 | 90→100% | update_file_status(done, chunk/image 计数) + `activity_events.complete_file`（warnings 随 detail）；异常时 error 状态 + `fail_file` |

错误统一经 `errors.actionable()` 转换（配置类异常保留「设置 > 内部模型」修正指引）。图片描述**不在管线内**——管线只登记 pending 图片，由 image worker 异步处理（§5.3）。

## 5. 异步任务系统（task_queue.KnowledgeWorker）

### 5.1 结构

```
KnowledgeWorker（FastAPI lifespan 启动，main.py 装配）
├── 3 个 worker 池（asyncio.Semaphore 限并发）
│   ├── file workers ×1     —— 领取 pending 文件 → pipeline 四阶段
│   ├── image workers ×2    —— 领取 pending 图片 → LLM 描述
│   └── compile workers ×1  —— Wiki 编译任务（见 2.6）
├── queue scanner            —— 每 5s 扫 DB 补队（见下）
└── _reset_interrupted_items —— 启动崩溃恢复（§5.4）
```

三个队列均为内存 asyncio.Queue；API 直接入队（enqueue_file/enqueue_image/enqueue_compile），扫描器兜底补队（API 与扫描器重复入队由 worker 侧状态检查幂等消化：非 pending 状态直接跳过）。compile 队列附 `_compile_enqueued` 集合防重复入队。

**queue scanner**（5s 周期）：`files WHERE status='pending'` 全量 → 入 file 队列；`get_pending_images(limit=50)` → 入 image 队列；`wiki_compile_tasks WHERE status='queued' LIMIT 5` → 入 compile 队列。扫描器保证「上传后进程重启」「API 入队丢失」等场景下任务不丢。

### 5.2 file worker

领取文件 → 校验 status=pending → 组装路径 `data/files/{project_id}/{file_id}/{filename}` → status=parsing → 从 settings 读解析配置构建管线 → 执行。完成后的善后：

- **删除竞态防护**：重查 file 与 project 是否仍存在（解析期间可能被删除），不存在则丢弃结果
- 图片逐张入队 LLM 描述；`update_file_image_status` 推导文件级 image_status
- 失败时 error 状态 + `activity_events.fail_file`（与管线内部 except 双写，靠通知未读查重保证幂等）

### 5.3 image worker（LLM 图片描述）

每张图片：

1. **小图自动归档**：宽高均 < 100px → status=archived（error_message 说明可手动强制解析）；用户手动重试带 force=True 跳过该检查
2. LLM 调用（§8）：返回 description + category
3. **分类落库**：category 有效（≠other）时写入 category 列
4. **无用类归档**：category ∈ AUTO_ARCHIVE_CATEGORIES（qr_code/signature/seal）→ archived（描述保留，注明不适合报告配图）
5. **入库**：done 状态 + 描述文本作为 figure chunk 写入 ChromaDB（id 经 `vector_store.image_doc_id` 构造：`img_{file_id}_{page_no}_{image_id}`，尾部 image_id 保证同页多图 id 唯一——旧格式 `img_{file_id}_{page_no}` 同页碰撞被 upsert 互相覆盖，2026-10-14 事故 498 张图描述丢失；page_no 为 NULL 时回退 0，页码从 1 起故无碰撞歧义；metadata 含 image_id 关联 SQLite）。单图向量删除（归档/删除/重试前置清理）走 `delete_by_image_id` 按 metadata.image_id 过滤，id 格式无关——delete_by_ids 对存量旧格式 id 静默 no-op，会残留可检索向量
6. 同样有删除竞态重查（image/file/project 三重）；结束时 `update_file_image_status` 刷新文件级状态

### 5.4 启动崩溃恢复（_reset_interrupted_items）

worker 启动前执行：

| 残留状态 | 恢复动作 |
|---|---|
| files.status=parsing（进程中断） | 清 ChromaDB（where file_id）+ FTS（LIKE 双模式）+ images 记录 → reset_file_for_retry → pending（重新入队） |
| images.status=processing | 直接置回 pending |
| wiki_compile_tasks 中断态 | reset_interrupted_compile_tasks（见 2.6） |

ChromaDB 清理经进程级共享单例 `get_chroma_client`（删除操作无需 embedding 模型）。**禁止裸 PersistentClient**：chromadb 按（路径， settings）缓存后端，裸 client 以默认 settings 注册后，后续所有 `VectorStore(...)` 均抛「different settings」——2026-10-07 事故：带中断文件重启后 181 个文件连环失败；同规则适用 `system._clean_knowledge`（先 `drop_chroma_client` 摘缓存再删目录）。

## 6. 检索引擎

### 6.1 VectorStore（dense 路）

- **bge-m3 模块级单例**：`_get_bge_m3_model` 双检锁加载 BGEM3FlagModel，全进程只加载一次；支持嵌套 HF cache snapshots 路径探测；模块导入即设 TRANSFORMERS_OFFLINE/HF_HUB_OFFLINE 防联网探测
- **设备自动选择**：`torch.cuda.is_available()` → `use_fp16=True, devices=["cuda"]`（fp16 约 2~3GB 显存）；无 NVIDIA GPU / CPU 版 torch 自动回退 `use_fp16=False`。FlagEmbedding 1.3 为首次 encode 时懒搬运权重（加载后参数仍在 CPU，首次 encode 后才上 GPU）——RTX 5050 实测（2026-10-07 spike）：3 段×3636 字 encode 5.99s（CPU fp32）→ 0.73s（CUDA fp16），约 8 倍；docling 的 layout/TableFormer 走其默认 `device='auto'` 随 CUDA torch 自动上 GPU，RapidOCR 为 ONNX Runtime CPU 版不受影响
- **BgeM3EmbeddingFunction**：ChromaDB 自定义 embedding 函数，委托单例——保证 add_documents 时不触发 ChromaDB 默认模型下载。入库 encode 显式 `batch_size=8, max_length=1024`（2026-10-09 崩溃根因修复：FlagEmbedding 默认 batch_size=256 会把整文件 chunks 一炮全进 GPU forward，8GB 显存爆掉 → 库内 OOM 降级循环反复满载重试 → 驱动 TDR → 后端进程假死；8×1024 单批峰值 ~250MB，与 chunker max_tokens=1024 对齐零截断损失）。查询编码另走 knowledge_search（max_length=512, batch_size=1，§6.4）。**fp16 NaN 入库消毒**（2026-10-14/15 事故）：fp16 CUDA 推理对个别输入会溢出产生非有限值，裸入库即永久毒化（该 chunk cosine 距离对任何查询恒 NaN，响应序列化 500）——encode 结果逐行检查，非有限行替换为单位基向量 e0 占位（cosine 可计算）+ warning 留痕提示重入库，该 chunk 仍可经 FTS 腿命中
- `search_dense`：query（1024 维）→ cosine 距离 → `_score = 1/(1+distance)`；**出口 NaN 守卫**（纵深防御）：非有限距离跳过 + warning——兜存量库遗留毒化向量，绝不让 NaN 进入响应序列化（回归：test_knowledge_nan_guard.py）
- 删除：delete_project（整集合）/ delete_by_file_id（where file_id）/ delete_by_ids
- `get_metadata_by_ids`：为 FTS-only 结果回填 metadata（§6.4）

### 6.2 FTSStore（关键词路，双路按语种分流）

unicode61 tokenizer 会把连续中文合并为单一 token，FTS5 MATCH 对中文词永远不命中（仅整句可中）。因此 `search()` 先分流：

| 路径 | 触发 | 实现 | 排序 |
|---|---|---|---|
| **CJK LIKE 路** | 任一 token 含 CJK | 每 token 切 bigram（≤2 字符原样），token 内 OR（LIKE 子串）、token 间 AND；通配符转义 | Python 侧重算命中数（兼容 RRF 只消费排名） |
| **拉丁 MATCH 路** | 全拉丁/数字 | token 去引号后包裹双引号转 phrase，空格连接（隐式 AND） | FTS5 bm25() 取绝对值 |

两路共用过滤子句：project_id = ? [AND content_type = ?] [AND chunk_id LIKE chunk_{file_id}_% OR img_{file_id}_%]（file_id 范围过滤靠 chunk_id 命名约定）。

### 6.3 HybridRetriever（RRF 融合）

```
score(d) = dense_weight/(rrf_k + rank_dense(d)) + fts_weight/(rrf_k + rank_fts(d))
默认 dense_weight=0.7, fts_weight=0.3, rrf_k=60；两路各取 top_k×2，融合后取 top_k
```

- **FTS 路失败降级**：FTS 异常（坏查询/索引问题）仅 warning 并置空结果——dense 路是主语义信号，不能被 FTS 500 拖垮
- **dense 路失败降级**（镜像）：query embedding 非有限（fp16 溢出）时 `KnowledgeSearchTool._embed_query` 返回 None → 检索降级 FTS-only——两腿任一失败不拖垮检索
- **metadata 回填**：融合结果中无 markdown_content 的（FTS-only 命中）从 ChromaDB get_metadata_by_ids 补齐（不覆盖已有字段）
- 每条结果携带 _score/_dense_score/_fts_score/_rank_dense/_rank_fts 便于前端与调试展示

### 6.4 KnowledgeSearchTool（统一入口）

组合三件套（VectorStore + FTSStore + HybridRetriever）提供 `search()`：query embedding 与融合检索均经 `asyncio.to_thread` 执行（bge-m3 推理与 Chroma/FTS 查询是 CPU 密集，直接跑会冻住事件循环）。查询编码复用 VectorStore 的单例模型（encode max_length=512）。

调用方：

| 调用方 | 场景 |
|---|---|
| `POST /knowledge/search`（本项目检索框） | top_k 等参数直传 |
| KnowledgeRAG（§7 项目问答） | top_k=5 |
| 报告引擎 knowledge 通道（2.5 §检索层） | 按项目 + 关联基础库分别检索 |
| TaskKnowledgeSearchTool（1.1 §3，Agent 工具） | general 模式 10 工具之一 |

`list_projects()`（kind='project' 聚合文档/块数）供 Agent 工具枚举可用项目。

## 7. RAG 问答（rag.KnowledgeRAG）

`POST /knowledge/projects/{id}/chat` 是知识库自己的问答引擎（与任务 Agent 完全独立，无多轮会话状态，单轮 Q&A）：

```
ask(project_id, message, file_id?, settings)
  ① KnowledgeSearchTool.search(top_k=5)
  ② [file_id 作用域] 对结果按 metadata.file_id 内存过滤
  ③ Wiki 骨架：search_wiki(top_k×2, enable_graph=True) → context_budget 截断
  ④ 无任何命中 → 固定文案「未找到相关内容…」+ 空 sources
  ⑤ 上下文组装（Wiki 页在前，标注「结构化参考」；片段逐条带来源/章节）
  ⑥ LLMClient.chat（模型经 rag_model 路由选档，llm/routing.py 档位制，空按标准档解析、标准/高配槽互为回退；系统提示：保留 Markdown 表格、注明来源、不足则如实说明）
  → {answer, sources[]}
```

sources 每条含 filename/page/section_path/content_type/score；Wiki 页面的 filename 为 `Wiki: {标题}`、content_type=wiki_page。图片块的 content_type=figure，其 markdown_content 即 LLM 图片描述。

**作用域交互**（前端 ProjectChatPanel，2.1 §5）：资料面板选中文件时 onFileSelect 上抛 → Chat 标题显示文件名、检索限定单文件；取消选中回全库。

**准入**：chat 端点双依赖校验 `ensure_ready("knowledge_search")` + `ensure_ready("task")`（embedding 与 LLM 缺一不可）；对应前端入口 guard。

## 8. 图片管线（llm/vision）

**架构决策（2026-10-21）**：独立 VLM 配置链路（settings 三键 + vlm_client.py 专属 HTTP 层 + thinking 参数端点特判）整体删除，图片理解统一走 LLM 链路——`python/llm/vision.py` 纯逻辑模块，HTTP 全部经 `LLMClient.chat_full`（standard 档，`resolve_model` 解析、两槽互为回退）。技术前提：LLMClient 的 messages 为 OpenAI 兼容透传（天然承载 image_url content 数组）；reasoning 兼容由既有机制承担（`reasoning_override`/`reasoning_effort` + HTTP 400 一次性回退 + GLM-5 null content 回退 reasoning_content）；max_tokens 走 budget floor 32K，思考型模型 reasoning 挤占输出预算的空正文缺陷整体消失。**前提契约：设置 > 外部模型 的标准/高配模型必须为多模态（支持图片输入）**，设置页 hint 注明；本模块对空正文/调用失败统一附加多模态引导（`_MULTIMODAL_HINT`）。存量数据零迁移：`images.vlm_description` 列名保留（仅数据来源改 LLM）；settings 三键经启动迁移幂等清理（已删即跳过）；历史 usage 行 source='vlm' 保留渲染，新数据走 LLMClient 出口收口（source=knowledge）。

两个入口：

- **通用问答（analyze_image，vision 工具消费）**：自然语言描述或按 question 作答，纯文本返回不做分类约束；`finish_reason=length` 且有正文 → 尾部追加显式截断标记（禁止静默缺尾）；零正文 + length → `LLMCallFailed`（禁止「空描述+截断标记」冒充成功，2026-10-21 vision 空描述缺陷修复）。消费方为 agent 的 `vision` 工具（tools/vision.py，chat/任务中解析图片与 PDF/DOCX/PPTX 内部图片，见 [0.0 §5.4](0.0architecture.md)）
- **Prompt 双任务（describe_image，知识库图片库专用）**：① 从 12 个固定类别选一（chart/photo/diagram/table/formula/logo/invoice/certificate/qr_code/signature/seal/other；invoice/certificate 为内容类进插图池，不自动归档）② 中文详细描述；附图片上下文（context_text）供参考；空正文 → `LLMCallFailed`（worker 既有容错标 error，替代静默空描述标 done）

共用机制：

- **messages 构造**：text + image_url content 数组；data URL 按扩展名映射真实 MIME（`_MIME_BY_EXT`，严格端点兼容；未知后缀兜底 image/png）
- **响应解析容错**（describe）：剥离 markdown 代码图栏 → JSON 解析 {category, description}；非法 category 归 other；整体非 JSON 时全文作 description、category=other
- **错误**：HTTP/网络错误全走 LLM* 错误族（LLMNotConfigured/LLMInvalidKey/LLMRateLimited/LLMNetworkError/LLMCallFailed，client 层统一映射）；LLMCallFailed 的 detail 统一附加多模态引导
- **usage**：chat_full 出口收口（2.10 §4.2），worker 以 `UsageContext(source="knowledge", purpose="describe")` 归属

图片策略汇总（与 §5.3 worker 配合）：

| 策略 | 规则 | 用户可见效果 |
|---|---|---|
| 小图自动归档 | 宽高均 <100px | archived，可手动强制解析（force） |
| 无用类自动归档 | qr_code / signature | archived，描述保留 |
| 手动分类修正 | 前端图片库改 category | PUT category 端点 |
| 手动归档 | 前端归档按钮 | archive 端点 |
| 手动删除 | 前端删除按钮（红色确认钮） | deleteImage 端点：ChromaDB 向量（delete_by_image_id）+ 磁盘文件 + DB 记录一并清除，刷新 file.image_status |
| 重试 | 单图 force / 整文件失败批量 | 重新入图片描述队列 |

## 9. 模型管理（model_manager）

### 9.1 模型注册表

### 9.2 完整性校验与进度

- **校验**：marker_files 存在（bge-m3: config.json；layout/tableformer: +model.safetensors；rapidocr: ≥3 个 onnx）且目录实际字节数 ≥ min_size_bytes（排除 *.incomplete 半成品）
- **进度**：独立监控线程每 1s 量目录字节数（计入 .incomplete——HF/modelscope 下载中的大文件均以此后缀落盘，排除会导致进度长期 0% 后瞬间跳变）；封顶 99%，成功后置 100%
- **多源尝试**：按 sources 顺序逐个尝试，全败才终态 failed；成功后清理 .cache/.lock

### 9.3 HF 离线窗口（引用计数）

进程级 HF_HUB_OFFLINE=1 防止 transformers 启动时联网探测，但同进程的 snapshot_download 会被同变量拦死。`_hf_online()` 上下文管理器：进入时引用计数 +1 并临时解除离线（同时 patch os.environ 与 huggingface_hub.constants 模块常量——后者在 import 时已固化），退出时计数归零后恢复。并行下载线程安全。

窗口内同时设 HF_HUB_DISABLE_XET=1：hf-mirror 不支持 Xet 传输协议（大文件被导向官方 cas-server.xethub.hf.co 重建，镜像签发 token 对其 401 Unauthorized，tableformer-v2 2026-10-05 两连败根因），禁用后大文件回退普通 HTTP CDN 下载；退出窗口还原为未设置（库默认启用）。

### 9.4 下载状态与 API

下载状态落 model_downloads 表（崩溃检测，0.4 §3.3）；终态经 activity_events 写全局 notifications（Toast + 首页进行中卡片）。routers/models.py 五条路由：

```
GET  /models/status                     # 各模型状态（含 downloading/progress/error）
POST /models/preload                    # 预热 bge-m3（Electron 窗口首屏加载完成后触发，见下）
POST /models/{name}/download            # 启动单模型下载（daemon 线程）
POST /models/download-all               # 一键下载全部缺失模型
GET  /models/libreoffice/status         # LibreOffice 可用性（check_libreoffice）
```

**bge-m3 预热错峰**：原实现在 lifespan 启动即起 daemon 线程加载 CUDA 模型，与渲染层模块装载争抢 CPU/磁盘，拖慢 dev 冷启动首屏（2026-10-13 实测 DCL 84s）；现改由 Electron 主窗口 `did-finish-load` 触发 `POST /models/preload`。端点幂等：预热线程存活 → `PRELOAD_IN_PROGRESS`；模型未下载 → `MODEL_NOT_DOWNLOADED`；否则起线程 → `PRELOAD_STARTED`。首查询不依赖预热——vector_store 单例懒加载（双检锁，§6.1）保证正确性。

模型下载作为长时活动接入活动中心（useActivity('model_download')），详见 [0.4 §3](0.4lifecycle-design.md)。

### 9.5 手动放置与 Office 检测

- 用户可手动将模型文件放入对应目录，管理器按 §9.2 规则检测后即视为已下载（无哈希强校验，体积 + 关键文件存在性双重门槛）
- check_office_converter / check_libreoffice 供解析层（§4.2）与前端设置页共用

### 10.2 上传数据流

```
前端 FileList → 逐文件 readAsDataURL（base64）
  → IPC knowledge:uploadFile / baseLib:uploadFile
  → Electron → POST /knowledge/projects/{id}/upload（JSON body）
  → ensure_ready("file_parsing") + 200MB 前置估算检查（base64 长度×3/4，先拒后解码）
  → _safe_filename 去路径 + to_thread 解码落盘 + MD5
  → find_duplicate_file 同项目去重（命中：删临时目录、返回已有 file_id + duplicate 标记）
  → create_file（pending）+ worker.enqueue_file
  → 返回 {file_id, queued: true}
```

上传是同步快速入队（解析异步），前端逐文件串行上传并在每个完成后刷新列表。无 SSE 进度通道——进度经 files.progress 列 + active-files 轮询 + 全局活动心跳呈现（§11.3）。

**入口与拖拽域（2026-10-25 用户裁决）**：可见入口为文件面板顶部上传区（Upload 图标 + 「点击上传，或拖拽文件到页面任意位置」虚线卡，点击唤起系统选文件）；拖拽响应域为**素材页任意位置**（KnowledgePage 根容器统一接 drop/dragover/dragleave，dragLeave 用 relatedTarget contains 判定防子元素间移动闪烁），拖拽悬停时整页遮罩反馈（accent 虚线框 + 「松开鼠标，上传到当前项目」，pointer-events:none 保证 drop 穿透到根容器）；上传区自身不再挂拖拽态，防冒泡双触发。基础库页复用同一组件，行为一致。

**任务页导入入口**（0.5 E2 已落地，2026-10-19）：任务工作区产出文件可从任务页导入到项目/基础库——用户裁决入口在任务页文件树/预览层（非首页）。前端 `src/features/task/ImportTargetDialog.tsx`（目标选择弹层：项目/基础库 Tab + 单选列表）挂载于 FileTree（选中行内按钮）与 FilePreview（预览 header 按钮）两处，导入走 `importTaskFile` 纯逻辑：`tasks:readFile {b64:true}` 读工作区文件 → 复用既有上传通道 `knowledge:uploadFile` / `baseLib:upload`（file 活动走现有解析队列，零新增 kind）；duplicate 语义透传（目标侧已有同 hash 文件仍返回其 file_id，toast 提示）。[2.11 §6](2.11scheduled-task-design.md) 定时任务自动导入复用此链。

### 10.3 IPC 通道（ipc-handlers.js）

知识库通道约 24 条（knowledge:* 前缀）：listProjects / createProject / getFiles / getActiveFiles / uploadFile / deleteFile / retryFile / retryFailedFiles / recentChunks / search / deleteProject / renameProject / updateProject / getProjectImages / getImages / deleteImage / retryImage / retryFailedImages / updateImageCategory / archiveImage / batchDeleteFiles / batchReprocessFiles / chat / queuePause（队列停止/继续，全局同一端点，基础库共用）。基础库通道（baseLib:*）与之平行，见 2.1 §4。

前端经 `KnowledgeIpcChannels` 类型注入通道名（DEFAULT_KNOWLEDGE_IPC_CHANNELS + 可覆盖）——同一 KnowledgePage 组件在项目资料 Tab 用 knowledge:*，在基础库页用 baseLib:*，两套后端隔离。例外：deleteImage/retryImage/updateImageCategory/archiveImage 在基础库页复用 knowledge 通道——base-lib 的 file 记录 project_id 即 lib_id，向量写入与清理同维度，端点按 image_id 全局定位、链路等价。

### 10.4 打开原文件（IPC file:openOriginal）

知识库文件列表与 Wiki 来源溯源（[2.6 §前端交互](2.6wiki-design.md)）共用一条「用系统默认程序打开原文件」链路。**后端不加端点**——文件落盘路径由既有约定推导（§2.3 `data/files/{project_id}/{file_id}/{filename}`），打开动作是纯 Electron 能力（`shell.openPath`，与报告产物打开同模式）。

**数据流**：

```
前端入口（file_id + filename 均来自已加载的列表/溯源数据）
  → IPC file:openOriginal { projectId, fileId, filename }
  → Electron：getDataDir()（与环境变量/dev/打包三态解析，与 system:openDataDir 共用 helper）
  → 路径拼装 → fs.existsSync 前置校验 → shell.openPath(absPath)
  → 成功 { success: true }；缺失 { success: false, reason: 'not_found' }；系统拒绝 { success: false, reason: 'open_failed', message }
```

**安全约束**（渲染层参数不可信）：filename 一律取 `path.basename`（削平任何路径成分）；projectId/fileId 仅允许 `[A-Za-z0-9_-]`；二者合力将可打开路径锁死在 `{dataDir}/files/` 子树内，不提供任何按任意路径打开的能力。

**入口清单**（3 处，同一 toast 反馈）：① 素材文件行 hover 三点菜单首项「打开原文件」（常驻，parsing/error 状态同样可用——文件上传即落盘，解析失败不影响原文件）；② WikiPageReader「来源文件」面板每行 hover 图标；③ src 来源摘要页预览 header「打开原文件」按钮。

## 12. 差异与下一步优化建议

### 12.1 文档与代码不一致登记（代码待修）

1. **死方法**：KnowledgeSearchTool.get_project_files SELECT 了 files 表不存在的 metadata/updated_at 列——无调用者，一旦被调用必抛 OperationalError；应删除。
2. **RAG 单文件过滤低效**：rag.ask 对 file_id 采用检索后内存过滤（top_k=5 截断后再滤，可能漏结果）；search 本身支持 file_id 参数（下推到 FTS/Chroma where），应直接传入。
3. **tools/knowledge_search.py 整文件死代码**：见 [1.1 §12](1.1task-agent-design-unified.md) 登记。
4. **代码注释历史标记**：knowledge 模块多处残留 L1/L5/M1/H1/H5、E2、v3.6 等阶段编号注释（同 1.1 §12 问题 ③）。

> 原 §12.1-1「图片 chunk ID 规则不一致（同页多图冲突）」已于 2026-10-15 修复（id 尾部加 image_id，构造统一走 vector_store.image_doc_id），从待修登记移除，id 规则见 §2.2/§5.3-5。

### 12.2 设计层面下一步建议

1. **多轮问答**：chat 目前单轮无状态（无对话历史）；若用户需要追问可考虑在内存/DB 维护短会话历史拼入 LLM messages。
2. **重检索实例开销**：每次请求新建 KnowledgeSearchTool/VectorStore/FTSStore（模型单例无碍，但对象与 collection 句柄重复创建）；可在 deps 层共享实例。
3. **FTS 中文分词**：CJK LIKE bigram 是无分词库下的近似方案，长查询性能与召回受限；可评估集成 jieba/SQLite 自定义分词器。
4. **批量重试粒度**：retry-failed / batch-reprocess 为逐文件串行 cleanup + 入队，文件量大时可优化为批量事务。
