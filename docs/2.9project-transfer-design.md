# 项目导出/导入设计（2.9）

> **概述**：本文档定义「项目导出/导入」（project transfer）子系统设计——面向机构内员工交换项目信息的桌面离线链路：导出方把一个项目的全部数据打包为 `.inkproj` 交换包（ZIP），接收方导入为**全新项目**（ID 重生成 + 引用重映射），全程不经任何服务器。作为前置改造，本文同时定义**基础库收敛**——删除「新建基础库」功能，仅保留两个内置预置库，从而让项目与基础库的关联天然可迁移。
>
> 关联文档：项目与基础库模型 [2.1](2.1project-design.md)、知识库管线 [2.2](2.2knowledge-base-design.md)、报告 [2.5](2.5report-design.md)、填表 [2.4](2.4forms-design.md)、Wiki [2.6](2.6wiki-design.md)、事务 [3.0](3.0project-lifecycle-design.md)、活动/轮询 [0.4](0.4lifecycle-design.md)。

## 1. 背景与目标

InkCube 是单机桌面应用，但机构场景中员工之间需要交换项目（工作交接、同事接力、案例共享）。现状没有任何项目级数据进出通道（仅单报告导出 Word、填表产物下载），项目只能在单机内生死。

**设计目标**：

1. 导出：把一个项目打包为单文件交换包，可在文件系统/IM/邮件中传递；
2. 导入：把交换包恢复为接收方的一个**新项目**，状态与导出方一致（知识层可检索、Wiki 可读、报告可看、事务可跟进），**零 API 成本、分钟级完成**；
3. 顺带收敛数据模型：基础库只剩两个预置库，项目-基础库关联按固定 ID 可跨机重放。

**非目标**：不做项目合并/同步（见 §12）、不做基础库导出（预置库无数据本体，见 §3）、不做端到端加密（机构内信任场景，交换包不加密，见 §12）。

## 3. 基础库收敛（前置改造）

### 3.1 收敛维度（已落地 2026-10-16，Task 1/2）

| 维度 | 收敛前 | 落地态（现状） |
|------|------|------|
| 基础库种类 | 预置 2 个 + 自定义（`lib_type='custom'`） | 仅预置 2 个 |
| 创建入口 | 侧边栏 [+ 新建基础库] → `POST /base-libs` | 已移除 |
| 改名/删除 | 自定义库可改名（PATCH）/可删除（DELETE） | 已移除（预置库本就禁改禁删） |
| 报告向导知识源 | 项目库 + 预置库 + 自定义库勾选 | 项目库 + 两个预置库（静态表） |
| `project_base_libs` | 可指向 custom 库 | 仅指向两个预置库 |

### 3.2 存量处理（无迁移）

项目未上线、无存量用户数据（2026-10-16 裁决）：不编写迁移代码，收敛直接落到目标态——

1. §3.3 代码退场落地后，`lib_type='custom'` 的库从此无法再被创建；
2. 开发机本地库若已存在 custom 库行（历史测试数据）：删除本地 `.db` 文件重启，由 `initialize()` 全新建表 + `ensure_preset_base_libs()` 重新 seed；
3. 无启动迁移、无发布说明标注需求。

## 4. 交换包格式（.inkproj）

### 4.1 载体

- 单文件 ZIP，扩展名 `.inkproj`（本质 `application/zip`，接收端同时接受 `.zip` 后缀以容错）；
- ZIP 顶层单一成员 `data/` 目录树（manifest.json 与全部分区、blobs 均在其内，实现现状）；
- 打包原子性：先写临时文件（`target_path + ".tmp"`），完成后 `os.replace` 原子改名到目标路径。

### 4.2 manifest.json（交换包的内存状态结构）

```json
{
  "format_version": 1,
  "app_version": "x.y.z",
  "exported_at": "2026-10-15T12:00:00",
  "embedder": { "model": "bge-m3", "dim": 1024 },
  "project": {
    "name": "...", "description": "...",
    "type": "recruitment | investment | general",
    "stage": "before | during | after | none",
    "company_name": "", "credit_code": "",
    "wiki_purpose": "", "wiki_overview": "",
    "playbook_seeded": 0, "archived_at": null,
    "created_at": "...", "updated_at": "..."
  },
  "counts": {
    "files": 0, "chunks": 0, "images": 0, "wiki_pages": 0,
    "reports": 0, "phase_tasks": 0, "form_fills": 0
  },
  "skipped": { "files_processing": 0, "reports_generating": 0, "forms_processing": 0 }
}
```

### 4.3 data/ 布局

```
data/
├── manifest.json           # §4.2（项目行字段内嵌于 manifest.project，无独立 project.json）
├── files.json              # { files: [...], images: [...] } 表行（附加包内元数据 rel_path）
├── chunks.npz              # 向量矩阵 float32 [N, dim]，行序对齐 chunk_meta 中 has_vector 条目
├── chunks_meta.json        # [{ chunk_id, document, metadata, in_fts, has_vector, old_file_id }]
├── wiki.json               # { pages, versions, sources, reviews, change_log }
│                           #   （wiki_pages / wiki_page_versions /
│                           #     wiki_page_sources / wiki_reviews /
│                           #     wiki_change_log；wiki_source_pages 是摄入态不导）
├── reports.json            # { reports, sections, logs }（reports 附加 content_dir 包内键）
├── affairs.json            # { phase_tasks }
├── forms.json              # { form_fills }
├── blobs/
│   ├── files/              # 原 files/{project_id}/ 整树（原文件 + 抽取图片）
│   ├── reports/{rid}/      # content.md / registry.json / token_usage.json / 导出 docx
│   └── form_fills/{fid}.docx              # 填表产物
```

### 4.4 导出范围与排除项

| 类别 | 来源（表/磁盘） | 导出规则 |
|------|----------------|---------|
| 项目元数据 | `projects`（kind='project'） | 全字段；`pending_compile_count` 不导（导入置 0）；`playbook_seeded` 原值保留 |
| 基础库关联 | `project_base_libs` | **不导出**（D6）：导入端按 project_type 自动关联（同 create_project） |
| 文件 | `files` + `blobs/files/` | 仅终态：`done` / `error`（error 文件可带原文件供接收方重试）；`pending`/`processing` **跳过**并计入 `skipped.files_processing` |
| 图片 | `images` 行 + VLM 描述/category | 行级全量（含 pending/error，接收方可重试）；VLM 描述是 API 成果，必须保留 |
| chunks | Chroma collection `project_{id}` | `collection.get` 全量导出（向量+文本+metadata）；文本 chunk `in_fts=true`，图片描述向量 `in_fts=false`（现状：图片向量仅入 Chroma） |
| Wiki | `wiki_pages`/`wiki_page_versions`/`wiki_page_sources`/`wiki_reviews`/`wiki_change_log` | 行级全量（LLM 编译成果，含版本历史快照）；`wiki_compile_tasks`（运行态）/`wiki_source_pages`（摄入态）不导 |
| 报告 | `reports`/`report_sections`/`report_logs` + `reports/{rid}/` | 仅终态 `done`/`error`；`generating`/`paused` **跳过**并计入 `skipped`（checkpoint 依赖本机运行态，不可迁移） |
| 报告模板 | `templates` | **不导出**（D5）：`reports.template_id` 保留原值悬空容错（无外键），接收方「重新生成」提示模板不可用 |
| 事务 | `phase_tasks` | 行级全量；`task_suggestions` 是临时态不导 |
| 台账 | `ledger_entries` | **不导**——设计上「可随时从 wiki_pages 全量重建」（[3.1](3.1intelligence-design.md) 不变量 1），导入后按需重建 |
| 填表 | `form_fills` + 产物 docx | 实例仅终态（success/failed），进行中跳过并计入 `skipped`；`form_templates` **不导出**（D5）：`template_id` 无外键（[2.4 §5.4 不变量 11](2.4forms-design.md)），悬空实例列表可见（LEFT JOIN）、修订/重填 409/404 有提示 |
| 通知/下载 | `notifications`/`model_downloads` | 不导（本机临时态） |

## 5. 导出流程

### 5.1 端点与活动

- 端点：`POST /knowledge/projects/{id}/export`，body `{ "target_path": "<绝对路径>" }`（Electron 原生对话框选定后传入，**只传路径不传内容**）；
- 校验：防重入（同项目导出进行中 409）；项目存在且 `kind='project'`，否则 404；
- 长时活动：注册 `project_export`（`activities_registry.py`），排队→执行→终态遵循 [0.4 §3.1](0.4lifecycle-design.md) 统一模型；
- 响应：完成后返回统计摘要（counts + skipped）。

### 5.2 执行步骤

1. 读 DB 快照（项目行、files/images、wiki 全家、终态 reports/sections/logs、phase_tasks、终态 form_fills）；
2. Chroma `collection.get`（include embeddings/documents/metadatas）；
3. 写入 `blobs/`（`files/{project_id}/` 整树复制、reports 产物、填表产物）；
4. 组装 manifest（counts/skipped 按实际统计，**数值必须精准**）；
5. ZIP 打包到临时文件 → 原子改名到 `target_path`；
6. 活动终态 + 完成通知。

## 6. 导入流程

### 6.1 端点与活动

- 端点：`POST /knowledge/projects/import`，body `{ "source_path": "<绝对路径>" }`；
- **同步快速校验**（`validate_package`）：zip 结构 / zip-slip / 解压炸弹守卫 / manifest / embedder 兼容，不合法 400 立即返回，不占后台活动；
- 响应：校验通过后**立即返回** `{ "project_id": "<新id>", "activity_id": "<活动id>" }`，导入后台执行（大包解压+落盘需时间）；全局单飞（导入进行中重复请求 409）；
- 长时活动：注册 `project_import`，阶段进度（unpack → validate → blobs → db → fts → vectors → done）映射到 progress/message。

### 6.2 执行步骤

1. **解压**到系统临时目录（`tempfile.mkdtemp(prefix="inkcube-import-")`，用后即清；zip-slip 防护见 §9）；
2. **校验** manifest：已在端点同步快速校验完成（`format_version == 1` 高版本拒绝；`embedder` 与本机 bge-m3 一致 dim=1024，不一致**明确报错**——包由不兼容版本导出，不做静默重解析兜底），导入线程不复检；
3. **ID 重映射**：为 bundle 内所有实体生成新 ID，构建 `old → new` 映射表（规则见 §6.3）；
4. **落盘 blobs**：`files/{new_pid}/`、`reports/{new_rid}/`、`form_fills/{new_fid}.docx`；重写 `images.local_path` 前缀为新目录；
5. **DB 单事务插入**全部行（projects/files/images/reports/sections/logs/wiki 全家/phase_tasks/form_fills）；
6. **基础库关联**：事务提交后按 project_type 自动关联（`get_auto_linked_base_libs(type)` + `link_project_to_base_lib(new_pid, lib, auto=True)`，与 create_project 同款；general 无映射则不关联）；
7. **FTS 重建**：`chunks_meta` 中 `in_fts=true` 条目批量写入（新 chunk_id + 新 project_id）；
8. **Chroma 重建**：`get_or_create_collection(project_{new_pid})` → `add_documents` 预计算向量分批写入（metadata 中 `file_id` 按映射表重写）；
9. 活动终态 + 完成通知（携带新项目名）。

### 6.3 ID 重映射规则

| 实体 | 新 ID 策略 | 内部引用重映射 |
|------|-----------|---------------|
| project | 新 uuid | files.project_id / images→files / reports.project_id / wiki*.project_id / phase_tasks.project_id / form_fills.project_id / chunks FTS project_id / Chroma collection 名 `project_{new}` |
| file | 新 uuid | **chunk_id 再生成**：`chunk_{old_file}_{idx}` → `chunk_{new_file}_{idx}`、`img_{old_file}_*` 同理（与现有 LIKE 清理模式 `chunk_{file_id}_%` 兼容）；chroma metadata.file_id；`wiki_page_sources.file_id`、`wiki_reviews.source_file_id`、`wiki_source_pages` 不导、`wiki_pages.last_compiled_file_id` |
| image | 新 uuid | `images.local_path` 前缀重写 |
| report / section / log | 新 uuid | sections.report_id、logs.report_id；**`reports.template_id` 保留原值**（无外键，悬空容错：接收方「重新生成」提示模板不可用）；**`reports.base_project_ids` 置空**（Review M2：源机知识源勾选是即时决策快照、导入端无重映射源，悬空 id 会让检索腿静默返空并为不存在的 id 创建垃圾空 collection——[2.7 §5.6](2.7baselib-rag-design.md)；接收方恢复/重试按项目库检索） |
| wiki_page / version / source / review / change_log | 新 uuid | wiki_page_versions.wiki_page_id、wiki_page_sources.wiki_page_id、wiki_reviews.affected_page_ids（JSON 内 ID 列表逐个重映射、悬挂剔除）、wiki_change_log.wiki_page_id / trigger_file_id（affected_page_keys 为 page_key 不重映射）；wiki_reviews/wiki_source_pages 的 project_id 随 project 映射 |
| phase_task | 新 uuid | `template_id` **不重映射**（指向全局 playbook 种子，种子随代码版本两机一致；版本错位时悬空仅影响展示回退，见 §12） |
| form_fill | 新 uuid | `template_id` 保留原值（无外键，悬空容错，[2.4 §5.4 不变量 11](2.4forms-design.md)） |
| base_lib 关联 | 不映射 | 导入端按 project_type 自动关联（`get_auto_linked_base_libs` + `auto=True`，与 create_project 同款；`auto_linked` 恒为 1） |

### 6.4 全局资产策略

| 资产 | 策略 |
|------|------|
| 模板（报告 `templates` / 填表 `form_templates`） | **不随包**（D5）：成品（报告章节内容 / 填表值集与产物 docx）已随包固化，配方留在生成方；引用列悬空容错（2.4 §5.4 不变量 11），接收方重填/重生成时有 409/404 提示 |
| 基础库关联 | 导入端按 project_type 自动关联（`get_auto_linked_base_libs` + `auto=True`，与 create_project 同款）；两预置库随应用 seed 必然存在，`auto_linked` 恒为 1 |
| playbook_templates / wiki_schemas | 不随包：类型级种子随应用版本两机一致（§12.3/§12.4） |

### 6.5 失败回滚（补偿性清理）

任一步失败：DB 事务回滚（或已提交则按项目删除链路级联清理）+ 已建 Chroma collection 删除 + 已落位 blobs 目录删除 + temp 清理 + 活动置 failed（错误信息经 message 呈现）。保证「导入失败不留半项目」。

## 8. 前端交互（三要素之一）

### 8.1 消费组件清单

| 组件 | 数据 | 界面呈现 |
|------|------|---------|
| `ProjectSidebar` 项目条目菜单 | IPC `projects:exportProject` | 菜单项「导出」；导出中：条目菜单按钮转 spinner，导出菜单项禁用 |
| `ProjectList`（新建项目按钮旁） | IPC `projects:importProject` | 「导入项目包」按钮；导入中禁用 |
| `useActivity('project_export')` | 心跳 | 导出中：条目 spinner；完成：操作 toast「项目已导出」（skipped>0 附未包含提示）+ 通知「项目《X》导出完成」；失败：toast 错误 |
| `useActivity('project_import')` | 心跳 | 导入中：「导入项目包」按钮禁用 + 文案「导入中 N%」；完成：列表刷新 + 自动选中；失败：toast 错误 |
| `ActivityMonitor` 通知（0.4） | 通知 | 导出/导入完成与失败通知；点击直达该项目 materials Tab（导入失败无 project_id 时不导航） |

### 8.2 状态-界面映射

| 状态 | 用户在哪里看到什么 |
|------|------------------|
| 空闲 | 项目条目菜单「导出」可点；「导入项目包」可点 |
| 导出中 | 侧边栏该项目条目菜单按钮 spinner；导出菜单项禁用；再次点击入口无效（后端 409 幂等防重） |
| 导出完成 | 操作 toast「项目已导出」（N>0 时追加「N 个处理中文件未包含」）+ 通知「项目《X》导出完成」 |
| 导入中 | 开始 toast「导入已开始」；「导入项目包」按钮禁用 + 文案「导入中 N%」；侧边栏暂不显示半成品项目（事务提交后才可见） |
| 导入完成 | 通知「项目《X》导入完成」+ 列表出现新项目并自动选中 |
| 校验拒绝 | toast 明确原因（版本过高 / 嵌入模型不兼容 / 包损坏） |
| 导入失败 | toast 错误 + 日志可查（`data/logs/app.log`）；无残留半项目 |

### 8.3 关键交互规则与不变量

1. **单项目同时只能有一个导出活动**（后端按 project_id 幂等去重，重复请求 409）；
2. **导入不产生任何 LLM/VLM 调用**（纯本地重建），导入耗时只取决于包大小与磁盘；
3. **半成品不可见**：DB 单事务提交前，新项目对列表查询不可见；
4. **导入必为新项目**：不改写任何既有项目数据；模板不随包、基础库关联自动重放（§6.4）；
5. i18n：全部新文案 zh/en 双语，无硬编码。
6. **导入完成仅条件选中**（Review m2/m3）：activity 快照只含 running 态、无终态区分，失败边沿同样触发完成上报——前端刷新列表后仅当新项目确已入库才自动选中；另设 10s（2×心跳周期）兜底收尾，防 <5s 快速导入整段落在两次快照之间导致完成边沿永不触发。

## 9. 安全设计

| 威胁 | 对策 |
|------|------|
| zip-slip（恶意条目路径穿越） | 解压前逐条目校验：解析后的规范路径必须位于目标目录内，否则中止并清理 |
| 反序列化 | manifest/各 json 全部 `json.loads`；**禁止 pickle**；npz 仅含 float32 数值矩阵 |
| 不可信绝对路径 | 包内不存储、不信任任何绝对路径；blobs 布局由包内相对路径 + 导入端重写规则唯一决定 |
| 资源放大 | 解压条目数/总大小上限守卫（超限拒绝），防止解压炸弹 |
| 路径注入 | target_path/source_path 由 Electron 对话框产生，Python 侧仍做存在性与规范路径校验 |

## 11. 关键设计决策

| # | 决策 | 理由 |
|---|------|------|
| 1 | 复制为新项目而非合并 | 员工交换是「给我一份你的项目」，增量合并需 diff/冲突策略，收益不抵复杂度；新项目零冲突、可重复导入 |
| 2 | 向量随包而非重解析 | bge-m3 随应用分发、全装机一致；重解析=小时级+VLM 花钱+描述结果漂移 |
| 3 | 只导终态（文件/报告/填表） | 运行态（checkpoint/进度）依赖本机管线状态，迁移必坏；跳过+计数提示比半迁移诚实 |
| 4 | 模板不随包（2026-10-15 修订） | 成品已固化随包，配方（模板）冗余；前置摘除 `form_fills.template_id` 外键（2.4 §5.4 不变量 11），`reports.template_id` 本无外键——悬空引用查看/下载可用，重填/重生成 409/404 有提示 |
| 5 | embedder 不匹配明确报错而非静默重解析 | 兜底不是解决方案：版本错配是包与应用不兼容，应拒绝并指引升级，静默重解析掩盖问题 |
| 6 | 导入注册统一活动而非同步接口 | 大包解压+落盘超时风险；遵循 0.4 统一模型，前端 useActivity 消费，不新增轮询 |
| 7 | chunk_id 随 file_id 再生成 | 现有清理/重试链路按 `chunk_{file_id}_%` LIKE 匹配，ID 结构是隐式契约，必须保持 |
| 8 | 顺带删除自定义基础库 | 固定 ID 预置库使关联可自动重放，交换包无需携带库本体与关联行；机构场景两库即全部共享知识 |
| 9 | 基础库关联自动重放（2026-10-15 修订） | 不携带源机关联状态：接收方按 project_type 走 `get_auto_linked_base_libs` 自动挂库（同新建项目），包内无需关联行 |

## 12. 已知边界与非目标

1. **不做项目合并/同步**：同项目多副本无法自动去重（v1 明确不支持，重复导入产生并列副本）；
2. **交换包不加密**：机构内信任场景；文件本身即可被接收方读取，加密不改变信任模型；
3. **wiki_schemas 不随包**：类型级共享资产，两机随版本一致；接收方若自改过 schema，外来 `page_key` 页面仍可读可编辑，只是不进入 schema 编译目标（记录为边界，不做处理）；
4. **phase_tasks.template_id 版本错位**：playbook 种子随应用版本演进，两机版本不一致时悬空引用仅影响展示回退（列可空无 FK），不阻断导入；
5. **进行中工作不迁移**：生成中报告、解析中文件、进行中填表一律跳过——交接前请等任务终态（导出摘要会提示）；
6. **Chat 会话不迁移**：会话为内存态（[2.1 §6.3](2.1project-design.md)），本无持久化数据。
