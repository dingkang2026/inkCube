### 1.1 报告 Tab 布局

| 状态 | 显示 | 点击行为 |

- 按模板的 `stage` 字段分组（before/during/after/null）

**知识来源自动匹配逻辑：**
- 项目知识库 → 始终勾选，不可取消
- 项目类型为“招商引资” → 自动勾选“招商基础库”
- 项目类型为“投资分析” → 自动勾选“投资基础库”
- 自定义基础库 → 从后端动态加载，用户手动勾选
- 用户可以手动增减任何非锁定的来源

**互联网检索：报告级总开关 + 章节级选择（两层）：**

大纲区顶部有一个**报告级互联网总开关**，其下每个 `standard` 章节右侧显示 `[☐ 🌐 互联网]` 逐节开关；`post_body` 章节不显示章节开关（不做检索）。

- **总开关 OFF**：本次报告全程仅用项目知识库——所有章节 `internet` 通道关闭，**派生变量解析也强制走 `knowledge`**（无视其 `data_sources` 是否声明 internet）。
- **总开关 ON**：互联网可用，各章节按逐节开关决定是否附加 `internet`；派生变量解析按其 `data_sources` 决定是否联网（§3.1.1）。
- 章节开关仅在总开关 ON 时生效；未勾选的章节只用项目知识库。
- 互联网通道**已落地实现**（Tavily，复用 `tools/web_search`）；能否使用还受**项目级设置**（Tavily key 是否配置）能力 gating——未配置 key 时总开关置灰不可开。

**补充说明：**

用户可输入一段项目级的自由文本指引，生成时追加到模板的 `global_requirements` 中，形成本次报告的有效全局要求：

```
effective_requirements = template.global_requirements + [用户补充说明]
```

注入到每个章节的 User Prompt，影响所有章节的写作方向。

**知识来源 → 后端通道映射：**

| 前端选项 | 后端通道 | 传递方式 |
|----------|----------|----------|
| 项目知识库 | `knowledge` | `project_id`（始终传递） |
| 项目 Wiki（无前端选项，自动启用） | `wiki` | `runner._detect_wiki_available()`：项目存在 compiled / user_edited Wiki 页面时自动追加 |
| 招商/投资/自定义基础库 | `knowledge` | `base_project_ids` 列表 |
| 报告级互联网总开关 | `internet`（总闸） | `internet_enabled: bool`（OFF 时全报告禁 internet，含派生变量解析） |
| 章节互联网开关 | `internet` | `section_internet: {section_id: true}` 映射（仅总开关 ON 时生效） |
| 派生变量 data_sources | `knowledge` / `internet` | 变量解析层按声明的 `data_sources` 取通道，但 `internet` 受报告级总开关 gating（§3.1.1） |

#### 报告生成：后台任务模式

用户点击“开始生成”后，前端调用后端 API 启动后台任务，随即返回看板。完整的状态机与异常恢复见 §3.8.1 ~ §3.8.6。

```
用户点击“开始生成”
        │
        ├─→ 后端启动后台任务（BackgroundTasks）
        │        ├─ status = 'generating'
        │        ├─ 逐章节生成 + 每节 checkpoint
        │        ├─ 进展日志写入 report_logs 表
        │        ├─ 完成后 status = 'done' / 'error'
        │        └─ 程序崩溃 → 重启扫描标记 error，用户手动重试续跑（§3.8.3）
        │
        └─→ 前端返回看板
                 ├─ 轮询刷新 generating 报告进度（3 秒间隔）
                 ├─ 切走 → 停止轮询，后端继续跑
                 ├─ 切回 → 重新轮询，加载最新状态
                 ├─ 点击卡片 → 进入报告详情页
                 └─ 详情页内日志面板 2 秒自动刷新 + 历史回放
```

#### 报告详情页（预览与详情整合）

报告详情页整合了内容查看、来源追溯、进度日志和导出操作。主要能力：

| 区域 | 内容 |
|------|------|
| 顶部工具栏 | 返回列表 + 报告标题 + Word 导出按钮 |
| 正文区 | ReactMarkdown + remarkGfm 渲染，支持标题/表格/代码块/引用/列表等 |
| 生成中状态 | 显示进度百分比 + 旋转图标 |
| 错误状态 | 显示错误信息 |
| 来源面板 | 可折叠，按文档聚合引用片段数 |
| 日志面板 | 可折叠，展示生成进度日志（生成中 2 秒自动刷新） |


### 1.2 报告编辑策略

采用**方案 B：应用内查看 + 导出 Office 精修**。

**产品边界清晰划分：**

| 层级 | 负责方 | 具体能力 |
|------|--------|--------|
| **内容生成（0→1）** | 墨方 | 按模板生成报告、Markdown 渲染查看、导出 Word |
| **格式呈现（1→100）** | Word | 字体样式排版、企业标识 Logo、页眉页脚、表格边框样式、最终审阅批注 |

**应用内提供的能力：**

| 功能 | 说明 |
|------|------|
| Markdown 渲染查看 | ReactMarkdown 格式化渲染，支持表格/代码块/引用等 |
| 来源追溯 | 查看报告引用的文档和片段 |
| 进展日志 | 查看报告生成的详细进度日志 |
| 导出 Word | 最终格式调整交给 Office |

**应用内不提供的编辑能力：**

- 字体/字号/颜色调整
- 段落缩进/行距设置
- 页眉页脚/Logo 插入
- 表格边框/样式美化
- 逐章节重新生成
- **新建报告时调整大纲**（大纲由模板定义，需在模板管理中修改）

这些全部由 Word 处理，用户导出后在 Office 中完成最终排版。

### 1.3 报告生成流程

```
用户选择模板 → 配置知识来源 + 补充说明 → 开始生成
                                        │
                          ┌───────────┤
                          │  后台异步生成                    │
                          │  ├─ 自动检索项目知识库       │
                          │  ├─ 自动检索关联基础库       │
                          │  ├─ 结合 Wiki 结构化知识     │
                          │  └─ 看板轮询进度           │
                          │                           │
                          │  每章节标注来源引用            │
                          └───────────┘
                                        │
                          详情页查看 → 导出 Word
```

**关键设计点：**
- **后台异步生成**：用户点击“开始生成”后返回看板，不阻塞操作
- **多源知识融合**：自动从项目知识库 + 基础库 + Wiki 中提取相关内容
- **来源可追溯**：每个章节标注引用了哪些文档
- **看板轮询**：3 秒间隔刷新 generating 状态报告进度

## 2. 模板系统

### 2.1 模板结构

每个模板由**元信息 + 大纲（outline）**两部分定义。大纲支持**任意层级嵌套**，模板书写自由，执行前由归一化层统一折叠为两级执行大纲。

#### 2.1.1 模板元信息

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `template_id` | string | 唯一标识 | `investment_analysis` |
| `template_name` | string | 模板名称 | 投资分析报告 |
| `version` | string | 版本号 | `1.0` |
| `project_types` | string[] | 适用项目类型（**多选**） | `["investment", "general"]` |
| `stage` | string/null | 所属阶段（**单选**，可为 null） | `before` / `during` / `after` / null |
| `output_format` | string | 默认导出格式 | `docx`（本阶段仅支持 Word；未来 PPT 作为扩展格式） |
| `role_hint` | string | 可选，从 project_types 自动推导 | 生成角色定位，注入 System Prompt |
| `audience` | string | 可选 | 报告场景/汇报对象，影响文风和深度 |
| `report_depth` | enum | `full` | 报告深度：`full`（长文）/ `brief`（精炼），影响 prompt 组装、检索量、校验目标 |
| `global_requirements` | string[] | 全局写作要求（可选） | `["数据须注明统计口径", "禁止编造数据"]` |
| `variables` | object[] | 可选，模板声明的变量（`user` / `derived` 两类），详见 §2.1.7 | 见 §2.1.6 示例 |

> **企业信息注入（隐式变量）**：项目的 `company_name`（企业工商名称，缺失时回退 `project_name`）、`credit_code`、`project_type`、`stage` 构成一组**隐式变量**——运行时自动可用、**无需在 `variables` 中声明**，既注入 System Prompt 的「报告主体」字段，也可在大纲文本中以 `{{company_name}}` 等直接引用。模板只需声明**用户输入变量**与**派生变量**（见 §2.1.7）。

#### 2.1.2 章节定义

每个章节（section）包含以下字段：

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `section_id` | string | 必填 | 章节唯一标识 |
| `title` | string | 必填 | 章节标题 |
| `description` | string | 可选 | 章节内容说明（给人看，用于搜索和预览） |
| `compose_mode` | enum | `standard` | 生成模式：`standard`（先检索再生成）/ `post_body`（基于全文摘要生成） |
| `prompt_hint` | string | 可选 | 内容生成指引（LLM 从中提取检索方向） |
| `optional` | bool | false | 材料不足时是否可跳过 |
| `position` | enum | 按大纲序 | post_body 章节的渲染位置：`front`（文首）/ `end`（文末） |
| `children` | section[] | 可选 | 子章节（支持多级大纲，执行前归一化为两级） |

#### 2.1.3 compose_mode 说明

| 模式 | 执行时机 | 输入 | 适用场景 |
|------|----------|------|----------|
| `standard` | 第一遍，按大纲顺序执行 | 知识库检索结果 + 前文摘要 | 正文主体章节（市场概况、财务分析等） |
| `post_body` | 第二遍，所有 standard 章节完成后 | 全文各节 digest + 关键数据表 | 摘要、投资建议、风险提示、结论等综述性章节 |

- `post_body` 章节**不进行任何知识检索**，仅基于其它章节已生成的内容（digest + 关键数据）进行综合
- `post_body` 章节**不得有子章节**

#### 2.1.4 role_hint / audience / report_depth 说明

**role_hint — 生成角色定位：**

| 项目类型 | 默认 role_hint | 文风倾向 |
|---------|----------------|--------|
| 招商引资 | 招商顾问/产业分析师 | 偏推介、突出优势、数据支撑吸引力 |
| 投资分析 | 投资分析师/尽调顾问 | 偏客观、风险导向、严谨审慎 |
| 通用 | 资深研究分析师 | 中性、专业 |

role_hint 可由用户自定义覆盖（如“法律尽调顾问”“财务分析师”）。

**audience — 报告场景/读者：**

| 示例 audience | 文风影响 |
|--------------|--------|
| “投委会成员，关注核心指标和风险” | 精炼、结论先行、风险突出 |
| “政府招商部门” | 正式、政策导向、数据丰富 |
| “内部研究备忘” | 详细、分析性强、可含推测 |
| “对外客户交付” | 专业、完整、格式严谨 |

audience 注入 System Prompt，指导 LLM 调整深度、用语和结构偏好。

**report_depth — 报告深度（贯穿全流水线的核心参数）：**

| 维度 | `full`（长文） | `brief`（精炼） |
|------|---------|----------|
| 字数范围 | 5000-20000+ | 1000-3000 |
| 章节数 | 8-15 章 | 3-5 章 |
| System Prompt 指令 | “撰写详尽的长篇研究报告” | “撰写精炼的短篇报告，每节 200-500 字” |
| 检索量（knowledge 通道） | top20 + BM25 top20 | top10 + BM25 top10 |
| digest 长度 | 每节 200 字 | 每节 100 字 |
| 校验字数目标 | 基于总字数 / 章节数推算 | 同左，但基数更小 |
| 典型场景 | 尽调报告、行研报告 | 快报、简报、摘要 |

#### 2.1.5 模板分类规则

- `project_types` 多选：一个模板可在多个项目类型下可见
- `stage` 单选：模板归入一个阶段（`before` / `during` / `after` / `null`），`null` 表示通用模板
- "通用"项目类型无阶段概念，所有匹配模板平铺显示

#### 2.1.6 模板 JSON 示例

```json
{
  "template_id": "investment_analysis",
  "template_name": "投资分析报告",
  "version": "1.0",
```

#### 2.1.7 变量模型（v2 补完）

**背景**：v2 初期曾一度移除模板变量、仅靠“企业信息自动注入”覆盖公司名。但报告存在**派生量**与**依赖链**的刚需——例如【企业评估】中，公司名已知，而 `产业领域` 须分析产生，`竞争对手` 依赖 `产业领域`，各对手信息又依赖 `竞争对手` 列表。扁平的 `{{}}` 字符串替换表达不了“派生”与“依赖”，故 v2 补入**结构化变量模型**。

**变量三分类：**

| 类别 | 声明位置 | 取值时机 | 例子 |
|---|---|---|---|
| 隐式·项目上下文 | 不声明，恒可用 | 运行时从项目读取 | `company_name` / `credit_code` / `project_name` / `project_type` / `stage` |
| 用户输入 `source:user` | `variables` | 向导 Step2 用户填写 | `报告期` / `目标区域` / `行业` |
| 派生 `source:derived` | `variables` | 生成前「变量解析层」算出（§3.1.1） | `产业领域` / `竞争对手` |

> **采集时机（决策 A）**：隐式变量在**项目新建引导**时采集（一次、全局复用）；user 变量在**报告生成向导 Step2** 采集（每份报告）——因为 `报告期` 等每份都变、且模板跨项目复用，项目新建时无法预知将来用哪些模板。**预填桥接**：向导中 user 变量若能从项目上下文取到匹配值则预填、允许用户改（当前项目仅存 `company_name`/`credit_code`，故多数 user 变量仍需手填；把 `行业`/`目标区域` 等稳定字段提升为项目级字段属后续可选增强，本阶段不做）。

**变量对象 schema：**

| 字段 | 适用 | 类型 | 说明 |
|---|---|---|---|
| `name` | 全部 | string | 唯一名，正文以 `{{name}}` 引用 |
| `source` | 全部 | enum | `user` / `derived` |
| `label` | 全部 | string | UI 展示名 |
| `required` | user | bool | 是否必填 |
| `placeholder` | user | string? | 输入提示 |
| `depends_on` | derived | string[] | 依赖的变量名（可指向隐式 / user / 其他 derived），构成 DAG |
| `derive_hint` | derived | string | 自然语言解析指令（给 LLM） |
| `data_sources` | derived | enum[] | 检索通道：`["knowledge"]` / `["internet"]` / 两者；**派生变量恒检索，不可为空** |
| `cardinality` | derived | enum | `scalar`（标量字符串）/ `list`（字符串数组，注入正文时顿号连接） |

**命名约定**：隐式项目变量用英文 snake_case（直映 DB 列，如 `company_name`）；user / derived 变量用自由名（预置模板用中文，如 `行业` / `产业领域`）。

**依赖链（DAG）**：`depends_on` 构成有向无环图，解析层按拓扑序求值，无依赖关系的分支可并行；成环则模板校验报错。

**变量消费方式（声明式 `{{}}` 注入，不动态改大纲）**：解析出的变量值（含 `list`）通过模板文本里的 `{{name}}` 占位符注入——注入到哪个节，完全由模板作者把 `{{name}}` 写在该节的 `title` / `description` / `prompt_hint` 里决定，**引擎不写死任何「变量→节」映射，也不会因数据多寡增删大纲节点**；`list` 以顿号连接为字符串注入。大纲 1/2 级结构恒定，三级及更深由归一化折叠为写作要求、交 LLM 在节内自行组织（§3.2）。

**企业评估示例（派生链 + 声明式注入）：**

```jsonc
"variables": [
  { "name": "产业领域", "source": "derived", "label": "产业领域",
    "depends_on": ["company_name"], "data_sources": ["knowledge", "internet"],
    "derive_hint": "根据公司主营业务与检索材料判定所属产业领域，输出一个名词短语", "cardinality": "scalar" },
  { "name": "竞争对手", "source": "derived", "label": "主要竞争对手",
    "depends_on": ["产业领域"], "data_sources": ["knowledge", "internet"],
    "derive_hint": "列出该产业领域 3-6 家主要竞争对手公司名称", "cardinality": "list" }
],
"outline": [
  { "section_id": "ch3", "title": "产业分析",
    "description": "基于 {{产业领域}} 分析产业链、格局与趋势" },
  { "section_id": "ch4", "title": "竞争对手分析",
    "description": "{{company_name}} 在 {{产业领域}} 与主要竞争对手（{{竞争对手}}）的多维度对比",
    "prompt_hint": "逐一分析 {{竞争对手}} 与 {{company_name}} 在 {{产业领域}} 的竞争关系、份额与打法" }
]
```

> 竞对名单（`list`）以顿号连接注入 ch4 文本；该节生成时用注入了具体对手名的 prompt 自行检索各家详情——DAG 只负责「研究出名单这个检索锚点」，大纲结构（ch3/ch4）不因对手数量变化。`internet` 是否真正启用受报告级总开关 gating。

**泛化能力**：同一模型覆盖多类报告——尽调（`company_name → 产业领域 → 竞争对手[list]`）、招商（`目标产业(user) → 龙头企业[list]`）、投后（`报告期(user) → 关键指标[list]`），`list` 变量均以 `{{}}` 注入固定节。新增报告类型只声明变量、在节文本里引用，**引擎不改**。

**降级与鲁棒性**（细则见 §3.1.1 / §3.8）：派生变量解析失败 → 其下游 `depends_on` 变量与消费该变量的节按 §3.8 降级（skip 或“材料不足”模式）；`list` 解析为空 → 注入为空串，消费节按“材料不足”降级。

**边界（不过度设计）**：本模型是“模板声明的、在 knowledge + internet 上的研究 DAG”，**不是运行时自主 agent**（遵循附录 A #31 流水线定位、#6 去 agent）。研究计划的“自适应/泛化”发生在**编写期**——§2.3.2 的 LLM 样例提取顺带产出变量 DAG 草稿，人在编辑器 review 冻结；运行期确定性执行。单变量解析当前为 **one-shot**（一轮检索 + 一次抽值）；resolver 是隔离原语，将来若某变量确需多跳可局部升级而不改 DAG 契约（非本次范围）。

### 2.3.1 自定义模板创建

三种创建入口，统一进入模板编辑器：

| 入口 | 说明 | 初始状态 |
|------|------|----------|
| **上传样例提取** | 上传 Word 样例，LLM 全文分析生成模板草稿 | 草稿（LLM 提取结果） |
| **从预置复制** | 复制一个预置模板为自定义模板 | 预置模板的完整副本 |
| **空白创建** | 从零开始创建新模板 | 空模板（仅基本信息） |

**设计理念：LLM 为主，人工编辑为辅。**

- LLM 负责从样例文档中智能提取结构化模板信息（大纲结构、写作风格等）
- 模板编辑器是**必备能力**，用户可对 LLM 提取结果进行全面审阅和调整
- LLM 提取结果作为草稿，编辑器出成品

### 2.3.2 上传样例 LLM 提取流程

用户上传已有的 Word 样例报告，LLM 全文分析生成模板草稿：

```
用户上传 Word 样例
        │
        ▼
┌─ Step 1: 文档解析 ─────────────────────────────────┐
│ Word: python-docx 读取全文文本 + 标题样式           │
│ 输出: 全文文本 + 标题列表（如有）                   │
└──────────────────────────────────────────────────────┘
        │
        ▼
┌─ Step 2: LLM 全文分析 ───────────────────────────────┐
│ 将全文文本发送给 LLM，要求结构化输出：                   │
│  • 大纲结构（章节标题 + 层级 + 顺序）                   │
│  • 每节写作风格/意图推断 → prompt_hint              │
│  • 每节内容说明 → description                         │
│  • 推断目标读者 → audience                            │
│  • 推断角色定位 → role_hint                           │
│  • 推断全局约束 → global_requirements                 │
│  • 推断 project_type / stage                          │
│  • 推断变量：user 输入项 + derived 依赖链 → variables DAG 草稿 │
│ 输出: 符合 _schema.json 的完整模板 JSON 草稿       │
└──────────────────────────────────────────────────────┘
        │
        ▼
┌─ Step 3: 进入模板编辑器 ────────────────────────────┐
│ 用户审阅 LLM 提取结果，可全面编辑：                   │
│  • 基本信息：名称、角色、受众、项目类型、阶段       │
│  • 大纲编辑：章节树形结构、拖拽排序、增删、层级调整 │
│  • 每节编辑：标题、内容说明、写作指引               │
│  • 全局配置：项目类型、阶段、全局要求               │
│ 编辑完成后保存为自定义模板                             │
└──────────────────────────────────────────────────────┘
        │
        ▼
保存到 DB（templates 表，is_custom=1）
```

**与旧方案的关键区别：**

| 维度 | 旧方案（程序化提取） | 新方案（LLM 驱动） |
|------|------|------|
| 提取范围 | 仅标题样式（Heading 1/2/3） | 全文语义分析 |
| 大纲质量 | 依赖 Word 标题样式是否正确 | LLM 理解内容结构 |
| 语义信息 | 无法提取 | prompt_hint / audience / role_hint 等 |
| 人工编辑 | 仅确认/微调 | 全面编辑（必备能力） |

**关键设计决策：**

| 决策 | 选择 | 理由 |
|------|------|------|
| 提取策略 | LLM 全文分析 | 样例格式千差万别，只有 LLM 能统一处理 |
| 编辑器定位 | 必备能力，非可选 | LLM 提取不完美，用户必须能全面调整 |
| 提取结果定位 | 草稿，不追求完美 | 用户通过编辑器二次调整是必要的 |
| Word 标题样式 | 作为 LLM 的辅助输入 | 有则更好，无则 LLM 独立推断 |

### 2.3.3 模板编辑器

模板编辑器是自定义模板的核心操作界面，**覆盖模板 JSON schema 的全部字段**（见 §2.1.1/§2.1.2 与 `resources/templates/_schema.json`），内嵌于编辑抽屉中。

**四种入口统一进入同一个编辑器（均在编辑抽屉中打开）：**
- 上传样例提取 → 编辑器（预填 LLM 草稿）
- 从预置复制 → 编辑器（预填副本，保存为新自定义模板）
- 空白创建 → 编辑器（空表单）
- 编辑已有自定义模板 → 编辑器（加载现有数据）

```
┌─ 编辑抽屉 ──────────────────────────────────────────────┐
│  编辑模板 / 新建模板      [结构化] [JSON 源码]     [保存模板] × │
```

### 2.3.4 模板 schema 版本化与升级迁移

模板 JSON 采用**显式 schema_version + 迁移注册表**的框架化版本管理，保证未来 schema 升级时存量模板可自动迁移，而非静默失效。

**版本常量与注册表（`python/report_generator/loader.py`）：**
- `CURRENT_SCHEMA_VERSION = 2`（当前版本；`_schema.json` 顶层 `schema_version` 以 `const` 强制等于当前值）
- `MIGRATIONS = {1: _migrate_v1_to_v2, ...}`：链式迁移注册表，未来升级只需追加 `{2: _migrate_v2_to_v3}` 等
- `detect_schema_version(data)`：优先读显式 `schema_version`；缺失时对无版本号的存量模板做**结构探测**（节点用 `id` 而非 `section_id`、存在 v1 专属废弃字段如 `terminology`/`word_count`、`output_format` 非 docx → 判为 v1）。注意 `variables` 在 v1（扁平字符串）与 v2（结构化对象）**均存在**，故**不作为版本判据**，仅靠其结构区分
- `migrate_template(data)`：幂等；已是当前版本原样返回并盖章；未知/更高版本返回 None

**v1 → v2 迁移内容：**
- 节点 `id` → `section_id`（递归）
- 顶层 `variables`（v1 扁平字符串数组，如 `["报告期","行业"]`）→ **转换**为 v2 结构化 user 变量（`{name, source:"user", label:name, required:true}`），保留原名，不再一律删除
- 删除已废弃字段：顶层 `terminology`；节点 `word_count`/`query_hints`/`notes`/`must_cite`/`data_sources`（节点级）/`promote_subhead`
- `output_format` 归一为 `docx`
- 盖章 `schema_version = 2`

**自定义模板升级机制（绝不静默删除用户数据）：**

| 情形 | 处理 |
|------|------|
| 迁移+校验成功 | **原地自动升级**：写回前先备份原文件为 `custom_xxx.json.bak`（仅首次，不覆盖已有备份），再写迁移后 JSON 到磁盘 + 更新 DB 缓存，用户无感 |
| 迁移/校验失败 | **保留文件与 DB 行**，记入 `_custom_problems`；列表以「待升级」徽章展示原因；提供**一键升级/引导修复**通道，删除为最后手段 |
| 文件解析失败 | 同上保留并标记，不删除 |

**升级触发链路（三条，自动为主、手动兜底，任何模板都不会卡死在不可用状态）：**
1. **冷启动单入口加载（无感）**：应用启动时 `main.py lifespan()` 一次性创建进程级 `TemplateLoader` 单例（存于 `deps.template_loader`），执行 `load_preset_templates()`（**内置以文件为准无条件重载、覆盖 DB 缓存**）+ `load_custom_templates()`（逐个 migrate+validate）；可迁移的自定义模板自动回写磁盘+DB 立即恢复可用，失败者记入 `_custom_problems` 并展示徽章。此后所有路由通过 `get_loader()` 复用该单例（`_custom_problems` 得以跨请求保留，徽章生效）。
2. **读取自愈**：`get_template()` 读 DB 缓存后再次迁移，若与缓存不同则回写 DB。
3. **手动一键升级/修复**：点「待升级」行的升级按钮 → `POST /templates/{id}/upgrade`：能修则立即 `save_custom_template` 治愈并刷新列表（徽章消失）；修不了则返回 best-effort `migrated` + `errors`，前端以 JSON 源码页 + 顶部错误条打开编辑器，用户最小改动后保存即治愈。

**写入盖章：** `save_custom_template` / `copy_template` 写入时均 `setdefault(schema_version, CURRENT)`，新数据即当前版本。

**校验单一真相（jsonschema）：** 模板结构校验统一由 `jsonschema.Draft7Validator` 对 `resources/templates/_schema.json` 执行，`_schema.json` 是模板结构的**唯一真相**；不再维护手写校验规则（原 `_validate_template` 手写分支与 `_validate_outline_nodes` 已删除），避免“schema 文件与 Python 校验逻辑”双份真相漂移。

**硬编码迁移职责边界（设计原则）：** schema 演进分两轨，硬编码迁移只服务于罕见的破坏性变更：

| 变更类型 | 升 `schema_version`？ | 写迁移？ | 老模板命运 |
|---|---|---|---|
| **新增可选字段**（optional + `default`） | 否 | **否** | 直接通过校验，读取端 `.get(key, default)` 补默认 |
| **破坏性变更**（重命名/删除/改类型/改必填/改结构） | 是 | 是（一次性，注册进 `MIGRATIONS`） | 能迁移则迁移；迁不动落“引导修复”，永不崩溃/丢数据 |

三条纪律：
1. **schema 只做可选加法演进**：新增字段一律 optional + `default`，不升版本、不写迁移；**永不新增必填字段**。
2. **破坏性变更才升 `schema_version` + 写一次性迁移**，`MIGRATIONS` 注册表是它唯一的落点。
3. **校验（jsonschema）是闸门、引导修复是兜底**：迁移只是“尽力而为的便利”，不要求穷尽所有跨版本路径；即便某版本跳跃没写迁移，模板也会 fall-through 到“待升级 + 引导修复”，不会死胡同。

**读取路径自愈：** `get_template()` 读 DB 缓存后再次迁移；若与缓存不同则回写 DB，保证陈旧缓存一次性自愈。`get_all_templates()` 对无法迁移的缓存行跳过（不影子服务）。

**查看补全：** 查看抽屉的「JSON 源码」输出归一化对象，**所有 schema key 均呈现**（缺失以 null/[]/默认值显示）；概览中 `global_requirements` 等空块也始终显示，不因空而隐藏。

## 3. 报告生成引擎

#### 3.1.1 变量解析层（研究 DAG）

在大纲实例化之前，把模板声明的 `derived` 变量解析成具体值。这是“关键字检索 + LLM 回答”单层逻辑升级为“深度探索”的关键：派生变量的检索 query 不再只来自模板静态文本，而是**来自运行时已解析出的上游变量值**（如 `产业领域 → 竞争对手`）。

**输入**：`template.variables` 中的 derived 变量、隐式项目变量、向导 Step2 的 user 输入。
**输出**：`resolved_variables: {name → scalar | list}`，供实例化（替换 `{{}}`，`list` 顿号连接）使用（在 §3.2 归一化之前）。

**解析算法（确定性、有界）：**

```python
def resolve_variables(template, project, user_inputs, internet_enabled):
    ctx = implicit_project_vars(project) | user_inputs            # 隐式 + user
    dag = build_dag([v for v in template.variables if v.source == "derived"])
    assert_acyclic(dag)                                            # 成环 → TemplateValidationError
    for v in topo_order(dag):                                      # 无依赖分支可并行
        deps = {d: ctx.get(d) for d in v.depends_on}
        if any(d is UNRESOLVED for d in deps.values()):            # 上游失败 → 本变量降级
            ctx[v.name] = UNRESOLVED; continue
        queries = generate_queries(v.derive_hint, deps)            # 复用 search_strategy
        evidence = multi_channel_retrieve(queries, gate(v.data_sources, internet_enabled)) # internet 受报告级总开关 gating（§1.1）
        ctx[v.name] = extract_value(v.derive_hint, deps, evidence, v.cardinality)  # one-shot
        checkpoint_variables(ctx)                                  # 进 checkpoint（§3.8.3），可断点续跑
    return ctx
```

**one-shot resolver**：单个变量 = 一轮检索 + 一次抽值（复用 `search_strategy` / `retrieval` / `card_builder` 取证，`prompts.extract_value` 抽值，与 §3.7 `extract_numbers` 同一套“LLM → 结构化值”机制）。抽值契约：`scalar` 输出一个名词短语字符串；`list` 输出字符串数组。

**解析证据**：用于抽值的知识卡片随 `resolved_variables` 存入 checkpoint（审计/溯源用），**默认不自动进 §3.7 参考文献**——消费该变量的节仍走自身检索与 `[N]` 引用，避免噪声。

**变量注入与联网 gating**（变量解析完成后、归一化前，由 normalizer 的 `instantiate` 执行）：把 `resolved_variables` 的值替换进大纲文本的 `{{name}}` 占位符——`scalar` 直接替换、`list` 以顿号连接为字符串后替换、`UNRESOLVED`(None) 替换为空串。**大纲节点数量恒定，不因 list 长度增删节**（不做 foreach 展开）。派生变量解析阶段的检索通道由变量 `data_sources` 声明，但其中 `internet` 受**报告级互联网总开关** gating：总开关 OFF 时强制降级为仅 `knowledge`（§1.1 Step2）。

**降级与边界**：解析失败的变量标记 `UNRESOLVED`，其下游变量与消费节按 §3.8 降级（skip 或“材料不足”模式）；解析阶段 token 计入 #38 统计；本层是**确定性流水线**（附录 A #31），非运行时 agent——研究计划的自适应发生在编写期（§2.3.2 提取器产出 DAG 草稿、人工 review 冻结）。

### 3.2 归一化层（多级大纲 → 两级执行大纲）

模板大纲支持任意层级嵌套（章 → 节 → 子节…），但执行时统一折叠为**两级**（章 → 节），保持书写自由与执行纪律分离。

**折叠规则（整枝合并，不拆散）：**

| 深层元素 | 归宿 |
|----------|------|
| 节点标题 + 子孙标题 | 二级节点一条 `须覆盖：标题——子孙标题` |
| `prompt_hint` | 合并进 writing_requirements |
| 折叠后 requirements | > 12 条 → 记告警日志（不阻断） |

**折叠算法（递归折叠，支持任意层级）：**

```python
def normalize_outline(raw):
    """将多级大纲折叠为两级执行大纲"""
    out = deepcopy(raw)
    for chapter in out:
        for sec in chapter.get("children", []):
            _flatten_section(sec)     # 递归折叠 sec 的所有后代
    return out

def _flatten_section(sec):
    """就地折叠一个节的所有 children（三级及更深 → 二级）"""
    reqs = sec.setdefault("writing_requirements", [])
    for sub in sec.pop("children", []):
        r = _fold_node(sub)           # 递归折叠整枝为一条要求
        if r not in reqs: reqs.append(r)
    if not reqs:
        reqs.append(f"须覆盖：{sec['title']}")

def _fold_node(node) -> str:
    """递归折叠一个子树为一条写作要求"""
    chain = [node["title"]] + _collect_titles(node.get("children", []))
    r = f"须覆盖：{'——'.join(chain)}"
    if node.get("prompt_hint"): r += f"（{node['prompt_hint']}）"
    return r

def _collect_titles(nodes) -> list[str]:
    """递归收集所有层级的标题（任意深度）"""
    titles = []
    for n in nodes:
        titles.append(n["title"])
        titles.extend(_collect_titles(n.get("children", [])))
    return titles
```

**归一化示例：**

输入（多级大纲）：
```
ch1 市场概况
├── ch1.1 市场规模与增长（prompt_hint="近3-5年数据"）
│   ├── ch1.1.1 历史规模数据
│   └── ch1.1.2 细分市场拆分
└── ch1.2 竞争格局
```

输出（两级执行大纲）：
```json
{
  "section_id": "ch1.1",
  "title": "市场规模与增长",
  "compose_mode": "standard",
  "writing_requirements": [
    "须覆盖：历史规模数据——细分市场拆分（近3-5年数据）"
  ]
}
```

### 3.3 检索层（多通道 + 知识卡片）

每个 `standard` 章节独立执行检索 + 知识卡片构建，分为四个阶段：

**阶段一：LLM 检索策略**

LLM 分析章节上下文（标题 + prompt_hint + writing_requirements），自动生成多组搜索关键词。

| 输入 | 说明 |
|------|------|
| 章节标题 | 当前节的 title |
| prompt_hint | 内容生成指引（LLM 从中提取检索方向） |
| writing_requirements | 写作要求，帮助 LLM 理解需要什么样的材料 |
| 前文 digests | 已完成章节的摘要，避免重复检索 |

| 输出 | 说明 |
|------|------|
| search_queries | 多组搜索关键词，每组针对不同的信息点 |

**阶段二：多通道检索**

根据 `data_sources` 将 search_queries 分发到对应通道——常规章节由「项目知识库（始终可用）+ Wiki 自动启用（项目存在已完成页面时，无用户开关）+ 报告级互联网总开关 + 章节互联网开关（Step 2 勾选）」决定，派生变量由模板声明的 `data_sources` 决定、但其中 `internet` 同受报告级总开关 gating（§3.1.1）：

| 通道 | 检索方式 | 说明 |
|------|---------|------|
| `knowledge` | full: 向量 top20 + BM25 top20 + RRF 融合；brief: 向量 top10 + BM25 top10 + RRF 融合 | 项目知识库（RAG），复用 knowledge/ 模块 |
| `internet` | 互联网搜索引擎 API | 外部互联网信息，需标注来源 URL |
| `wiki` | 项目已完成 Wiki 页面检索（关键词 + 图谱邻居扩展，复用 `wiki_search` 引擎；仅 compiled / user_edited 页面） | ✅ 已接入：`runner` 检测到项目存在已完成页面时自动启用（见 2.6 §8.2） |

每个通道返回原始结果（chunks / 网页内容），统一传递给下一阶段。

**阶段三：LLM 知识卡片构建**

LLM 对所有通道的原始结果进行结构化处理，生成知识卡片：

```json
{
  "card_id": "Cch1_001",
  "section_id": "ch1.1",
  "content": "根据2024年行业报告，市场规模达500亿元，同比增长12%...",
  "source_type": "knowledge",
  "source_title": "2024年行业研究报告",
  "source_from": "industry_report_2024.pdf (p.15)",
  "source_date": "2024-03-15"
}
```

**知识卡片 Schema：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `card_id` | String | 唯一标识，格式 `C{section_id前4字符}_{seq:03d}`，如 `Cch1_001` |
| `section_id` | String | 所属章节 ID |
| `content` | String | 结构化后的内容（提取关键事实，非原文截断） |
| `source_type` | String | 来源类型：`wiki` / `knowledge` / `internet` |
| `source_title` | String | 来源标题（文档名 / 网页标题） |
| `source_from` | String | 来源出处（文件路径+页码 / 网页 URL） |
| `source_date` | String? | 来源日期（internet 有，其他可能为 null） |

**LLM 知识卡片构建的核心职责：**

| 职责 | 说明 |
|------|------|
| 信息提取 | 从原始 chunks 中提取与章节相关的关键事实和数据，去除噪音 |
| 来源归因 | 为每条信息准确标注来源类型、标题、出处 |
| 语义去重 | 不同通道/文档中描述同一事实的卡片合并，保留最权威来源 |
| 交叉验证 | 多通道信息相互印证，矛盾信息标注采信优先级：wiki > knowledge > internet（Wiki 已编译结论最权威） |
| 充足性评估 | 判断收集到的信息是否足够支撑该章节写作 |

**阶段四：充足性评估与降级**

LLM 在构建知识卡片的同时输出充足性评估：

| 评估结果 | 处理 |
|------|------|
| **充足** | 正常进入写作阶段，按写作要求深度分析 |
| **不足** + `optional: true` | 跳过该节，日志记录「内容缺口」 |
| **不足** + `optional: false` | 降级为「分析推理模式」，prompt 注明信息不足，LLM 基于已有材料+专业知识论述，明确标注数据缺口 |

**降级策略（程序化判断）：**

| 场景 | 处理 |
|------|------|
| 所有通道均无结果 | 视同“不足”，走降级 |
| 知识库 RRF 分数全 < 0.01 | 视同材料不足，走降级 |
| 仅 internet 通道有结果 | 标注“仅互联网来源，请谨慎引用” |

### 3.4 全局引用 Registry

所有知识卡片通过全局引用注册器统一管理：

| 属性 | 说明 |
|------|------|
| 去重 key | `(source_type, source_from, content_hash)`，语义去重由 LLM 在卡片构建阶段完成 |
| 编号规则 | 按注册顺序分配全局唯一编号 `[1]` `[2]` ... |
| 持久化 | 随每节 checkpoint 持久化 |
| Prompt 呈现 | `[3] 《2024年报》(knowledge) p.12：「结构化后的卡片内容……」` |

引用编号在 LLM 输出中的格式：紧跟被支撑句末，如 `市场规模达 500 亿元[3][7]`。

> 注：Registry 的注册单元从 raw chunks 升级为知识卡片。每张卡片可能融合了多通道的同一事实，比原始 chunk 信息密度更高、来源更明确。

### 3.5 生成层

**System Prompt（全文共享）：**

```
你是一位{role_hint}，为机构客户撰写正式研究报告。
【报告场景】
本报告面向：{audience}
据此调整：深度、用语、结构偏好
【报告主体】
本报告为：{company_name}
【报告深度】
{depth_instruction}
  — full 时解析为：“撰写详尽的长篇研究报告，每节充分展开，多角度分析，数据详实”
  — brief 时解析为：“撰写精炼的短篇报告，每节 200-500 字，结论先行，言简意赅”
【角色与文风】
- 专业、客观、克制；观点须有证据支撑，不使用夸张修辞
- 书面语，段落 150-300 字；分析性语言优先于描述性语言
- 给出判断时说明依据与不确定性
- 数字规范：千分位、单位统一、不确定数据用区间；数据须注明口径
- 行文用“本报告”“我们认为”
【输出契约】（严格遵守）
1. 不输出本节章节标题，首行直接开始正文
2. 引用标注紧跟被支撑句末，格式 [n]，句内可多个如 [3][7]
3. 只能引用参考资料中列出的编号；无材料支撑的具体数据禁止出现
4. 列表仅用于并列枚举，连续不超过 5 项；论证性内容必须成段
5. 末尾不写总结套话，不以“综上所述”“总而言之”收尾
6. 直接输出正文，不要任何前言说明
```

**standard 章节 User Prompt 结构：**

```
【全局上下文】
报告题目：{title}
本节位置：第 {section_id} 节（隶属 {chapter_title}）
前文各节摘要（供衔接，勿重复）：{completed digests，full: 每节 200 字 / brief: 每节 100 字}

【本节写作任务】
写作要求：{prompt_hint + effective_requirements}

【信息充足性】
{sufficiency_assessment}
— 充足时：正常写作
— 不足时：「本节检索材料有限，侧重分析推理，禁止虚构具体数据与引用」

【知识卡片】（带全局编号的结构化卡片）
{knowledge_cards}
每张卡片格式：
  [n] {card_id} | 来源: {source_type} - {source_title}
      {content}
```

**post_body 章节 User Prompt 结构：**

```
【全文摘要视图】
{各章 digest 全量，按章节顺序}

【全文关键数据表】
{extract_numbers 抽取的指标/数值}

【本节写作任务】
写作要求：{prompt_hint + effective_requirements}
附加要求：不得简单重复正文内容，须基于以上各节内容给出跨章节的综合判断
```

### 3.6 校验层

**单节校验（每节生成后立即执行）：**

| # | 规则 | 违规处理 |
|---|------|----------|
| 1 | 引用编号 ⊆ 本节给定编号集 | 重试（反馈违规清单） |
| 2 | 出现 markdown 标题 `^#{1,6}` 或加粗 `**` | 重试 |
| 3 | 字数偏差 > ±20%（仅 `full` 深度的 standard 节启用，目标 1200 字/节；v2 模板已删除 `word_count`，目标由 `report_depth` 推算。`brief` 深度不启用——§3.5 指示 brief 每节 200-500 字，与固定目标冲突会触发无谓重试；`post_body` 节天然短小，亦不启用） | 重试 |
| 4 | ◆ 小标题超过 15 字（v2 已删除 `promote_subhead`，不再检查小标题数量） | 重试或告警 |
| 5 | 结尾"综上所述""总而言之"套话 | 重试或程序截尾 |
| 6 | （v2 已移除）原 `must_cite` 章节强制引用校验——模板 schema 已删除 `must_cite` 字段；编号保留空位以对齐代码 `SectionViolation.rule` | — |
| 7 | 首行不是正文（输出了标题/前言） | 重试 |
| 8 | 3 次重试仍不合规（由 runner 重试循环判定，非 `validate_section` 规则） | 降级接受 + 记录违规日志 |

**全局校验（所有章节完成后）：**

| 规则 | 处理 |
|------|------|
| 幻觉引用（cited - defined 非空） | 定位删除或标记人工复核 |
| 未被引用（defined - cited） | 从 registry 删除，编号重排 |
| 编号连续性检查 | 回填需用提取重建而非字符串替换 |

### 3.7 全局收尾流水线

```
① 引用全局校验 → ② 未引用清理 + 重排 → ③ 一致性检查
（前后数字矛盾检测 / 章节间重复检测）
→ ④ 衔接润色（规则驱动：清除悬空过渡词、节首重复标题、连续空行压缩）
→ ⑤ 目录生成（标题树来自模板） → ⑥ 渲染
```

**一致性检查细节：**

| 检查项 | 方法 |
|--------|------|
| 数字矛盾 | 正则提取数字+单位（亿元/万元/%等），取前后各 15 字上下文，将数字替换为 `{N}` 后作为指标指纹，同一指纹出现不同数值时日志告警 |
| 章节间重复 | 相邻章节段落级 bigram Jaccard 相似度检测（阈值 0.6），超过时日志告警 |

**数据提取 `extract_numbers`：**

从已生成的 standard 章节中提取关键数据点（指标 / 数值 / 来源编号），形成结构化数据表，作为 post_body 章节的输入之一。

实现方式：LLM 调用，输入为所有 standard 章节正文拼接（截取前 8000 字），输出格式为 `- 指标名称: 数值（来源引用编号）`。调用失败时返回空字符串，post_body 章节仅基于 digest 写作。

**渲染规则：**

| 元素 | 来源 | 渲染 |
|------|------|------|
| 一级/二级标题 | 模板 outline | 目标格式样式（docx 样式 / markdown ##/###） |
| 内部小标题 | 模型输出 `◆ xxx` | 统一转换为下一级标题样式（三层分离） |
| 引用 `[n]` | 原样保留或转上标 | markdown/docx 均由程序处理 |
| 尾注列表 | registry | 按编号序；同文档相邻 chunk 可合并为页码范围条目 |
| 章节排序 | post_body 按 `position`（front/end）插入 | 渲染时拼接 |

> 注：本阶段渲染目标格式为 Word（docx），PPT 未来扩展。

### 3.8 异常处理与生命周期管理

#### 3.8.1 报告状态机

```
               用户点击“开始生成”
                      │
                      ▼
              ┌──── generating ────┐
              │                    │
              │  每节 checkpoint   │
              │                    │
         全部完成         程序崩溃/异常/生成失败
              │                    │
              ▼                    ▼
            done                 error
                                   │
                         重启后扫描 generating
                         → 标记 error（程序异常中断）
                                   │
                         用户在详情页点 [重新生成]
                         → 从 checkpoint 续跑 → done
```

| 状态 | 含义 | 看板显示 |
|------|------|----------|
| `generating` | 生成中 | ⏳ 60% |
| `done` | 已完成 | ✅ 完成日期 |
| `error` | 失败 / 程序中断（保留 checkpoint，可重试续跑） | ❌ 失败 |

> **状态命名**：统一用 `error`（与代码、前端一致），不再使用设计早期的 `failed` / `interrupted` / `cancelled`。**不提供取消生成**：生成中的报告无法主动中止；程序异常中断由启动扫描标记 `error`，用户靠 [重新生成] 从 checkpoint 续跑。

#### 3.8.2 LLM 调用级重试

LLM 调用失败时，根据失败类型采取不同策略，而非统一重试：

| 失败类型 | 识别方式 | 重试策略 |
|----------|----------|----------|
| 内容安全过滤 | API 返回 content_filter / safety 错误 | 不重试，直接降级，日志记录 |
| JSON 解析错误 | LLM 输出非合法 JSON（工具调用场景） | 重试，附加提示「上次输出格式错误，请严格输出合法 JSON」 |
| 上下文溢出 | token 超限错误 | 截断 user_prompt 到 4000 字后重试（一次机会） |
| 模型超时/限流 | 超时 / 429 状态码 | 指数退避重试 3 次，仍失败则记录待完成节 |
| 文本规则违规 | 校验层检测的格式违规 | 重试，反馈具体违规清单（现有逻辑） |
| 空输出 | LLM 返回空字符串 | 重试，附加提示「上次未输出内容，请完整输出」 |

#### 3.8.3 程序崩溃与恢复

**核心机制：每节 checkpoint + 启动时扫描标记 + 用户手动重试续跑。**

**Checkpoint 内容（每节完成后持久化到 DB）：**

| 数据 | 说明 |
|------|------|
| `outputs` | 已完成章节的正文内容 |
| `digests` | 已完成章节的摘要 |
| `registry` | 全局引用注册表（已累积的卡片） |
| `order` | 已完成章节 ID 序列 |
| `token_usage` | 累计 Token 消耗 |
| `current_section` | 当前正在处理的章节 ID |
| `updated_at` | 最后更新时间戳 |

**启动时恢复流程：**

```
应用启动（main.py lifespan）
  │
  ├─→ 扫描 DB: SELECT * FROM reports WHERE status = 'generating'
  │
  ├─→ 对每个 generating 报告：
  │     ├─ 检查 updated_at（最后 checkpoint 时间）
  │     │    ├─ 距今 > 5 分钟 → 判定程序异常中断
  │     │    │    ├─ 标记 status = error，原因「程序异常中断，请重新生成」
  │     │    │    ├─ 保留 checkpoint（outputs/digests/registry/order）不删除
  │     │    │    └─ 日志追加「检测到中断报告，已标记失败，可重试续跑」
  │     │    └─ 距今 ≤ 5 分钟 → 暂不处理（可能仍在其它进程运行，下次启动或超时后再判）
  │
  └─→ 用户在详情页点 [重新生成]（retry）
        ├─ 有 checkpoint → 加载已完成章节、跳过、从下一节续跑
        └─ 无 checkpoint（归一化前就崩） → 从头重新生成

  注：启动时不自动拉起后台续跑（避免启动期并发与不确定性），一律标记 error 等用户手动重试。

> 崩溃中断的报告由 `main.py` 启动扫描**补发失败通知**（写全局 notifications 表 → ActivityMonitor 弹 Toast，0.4 §4.1）；运行期终态通知由 `database.py::update_report_status` 内聚写入（含未读查重）。
```

**重试续跑边界（用户点 [重新生成] 时）：**

| 中断时机 | 续跑策略 |
|----------|----------|
| 章节间中断（刚完成一节） | 从下一节续跑，已生成内容完整保留 |
| 章节内中断（LLM 调用中崩溃） | 当前章节从头重做，之前章节保留 |
| 归一化阶段中断 | 无 checkpoint，从头重新生成 |
| 收尾流水线中断 | 已生成内容保留，重新执行收尾（校验+润色+渲染） |

#### 3.8.4 前端导航与状态反馈

**场景一：生成中切走（用户点击其它菜单）**

```
用户切走
  │
  ├─→ 后端：任务继续运行，日志持续写入 DB
  ├─→ 前端：停止轮询（组件卸载），不清理定时器引用
  └─→ 侧边栏“报告”Tab 显示徽章：`1`（生成中报告数）
```

**场景二：切回来**

```
用户切回报告 Tab
  │
  ├─→ GET /reports?project_id=xxx  → 获取最新状态
  ├─→ 重新建立轮询（3 秒间隔）
  ├─→ 看板卡片显示当前进度（基于 DB status）
  └─→ 点击卡片进入详情 → 日志面板加载全部历史日志 + 继续实时刷新
```

**场景三：程序异常关闭后重启**

```
程序重启
  │
  ├─→ 后端启动扫描：中断的 generating 报告 → 标记 error（§3.8.3）
  ├─→ 前端加载看板 → 这些报告显示 ❌「生成失败」
  └─→ 用户进入详情 → 日志回放历史 + [重新生成] 按钮 → 从 checkpoint 续跑
```

**状态检测与反馈汇总：**

| 场景 | 后端状态 | 看板卡片 | 详情页 |
|------|----------|----------|--------|
| 正常生成中 | `generating` | ⏳ 60% | 进度条 + 实时日志 |
| 切走中（后端仍在跑） | `generating` | ⏳ 60%（切回后刷新） | — |
| 切回 | `generating` | ⏳ 75%（最新） | 历史日志 + 实时追加 |
| 程序崩溃重启 | `generating` → `error`（启动扫描标记） | ❌ 失败 | 错误原因 + [重新生成]（从 checkpoint 续跑） |
| 生成失败 | `error` | ❌ 失败 | 错误原因 + [重新生成] 按钮 |

#### 3.8.5 日志持久化与回放

**日志存储：**

每条日志写入 `report_logs` 表，包含：

| 字段 | 说明 |
|------|------|
| `report_id` | 所属报告 |
| `section_id` | 相关章节（可为 null） |
| `level` | `info` / `warn` / `error` |
| `message` | 日志内容（如「第 3 章：检索完成，获取 12 条知识卡片」） |
| `created_at` | 时间戳 |

**回放机制：**

用户进入详情页时加载最近日志并轮询刷新（全量重取最近 N 条、前端按 `created_at` 去重追加，**不做 `?after=` 增量**——单报告日志量有限，全量重取足够且实现简单）：

```
进入详情页
  │
  ├─→ GET /reports/{id}/logs?limit=N  → 加载最近 N 条历史日志
  ├─→ 日志面板按时间序渲染
  └─→ 每 2 秒轮询 GET /reports/{id}/logs?limit=N
        └─→ 前端按 created_at 去重，追加新日志到面板底部
```

**日志内容示例：**

```
10:00:01  [INFO] 开始生成报告「招商推介方案」
10:00:02  [INFO] 归一化完成：8 章 → 两级执行大纲
10:00:03  [INFO] 第 1 章 项目概况：开始检索...
10:00:08  [INFO] 第 1 章：检索完成，获取 8 条知识卡片
10:00:15  [INFO] 第 1 章：生成完成（1,203 字）
10:00:16  [INFO] 第 2 章 企业核心优势：开始检索...
10:00:22  [WARN] 第 2 章：材料不足，降级为分析推理模式
10:00:30  [INFO] 第 2 章：生成完成（980 字）
...
```

#### 3.8.6 消息通知（Activity Hub，已实施）

终态通知写全局 `notifications` 表（`update_report_status` 内聚，含未读查重），前端 ActivityMonitor 单一常驻轮询分发——用户切走页面或离开报告 Tab 仍能收到提醒（[0.4 §6](0.4lifecycle-design.md)）：

| 事件 | 通知方式 | 内容 |
|------|----------|------|
| 生成完成 | 全局 Toast（点击直达报告）+ 看板卡片更新 + 首页「最近动态」 | 「《招商推介方案》生成完成」 |
| 生成失败 | 全局 Toast + 看板卡片标记 | 「《招商推介方案》生成失败：{原因}」 |
| 部分完成（有 optional 章节跳过） | Toast 通知 | 「生成完成，2 节因材料不足已跳过」 |
| 启动扫描到中断报告 | main.py 补发失败通知（全局 Toast）+ 日志面板追加 | 「检测到中断报告，已标记失败，可重新生成续跑」 |
| 进行中指示 | 项目报告 Tab 角标 + 首页「进行中」卡片（进度百分比） | 生成中报告数 / 进度 |

> 生成入口另接入就绪度校验：后端 `ensure_ready("report")`（LLM/embedding 缺失时结构化报错），前端 ReportWizard 发送前 useFeatureGuard 引导弹层（0.4 §10.3）。

#### 3.8.7 工程保障

| 场景 | 处理 |
|------|------|
| 上下文溢出 | 前文 digest 窗口控制（最近 3 节 + 全局一页纸摘要）；知识卡片数量限制 |
| 模板不合规 | 入口 Schema 校验失败直接拒绝，不进入流水线 |
| Token 统计 | 每次 LLM 调用记录 token 消耗（prompt_tokens/completion_tokens），报告完成时汇总写入 DB |

### 3.9 执行主流程（伪代码）

```python
def run_report(template, project, kb, registry, user_inputs, internet_enabled):
    # ── 阶段零：变量解析（研究 DAG，见 §3.1.1）──
    resolved = resolve_variables(template, project, user_inputs, internet_enabled)  # derived → 值（internet 受报告级总开关 gating）
    outline = instantiate(template, resolved)    # 替换 {{}}：隐式 / user / derived（list 顿号连接）
    outline = normalize_outline(outline)         # 归一化（§3.2）
    validate_execution_outline(outline)
    outputs, digests, order = {}, {}, []
    token_usage = TokenTracker()                          # Token 统计追踪

    # ── 第一遍：standard 章节（大纲顺序串行）──
    for sec in sections_of(outline):
        if sec.compose_mode != "standard": continue

        # 阶段一：LLM 检索策略
        search_queries = llm_generate_queries(sec, digests)    # 基于 prompt_hint + 上下文生成多组 query

        # 阶段二：多通道检索
        raw_results = multi_channel_retrieve(
            search_queries, data_sources=sec_internet_sources(sec, project, internet_enabled),
            kb=kb)

        # 阶段三：LLM 知识卡片构建 + 充足性评估
        cards, sufficiency = llm_build_knowledge_cards(
            raw_results, sec, registry)
        refs = [registry.get_or_add(**c) for c in cards]

        # 阶段四：生成 + 智能重试（最多 3 次）
        for attempt in range(3):
            try:
                output, tokens = llm(
                    SYSTEM_PROMPT,
                    build_prompt(sec, refs, digests, sufficiency))
                token_usage.record(tokens)
                violations = validate_section(output, refs, sec)
                if not violations: break
            except ContentFilterError:
                output = FALLBACK_TEXT; break             # 内容安全过滤，不重试
            except TokenLimitError:
                truncated = truncate_prompt(build_prompt(sec, refs, digests, sufficiency), 4000)
                output, tokens = llm(SYSTEM_PROMPT, truncated)  # 截断上下文后重试（一次机会）
        else:
            pass                                          # 3 次重试仍有违规，降级接受

        outputs[sec.section_id] = output
        digest_len = 200 if report_depth == "full" else 100
        digests[sec.section_id] = summarize(output, digest_len)
        order.append(sec.section_id)
        save_checkpoint(outputs, digests, registry, order, token_usage)

    # ── 第二遍：post_body 章节 ──
    for sec in [s for s in outline if s.compose_mode == "post_body"]:
        output, tokens = llm(SYSTEM_PROMPT, build_post_body_prompt(
            sec, digests, extract_numbers(outputs)))
        token_usage.record(tokens)
        outputs[sec.section_id] = output

    # ── 全局收尾 ──
    report = finalize(outputs, outline, registry)
    save_token_usage(token_usage)                        # Token 统计写入 DB
    return report
```

### 3.10 设计决策一览

| 决策 | 理由 |
|------|------|
| 两遍执行（standard 先，post_body 后） | 摘要/结论类章节须基于全文综合，不能独立检索生成 |
| 模板多级自由书写，执行严格两级 | 书写自由与执行纪律分离 |
| 深层内容整枝折叠为“须覆盖”要求 | 保持结构语义，粒度受控 |
| 标题三层分离（模板/模型 ◆/程序） | 换渲染格式不改生成逻辑 |
| post_body 输入 = digest + 数据清单 | 省上下文 + 逼综合 |
| 引用 key=(source_type, source_from, content_hash) 全局注册 | 尾注全局唯一、语义去重、可溯源 |
| 通道间并行 + 通道内多 query 并行 | 通道间 asyncio.gather 并行，通道内 Semaphore 控制并发数，显著缩短检索时间 |
| post_body 禁新检索、只综合已有内容 | 摘要论据必须来自正文已生成内容，保证一致性 |
| System Prompt 与内容解耦 | 全文文风一致 |
| 入口校验 + 出口严格校验 + 3 次重试 | 质量兜底 |
| 每节 checkpoint + 启动时自动恢复 | 长报告生成可中断恢复，崩溃不丢进度 |
| 日志持久化 + 回放 | 切走/切回/崩溃重启均可追溯完整生成过程 |
| 知识卡片中间层 | 多通道异构数据统一为结构化卡片，写作 Agent 输入质量可控 |
| LLM 驱动检索策略 | 自动生成搜索关键词，比固定 prompt_hint 更灵活、更贴合章节需求 |
| 信息充足性评估 | 检索后评估材料充足性，LLM 自适应调整写作策略，避免虚构数据 |
| 智能重试分类 | 区分内容安全/溢出/解析/空输出等失败模式，针对性处理，避免无效重试 |
| Token 统计追踪 | 每次 LLM 调用记录消耗，报告级汇总，为成本控制和优化提供数据支撑 |
| report_depth 贯穿全流水线 | 同一模板可出长文/精炼两档报告，prompt、检索量、校验目标均随 depth 调整 |
| 变量解析＝声明式研究 DAG（非运行时 agent） | 跨报告类型泛化靠“声明变量”、引擎不变；确定性/可复现/可审计/成本有界，契合 #31 流水线、#6 去 agent |
| 研究计划的自适应放在编写期 | §2.3.2 提取器 LLM 产出 DAG 草稿、人工 review 冻结，兼得 agent 的规划泛化与执行的确定性 |
| 单变量 one-shot resolver | 一轮检索 + 一次抽值，复用既有 search_strategy/retrieval/extract_numbers；多跳留作隔离原语的局部升级（非本次范围） |
| 派生变量恒检索 + 变量级 data_sources | 派生值须有证据支撑；通道由 data_sources 声明，internet 受报告级总开关 gating |
| DAG 只产锚点值、大纲静态不动态展开 | 变量以 {{}} 注入固定节（list 顿号连接），1/2 级结构恒定、深层交 LLM 组织，避免数据驱动改骨架（已移除 foreach） |

### 3.11 模块结构与架构定位

**架构定位：独立模块**（非 Tool、非 Skill）

报告生成引擎是独立模块 `python/report_generator/`，与 `python/knowledge/` 同级。理由：

| 特征 | Tool/Skill | 报告引擎 |
|------|-----------|---------|
| 调用模式 | 单次调用，输入→输出 | 多步流水线，长时间运行 |
| 状态管理 | 无状态 | 有状态（Registry、checkpoint、digest 累积） |
| 运行时长 | 秒级 | 分钟级（5-20 分钟） |
| 中断恢复 | 不支持 | 每节 checkpoint，断点续跑 |
| API 暴露 | Agent 内部调用 | 独立 REST 路由 + 轮询进度 |

**与现有模块的关系：**

```
report_generator（独立模块）
    ├── 复用 → knowledge/hybrid_retriever（知识库检索通道）
    ├── 复用 → knowledge/vector_store + fts_store（底层存储）
    ├── 复用 → llm/client（LLM 调用 + Token 统计）
    ├── 复用 → tools/web_search（互联网检索通道，任务系统内置工具）
    ├── 复用 → db/database（持久化）
    └── 独立 → 自己的流水线逻辑、状态管理、API 路由
```
