## 1. 背景与目标 

### 1.1 现状问题

墨方当前导航有 5 个入口，其中"知识库"和"报告"在概念上割裂：

- **知识库**：上传文档 → 向量化 → RAG 检索/问答（已实现）
- **报告**：预留入口，尚未实现（导航中已禁用）
- 两者的目标用户和工作流高度重叠，却分属不同入口

### 1.2 设计目标

将"知识库"和"报告"合并为**"项目"**——面向招商经理和投资经理的统一工作空间。

**核心价值主张：**

> 一个项目 = 一套完整的工作闭环：收集资料 → 知识编译 → 生成报告/填表

**项目核心定位：**

> **报告生成引擎是墨方的核心功能，重中之重。**
>
> 不同于市面上的通用智能体，墨方通过“模板定义 + 知识库检索 + 专业生成流水线”的组合，实现大模型在招商/投资垂直行业的深度落地。通用智能体只能给出“一次性回答”，墨方能产出**专业级、可交付、引用可溯源**的行业报告——这是从“AI 聊天”到“AI 生产力工具”的本质跨越。

### 1.3 目标用户

| 角色 | 核心工作 | 典型产出物 |
|------|---------|-----------|
| **招商经理** | 招商引资、企业引进、园区推介 | 招商推介方案、项目评估报告、招商跟踪表 |
| **投资经理** | 投资分析、项目分析、投后管理 | 尽职调查报告、投资分析报告、尽调清单 |

## 2. 信息架构

### 2.1 导航结构

**变更前 → 变更后：**

```
变更前:                          变更后:
┌──────────┐                    ┌──────────┐
│ 🏠 首页   │                    │ 🏠 首页   │
│ 💬 产业洞察 │ ──┐               │ 🛠 任务    │ ← 通用 Agent（主推通用模式）
│ 📚 知识库   │   ├→              │ 📂 项目    │ ← 合并
│ 🛠 任务    │   │               └──────────┘
│ 📊 报告(禁) │ ──┘
└──────────┘
```

- 导航项从 5 个（含 1 个禁用）精简为 **3 个**
- “产业洞察”有意撤掉，其通用 Agent 能力由“任务”承接
- 快捷键映射：Ctrl+1 首页, Ctrl+2 任务, Ctrl+3 项目

### 2.2 “任务”定位说明

“任务”是通用 Agent 入口，**主推通用模式**，同时包含编程模式。内置互联网工具，可独立完成各类任务。

**任务能做什么：**

| 能力 | 说明 |
|------|------|
| 产业问询 | 联网搜索，了解行业动态、政策信息 |
| 企业调研 | 查询企业基本情况、工商信息、融资历史 |
| 简单报告 | 生成轻量级的分析、总结、报告 |
| 通用问答 | 任何不属于具体项目的问答 |
| 编程模式 | 代码编写、数据处理等技术任务 |

**“任务”与“项目”的关系：**

| 维度 | 任务 | 项目 |
|------|------|------|
| 定位 | 轻量、即时、通用 | 重量、持续、专业 |
| 知识来源 | 互联网 + 通用能力 | 项目知识库 + Wiki + 基础库 |
| 产出物 | 一次性结果（对话、简单报告） | 结构化产出（报告、填表、Wiki） |
| 生命周期 | 用完即走 | 长期跟踪，分阶段管理 |
| 衔接 | 暂不考虑两者间的功能衔接 | — |

**Agent 能力不消失，而是下沉到项目内部：**

```
项目内部每个 Tab 都有 Agent 参与:
├── 📁 资料 — Agent 负责文档解析、RAG 检索
├── 📖 Wiki — Agent 负责知识编译、增量更新
├── 📊 报告 — Agent 负责按模板生成内容
├── 📋 填表 — Agent 负责数据提取和填充
└── 💬 Chat — Agent 负责项目级问答
```

**产品边界划分：**
- **墨方负责内容生成**（从 0 到 1）：生成报告内容、编译 Wiki、填充数据
- **Office 负责格式呈现**（从 1 到 100）：字体排版、企业标识、最终审阅

### 2.3 项目分类体系

项目分为三大类：**普通项目**、**预置基础库**和**自定义基础库**。

```
侧边栏:
┌──────────┐
│ 🏠 首页    │
│ 🛠 任务    │
│           │
│ ─ 项目 ── │
│ 📁 XX科技   │  ← 普通项目
│ 📁 YY生物   │
│ 📁 ZZ新能源  │
│           │
│ ─ 基础库 ─ │
│ 📚 招商基础库 │  ← 预置（招商引资类项目自动关联）
│ 📚 投资基础库 │  ← 预置（投资分析类项目自动关联）
│ 📚 我的资料库 │  ← 用户自定义基础库
│    [+ 新建]  │
│           │
│ ──────── │
│ 👤 Kelvin │
│    📊  ⚙  │
└──────────┘
```

- **普通项目**：完整四 Tab 工作空间（资料 → Wiki → 报告 → 填表）
- **预置基础库**：系统内置，按角色分为招商基础库 / 投资基础库，简化版两 Tab（资料 + Wiki）
- **自定义基础库**：用户自行创建的基础库，自定义名称，同样两 Tab 结构
- 基础库被普通项目引用，报告生成时自动注入为上下文

## 3. 项目类型

### 3.1 类型定义

创建项目时选择类型，类型决定默认预设（模板可见性、Wiki 编译规则、填表模板）：

| 项目类型 | 适用角色 | 默认报告模板 | 默认 Wiki 结构 |
|---------|---------|------------|---------------|
| 🏭 **招商引资** | 招商经理 | 招商推介方案、项目评估报告、落地跟踪报告 | 招商政策、目标企业画像、园区概况、产业链、竞品园区对比 |
| 💰 **投资分析** | 投资经理 | 尽职调查报告、投资分析报告、投后管理报告 | 公司概况、团队、财务健康度、法律风险、估值参考、风险清单 |
| 📁 **通用** | 不限 | 全部模板可见 | 由 LLM 根据文档自动推断 |

### 3.2 类型的影响范围

项目类型**不改变**四 Tab 的基本结构，但影响：

| 影响维度 | 说明 |
|---------|------|
| 默认可见报告模板 | 按 project_type + stage 过滤，不同角色看到不同的推荐模板 |
| 默认 Wiki 结构 | LLM Wiki 编译时遵循不同的 Schema |
| 默认可见填表模板 | 不同角色看到不同的推荐表格 |
| 生成角色（role_hint） | 项目类型决定报告生成的默认角色定位和文风立场 |

**关键原则：**
- 项目类型只是默认预设，不是限制——任何项目类型下都可以访问所有模板
- 用户可以随时在模板管理中启用/禁用特定模板
- 项目类型创建后不可更改（建议用户新建项目）

### 3.3 项目阶段（生命周期）

项目不是一次性工作，而是贯穿业务周期的持续管理。每个项目类型对应一套阶段定义：

| 项目类型 | 阶段 |
|---------|------|
| 🏭 招商引资 | 招商前 → 招商中 → 招商后 |
| 💰 投资分析 | 投前 → 投中 → 投后 |
| 📁 通用 | 不分阶段（所有模板平铺显示） |

模板的 `stage` 字段可为 `null`，表示不属于任何特定阶段。在向导和报告列表中，`stage = null` 的模板/报告统一归入第四列显示。

**各阶段典型产出物：**

| 阶段 | 招商引资 | 投资分析 |
|------|---------|----------|
| **前期** | 产业研究报告、目标企业筛选、园区推介材料 | 行业研究报告、企业调研报告、项目初筛表 |
| **中期** | 招商推介方案、项目评估报告、政策申报表 | 尽职调查报告、估值对比表、投资决策表 |
| **后期** | 落地跟踪报告、政策兑现跟踪表、企业经营跟踪表 | 投后管理报告、财务监控表、重大事项跟踪表 |

**阶段管理规则：**
- 用户**手动推进**阶段（“进入下一阶段”按钮），不是流程引擎
- 报告/填表按当前阶段分组显示
- 后期是**长周期**，会持续产出多份报告/填表（如季度投后管理报告）
- 阶段可以回退（如从“投中”退回“投前”补充材料）

### 3.4 项目企业信息

项目创建时可选填企业工商名称和统一社会信用代码，用于报告生成时自动注入企业信息（如报告封面、变量替换等）。

| 字段 | DB 列名 | 类型 | 必填 | 说明 |
|------|---------|------|:----:|------|
| 企业工商名称 | `company_name` | TEXT | 否 | 企业全称，如"XX科技有限公司" |
| 统一社会信用代码 | `credit_code` | TEXT | 否 | 18 位统一社会信用代码 |

**设计要点：**
- 两个字段均为可选，创建项目时收集
- 所有项目类型均可填写（不限于招商/投资）
- 创建后可在项目详情头部查看，后续支持编辑
- 报告生成时可通过模板变量 `{{company_name}}` / `{{credit_code}}` 自动注入

### 4.2 各 Tab 职责

| Tab | 职责 | 对应现有功能 |
|-----|------|------------|
| **📁 资料** | 上传/管理原始文档，查看解析状态，RAG 检索，图片库 | = 现有知识库页面 |
| **📖 Wiki** | 浏览 LLM 编译的结构化知识页面，互相链接，可编辑 | 🆕 新增 |

## 5. 项目 Wiki（LLM Wiki）

> 详细设计见 [2.6wiki-design.md](2.6wiki-design.md)，本节为架构概要。

### 5.1 功能定位

引入 **LLM Wiki 范式**（Raw→Wiki→Schema 三层架构），作为现有 RAG 知识库的上层建筑——将原始文档编译为结构化、互相链接的 Wiki 页面，实现知识沉淀与复利效应。

| 维度 | RAG（现有） | LLM Wiki（新增） |
|------|-----------|------------------|
| 知识形态 | 向量切片（机器检索） | 结构化页面（人+AI 可读） |
| 核心价值 | 精准召回 | 知识沉淀、一致性输出 |
| 人类可读性 | 低（碎片化切片） | 高（完整 Wiki 页面） |
| 知识积累 | 无积累（每次重新拼凑） | 持续编译，产生复利 |

### 5.2 架构：项目 Wiki + 基础库 RAG 直达

采用务实的简化架构（详见 [2.6wiki-design.md §1.3](2.6wiki-design.md)）：

- **项目 Wiki**（实施）：将碎片化项目文档编译为结构化结论
- **基础库 RAG 直达**（已实现）：基础库文件通过 RAG 直接检索注入，不做额外 Wiki 编译
- **基础库 Wiki**（可选延后）：如果未来基础库文件量大到 RAG 质量下降，再考虑增加

```
基础库（RAG 直达，无需 Wiki 编译）
├── 招商基础库 RAG：政策、园区、产业
├── 投资基础库 RAG：估值、法规、行业
└── 自定义基础库 RAG
        │  编译/报告时 RAG 检索注入
        ↓
项目 Wiki（编译为结构化结论，直接服务 Chat 和报告）
├── 招商引资项目：企业画像、政策匹配、园区配套、产业链分析、落地方案
├── 投资分析项目：公司概况、团队、财务健康度、法律风险、估值、风险清单
└── 通用项目：LLM 自动推断
```

### 5.3 核心能力

| 能力 | 说明 |
|------|------|
| 知识编译 | 文档解析完成后，LLM 按 Schema 将原始资料编译为结构化 Wiki 页面（两阶段 ingest）。采用“通知 + 人工触发”模式，用户决定何时编译 |
| 按类型编译 | 不同项目类型对应不同的 Wiki Schema（页面结构） |
| 基础库注入 | 编译时自动检索关联基础库 RAG chunks 注入 Prompt |
| 增量更新 | 新文档摄入后通知用户有新素材，用户手动触发增量编译，仅更新受影响的 Wiki 页面 |
| 来源追溯 | 每个 Wiki 页面标注来自哪些原始文档 |
| 冲突处理 | 不同来源信息冲突时保留各方说法，标注来源和时间 |
| 页面编辑 | 用户可手动编辑 Wiki 内容，编辑后不被自动编译覆盖 |
| 健康检查 | Lint 机制保障 Wiki 质量（结构层 + 语义层） |

### 5.4 与 Chat / 报告生成的集成

Chat 问答和报告生成共用同一套知识优先级：
1. **项目 Wiki 页面**（最高 — 已编译的结构化知识）
2. 项目 RAG chunks（补充 Wiki 未覆盖的细节）
3. 关联基础库 RAG chunks（共享知识补充）

Wiki 页面作为“骨架”上下文，RAG chunks 作为“细节”补充。详见 [2.6wiki-design.md §8](2.6wiki-design.md)。

### 5.5 前置依赖

Wiki 功能依赖**基础库 RAG 先实现**（基础库 CRUD、文件上传解析、向量索引、项目-基础库关联）。基础库 RAG 基础设施已完成（见 §2.3 / §4.3 / 附录 A #1）。

### 6.2 报告编辑策略

采用**方案 B：应用内轻量编辑 + 导出 Office 精修**。

**产品边界清晰划分：**

| 层级 | 负责方 | 具体能力 |
|------|--------|--------|
| **内容生成（0→1）** | 墨方 | 按模板生成报告、逐章节重新生成、Markdown 级文字修改、调整大纲 |
| **格式呈现（1→100）** | Word/PDF | 字体样式排版、企业标识 Logo、页眉页脚、表格边框样式、最终审阅批注 |

**应用内提供的编辑能力：**

| 功能 | 说明 |
|------|------|
| Markdown 预览 + 编辑 | 修改文字内容，满足内容级修改需求 |
| 逐章节重新生成 | 对某一章节不满意，单独重新生成 |
| 调整大纲 | 增删、重排章节顺序 |
| 补充说明后重新生成 | "这段加上XX角度再写一遍" |
| 导出 Word/PDF | 最终格式调整交给 Office |

**应用内不提供的编辑能力：**

- 字体/字号/颜色调整
- 段落缩进/行距设置
- 页眉页脚/Logo 插入
- 表格边框/样式美化

这些全部由 Word/PDF 处理，用户导出后在 Office 中完成最终排版。

### 6.4 模板结构

每个模板由**元信息 + 大纲（outline）**两部分定义。大纲支持**任意层级嵌套**，模板书写自由，执行前由归一化层统一折叠为两级执行大纲。

#### 6.4.1 模板元信息

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `template_id` | string | 唯一标识 | `investment_analysis` |
| `template_name` | string | 模板名称 | 投资分析报告 |
| `version` | string | 版本号 | `1.0` |
| `project_types` | string[] | 适用项目类型（**多选**） | `["investment", "general"]` |
| `stage` | string/null | 所属阶段（**单选**，可为 null） | `before` / `during` / `after` / null |
| `output_format` | string | 默认导出格式 | `Word` / `PDF`（本阶段仅支持 Word/PDF；未来 PPT 作为 Word 内容的下游渲染，非独立生成管线） |
| `role_hint` | string | 可选，从 project_types 自动推导 | 生成角色定位，注入 System Prompt |
| `audience` | string | 可选 | 报告场景/汇报对象，影响文风和深度 |
| `report_depth` | enum | `full` | 报告深度：`full`（长文）/ `brief`（概文/简报） |
| `terminology` | object[] | 术语规范（可选） | `{"canonical": "ROI", "aliases": ["投资回报率", "收益率"]}` |
| `variables` | string[] | 模板变量声明（可选） | `["公司名", "行业", "报告日期"]` |
| `global_requirements` | string[] | 全局写作要求（可选） | `["数据须注明统计口径", "禁止编造数据"]` |

#### 6.4.2 章节定义

每个章节（section）包含以下字段：

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `section_id` | string | 必填 | 章节唯一标识 |
| `title` | string | 必填 | 章节标题 |
| `description` | string | 可选 | 章节内容说明（给人看，用于搜索和预览） |
| `compose_mode` | enum | `standard` | 生成模式：`standard`（先检索再生成）/ `post_body`（基于全文摘要生成） |
| `word_count` | int | 1200 | 目标字数 |
| `prompt_hint` | string | 可选 | 内容生成指引 |
| `notes` | string[] | 可选 | 附加写作注意事项（折叠进 writing_requirements） |
| `promote_subhead` | bool | false | 是否要求模型使用 `◆` 内部小标题 |
| `query_hints` | string[] | 可选 | 检索关键词提示（替代原 knowledge_hints） |
| `must_cite` | bool | false | 是否必须有引用支撑 |
| `optional` | bool | false | 材料不足时是否可跳过 |
| `position` | enum | 按大纲序 | post_body 章节的渲染位置：`front`（文首）/ `end`（文末） |
| `children` | section[] | 可选 | 子章节（支持多级大纲，执行前归一化为两级） |

#### 6.4.3 compose_mode 说明

| 模式 | 执行时机 | 输入 | 适用场景 |
|------|----------|------|----------|
| `standard` | 第一遍，按大纲顺序执行 | 知识库检索结果 + 前文摘要 | 正文主体章节（市场概况、财务分析等） |
| `post_body` | 第二遍，所有 standard 章节完成后 | 全文各节 digest + 关键数据表 + 已有引用列表 | 摘要、投资建议、风险提示、结论等综述性章节 |

- `post_body` 章节**不进行新知识检索**，仅复用 standard 阶段已注册的引用
- `post_body` 章节**不得有子章节**

#### 6.4.4 role_hint / audience / report_depth 说明

**role_hint — 生成角色定位：**

| 项目类型 | 默认 role_hint | 文风倾向 |
|---------|----------------|--------|
| 招商引资 | 招商顾问/产业分析师 | 偏推介、突出优势、数据支撑吸引力 |
| 投资分析 | 投资分析师/尽调顾问 | 偏客观、风险导向、严谨审慎 |
| 通用 | 资深研究分析师 | 中性、专业 |

role_hint 可由用户自定义覆盖（如“法律尽调顾问”“财务分析师”）。

**audience — 报告场景/读者：**

| 示例 audience | 文风影响 |
|--------------|--------|
| “投委会成员，关注核心指标和风险” | 精炼、结论先行、风险突出 |
| “政府招商部门” | 正式、政策导向、数据丰富 |
| “内部研究备忘” | 详细、分析性强、可含推测 |
| “对外客户交付” | 专业、完整、格式严谨 |

audience 注入 System Prompt，指导 LLM 调整深度、用语和结构偏好。

**report_depth — 报告深度：**

| 模式 | 字数范围 | 章节数 | 检索深度 | 典型场景 |
|------|---------|--------|---------|--------|
| `full`（长文） | 5000-20000+ | 8-15 章 | 完整流水线（多轮检索+rerank+校验） | 尽调报告、行研报告 |
| `brief`（概文） | 1000-3000 | 3-5 章 | 简化版（轻量检索、减少校验） | 快报、简报、摘要 |

#### 6.4.5 模板分类规则

- `project_types` 多选：一个模板可在多个项目类型下可见
- `stage` 单选：模板归入一个阶段（`before` / `during` / `after` / `null`），`null` 表示通用模板
- "通用"项目类型无阶段概念，所有匹配模板平铺显示

**模板操作规则：**
- 预置模板**不可修改**，但可以“复制”为自定义模板后编辑
- 自定义模板支持：编辑名称、阶段、章节结构、每章节的内容说明（description）和生成指引（prompt_hint）、适用项目类型、术语规范、模板变量、全局要求、检索关键词

#### 6.6.1 自定义模板创建

三种创建入口，统一进入模板编辑器：

| 入口 | 说明 | 初始状态 |
|------|------|----------|
| **上传样例提取** | 上传 Word/PDF 样例，LLM 全文分析生成模板草稿 | 草稿（LLM 提取结果） |
| **从预置复制** | 复制一个预置模板为自定义模板 | 预置模板的完整副本 |
| **空白创建** | 从零开始创建新模板 | 空模板（仅基本信息） |

**设计理念：LLM 为主，人工编辑为辅。**

- LLM 负责从样例文档中智能提取结构化模板信息（大纲、写作风格、术语等）
- 模板编辑器是**必备能力**，用户可对 LLM 提取结果进行全面审阅和调整
- LLM 提取结果作为草稿，编辑器出成品

#### 6.6.2 上传样例 LLM 提取流程

用户上传已有的 Word/PDF 样例报告，LLM 全文分析生成模板草稿：

```
用户上传 Word/PDF 样例
        │
        ▼
┌─ Step 1: 文档解析 ─────────────────────────────────┐
│ Word: python-docx 读取全文文本 + 标题样式           │
│ PDF: PyMuPDF 提取全文文本 + 字体信息               │
│ 输出: 全文文本 + 标题列表（如有）                   │
└──────────────────────────────────────────────────────┘
        │
        ▼
┌─ Step 2: LLM 全文分析 ───────────────────────────────┐
│ 将全文文本发送给 LLM，要求结构化输出：                   │
│  • 大纲结构（章节标题 + 层级 + 顺序）                   │
│  • 每节写作风格/意图推断 → prompt_hint              │
│  • 每节目标字数估算 → word_count                      │
│  • 每节内容说明 → description                         │
│  • 推断目标读者 → audience                            │
│  • 推断角色定位 → role_hint                           │
│  • 提取术语/缩写 → terminology                        │
│  • 识别可替换字段 → variables                         │
│  • 推断全局约束 → global_requirements                 │
│  • 推断 project_type / stage                          │
│ 输出: 符合 _schema.json 的完整模板 JSON 草稿       │
└──────────────────────────────────────────────────────┘
        │
        ▼
┌─ Step 3: 进入模板编辑器 ────────────────────────────┐
│ 用户审阅 LLM 提取结果，可全面编辑：                   │
│  • 基本信息：名称、角色、受众、项目类型、阶段       │
│  • 大纲编辑：章节树形结构、拖拽排序、增删、层级调整 │
│  • 每节编辑：标题、写作指导、字数、检索关键词       │
│  • 全局配置：术语规范、全局要求、模板变量           │
│ 编辑完成后保存为自定义模板                             │
└──────────────────────────────────────────────────────┘
        │
        ▼
保存到 DB（templates 表，is_custom=1）
```

**与旧方案的关键区别：**

| 维度 | 旧方案（程序化提取） | 新方案（LLM 驱动） |
|------|------|------|
| 提取范围 | 仅标题样式（Heading 1/2/3） | 全文语义分析 |
| 大纲质量 | 依赖 Word 标题样式是否正确 | LLM 理解内容结构 |
| 语义信息 | 无法提取 | prompt_hint / audience / role_hint / terminology 等 |
| PDF 支持 | 字体大小启发式（不可靠） | LLM 统一处理（可靠） |
| 人工编辑 | 仅确认/微调 | 全面编辑（必备能力） |

**关键设计决策：**

| 决策 | 选择 | 理由 |
|------|------|------|
| 提取策略 | LLM 全文分析 | 样例格式千差万别，只有 LLM 能统一处理 |
| 编辑器定位 | 必备能力，非可选 | LLM 提取不完美，用户必须能全面调整 |
| 提取结果定位 | 草稿，不追求完美 | 用户通过编辑器二次调整是必要的 |
| Word 标题样式 | 作为 LLM 的辅助输入 | 有则更好，无则 LLM 独立推断 |

### 6.7 报告生成引擎

报告生成采用**两遍执行 + 全局收尾**的流水线架构，确保长文质量与引用可溯源。

#### 6.7.1 数据流全景

```
模板 ─实例化→ 多级大纲 ─归一化→ 两级执行大纲 ─校验→
   │                                            │
   │                                    ┌────┴────────┐
   │                              standard 节       post_body 节（延迟）
   │                                    │                │
   │                            ┌───┴────────────┐
   │                            │ LLM 检索策略      │  ← 基于 query_hints + 章节上下文
   │                            │ 自动生成搜索关键词  │     生成多组搜索 query
   │                            └───┬────────────┘
   │                                    │
   │                            ┌───┴────────────┐
   │                            │ 多通道检索        │  ← 按 data_sources 配置
   │                            │ 知识库/互联网       │     分发到各通道
   │                            └───┬────────────┘
   │                                    │
   │                            ┌───┴────────────┐
   │                            │ LLM 知识卡片构建 │  ← 结构化、来源归因、语义去重
   │                            │ + 充足性评估     │     判断材料是否充足
   │                            └───┬────────────┘
   │                                    │
   │                            知识卡片 ─全局注册→ 带编号卡片   │
   │                                    │                │
   │                              生成 + 单节校验       │
   │                                    │                │
   │                       digest + checkpoint ─BODY_DONE─→
   │                                             │
   │                                     digest 视图 + 数据清单
   │                                     生成 post_body 章节
   └─────────────────────────────────────────────┘
                           ↓
           全局校验 → 引用清理重排 → 衔接润色 → 渲染输出
```

#### 6.7.2 归一化层（多级大纲 → 两级执行大纲）

模板大纲支持任意层级嵌套（章 → 节 → 子节…），但执行时统一折叠为**两级**（章 → 节），保持书写自由与执行纪律分离。

**折叠规则（整枝合并，不拆散）：**

| 深层元素 | 归宿 |
|----------|------|
| 节点标题 + 子孙标题 | 二级节点一条 `须覆盖：标题——子孙标题` |
| `notes` | 括号附加：`（note1；note2）` |
| `query_hints` | 上浮合并去重 |
| `word_count` | 累加 |
| `must_cite` / 约束类 notes | 上浮 OR 合并 |
| `promote_subhead: true` | 附加 `并以内部小标题形式呈现` |
| 折叠后 requirements | > 12 条 → 记告警日志（不阻断） |

**折叠算法：**

```python
def normalize_outline(raw):
    """将多级大纲折叠为两级执行大纲"""
    out = deepcopy(raw)
    for chapter in out:
        for sec in chapter.get("children", []):
            reqs = sec.setdefault("writing_requirements", [])
            hints = sec.setdefault("query_hints", [])
            for sub in sec.pop("children", []):
                r = fold_node(sub)               # 递归折叠整枝
                if r not in reqs: reqs.append(r)
                hints.extend(h for h in sub.get("query_hints", []) if h not in hints)
                sec["word_count"] = sec.get("word_count", 1200) + sub.get("word_count", 0)
                if sub.get("must_cite"): sec["must_cite"] = True
            if not reqs:
                reqs.append(f"须覆盖：{sec['title']}")
    return out

def fold_node(node) -> str:
    """递归折叠一个子树为一条写作要求"""
    chain = [node["title"]] + collect_titles(node.get("children", []))
    r = f"须覆盖：{'——'.join(chain)}"
    if node.get("notes"): r += f"（{'；'.join(node['notes'])}）"
    if node.get("promote_subhead"): r += "，并以内部小标题形式呈现"
    return r
```

**归一化示例：**

输入（多级大纲）：
```
ch1 市场概况
├── ch1.1 市场规模与增长（word_count=1500, must_cite=true, notes=["近3-5年数据"]）
│   ├── ch1.1.1 历史规模数据
│   └── ch1.1.2 细分市场拆分
└── ch1.2 竞争格局（word_count=1200）
```

输出（两级执行大纲）：
```json
{
  "id": "ch1.1",
  "title": "市场规模与增长",
  "compose_mode": "standard",
  "must_cite": true,
  "word_count": 2600,
  "writing_requirements": [
    "须覆盖：历史规模数据——细分市场拆分（近3-5年数据）",
    "须覆盖：增长驱动因素"
  ],
  "query_hints": ["市场规模", "增长率", "细分市场"]
}
```

#### 6.7.3 检索层（多通道 + 知识卡片）

每个 `standard` 章节独立执行检索 + 知识卡片构建，分为四个阶段：

**阶段一：LLM 检索策略**

LLM 分析章节上下文（标题 + query_hints + writing_requirements），自动生成多组搜索关键词，而非机械使用固定 query_hints。

| 输入 | 说明 |
|------|------|
| 章节标题 | 当前节的 title |
| query_hints | 模板中定义的检索关键词（作为 LLM 的参考输入） |
| writing_requirements | 写作要求，帮助 LLM 理解需要什么样的材料 |
| 前文 digests | 已完成章节的摘要，避免重复检索 |

| 输出 | 说明 |
|------|------|
| search_queries | 多组搜索关键词，每组针对不同的信息点 |

**阶段二：多通道检索**

根据章节的 `data_sources` 配置，将 search_queries 分发到对应通道：

| 通道 | 检索方式 | 说明 |
|------|---------|------|
| `knowledge` | 向量检索 top20 + BM25 top20 + RRF 融合 | 项目知识库（RAG），复用 knowledge/ 模块 |
| `internet` | 互联网搜索引擎 API | 外部互联网信息，需标注来源 URL |
| `wiki` | Wiki 页面检索 + 内容提取 | 🚫 下一阶段接入，架构预留 |

每个通道返回原始结果（chunks / 网页内容），统一传递给下一阶段。

**阶段三：LLM 知识卡片构建**

LLM 对所有通道的原始结果进行结构化处理，生成知识卡片：

```json
{
  "card_id": "kb-ch1.1-001",
  "section_id": "ch1.1",
  "content": "根据2024年行业报告，市场规模达500亿元，同比增长12%...",
  "source_type": "knowledge",
  "source_title": "2024年行业研究报告",
  "source_from": "industry_report_2024.pdf (p.15)",
  "source_date": "2024-03-15"
}
```

**知识卡片 Schema：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `card_id` | String | 唯一标识，格式 `C{section_id前4字符}_{seq:03d}`，如 `Cch1_001` |
| `section_id` | String | 所属章节 ID |
| `content` | String | 结构化后的内容（提取关键事实，非原文截断） |
| `source_type` | String | 来源类型：`knowledge` / `internet`（`wiki` 预留） |
| `source_title` | String | 来源标题（文档名 / 网页标题） |
| `source_from` | String | 来源出处（文件路径+页码 / 网页 URL） |
| `source_date` | String? | 来源日期（internet 有，其他可能为 null） |

**LLM 知识卡片构建的核心职责：**

| 职责 | 说明 |
|------|------|
| 信息提取 | 从原始 chunks 中提取与章节相关的关键事实和数据，去除噪音 |
| 来源归因 | 为每条信息准确标注来源类型、标题、出处 |
| 语义去重 | 不同通道/文档中描述同一事实的卡片合并，保留最权威来源 |
| 交叉验证 | 多通道信息相互印证，矛盾信息标注采信优先级：knowledge > internet |
| 充足性评估 | 判断收集到的信息是否足够支撑该章节写作 |

**阶段四：充足性评估与降级**

LLM 在构建知识卡片的同时输出充足性评估：

| 评估结果 | 处理 |
|------|------|
| **充足** | 正常进入写作阶段，按写作要求深度分析 |
| **不足** + `optional: true` | 跳过该节，日志记录「内容缺口」 |
| **不足** + `optional: false` | 降级为「分析推理模式」，prompt 注明信息不足，LLM 基于已有材料+专业知识论述，明确标注数据缺口 |

**降级策略（程序化判断）：**

| 场景 | 处理 |
|------|------|
| 所有通道均无结果 | 视同“不足”，走降级 |
| `must_cite: true` 但知识库 RRF 分数全 < 0.01 | 视同材料不足，走降级 |
| 仅 internet 通道有结果 | 标注“仅互联网来源，请谨慎引用” |

#### 6.7.4 全局引用 Registry

所有知识卡片通过全局引用注册器统一管理：

| 属性 | 说明 |
|------|------|
| 去重 key | `(source_type, source_from, content_hash)`，语义去重由 LLM 在卡片构建阶段完成 |
| 编号规则 | 按注册顺序分配全局唯一编号 `[1]` `[2]` ... |
| 持久化 | 随每节 checkpoint 持久化 |
| Prompt 呈现 | `[3] 《2024年报》(knowledge) p.12：「结构化后的卡片内容……」` |

引用编号在 LLM 输出中的格式：紧跟被支撑句末，如 `市场规模达 500 亿元[3][7]`。

> 注：Registry 的注册单元从 raw chunks 升级为知识卡片。每张卡片可能融合了多通道的同一事实，比原始 chunk 信息密度更高、来源更明确。

#### 6.7.5 生成层

**System Prompt（全文共享）：**

```
你是一位{role_hint}，为机构客户撰写正式研究报告。
【报告场景】
本报告面向：{audience}
据此调整：深度、用语、结构偏好
【角色与文风】
- 专业、客观、克制；观点须有证据支撑，不使用夸张修辞
- 书面语，段落 150-300 字；分析性语言优先于描述性语言
- 给出判断时说明依据与不确定性
- 术语首次出现用全称，此后用简称：{terminology 注入}
- 数字规范：千分位、单位统一、不确定数据用区间；数据须注明口径
- 行文用“本报告”“我们认为”
【章节内部标题格式】（仅当 promote_subhead: true 时启用）
- 允许使用小标题，格式：以「◆ 」开头的独立行，后接不超过 15 字的标题
- 每约 800-1000 字一个小标题
- 禁止：markdown 的 #/##/###、数字编号小标题、加粗
【输出契约】（严格遵守）
1. 不输出本节章节标题，首行直接开始正文
2. 引用标注紧跟被支撑句末，格式 [n]，句内可多个如 [3][7]
3. 只能引用参考资料中列出的编号；无材料支撑的具体数据禁止出现
4. 列表仅用于并列枚举，连续不超过 5 项；论证性内容必须成段
5. 末尾不写总结套话，不以"综上所述""总而言之"收尾
6. 目标字数 ±20% 以内；直接输出正文，不要任何前言说明
```

**standard 章节 User Prompt 结构：**

```
【全局上下文】
报告题目：{title}
本节位置：第 {section_id} 节（隶属 {chapter_title}）
前文各节摘要（供衔接，勿重复）：{completed digests，每节 200 字}

【本节写作任务】
目标字数：约 {word_count} 字
写作要求：{prompt_hint + global_requirements}
{must_cite 提示}

【信息充足性】
{sufficiency_assessment}
— 充足时：正常写作
— 不足时：「本节检索材料有限，侧重分析推理，禁止虚构具体数据与引用」

【知识卡片】（带全局编号的结构化卡片）
{knowledge_cards}
每张卡片格式：
  [n] {card_id} | 来源: {source_type} - {source_title}
      {content}
```

**post_body 章节 User Prompt 结构：**

```
【全文摘要视图】
{各章 digest 全量，按章节顺序}

【全文关键数据表】
{extract_numbers 抽取的指标/数值/来源编号}

【本节写作任务】
目标字数：约 {word_count} 字
写作要求：{prompt_hint}
附加要求：不得简单重复正文内容，须给出跨章节的综合判断

【可用知识卡片】
{registry 卡片列表：编号 + 来源类型 + 来源标题}
```

#### 6.7.6 校验层

**单节校验（每节生成后立即执行）：**

| # | 规则 | 违规处理 |
|---|------|----------|
| 1 | 引用编号 ⊆ 本节给定编号集 | 重试（反馈违规清单） |
| 2 | 出现 markdown 标题 `^#{1,6}` 或加粗 `**` | 重试 |
| 3 | 字数偏差 > ±20%（与 System Prompt 输出契约一致） | 重试 |
| 4 | `◆` 小标题超过 15 字 / 数量异常 | 重试 |
| 5 | 结尾"综上所述""总而言之"套话 | 重试或程序截尾 |
| 6 | `must_cite` 节内无任何 `[n]` | 重试，提示须补引用 |
| 7 | 首行不是正文（输出了标题/前言） | 重试 |
| 8 | 3 次重试仍不合规 | 降级接受 + 记录违规日志 |

**全局校验（所有章节完成后）：**

| 规则 | 处理 |
|------|------|
| 幻觉引用（cited - defined 非空） | 定位删除或标记人工复核 |
| 未被引用（defined - cited） | 从 registry 删除，编号重排 |
| 编号连续性检查 | 回填需用提取重建而非字符串替换 |

#### 6.7.7 全局收尾流水线

```
① 引用全局校验 → ② 未引用清理 + 重排 → ③ 一致性检查
（术语统一 via terminology aliases / 前后数字矛盾检测 / 章节间重复检测）
→ ④ 衔接润色（规则驱动：清除悬空过渡词、节首重复标题、连续空行压缩）
→ ⑤ 目录生成（标题树来自模板） → ⑥ 渲染
```

**一致性检查细节：**

| 检查项 | 方法 |
|--------|------|
| 术语统一 | 通过 `terminology` 中的 aliases 检测同一概念的不同表述，日志告警（当前为轻量版，不自动修改） |
| 数字矛盾 | 正则提取数字+单位（亿元/万元/%等），以 15 字上下文为指纹，同一指标不同数值时日志告警 |
| 章节间重复 | 相邻章节段落级 bigram Jaccard 相似度检测（阈值 0.6），超过时日志告警 |

**数据提取 `extract_numbers`：**

从已生成的 standard 章节中提取关键数据点（指标 / 数值 / 来源编号），形成结构化数据表，作为 post_body 章节的输入之一。

**渲染规则：**

| 元素 | 来源 | 渲染 |
|------|------|------|
| 一级/二级标题 | 模板 outline | 目标格式样式（docx 样式 / markdown ##/###） |
| 内部小标题 | 模型输出 `◆ xxx` | 统一转换为下一级标题样式（三层分离） |
| 引用 `[n]` | 原样保留或转上标 | markdown/docx 均由程序处理 |
| 尾注列表 | registry | 按编号序；同文档相邻 chunk 可合并为页码范围条目 |
| 章节排序 | post_body 按 `position`（front/end）插入 | 渲染时拼接 |

> 注：本阶段渲染目标格式为 Word（docx）和 PDF，PPT 后续扩展。

#### 6.7.8 异常处理与工程保障

**智能重试分类：**

LLM 调用失败时，根据失败类型采取不同策略，而非统一重试：

| 失败类型 | 识别方式 | 重试策略 |
|----------|----------|----------|
| 内容安全过滤 | API 返回 content_filter / safety 错误 | 不重试，直接降级，日志记录 |
| JSON 解析错误 | LLM 输出非合法 JSON（工具调用场景） | 重试，附加提示「上次输出格式错误，请严格输出合法 JSON」 |
| 上下文溢出 | token 超限错误 | 截断 user_prompt 到 4000 字后重试（一次机会） |
| 模型超时/限流 | 超时 / 429 状态码 | 指数退避重试 3 次，仍失败则记录待完成节 |
| 文本规则违规 | 校验层检测的格式违规 | 重试，反馈具体违规清单（现有逻辑） |
| 空输出 | LLM 返回空字符串 | 重试，附加提示「上次未输出内容，请完整输出」 |

**工程保障：**

| 场景 | 处理 |
|------|------|
| 生成中断 | 每节 checkpoint（outputs/digests/registry/order），重启从断点续跑 |
| 上下文溢出 | 前文 digest 窗口控制（最近 3 节 + 全局一页纸摘要）；知识卡片数量限制 |
| 模板不合规 | 入口 Schema 校验失败直接拒绝，不进入流水线 |
| Token 统计 | 每次 LLM 调用记录 token 消耗（prompt_tokens/completion_tokens），报告完成时汇总写入 DB |

#### 6.7.9 执行主流程（伪代码）

```python
def run_report(template, variables, kb, registry):
    outline = normalize_outline(instantiate(template, variables))  # 实例化 + 归一化
    validate_execution_outline(outline)
    outputs, digests, order = {}, {}, []
    token_usage = TokenTracker()                          # Token 统计追踪

    # ── 第一遍：standard 章节（大纲顺序串行）──
    for sec in sections_of(outline):
        if sec.compose_mode != "standard": continue

        # 阶段一：LLM 检索策略
        search_queries = llm_generate_queries(sec, digests)    # 基于 query_hints + 上下文生成多组 query

        # 阶段二：多通道检索
        raw_results = multi_channel_retrieve(
            search_queries, data_sources=sec.data_sources,
            kb=kb)

        # 阶段三：LLM 知识卡片构建 + 充足性评估
        cards, sufficiency = llm_build_knowledge_cards(
            raw_results, sec, registry)
        refs = [registry.get_or_add(**c) for c in cards]

        # 阶段四：生成 + 智能重试
        for attempt in range(3):
            try:
                output, tokens = llm(
                    SYSTEM_PROMPT,
                    build_prompt(sec, refs, digests, sufficiency))
                token_usage.record(tokens)
                violations = validate_section(output, refs, sec)
                if not violations: break
            except ContentFilterError:
                output = FALLBACK_TEXT; break             # 内容安全过滤，不重试
            except TokenLimitError:
                user_prompt = truncate_prompt(user_prompt, 4000)  # 截断上下文后重试
            output, tokens = llm(..., retry_feedback=violations)

        outputs[sec.id] = output
        digests[sec.id] = summarize(output, 200)
        order.append(sec.id)
        save_checkpoint(outputs, digests, registry, order, token_usage)

    # ── 第二遍：post_body 章节 ──
    for sec in [s for s in outline if s.compose_mode == "post_body"]:
        output, tokens = llm(SYSTEM_PROMPT, build_post_body_prompt(
            sec, digests, extract_numbers(outputs), registry))
        token_usage.record(tokens)
        validate_section(output, registry.all_ids(), sec)
        outputs[sec.id] = output

    # ── 全局收尾 ──
    report = finalize(outputs, outline, registry)
    save_token_usage(token_usage)                        # Token 统计写入 DB
    return report
```

#### 6.7.10 设计决策一览

| 决策 | 理由 |
|------|------|
| 两遍执行（standard 先，post_body 后） | 摘要/结论类章节须基于全文综合，不能独立检索生成 |
| 模板多级自由书写，执行严格两级 | 书写自由与执行纪律分离 |
| 深层内容整枝折叠为“须覆盖”要求 | 保持结构语义，粒度受控 |
| 标题三层分离（模板/模型 ◆/程序） | 换渲染格式不改生成逻辑 |
| post_body 输入 = digest + 数据清单 | 省上下文 + 逼综合 |
| 引用 key=(source_type, source_from, content_hash) 全局注册 | 尾注全局唯一、语义去重、可溯源 |
| 通道间并行 + 通道内多 query 并行 | 通道间 asyncio.gather 并行，通道内 Semaphore 控制并发数，显著缩短检索时间 |
| post_body 禁新检索、只复用编号 | 摘要论据必须正文可溯源 |
| System Prompt 与内容解耦 | 全文文风一致 |
| 入口校验 + 出口严格校验 + 3 次重试 | 质量兜底 |
| 每节 checkpoint | 长报告生成可中断恢复 |
| 知识卡片中间层 | 多通道异构数据统一为结构化卡片，写作 Agent 输入质量可控 |
| LLM 驱动检索策略 | 自动生成搜索关键词，比固定 query_hints 更灵活、更贴合章节需求 |
| 信息充足性评估 | 检索后评估材料充足性，LLM 自适应调整写作策略，避免虚构数据 |
| 智能重试分类 | 区分内容安全/溢出/解析/空输出等失败模式，针对性处理，避免无效重试 |
| Token 统计追踪 | 每次 LLM 调用记录消耗，报告级汇总，为成本控制和优化提供数据支撑 |

#### 6.7.11 模板变量实例化

模板支持 `{{variable}}` 占位符，实例化时替换为实际值：

```python
def instantiate(template, variables: dict):
    text = json.dumps(template, ensure_ascii=False)
    for k, v in variables.items():
        text = text.replace("{{" + k + "}}", v)
    return json.loads(text)
```

示例：模板中 `"title": "{{公司名}}投资分析报告"` + `variables: {"公司名": "XX科技"}` → `"title": "XX科技投资分析报告"`

**校验规则：** 变量引用 `{{x}}` 必须在 `variables` 中声明。

#### 6.7.12 模块结构与架构定位

**架构定位：独立模块**（非 Tool、非 Skill）

报告生成引擎是独立模块 `python/report_generator/`，与 `python/knowledge/` 同级。理由：

| 特征 | Tool/Skill | 报告引擎 |
|------|-----------|---------|
| 调用模式 | 单次调用，输入→输出 | 多步流水线，长时间运行 |
| 状态管理 | 无状态 | 有状态（Registry、checkpoint、digest 累积） |
| 运行时长 | 秒级 | 分钟级（5-20 分钟） |
| 中断恢复 | 不支持 | 每节 checkpoint，断点续跑 |
| API 暴露 | Agent 内部调用 | 独立 REST 路由 + SSE 流式推送 |

**与现有模块的关系：**

```
report_generator（独立模块）
    ├── 复用 → knowledge/hybrid_retriever（知识库检索通道）
    ├── 复用 → knowledge/vector_store + fts_store（底层存储）
    ├── 复用 → llm/client（LLM 调用 + Token 统计）
    ├── 复用 → tools/web_search（互联网检索通道，任务系统内置工具）
    ├── 复用 → db/database（持久化）
    └── 独立 → 自己的流水线逻辑、状态管理、API 路由
```

**文件结构：**

```
python/report_generator/
├── __init__.py
├── loader.py              # 模板加载器（扫描预置/自定义模板 + schema 校验 + manifest 版本比对）
├── template_extractor.py  # 上传样例 LLM 提取（全文解析 + LLM 结构化分析 → 模板草稿）
├── normalizer.py          # 模板变量实例化 / 多级大纲归一化 / 执行校验
├── search_strategy.py     # LLM 检索策略（基于 query_hints + 上下文自动生成搜索关键词）
├── retrieval.py           # 混合检索封装（复用 knowledge/ 内置 RRF）/ 降级策略
├── card_builder.py        # LLM 知识卡片构建（结构化/来源归因/语义去重/充足性评估）
├── registry.py            # 全局引用注册（去重 key=(doc_id,chunk_id)，编号管理）
├── prompts.py             # System Prompt / User Prompt 模板构建
├── runner.py              # 两遍执行主流程 / checkpoint / 断点恢复
├── token_tracker.py       # Token 统计追踪（每次 LLM 调用记录，报告级汇总）
├── validator.py           # 单节校验（8 条规则）/ 全局校验
├── finalizer.py           # 一致性检查 / 衔接润色 / 引用清理重排
└── renderer.py            # Markdown → docx / PDF 渲染输出
```

## 9. 数据生命周期与存储策略

报告系统涉及多种数据，它们的性质和生命周期不同，必须明确存储位置和更新策略。

### 9.1 数据分类

| 数据类型 | 性质 | 生命周期 | 存储位置 |
|----------|------|----------|----------|
| 预置模板 | 程序资源（只读） | 随版本更新 | 安装包内 `resources/templates/` |
| 自定义模板 | 用户数据 | 永久，跨版本保留 | `%APPDATA%/InkCube/data/templates/` |
| 生成的报告 | 用户数据 | 永久，跨版本保留 | SQLite `data.db` + `%APPDATA%/InkCube/data/reports/` |
| 知识库文档 | 用户数据 | 永久，跨版本保留 | `%APPDATA%/InkCube/data/projects/{id}/` |
| 生成日志 | 用户数据 | 永久，跨版本保留 | SQLite `data.db` + `%APPDATA%/InkCube/data/logs/` |
| 基础库 | 程序资源 + 用户数据 | 预置随版本，自定义永久 | 预置在安装包，自定义在用户数据目录 |

**基础库更新策略：**

| 场景 | 处理 |
|------|------|
| 预置基础库更新（新增文档） | 新版本自动覆盖安装包内资源，用户下次启动可见 |
| 用户往预置基础库添加自定义文档 | 写入 `%APPDATA%/InkCube/data/projects/base_{type}/custom/`，不受程序更新影响 |
| 自定义基础库 | 完全存储在用户数据目录，与程序更新无关 |

> 核心原则：预置基础库的“预置文档”是只读程序资源，“用户添加的文档”是用户数据，两者存储在不同目录，互不干扰。

### 9.2 运行时目录结构

```

  │   ├── industry_research.json

  │   └── ...
  └── base_libraries/         ← 预置基础库（招商/投资）

  ├── data/
  │   ├── templates/          ← 自定义模板（.inktpl）
```

| 存储位置 | 安装包 `resources/templates/`（只读） |
| 加载方式 | 启动时扫描目录，加载所有 `.json` 模板 |
| 用户修改 | 不允许。用户只能“复制”为自定义模板后编辑 |
| 版本更新 | 新版本安装包覆盖旧版本，预置模板自动更新 |
| 新增模板 | 新版本可新增模板，用户下次启动即可看到 |
| 删除模板 | 新版本可移除模板，但已基于该模板生成的报告不受影响 |

**模板版本管理：**
- 每个预置模板带 `version` 字段
- 安装包内附带 `templates/manifest.json`，记录所有预置模板的版本号
- 启动时比较 manifest 与上次加载记录，有变化则刷新模板缓存

**预置模板更新与用户自定义的隔离：**

用户“复制”预置模板为自定义模板后，两者完全独立：

| 场景 | 处理 |
|------|------|
| 预置模板 A 结构更新（字段增删） | 自定义模板 B 不受影响，B 是独立副本 |
| 预置模板 A 被移除 | B 仍可用，基于 A 生成的报告仍可查看/导出 |
| 用户想同步 A 的新版本 | 需手动重新复制并手动迁移内容（程序不自动合并） |

> 核心原则：预置模板是只读程序资源，自定义模板是用户数据，两者通过“复制”操作断开关联，互不影响。

### 9.4 报告存储策略

报告内容采用 **SQLite 元信息 + 文件系统内容** 的混合存储：

**SQLite（data.db）存储：**
- 报告元信息（id、title、template_id、project_id、status、created_at 等）
- 报告内容摘要（用于列表预览）
- 生成日志摘要（每节的耗时、字数、违规记录）
- 模板缓存（预置模板的加载记录）

**文件系统存储：**
- 报告完整内容（Markdown）
- 引用 Registry 快照（用于来源追溯和重新生成）
- Checkpoint 数据（断点恢复）
- 完整生成日志（prompt 全文）

**理由：**
- 报告内容可能很大（几万字 + 引用数据），不适合全放 SQLite
- 文件系统便于调试和导出（直接读 Markdown）
- SQLite 存元信息便于快速查询和列表展示

### 9.5 程序更新影响分析

| 场景 | 影响 | 用户感知 |
|------|------|----------|
| 应用更新（正常安装） | 预置模板更新，用户数据不受影响 | 无感知，可能看到新模板 |
| 应用更新（新增预置模板） | 新模板自动可用 | 模板列表中多出选项 |
| 应用更新（移除预置模板） | 旧模板不再显示，但已生成的报告可正常打开 | 报告列表中历史报告不受影响 |
| 应用更新（模板结构变更） | 通过 `_schema.json` 版本检测，启动时迁移 | 无感知 |
| 卸载重装 | 安装包内数据丢失，`%APPDATA%/InkCube/` 用户数据保留（NSIS 配置 `deleteAppDataOnUninstall: false`） | 重装后数据还在 |
| 手动删除 `%APPDATA%` | 用户数据全部丢失 | 灾难性，需要引导用户备份 |

### 9.6 数据迁移策略

程序更新时，通过 `data.db` 中的 `schema_version` 字段检测是否需要迁移：

```
启动时:
  读取 data.db 的 schema_version
  与当前程序期望的 latest_version 比较
  若有差距 → 依次执行迁移脚本（v1→v2→v3...）
  迁移完成 → 更新 schema_version
```

**迁移原则：**
- 只迁移结构，不修改用户内容
- 迁移前自动备份 `data.db` → `data.db.bak.{timestamp}`
- 迁移失败 → 回滚 + 日志记录 + 提示用户

### 9.7 与现有打包方案的集成

当前打包方案（参见 [packaging-design.md](0.2packaging-design.md)）已有：
- `%APPDATA%/InkCube/` 作为用户数据持久化目录
- `extraResources` 机制将资源捆绑到安装包
- `tool-initializer.js` 处理首次启动初始化

报告系统只需复用现有机制：

| 现有机制 | 报告系统复用方式 |
|----------|------------------|
| `extraResources` | 增加 `resources/templates/` → `templates/` 和 `resources/base_libraries/` → `base_libraries/` 的映射 |
| `%APPDATA%/InkCube/` | 在其下新建 `data/templates/`、`data/reports/` 等目录 |
| `tool-initializer.js` | 扩展初始化逻辑：首次启动时创建 `data/` 子目录结构 |
| `data.db` | 复用现有数据库，新增报告/模板相关表 |
