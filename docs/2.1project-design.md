# 项目设计

> **概述**：本文档定义「项目」子系统的产品与数据设计——项目是面向招商经理与投资经理的统一工作空间，把资料收集、知识编译（Wiki）、报告生成、填表四类工作合入同一容器。项目与基础库共用一套数据模型（`projects` 表以 `kind` 列区分），基础库是跨项目共享的知识容器，由报告检索与 Wiki 编译两类消费方按需引用。本文覆盖：信息架构与导航（§2）、项目分类体系（§3）、类型与阶段模型（§4）、表结构（§5）、项目详情页交互（§6）、基础库机制与 API（§7）、知识消费矩阵（§8）、报告/填表概要（§9/§10）、数据生命周期与存储策略（§11）。
>
> 详细设计见各专项文档：知识库管线 [2.2](2.2knowledge-base-design.md)、报告引擎 [2.5](2.5report-design.md)、Wiki [2.6](2.6wiki-design.md)、基础库 RAG [2.7](2.7baselib-rag-design.md)；活动/轮询遵循 [0.4](0.4lifecycle-design.md)。

## 1. 背景与定位

### 1.1 设计目标

将原本割裂的「知识库」（上传文档 → 向量化 → RAG 检索/问答）与「报告」入口合并为**项目**——一套完整的工作闭环：

> 一个项目 = 收集资料 → 知识编译 → 生成报告/填表

### 1.2 核心价值主张

> **报告生成引擎是墨方的核心功能，重中之重。**
>
> 墨方通过「模板定义 + 知识库检索 + 专业生成流水线」的组合，实现大模型在招商/投资垂直行业的深度落地。通用智能体只能给出一次性回答，墨方能产出**专业级、可交付、引用可溯源**的行业报告——从「AI 聊天」到「AI 生产力工具」的跨越。

### 1.3 目标用户

| 角色 | 核心工作 | 典型产出物 |
|------|---------|-----------|
| **招商经理** | 招商引资、企业引进、园区推介 | 招商推介方案、项目评估报告、招商跟踪表 |
| **投资经理** | 投资分析、项目分析、投后管理 | 尽职调查报告、投资分析报告、尽调清单 |

## 2. 信息架构

### 2.1 导航结构

```
┌──────────┐
│ 🏠 首页   │  Ctrl+1
│ 🛠 任务    │  Ctrl+2   ← 通用 Agent（编程/通用双模式，默认编程）
│ 📂 项目    │  Ctrl+3   ← 项目 + 基础库 + 模板管理
└──────────┘
```

- 导航 3 个入口；历史「产业洞察」「知识库」「报告（禁用）」入口已合并/撤除，通用问答能力由「任务」承接
- 「项目」导航内部互斥三态：项目详情页（选中项目）/ 模板管理页 / 基础库详情页（[§3.3](#33-视图互斥)）

### 2.2 「任务」与「项目」的分工

| 维度 | 任务 | 项目 |
|------|------|------|
| 定位 | 轻量、即时、通用 | 重量、持续、专业 |
| 知识来源 | 互联网 + 通用能力 + 全局知识检索工具 | 项目知识库 + Wiki + 关联基础库 |
| 产出物 | 一次性结果（对话、简单报告） | 结构化产出（报告、填表、Wiki） |
| 生命周期 | 用完即走（可归档） | 长期跟踪，分阶段管理 |

任务子系统详见 [1.1](1.1task-agent-design-unified.md)。

### 2.3 产品边界

- **墨方负责内容生成**（从 0 到 1）：生成报告内容、编译 Wiki、填充数据
- **Office 负责格式呈现**（从 1 到 100）：字体排版、企业标识、最终审阅——导出为 Word 后由用户在 Office 内精修

### 2.4 项目内 Agent 参与形态

```
项目内部每个 Tab 都有 Agent 参与:
├── 📁 资料 — 文档解析向量化、RAG 检索、图片描述（2.2）
├── 📖 Wiki — LLM 知识编译、增量更新、审阅（2.6）
├── 📊 报告 — 按模板检索生成、校验重试（2.5）
├── 📋 填表 — 数据提取和填充（2.4，现状 UI 原型）
└── 💬 Chat — 项目级 RAG 问答（可归档入 Wiki）
```

## 3. 项目分类体系

### 3.1 三类对象

| 类别 | kind / lib_type | 结构 | 说明 |
|------|----------------|------|------|
| 普通项目 | `kind='project'` | 四 Tab（资料/Wiki/报告/填表）+ Chat；V2-E1a T11 收敛为**事务/知识/产出（报告+填表合并）/资料**四 Tab（0.6 §3.4 V2 翻转决议：事务置首，用户认可 2026-10-23）（[0.6 §3.2](0.6v2-ux-redesign.md)、[3.0 §2.2](3.0project-lifecycle-design.md)） | 完整工作空间 |
| 预置基础库 | `kind='base_lib'`, `lib_type='preset_recruitment' \| 'preset_investment'` | 单页（资料 + Chat） | 系统内置 2 个，启动幂等创建，不可改名/删除（2.9 D3 收敛后仅此两类，无自定义库） |

另有**模板管理**入口（非项目实体）：预置模板 + 自定义模板，跨项目共享，详见 [2.5 §模板](2.5report-design.md)。

```
┌──────────────┐
│ 项目列表（滚动区）│  ← ProjectSidebar（ProjectList 包装）
│ [有效|归档]    │     新建/重命名/归档/恢复/删除（先归档再删除，§11.6）

│   📁 YY生物    │
├──────────────┤

│   🏭 招商基础库  │     预置徽记、活跃点指示
│   💲 投资基础库  │
├──────────────┤
│ 📋 报告模板     │  ← 模板管理入口（peer 高亮）
└──────────────┘
```

### 3.3 视图互斥

App 层在「项目」导航内维护两个状态：`selectedProjectId` / `selectedBaseLibId` / `showTemplateManagement`，渲染时互斥三选一：

| 条件 | 渲染 |
|------|------|
| 选中项目 | `ProjectDetailPage` |
| `showTemplateManagement` | `TemplateManagement` |
| 选中基础库 | `BaseLibDetailPage` |

进入「项目」导航且无任何选中时自动选中第一个项目；切换导航（Ctrl+1/2/3）复位模板管理与基础库选中态。

侧边栏滚动区的项目 / 任务列表与导航内容绑定，由 `peerPageOpen` 统一判定：设置 / 模板管理 / 基础库详情任一打开时列表清空（与首页一致，不残留），经 NavTabs 切回后复原；底部基础库 / 模板管理入口常驻不受影响。

## 4. 项目类型与阶段

### 4.1 项目类型

| 类型 | 值 | 阶段 | 预置基础库自动关联 |
|------|-----|------|------------------|
| 招商引资 | `recruitment` | 前期接触 / 推进中 / 已落地 | 招商基础库 |
| 投资分析 | `investment` | 投前 / 投中 / 投后 | 投资基础库 |
| 通用 | `general` | 无阶段 | 无 |

类型决定：默认关联基础库、Wiki Schema 结构（2.6）、报告模板过滤（2.5）、阶段 pill 与看板列。

### 4.2 阶段模型

`ProjectStage = 'before' | 'during' | 'after' | 'none'`。`STAGE_MAP` 按类型定义阶段序列（general 为空数组）；报告看板列 `STAGE_COLUMNS` 固定 4 列（before/during/after/none），general 类型只显示「其他」单列。

### 4.3 企业信息字段

创建项目时可选填 `company_name`（企业工商名称）与 `credit_code`（统一社会信用代码），全类型适用，展示在项目头部。

### 4.4 切换与持久化

- **阶段切换**：头部阶段 pill 双向可点（可前进也可回退），乐观更新 + `PATCH /projects/{id}` 持久化，失败回滚并提示
- **类型切换**：头部下拉选择，切换后阶段重置为该类型初始阶段，一并持久化（type + stage 同请求）
- 两者均经 IPC `knowledge:updateProject`，成功后回调 App 刷新侧边栏数据

### 4.5 产业画像（industry_profile，2026-10-25）

项目的产业链/细分领域结构化标签，AI 从 Wiki 编译产物提取（提取链路见 [2.6 §4.8](2.6wiki-design.md)），人在头部可修正；主消费方 = 订阅创建预填 `{产业}` 占位符（[2.11 §8.1](2.11scheduled-task-design.md)「从项目画像」渠道）。

- **数据形态**：`[{"chain":"具身智能","segment":"四足机器狗"},...]`（多值，chain=产业链、segment=细分领域，segment 可空；不表达上下游位置——产业舆情订阅本身覆盖上下游语义）；NULL=未提取 / `[]`=已提取未识别
- **人工优先**：头部画像行可增删改条目，编辑后 `profile_source='manual'`，后续编译不自动覆盖；「重新提取」显式动作可覆盖（POST `/projects/{id}/profile/extract`，异步受理，活动 kind=`profile_extract`，完成经心跳边沿刷新）
- **发起订阅**：每条画像尾部「盯产业」钮 → App 级新建订阅弹层（与线索升级同一条弹层链），预选「产业舆情扫描」模板 + `{产业}` 预填细分领域（无细分用链条名），分类自动映射 industry

## 5. 表结构

### 5.1 projects 表（项目与基础库共用）

```sql
-- 基础 DDL（database.py）
CREATE TABLE IF NOT EXISTS projects (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    description TEXT DEFAULT '',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
-- 迁移列（_migrate_add_column，启动时幂等补齐）
ALTER TABLE projects ADD COLUMN type TEXT DEFAULT 'general';        -- 项目类型
ALTER TABLE projects ADD COLUMN stage TEXT DEFAULT 'none';          -- 项目阶段
ALTER TABLE projects ADD COLUMN company_name TEXT DEFAULT '';       -- 企业工商名称
ALTER TABLE projects ADD COLUMN credit_code TEXT DEFAULT '';        -- 统一社会信用代码
ALTER TABLE projects ADD COLUMN kind TEXT DEFAULT 'project';        -- 'project' | 'base_lib'
ALTER TABLE projects ADD COLUMN lib_type TEXT DEFAULT NULL;         -- 'preset_*'（base_lib 专用；2.9 D3 后仅预置）
ALTER TABLE projects ADD COLUMN archived_at DATETIME DEFAULT NULL;  -- 归档时间戳（NULL=有效，非空=已归档，§11.6）
ALTER TABLE projects ADD COLUMN industry_profile TEXT DEFAULT NULL; -- 产业画像 JSON 数组（§4.5；NULL=未提取，[] =已提取未识别）
ALTER TABLE projects ADD COLUMN profile_source TEXT DEFAULT NULL;   -- 画像来源 wiki_compile/manual；manual 行编译不自动覆盖
```

| 列 | 读写行为 |
|----|---------|
| `kind` | 列表查询按 kind 过滤分流：`GET /projects` 只返回 `kind='project'`，`GET /base-libs` 只返回 `kind='base_lib'`；`delete_project` 带 kind 条件防止误删基础库 |
| `lib_type` | `preset_` 前缀 = 预置库（禁改名/禁删除）；仅预置 2 个（2.9 D3 收敛，`custom` 库已退场） |
| `type` / `stage` | 项目专用；基础库行保持默认值 |
| `industry_profile` / `profile_source` | 项目专用（§4.5）：写方 = 编译后自动提取（profile_service，manual 行跳过）/ 头部人工编辑（置 manual）/ 重新提取（覆盖 manual）；读方 = 详情头部画像行 + 订阅创建预填；`list_projects` 出参直出两列 |
| `archived_at` | 项目专用（§11.6）：`list_projects(archived)` 按是否为 NULL 过滤（默认有效集，`archived=true` 返回归档集）；`archive/unarchive` 是唯一写方；`list_due_phase_tasks` 排除归档项目（周期任务不为其铺入新期次）；基础库行不参与归档 |

预置库固定 ID：`bl-recruitment`（招商基础库）、`bl-investment`（投资基础库），启动时 `ensure_preset_base_libs()` 幂等创建（存在即跳过，不覆盖用户数据）。

### 5.2 project_base_libs 关联表

```sql
CREATE TABLE IF NOT EXISTS project_base_libs (
    project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    base_lib_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    auto_linked INTEGER NOT NULL DEFAULT 0,          -- 1 = 创建时按类型自动关联
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (project_id, base_lib_id)
);
```

- **写入方**：项目创建时自动关联（`_AUTO_LINK_MAP`: recruitment→bl-recruitment, investment→bl-investment）；报告向导完成后把用户勾选回写为项目关联集（[§9.1](#91-创建向导2-步)）
- **读取方**：报告检索（base_project_ids）、Wiki 编译（[§8](#8-知识架构与基础库消费方)）
- `INSERT OR IGNORE` 保证幂等；项目删除时级联清理

### 5.3 关联表（引用）

文件/图片/chunk 表以 `project_id` 外键指向 projects.id——**基础库与项目共用同一套文件管线与检索索引**（详见 [2.2 §表结构](2.2knowledge-base-design.md)）；报告表见 [2.5](2.5report-design.md)；模板表见 [2.5 §模板管理](2.5report-design.md)。

## 6. 项目详情页（前端交互）

### 6.1 页面结构

```
┌─ 头部 ────────────────────────────────┐

├─────────────────────────┬──────────┤
│ Tab 内容                 │ Chat 面板 │
│ （materials 嵌入 KnowledgePage│ （可开合  │
│   compact 模式）          │  可拖宽）  │

```

> **V2 现状（2026-10-24）**：四 Tab = **事务（置首/默认）/ 知识 / 产出 / 资料**——[0.6 §3.4](0.6v2-ux-redesign.md) V2 翻转决议（用户认可 2026-10-23：四支柱排序生命周期 > 知识）+ V2-E1a T11 产出合并（报告/填表并入产出二级分区，PPT 留报告分区）；3.0 一/二期交付时的「知识置首五 Tab」结构已被取代。脉搏带定位不变（header 与 Tab 栏之间）。

### 6.2 消费组件清单

| Tab | 组件 | 数据来源 | 界面呈现 |
|-----|------|---------|---------|
| （Tab 栏上方） | `PulseBar` | 心跳 + `wiki:listReviews` + `wiki:listPages` | 状态句 + chips（矛盾/缺口/待编译/报告），折叠偏好 per 项目；chip 直达知识 Tab 治理视图（3.0 一期，详见 [3.0 §6.1.1](3.0project-lifecycle-design.md)） |
| （头部，企业信息行下方） | `ProjectProfileLine` | `project.industry_profile`/`profile_source` + 心跳 `useActivity('profile_extract')` | 产业画像标签行（§4.5）：每条「链条·细分」标签带「盯产业」钮（经 `app:open-schedule-wizard` 事件开 App 级订阅弹层预填）；增删改条目（置 manual）；「重新提取」钮（`knowledge:extractProfile`，异步受理）；提取中态经心跳呈现；NULL 态提示「编译 Wiki 后自动提取」 |
| affairs（置首/默认） | `AffairsTab`（PhaseBoard / RhythmCards / CalendarView） | `affairs:listByProject` | 时期看板/周期节奏/日历三视图 + 任务表单弹窗与执行抽屉（3.0 二期，见 [3.0 §6.1.3-6.1.7](3.0project-lifecycle-design.md)） |
| wiki | `WikiTab` + 内部视图集 | `wiki:*` IPC | 阅读层（封面/目录语义分组/台账时间轴/搜索/图谱）+ 整理层（汇编/知识体检/知识框架/时间线），详见 2.6 §7 |
| output（V2-E1a T11 合并） | `OutputTab`（二级分区「报告 / 填表」+ 头部「模板管理」直达钮） | 报告分区 = `reports:*` IPC；填表分区 = `form-fill:*` / `form-template:list` IPC + `useActivity('form_fill')` | 报告分区：看板/向导/预览/PPT 区块（见 2.5）；填表分区：list→preview 两视图：实例卡（进度常显/打开/下载/删除）+ 发起弹窗 + 六型动态表单结果编辑（见 2.4） |
| materials | `KnowledgePage`（compact） | `knowledge:*` IPC | 文件列表/搜索/图片库/上传（见 2.2） |
| Chat | `ProjectChatPanel` | `knowledge:chat` | 右侧可拖宽面板（[§6.3](#63-chat-面板)） |

### 6.3 Chat 面板

- **常驻可开合**：面板始终挂载在内容区右侧，默认收起；与 Wiki 预览互斥（打开 Chat 关闭预览，反之亦然）
- **宽度可拖**：260–720px，默认 720px
- **点击外部收起**：展开时全屏半透明遮罩（模板管理 drawer 同款，z-index 199 垫在面板之下），点击面板外任意处收起；遮罩不透传点击（第一次点击仅收起，基础库详情页同款行为）
- **检索范围切换**：默认项目级（`scope='project'`）；从文件列表选中文件后切换为文件级（`fileId` 限定检索），面板标题与图标随范围变化，可手动清除文件限定
- **检索范围现状**：`KnowledgeRAG.ask` 仅检索当前项目（或文件），**不含关联基础库**——差异登记见 [§13.1](#131-文档--代码差异)
- **归档到 Wiki**：任一回答可「保存为 Wiki 页面」——弹出标题输入，经 IPC `wiki:archive`（问题+回答+标题）写入项目 Wiki（详见 2.6）
- **会话内存态**：消息列表不落库，切换项目即清空（归档是唯一的持久化路径）

### 6.4 Tab 角标与活动指示

角标从全局心跳 `byProject` 派生（0.4 §5.7），不自建轮询：

| Tab | 指示 | 条件 |
|-----|------|------|
| materials | 脉动点 | `byProject.files > 0`（解析中） |

## 7. 基础库

### 7.1 预置基础库

## 9. 报告系统概要

报告引擎是独立模块（非 Tool/Skill），完整设计见 [2.5](2.5report-design.md)。本节仅记入口与项目侧交互。

### 9.1 创建向导（2 步）

1. **Step 1 选模板**：按项目类型 + 阶段过滤模板列表（预置 + 自定义，来源 `reports:listTemplates`）
2. **Step 2 配置**（左右分栏：左配置区/右大纲区）：模板变量 → 知识源勾选 → 补充说明 → 互联网开关（需已配置网络搜索——供应商已选且对应 Key 非空，未配置时置灰）→ thinking 深度（可选）

**知识源与关联同步**：知识源 = 项目知识库（必选）+ 招商/投资预置库（按关联预勾；2.9 D3 收敛后无自定义库）。向导完成后把勾选集回写 `project_base_libs`（勾选=关联、取消=解除），下次向导按当前关联集预勾选（勾选结果即项目关联集，见 2.7 §5.5）。

### 9.2 看板与详情

- **看板**：按报告 stage 分列（general 类型仅「其他」单列）；卡片显示状态/进度/模板名/删除/重试；生成中时由全局心跳驱动 3s 轮询刷新，终态边沿补拉
- **详情**：正文 Markdown 渲染 + 来源面板 + 进展日志 + 导出（Word）/重试
- **重试**：`resume`（从 checkpoint 续跑）/ `restart`（删 checkpoint 完全重生成）；重试恢复原始变量、基础库 ID、互联网开关
- **并发限制**：全局同时生成上限 `report_max_concurrent`（默认 2，超限 429）

### 9.3 模板管理

跨项目共享，侧边栏「报告模板」入口进入 `TemplateManagement` 页：

- **预置模板**（只读，可复制为自定义）：行业研究、尽职调查、招商方案、项目简介、投后报告共 5 个（`resources/templates/*.json`）
- **自定义模板**：三种创建入口——空白创建 / 上传样例 LLM 提取 / 从预置复制——统一进入 `TemplateEditor`（大纲/元数据/术语/变量全编辑）
- **加载策略**：启动时预置模板无条件重载覆盖 DB 缓存（文件为准）；自定义模板自动迁移升级并标记问题项

## 11. 数据生命周期与存储策略

### 11.1 数据分类

| 类别 | 内容 | 位置 | 删除策略 |
|------|------|------|--------|
| 程序资源（只读） | 预置模板/捆绑工具 | 应用包内 `resources/` | 随应用更新覆盖 |
| 用户数据 | DB/文件/向量/报告/任务 venv/自定义模板/日志 | 数据目录（见下） | 用户主动删除；卸载不删（NSIS 保留） |

### 11.2 目录结构

数据目录由 `get_data_dir()`（`python/paths.py`，单一来源）决定：环境变量 `INKCUBE_DATA_DIR` 优先；打包态为 `user_data_dir("InkCube","InkCube")/data`（Windows 即 `%APPDATA%/InkCube/InkCube/data`）；开发态为 `python/data`。

```
{data_dir}/
├── inkcube.db              # SQLite（含 WAL/SHM）
├── files/{project_id}/     # 原始文件（项目与基础库共用，基础库 ID 即目录名）
├── chroma/                 # 向量索引（按 project_id 隔离 collection）
├── models/                 # 本地嵌入模型（bge-m3）
├── tasks/{task_id}/        # 任务工作区 + venv（懒创建，1.1 §2；首次执行代码才落盘 .venv）
├── uv-cache/               # uv 全局缓存（UV_CACHE_DIR 同盘，同版本包硬链接零增量）
├── templates/              # 自定义报告模板（v2 schema）
├── reports/{report_id}/    # 报告产物：content.md / registry.json /
│                           #   checkpoint.json / 导出 docx（token 明细在 DB llm_usage 表，2.10）
├── temp/                   # 上传中转
└── logs/app.log            # 统一日志（Python + Electron 共写，轮转 5MB×3）
```

### 11.3 预置资源分发

- **预置模板**：打包进应用（`resources/templates/`，manifest 清单 + `_schema.json` 校验 schema），启动时重载——应用更新后新模板自动生效，DB 只是缓存
- **预置基础库**：不随包分发文档，启动时按固定 ID 幂等创建空库记录；版本更新不会覆盖库内用户数据（存在即跳过）

### 11.4 删除链路

| 操作 | 清理范围 |
|------|--------|
| 删除项目 | **准入 = 已归档**（未归档 409，[§11.6](#116-项目归档先归档再删除)）：Chroma 向量 + FTS 索引 + `files/{id}/` 磁盘 + Wiki 数据（预清理+级联）+ DB 级联（files/images/reports/...）+ 线索立项引用置 NULL（`detach_leads_for_project`，线索行保留，[0.6 §4.1](0.6v2-ux-redesign.md)）；报告产物目录随报告删除或级联 |
| 删除基础库 | 无入口（2.9 D3 收敛后仅预置库，禁删） |
| 删除报告 | `reports/{id}/` 磁盘目录 + DB 记录 |
| 删除文件 | 单文件向量/FTS/磁盘 + Wiki pending 计数+1 |

**导出对照**：项目导出（[2.9project-transfer-design.md](2.9project-transfer-design.md)）= 删除链路的反向打包，数据边界同删除链路——同样只带走终态数据（非终态跳过并计数），落盘范围与删除清理半径一一对应。

### 11.5 应用更新影响

- DB 结构变更全部经 `_migrate_add_column` 启动幂等迁移，用户数据不受影响
- 自定义模板 schema 升级：启动时自动迁移，无法自动修复的标记为问题项在模板页提示
- 用户数据与程序资源分离：重装/更新应用不触碰数据目录；NSIS 卸载默认保留用户数据

### 11.6 项目归档（先归档再删除）

投前停止或走完生命周期的项目：**先归档（可逆软关闭），再删除（不可逆物理清理）**。归档只是状态层：列表分组 + 可恢复软关闭，不改变详情页行为（本地单用户桌面应用，API 唯一调用方是自身前端，不做只读穿线与 API 守门）。

**语义与准入**

| 规则 | 说明 |
|------|------|
| 归档可逆 | `archived_at` 非空 = 已归档；恢复即清空，数据零损失 |
| 删除准入 | 仅已归档项目可删：未归档 DELETE 返回 409 `PROJECT_NOT_ARCHIVED`；已归档但有进行中活动同样 409 `PROJECT_HAS_ACTIVE_WORK`（归档仅是状态层，归档后详情页仍可发起活动，删除前必须复查，防 runner 写已删行产出孤儿产物） |
| 活动守门 | 归档与删除端点共用同一活动查询：存在进行中活动（文件解析 pending+parsing / 报告 generating / 填表 pending+filling / Wiki 编译 queued+ingesting+storing / 图片描述 pending+processing）时拒绝，409 `PROJECT_HAS_ACTIVE_WORK`——归档时杜绝「归档后活动仍在写」，删除时杜绝「删除后活动写孤儿」 |
| 周期任务 | 归档项目被 `list_due_phase_tasks` 排除，滚动生成器不再为其铺入新期次（存量任务保留可查） |

**表结构**

`projects.archived_at DATETIME DEFAULT NULL`（DDL 见 [§5.1](#51-projects-表项目与基础库共用)）：NULL = 有效；非空 = 已归档。`list_projects(archived)` 服务端过滤两套列表；`archive_project` / `unarchive_project` 是该列唯一写方。

**数据流**（端点 → IPC → 前端）

| 动作 | 端点（python/routers/knowledge.py） | Electron IPC（ipc-handlers.js） | 前端消费（App.tsx） |
|------|------------------------------------|--------------------------------|--------------------|
| 列表（有效/归档） | `GET /knowledge/projects?archived=` | `knowledge:listProjects` | `loadProjects` / `loadArchivedProjects`（归档集懒加载，首次切 tab 拉取；各自独立请求代际 ref，乱序返回丢弃陈旧集，防双 tab 快速切换错挂列表） |
| 归档 | `POST /knowledge/projects/{id}/archive` | `knowledge:archiveProject` | `handleArchiveProject`（confirmDialog 确认 → invoke → 双列表刷新 → 清选中） |
| 恢复 | `POST /knowledge/projects/{id}/unarchive` | `knowledge:unarchiveProject` | `handleUnarchiveProject`（无确认） |
| 删除 | `DELETE /knowledge/projects/{id}` | `knowledge:deleteProject` | `handleDeleteProject`（409/404 经 errorCodes 映射提示） |
| 导出 | `POST /knowledge/projects/{id}/export` | `projects:exportProject`（showSaveDialog → target_path，600s 超时） | `handleExportProject`（完成 toast；skipped>0 时附「进行中工作未包含」提示；409 防重入；[2.9 §5](2.9project-transfer-design.md)） |
| 导入 | `POST /knowledge/projects/import` | `projects:importProject`（showOpenDialog → source_path，120s 超时） | `handleImportProject`（同步快速校验，400 即时提示 → 后台导入；完成边沿 `handleImportCompleted` 刷新列表并自动选中，[2.9 §6](2.9project-transfer-design.md)） |

归档/恢复/删除三通道 IPC 不走抛错：`structuredPythonResponse` 把 `{error, code}` 响应体转为结构化返回值 `{ok:true} \| {ok:false, code, error}`（Electron `ipcMain.handle` 抛错跨进程仅保留 `message`，`errorCode` 丢失）；三 handler 判 `res.ok` 失败即 `apiErrorText(res.code, ...)` 提示并中止，catch 仅兜网络错误。其余 100+ 通道维持 `handlePythonResponse` 抛错模式（存量通道 fallback 为后端原文，可读性可接受，全局改返回契约破坏面过大不随本次收口）。

错误码（`ERROR_CODE_I18N` → `errors.codes.*` 双语）：`PROJECT_HAS_ACTIVE_WORK`（有进行中活动，拒绝归档/删除）/ `PROJECT_NOT_ARCHIVED`（未归档不可删）/ `PROJECT_ALREADY_ACTIVE`（已有效无需恢复，独立码不与删除共用）。归档零新增轮询（活动守门读库内活动状态，与全局心跳同源）。

## 12. 关键设计决策

| # | 决策 | 理由 |
|---|------|------|
| 1 | 知识库与报告合并为项目 | 目标用户/工作流高度重叠，割裂入口增加认知成本 |
| 2 | 项目类型精简为 3 种（招商/投资/通用） | 覆盖目标用户主场景，避免类型爆炸 |
| 3 | 基础库与项目共用 projects 表（kind 区分） | 文件/检索/Chat 全链路复用，一套 UI 两套 API 仅通道映射 |
| 4 | 预置基础库空库交付，不做预置文档填充 | 预置数据与用户数据冲突难处理；降低包体积；用户自传即用 |
| 5 | 报告引擎为独立模块而非 Agent Tool/Skill | 长流水线（检索-生成-校验-收尾）需要断点/重试/进度管理，不适合塞进 FC 循环 |
| 6 | 阶段可双向点击（非单向推进） | 招商/投资实际流程有回退；看板按阶段归档报告 |
| 7 | 企业信息字段全类型适用 | 工商名称/信用代码是报告变量高频来源 |
| 8 | 向导知识源勾选回写项目关联集 | 勾选即关联，下次向导预勾一致，避免两处状态漂移 |
| 9 | 任务与项目不做功能衔接 | 任务是轻量即时代理；项目知识经任务的知识检索工具访问已足够，避免 UI 耦合 |
| 10 | ~~本阶段报告导出仅 Word/PDF，不做 PPT~~ → 已立项（2026-10-16），已实施 | PPT 交付物改由内置 ppt-master skill 承载（LLM 生成管线，非下游渲染），设计见（2.3） |
| 11 | 项目先归档再删除，归档可逆 | 删除是不可逆物理清理；投前停止或走完生命周期的项目先经归档软关闭（可恢复），删除入口仅出现在归档 tab，防误删。归档只是状态层，不做只读穿线与 API 守门（YAGNI：本地单用户应用，API 无第二调用方） |
