# Wiki（LLM Wiki）功能设计文档

> **概述**：Wiki 系统将项目的碎片化文档逐文件增量编译为结构化 Markdown 知识页面——每个文件经「LLM 分析 → LLM 生成」两步链式思考，创建来源摘要页、更新实体/概念/主题页、产出发现项（REVIEW），并以连续逐文件摄入执行（单文件失败隔离，全程可停止，完成后统一审阅逐文件摘要）。编译结果双向消费：作为报告引擎与 Chat 的高权重检索通道（采信优先级 Wiki > 知识库 > 互联网），以及供用户直接浏览编辑的 Wiki Tab（首页/图谱/时间线/知识体检/知识框架五视图，2026-10-26 IA 收敛）。本文覆盖：定位与 Schema（§1-§2）、数据模型九表（§3）、编译管线与韧性（§4）、健康检查（§5）、增量更新（§6）、浏览编辑（§7）、检索集成（§8）、API/IPC 与前端（§9-§10）、模块实现规格（§11-§12）、差异与下一步（§13）。
>
> 关联：文件解析与知识库分片见 [2.2](2.2knowledge-base-design.md)（chunks_fts 是摄入原文的重建来源）；报告引擎的 wiki 检索通道见 [2.5 §3.3](2.5report-design.md)（本文 §8.2 与其互引）；编译作为长时活动接入活动中心与就绪度校验（[0.4](0.4lifecycle-design.md) §3/§7.3）；Chat 面板是归档入口与查询消费方（[2.1](2.1project-design.md) 项目页结构）。

## 1. 背景与定位

### 1.1 核心理念

引入 **Karpathy LLM Wiki** 范式——知识不是被"存"起来的，而是被**编译**成更有价值的结构。

传统 RAG 的问题：每次提问都从碎片里重新拼答案，答完就散，知识没有积累。LLM Wiki 的思路相反：给 AI 安排一份长期工作——持续维护知识库，每次新资料输入都增量编译，产生**知识复利**。

**核心机制——逐文件增量摄入（Per-Source Ingest）：**

1. **读取完整原文**（从 FTS chunks 重建全文，不碎片化），深入理解全文内容
2. **创建来源摘要页**（source page），记录该文件的关键要点
3. **触碰多个相关页面**——创建或更新实体页、概念页、主题页，建立交叉引用（[[wiki-link]]）
4. **更新全局摘要**（overview）并追加**时间线**（change log）

这种模式确保：知识被**编译一次、持续更新**，而非每次查询重新推导。每摄入一篇资料，知识库的交叉引用更密、综合更深、矛盾更显。

**设计哲学：**

- **高质量整理 > 大规模摄入**：每次摄入深入理解完整原文、建立交叉引用、发现矛盾，比索引更多文件更有价值
- **透明性与可解释性**：Wiki 页面是纯 Markdown，人类可读、可编辑、可审查；不需要知识图谱等重型可视化作为前置依赖（图谱是浏览的增强视图，§7.1）
- **维护成本趋近于零**：更新交叉引用、保持摘要同步、标注矛盾等"记账"工作由 LLM 承担；人类负责策展来源、审阅发现项、纠正错误

**Wiki 的两大核心目标：**

| 目标 | 说明 |
|------|------|
| **服务报告与问答** | 编译产出的结构化结论作为报告生成与 Chat 的高权重上下文（§8），保证一致性和质量 |
| **Markdown 可视呈现** | 页面以 Markdown 渲染后供用户阅读浏览（§7），项目知识"看得见" |

### 1.2 与 RAG 的关系

Wiki 不是替代 RAG，而是 RAG 的**上层建筑**——RAG 负责精准召回（机器检索），Wiki 负责知识沉淀（人 + AI 可读）。

| 维度 | RAG（知识库） | LLM Wiki |
|------|-----------|------------------|
| 知识形态 | 向量切片（机器检索） | 结构化页面（人 + AI 可读） |
| 核心价值 | 精准召回 | 知识沉淀、一致性输出 |
| 人类可读性 | 低（碎片化切片） | 高（完整 Wiki 页面） |
| 知识积累 | 无积累（每次重新拼凑） | 持续编译，产生复利 |

### 1.3 架构：项目 Wiki + 基础库 RAG 直达

从核心目标出发的务实简化架构：

- **项目 Wiki**（本文范围）：将碎片化项目文档编译为结构化结论
- **基础库 RAG 直达**（已实现，见 2.2）：基础库文件通过 RAG 直接检索注入（报告通道与摄入上下文），不做 Wiki 编译
- **基础库 Wiki**（可选延后）：如果未来基础库文件量大到 RAG 质量下降再考虑

```
┌────────────────────────────────────────────────────────┐
│  基础库（RAG 直达，无需 Wiki 编译）                       │
│  ┌──────────────────┐  ┌──────────────────┐            │
│  │ 招商基础库 RAG    │  │ 投资基础库 RAG    │            │
│  └────────┬─────────┘  └────────┬─────────┘            │
│           │  编译上下文注入（§4.5）/ 报告检索通道          │
│  ┌────────┴────────┐  ┌────────┴────────┐              │
│  │ 项目A Wiki       │  │ 项目B Wiki       │              │
│  └─────────────────┘  └─────────────────┘              │
│  项目 Wiki（编译为结构化结论，服务报告与阅读）              │
└────────────────────────────────────────────────────────┘
```

**为什么基础库暂不做 Wiki？** 基础库 RAG 已能精准检索具体条款和数据；编译成摘要反而可能丢失细节；基础库文件量通常有限；减少一层复杂度（重编译时机、跨层一致性等维护成本）。

### 1.4 三层架构映射（Raw → Wiki → Schema）

```
Raw（原始文件）──摄入──▶ Wiki Pages（知识页面）──归类──▶ Schema（结构页骨架）
```

- **Raw**：项目上传的原始文档（FTS chunks 索引，RAG 检索可用）
- **Wiki Pages**：LLM 编译产出的知识页面（动态页面类型，§2.1）
- **Schema**：项目类型的结构页骨架（结构页定义 + 编译指引，§2.2）——结构页由编译过程填充，实体/概念页由 LLM 自主发现

### 1.5 功能目的与工程要求

**功能目的：**

| 编号 | 目的 |
|------|------|
| F1 | 文档上传后一键编译，产出结构化 Wiki（来源页 + 实体页 + 概念页 + 结构页） |
| F2 | 连续编译：逐文件摄入一次跑完（失败隔离不中断），用户可随时停止，完成后在明细面板统一审阅逐文件摘要 |
| F3 | 双向消费：报告/Chat 检索通道 + 用户浏览编辑 |
| F4 | 健康检查：结构层 + 语义层 Lint 与发现项清扫 |
| F5 | 溯源：每页可追溯到源文件（page_sources），变更全程留痕（change_log） |
| F6 | 用户编辑保护：手动编辑的页面不被后续编译覆盖 |

**工程要求（摘要）：**

| 类别 | 要求 |
|------|------|
| 有效性 | 编译完全独立于前端（Tab 切换/窗口关闭/进程重启不影响）；崩溃后可恢复续跑 |
| 健壮性 | LLM 瞬时错误重试、凭据类错误可行动提示；重复触发防重入（409）；空分析/空文本显式失败 |

## 2. Wiki Schema 定义

### 2.0 Schema 共同演化

Schema 不是固定蓝图：结构页（structure）由 Schema 定义并作为编译指引注入；实体/概念/主题/来源页由 LLM 在摄入中自主发现与更新。项目类型无 Schema 时回退 `general`。

### 2.1 动态页面类型

页面类型由编译过程动态决定，存储在 `wiki_pages.page_type`：

| 类型 | 说明 | 来源 |
|------|------|------|
| `source` | 来源摘要页（`src_{file_slug}`），记录单篇源文件关键要点 | 每次摄入必建 |
| `entity` | 具名实体（人、组织、产品、技术） | LLM 识别 |
| `concept` | 概念、方法、理论 | LLM 识别 |
| `topic` | 综合分析主题 | LLM 识别 |
| `structure` | 项目结构页（企业画像、政策匹配等） | Schema 定义 |

**YAML Frontmatter 规范**（PAGE block 元数据，§4.3）：

```markdown
---PAGE: {page_key}---
type: entity
title: {页面标题}
refs: [{相关页面 page_key 列表}]
tags: [{标签列表}]

{Markdown 正文，使用 [[page_key]] 引用其他页面}
---END PAGE---
```

解析侧（§12.2.1）对元数据行做容错处理（缺失字段取默认值：type=entity、title=page_key）。`refs` 是结构化出链（供图谱/搜索/backlinks 计算），正文 `[[wiki-link]]` 会被 lint 补充进 refs 口径。

**wiki-link 互联**：正文中 `[[page_key]]` 或 `[[page_key|显示别名]]` 语法构成页面互联网络；反向链接由 refs 聚合（`GET backlinks`）。

### 2.2 项目结构页 Schema

Schema 存于 `wiki_schemas` 表，应用启动时从 `python/db/wiki_seed.py` 幂等种子化（INSERT OR REPLACE；废弃页 id 按 `RETIRED_SCHEMA_IDS` 显式清理，见下文「Schema 演化」）。每组 Schema 含 `page_key` / `title` / `compile_hint`（编译指引，注入摄入 Prompt）/ `base_lib_search_hints`（基础库检索词，§4.5）/ `position`（顺序）。

**页面生命周期语义**（E2-2026-10 引入，体现在 compile_hint 文本中，不新增表列）：

| 语义 | 说明 | 增量编译写作规则 |
|---|---|---|
| 画像页（profile） | 一次成型、后续小幅修订（企业画像、园区配套、估值参考） | 合并修订，保留已有正确信息；状态变迁型信息（经营/财务指标、实控人与股权、管理层任职、资质等）按时期分段保留历史值并标注数据时点，禁止静默替换（通用规则 8，§4.3） |
| 监控页（ledger） | 台账式，随材料滚动累积（里程碑、政策兑现、风险预警、财务监控） | 新事件**追加**到时间线末尾，禁止改写/删除历史条目，每条记录带日期/期间标注 |

监控页语义是「后阶段陪跑」的结构基础：企业落地/投资交割后的月报、季报、兑付记录、预警事件持续上传，逐份增量摄入自动追加到对应台账页（skip-if-unchanged 队列机制保证只处理新文件，§3.7）；台账页本身 `user_edited` 保护不变（§6.4）。

**Schema 演化与存量数据**：v1→v2 重命名 2 个 page_key（recruitment `policy_match`→`policy_ledger`、investment `financial_health`→`financial_monitor`）。废弃 schema 行由 `seed_wiki_schemas` 按显式清单（`RETIRED_SCHEMA_IDS`）删除；已编译项目的同名旧页面保留在 `wiki_pages` 不自动迁移，由 orphan Lint 提示清理（§5.1）。

Schema 支持 CRUD API（§9.1 schemas 四条路由）用于定制，前端入口为 WikiTab「知识框架」视图（WikiSchemaManager，§10.2）；同类型内重复 page_key 创建返回 409（幂等保护，与 archive 409 同款）。

### 2.3 基础库 Wiki（延后，可选）

基础库知识经 RAG 直接检索注入（§4.5 编译上下文、§8.1 检索通道），不做 Wiki 编译。若未来基础库规模导致 RAG 质量下降，再评估本节扩展。

## 3. 数据模型

九张表 + projects 表新增字段。DDL 定义于 `python/db/database.py`（`# ── Wiki tables` 起），全部含 JSON 文本列与幂等迁移。

### 3.1 wiki_schemas 表

| 列 | 类型 | 说明 |
|---|---|---|
| id / project_type / page_key | TEXT | 主键 / 项目类型 / 页面键（同类型内唯一） |
| title / compile_hint | TEXT | 标题 / 编译指引（注入 Prompt） |
| base_lib_search_hints | TEXT(JSON) | 基础库检索词列表 |
| position | INTEGER | 展示与注入顺序 |
| is_ledger | INTEGER | 1 = 台账页（监控式，只追加，[3.1 §3.4](3.1intelligence-design.md)）：编译后台账结构化解析的范围判定；种子数据已为监控页标注，用户经 Schema 管理视图勾选（四期 T10） |

启动种子化（§2.2）；查询按 `position ASC`。

### 3.2 wiki_pages 表

| 列 | 类型 | 说明 |
|---|---|---|
| id / project_id / page_key | TEXT | 页面键在项目内唯一（UNIQUE(project_id, page_key)） |
| title / content | TEXT | 标题 / Markdown 正文 |
| status | TEXT | draft（默认）/ compiled / user_edited |
| compile_version | INTEGER | 编译版本号，递增时自动写版本快照（§3.8 后述 wiki_page_versions） |
| last_compiled_at / last_compiled_file_id | — | 最近编译时间 / 触发文件 |
| page_type | TEXT | 迁移列：source / entity / concept / topic / structure |
| refs | TEXT(JSON) | 迁移列：出链 page_key 列表（图谱与搜索的边数据） |
| sources | TEXT(JSON) | 迁移列：来源文件 id 列表 |
| tags | TEXT(JSON) | 迁移列：标签列表 |

`status` 语义（2026-10-28 B2 起）：`draft` 仅为 DB 默认值兜底——**无写入路径**（摄入新页直接写 compiled，前端无手动建页入口；原「源文件删除标记」语义已退役为删页，§6.5）；`compiled` 编译产出；`user_edited` 用户手动编辑或矛盾裁决替换（编译跳过保护，§6.4/§5.5）。

### 3.3 wiki_page_sources 表

页面 ↔ 源文件溯源关联：`(wiki_page_id, file_id)` 幂等 upsert，`contribution` 记录贡献说明（如「摄入自 {filename}」）。Lint 的 missing-source 检查依赖本表（§5.1）。

### 3.4 wiki_change_log 表（log.md 等价物）

| 列 | 类型 | 说明 |
|---|---|---|
| action | TEXT | created / updated / ingest / user_edited / deleted / archived / enriched / dedup_merge / source_removed（源文件删除连带清除页面，§6.5；wiki_page_id=NULL、affected_page_keys=[被删页 key]） |
| wiki_page_id | TEXT NULL | 关联页面（页面级动作）；项目级动作（ingest/deleted/dedup_merge）为空 |
| trigger_file_id | TEXT NULL | 迁移列：触发文件 |
| source_title / affected_page_keys | TEXT | 迁移列：触发源标题 / 受影响页面键列表（JSON） |
| summary | TEXT | 人可读摘要（「摄入 X: 创建 N 页, 更新 M 页」等） |

时间线视图（§7.1 ChangeLog）与页面详情的动作历史均读本表。

### 3.5 wiki_reviews 表

| 列 | 类型 | 说明 |
|---|---|---|
| id | TEXT | 稳定 ID：`review_{FNV-1a(project_id::type::title)}`——项目作用域内同 type+title 幂等去重（摄入与 Lint 共用本算法；不含 project_id 会跨项目撞车致发现项串台，review H-1） |
| type | TEXT | missing-page / contradiction / suggestion / confirm / data-gap / stale-claim / empty-page / missing-source / orphan / orphan-review / broken-link / no-outlinks（摄入与结构/语义 Lint 的合集） |
| title / description | TEXT | 标题 / 详情（Lint 产物会附 severity、PAGES、建议链接后缀） |
| evidence | TEXT(JSON) NULL | 矛盾证据结构化（E2-2026-10 迁移列）：`[{page_key, quote}]`——摄入产出的 contradiction 附带两侧原文引用（§4.3 契约），供 Lint 视图两栏对比裁决（§5.5）；存量项与 Lint 产物为空（前端降级为普通展示）；UPSERT 以 COALESCE 保留旧值——Lint 重跑不传 evidence 不得抹除摄入产出的证据（§4.4） |
| affected_page_ids | TEXT(JSON) NULL | 涉及页面 id 列表 |
| resolved / resolved_action | INTEGER / TEXT | 0 待处理；1 已处理（dismiss / create_page / auto_resolved / auto_confirmed——confirm 归档专用，§4.4 / fixed——死链一键修复，§5.4 / adjudicated——矛盾裁决，§5.5） |
| source_file_id | TEXT NULL | 产生该发现项的源文件（文件删除时置 NULL 保留发现项，§6.5） |

### 3.6 projects 表新增字段

| 列 | 说明 |
|---|---|
| wiki_purpose | Wiki 目标（purpose.md 等价物，注入摄入 Prompt，首页可编辑） |
| wiki_overview | 全局摘要（overview.md 等价物，摄入增量更新或按类型自动生成，§4.6） |

## 4. 编译流程（逐文件增量摄入）

### 4.1 编译触发：事件驱动自动 + 通知 + 人工触发（2026-10-27 起自动点火）

文件解析完成自然进入待编译集合（实时口径，§3.7）；触发分两路——**路径 A 自动点火**（全局开关默认开，`wiki/auto_compile.py`）与**路径 B 人工触发**（通知引导，入口保留）：

```
路径 A（自动，事件驱动 + 聚合延迟，2026-10-28 A1）：
文件解析完成（KnowledgeWorker _process_file 成功分支）
  → files.status='done' → 即时计入待编译集合（实时 SQL，无事件写入）
  → 边沿仅登记点火意图 schedule_auto_compile（项目级，首完成起算 60s 不重置
    ——窗口最坏延迟有界；进程内存态，重启丢失 = 该批次退化手动入口，与冷却
    同语义）
  → 5s QueueScanner 周期取出到期项 pop_due_projects（取出即移除，失败不重试）
  → try_auto_compile 六重守卫全过才创建任务：
    ① settings.auto_wiki_compile（全局开关，默认 true）
    ② 项目存在且 kind='project' 且未归档（archived_at IS NULL；基础库不编译，§1.3）
    ③ 待编译集合非空（get_pending_wiki_files）——窗口内后续完成文件由到期时
       集合一次性吸收，批量上传聚合为一次编译（消除「编译比解析快」的碎片化
       小编译：重复 Stage 2 注入已有页面 + UI 噪音 + 编译后挂点多次触发）
    ④ 无活跃编译任务（与下方 409 判定同口径；运行中编译逐轮重查待编译
       集合，新完成文件由当前轮自动吸收，无需点火）
    ⑤ 不在冷却期（stop 端点成功即写该项目 30 分钟冷却，进程内存态、重启
       清零；手动触发不受冷却限制）
    ⑥ LLM/嵌入就绪（readiness 同源缓存判定；未就绪静默跳过 + 日志，不在
       解析链路弹错——配置引导仍由人工入口 guard 承担，0.4 §7.3）
  → create_wiki_compile_task(trigger_type='auto') → enqueue_compile
    （入队失败由扫描器 queued compiles 拾取下一轮兜底重入队，与人工路径同韧性）

路径 B（人工，通知引导）：脉搏带待汇编 chip / 首页空态「开始汇编（N）」
  / 文件完成 Toast「整理进知识页」/ Wiki Tab 状态条
  → guard('wiki_compile') 就绪校验（缺 LLM/嵌入模型引导弹层，0.4 §7.3）
  → POST /wiki/projects/{id}/compile { force: false }（trigger_type='manual'）
```

- **防重入**：存在 `queued/ingesting/storing` 状态任务时返回 409（自动路径以守卫④同口径跳过；守卫检查与任务创建同为同步 DB 操作，事件循环内原子，无 check-then-act 竞态）
- **停止语义**：stop 端点成功即写该项目 30 分钟自动点火冷却——防止「停止后下一文件解析完立刻重燃」使停止形同虚设；冷却仅抑制路径 A，人工触发即刻可用
- 编译逐文件消费待编译集合，完成后计数自然归零（无清零动作——原「触发即清零」随事件计数器废弃一并删除）
- **force 重新编译**：清空项目全部 Wiki 数据（pages/versions/change_log/reviews/source_pages 五表 DELETE + overview 重置；purpose 保留）后从零摄入——前端二次确认对话框（「清除所有 Wiki 页面、版本历史、审查项和变更日志，从零开始」）；触发失败（如 409）时前端保留原页面列表仅 toast 提示，本地清空发生在触发成功之后
- **升级存量**：`auto_wiki_compile` 为 settings kv 新键、缺省即真（无迁移）；存量待编译积压不在启动时补点火（避免升级即全项目烧 token 的成本惊吓），积压仍走路径 B 手动入口，仅新解析边沿点火
- 编译完全独立于前端：任务入队 KnowledgeWorker 编译队列（5s 扫描器兜底重入队），Tab 切换/窗口关闭不影响；自动点火发生在后端解析边沿，同样独立于前端

### 4.2 单文件摄入管线

**V2 逐文件引擎**（`python/wiki/ingest.py` WikiIngestor）——唯一编译路径：

```
Step 1  准备上下文
        - 全文重建：chunks_fts 按 chunk_{file_id}_% 前缀 rowid 序拼接（>100K 字符截断）
        - purpose / overview（projects 列）
        - schemas（项目类型，空则回退 general）→ schema_hints
        - index_summary：现有页面每页一行「[type] key: title — 内容前 120 字」
        - base_lib_context：Schema 检索词 × 已关联基础库 RAG top-3，上限 30 条（§4.5）
        - 空文本（无文本 chunks，如纯扫描件/空文件）→ skipped：写
          wiki_source_pages(status='skipped') 留痕后跳过，CompilePanel 计入「跳过」
          ——不再进入待编译集合（否则每轮增量重复撞同一文件且计入 completed，
          伪装成功；修复后条件不变的文件无重试意义）
Step 2  LLM 分析（第一次调用）
        输入=原文+上述上下文；输出=结构化分析（key_entities / key_concepts /
        recommended_pages / cross_source_findings / contradictions /
        suggested_base_lib_queries）
        max_tokens 经 floor 抬升（llm/budget.py，≥32K，不在此覆写）；reasoning_effort 沿用用户设置
        防护：分析结果 <50 字符视为 LLM 静默失败 → failed + LLMNetworkError
Step 3  LLM 生成（第二次调用）
        输入=原文+分析结果+已有页面内容（每页前 2000 字，总量 30K 上限；
        截断按整页粒度——放不下整页即止，不切半页）
        输出=PAGE block（含 frontmatter）+ REVIEW block + OVERVIEW block（§4.3）
Step 4  存储与追踪
        - user_edited 页面跳过不覆盖（§6.4）——以落库前实时状态重读判定
          （Step 1 快照在两次 LLM 调用的分钟级窗口内会陈旧，矛盾裁决可能
          恰落在窗口内，§4.4），计入「处理」但不记 updated
        - 新页 create（page_type/refs/sources=[file_id]/tags）；旧页 update
          （compile_version+1 → 自动版本快照）
        - 每页 add_wiki_page_source（幂等溯源，§3.3）
        - reviews：稳定 ID 幂等写入（affected_page_ids 解析 + source_file_id +
          evidence——contradiction 的 EVIDENCE 行解析为 [{page_key, quote}] JSON）
        - RESOLVES 归档：解析 `---RESOLVES: {编号}---`，按 Stage 2 注入的缺口
          编号映射 review_id → auto_resolved（缺口闭环，§4.3/§4.4）
        - wiki_source_pages upsert（content_hash / pages_touched）
        - change_log：action=ingest，summary=「摄入 {文件}: 创建 N 页, 更新 M 页,
          K 个发现项」，affected_page_keys 排除 user_edited
        - overview：LLM 提供 OVERVIEW block 则截 3000 字更新；否则按页面类型
          分组自动生成（「实体（N 页）: ...」）
```

**连续编译循环**（`task_queue._run_per_file_ingest`）：

```
loop:
  stop_requested? → stopped（用户主动，通知静默）→ 结束
  get_pending_wiki_files（排除已处理）为空? → completed（pages_total=实际处理数，
    终态事件 complete_compile）→ 结束
  摄入下一文件（任务状态由本循环管理）+ append_ingest_summary
    （成功记 result 摘要；失败记 actionable error 摘要——不中断队列，
     含凭据类错误，修正后重新编译即重跑失败文件）
```

worker 崩溃恢复衔接：启动扫描把 ingesting/storing 重置为 queued，扫描器重新入队；`compile-status` 端点以「queued 且已有 ingest_summaries」判定 is_resumed，前端顶栏显示「上次编译被中断，已从第 N 个文件恢复继续」。

**LLM 调用韧性**（`_chat_with_retry`）：ingest 任务模型路由（§12.2.13）；每 attempt 硬超时（`llm_read_timeout + 60s`，防 API 挂起）；瞬时错误（网络/5xx）重试 2 次、退避 15s/30s；凭据类错误（Key 失效/限流/欠费/模型名错）不重试直接冒泡，由任务层转 failed + 可行动文案（0.4 §7.3）。

### 4.3 摄入 Prompt 结构（两步式）

**领域角色注入**（按 `project.type`，两阶段 System 共用）：

| 类型 | 角色设定 |
|---|---|
| recruitment | 园区招商引资顾问，服务企业全生命周期（线索评估 → 落地推进 → 投产后监管服务）；分析材料始终围绕企业与本项目的匹配度、政策匹配与兑现、落地可行性、投产后经营与履约风险 |
| investment | 投资机构分析师，覆盖尽调 → 投决 → 投后 → 退出全流程；分析材料始终围绕投资价值与风险定价、财务真实性与健康度、条款保护（对赌/优先权）、投后监控信号与退出路径 |
| general | 不注入领域角色（保持通用知识分析/编译定位） |

**Stage 1 分析 Prompt**（`build_ingest_analysis_prompt`）：

- System：**领域角色（按 project_type）** + purpose / overview + 页面类型规则（五类）+ 输出要求（六部分结构化文本：key_entities / key_concepts / recommended_pages（page_key、type、action create/update、reason）/ cross_source_findings / contradictions / suggested_base_lib_queries）
- User：原始资料（全文）+ 当前 Wiki 索引（index_summary）+ 结构页编译指引（schema_hints）+ 基础库参考

**Stage 2 生成 Prompt**（`build_ingest_generation_prompt`）：

- System：输出格式契约——
  - PAGE block：`---PAGE: {page_key}---` + frontmatter（type/title/refs/tags）+ Markdown 正文 + `---END PAGE---`
  - 来源摘要页必须创建：`src_{file_slug}`，type: source，refs=本次触碰页面，要点列表
  - REVIEW block：`---REVIEW: {type} | {title}---`（type：missing-page / contradiction / suggestion / confirm / data-gap）；contradiction 须在 description 开头为每一侧写证据行 `EVIDENCE: [[{page_key}]] 「{最小对立原文}」`（两侧各一行、原文照抄尽量短——落库为 evidence JSON，裁决替换的依据，§4.4/§5.5）
  - RESOLVES block（缺口闭环，E2-2026-10）：User 注入未解决缺口编号清单（data-gap / missing-page，含截断描述）时，LLM 认定本文件确实补上某缺口则在输出末尾输出 `---RESOLVES: {缺口编号}---`（可多行；未补上不输出）——后端按编号确定性映射 review_id 归档，用户无需回访核对（§4.4）
  - OVERVIEW block：末尾输出更新后的全局摘要（1-2 段浓缩）
  - 八条规则：必建来源页；正文必须用 `[[page_key]]` 引用；增量补充不覆盖正确信息；冲突保留各方并标注来源时间；无法确认标「待核实」；发现缺失/矛盾/建议输出 REVIEW；监控页追加规则（E2-2026-10）：compile_hint 声明为台账/监控语义的页面，新事件追加到时间线末尾，禁止改写或删除历史条目，每条记录带日期/期间标注；画像页时间演化规则（E2-2026-10）：画像页中随时间变化的信息（经营/财务指标、实控人与股权、任职、资质等）更新时按时期分段保留历史值、新旧值各标注数据时点，禁止静默替换
- User：原文 + 分析结果 + 已有页面内容（增量参考）+ 编译指引 + 基础库补充

**输出解析**（`parse_compile_output_v2`，§12.2.1）：正则提取三类 block；frontmatter 元数据行容错解析（缺失默认值）；REVIEW type 白名单过滤；OVERVIEW 提取。EVIDENCE 行提取（contradiction 证据，E2-2026-10）：`EVIDENCE: [[page_key]] 「quote」` 逐行正则提取为 `[{page_key, quote}]` 并从 description 剥离（中英引号容错）；`---RESOLVES: {编号}---` 提取（缺口闭环，§4.3）：容忍逗号并列与多余空白，返回编号列表供 ingest 映射归档。

### 4.4 REVIEW 协议

摄入与 Lint 产出统一进入 `wiki_reviews`（§3.5）：

- **稳定 ID**：`FNV-1a(project_id::type::title 小写)`——同一问题重复出现幂等更新而非堆积；跨项目同标题互不干扰（review H-1）
- **confirm 自动归档**：摄入产出的 confirm（「材料与百科吻合」类正面结论）不是待办——落库即 `resolved=1, resolved_action='auto_confirmed'`，不占 Lint 待处理列表；存量 pending confirm 由启动迁移一次性归档（幂等）
- **矛盾 evidence 全链路**：Stage 2 按契约输出 EVIDENCE 行（§4.3）→ parser 提取 `[{page_key, quote}]`（§12.2.1）→ 落库 evidence 列 → Lint 对比卡两栏展示 → adjudicate 端点对被否决侧执行 quote→选中侧 quote 的**确定性全量替换**（不经 LLM）→ 替换侧页面 status=user_edited（编译保护，§6.4）+ compile_version+1 自动版本快照 → 全部替换成功才 `resolved=1, resolved_action='adjudicated'`；任一侧失配（页面不存在 / quote 已不在页面）则保留待处理并返回逐侧明细，宁可留待人工不误归档（§5.5）；重试时已被上轮替换为选中侧结论的页面视为达成（already_applied，不产生写操作）——三侧以上部分失败修复后可重试归档；裁决与编译互斥——编译进行中 409 拒绝（与 trigger_compile 同一防重入模式），ingest Step 4 亦实时重读 user_edited 兜底
- **缺口自动闭环**：摄入时查未解决 data-gap/missing-page 注入编号清单（§4.3）→ 用户新上传的文件补上缺口 → RESOLVES 编号映射 → `auto_resolved`——清单自动消失
- **消费路径**：Lint 视图治理工作台（§5.5）逐类处置：矛盾对比裁决 / 缺口补料上传 / 死链分型修复；sweep 两阶段自动解决（§5.3）；`create_page` 动作保留给「为缺失概念建页」的场景（当前前端仅 dismiss）
- **生命周期**：关联页面全部删除时 orphan-review 检查提示清理（§5.1）；源文件删除时发现项保留仅解除文件关联（§6.5）

### 4.5 基础库关联规则

摄入上下文的基础库知识注入（`_collect_base_lib_context`）：

```
for schema in schemas:
    for hint in schema.base_lib_search_hints:   # §2.2 定义的检索词
        for lib in 已关联基础库（project_base_libs）:
            KnowledgeSearchTool.search(query=hint, project_id=lib.id, top_k=3)
→ 拼接「[库名] 片段内容」，上限 30 条
```

即：结构页的检索词决定注入哪些基础库知识；基础库无关联或无命中时静默为空（不阻断摄入）。

对齐参考实现中的四导航文件，本系统 DB 化承载：

### 4.7 编译状态与韧性

**状态机**：

```
queued → ingesting（stage: read_source / stage1_analysis / stage2_generation）
       → storing（stage: store）
       → completed / failed
       ↘ stopped（用户停止，当前文件完成后生效）
```

**失败隔离**：单文件失败（含凭据类）记 actionable 文案入 ingest_summaries，不中断队列；修正问题后重新编译即重跑失败文件（已成功文件不在待编译集合）。任务级无重试机制。

**前端状态展示**（WikiTab 顶栏）：

| 状态 | 展示 | 操作 |
|---|---|---|
| queued | 排队中... | — |
| ingesting / storing | 摄入文件内容... / 保存知识库... + N/M **文件**（pages_completed/total 实为文件数，量词归位——2026-10-26 修复旧「页面」错位，免培训 §2.10） | 状态条「停止」（无队列暂停，0.4 §6.7 修订） |
| completed | 产出导向（2026-10-26 免培训 §2.10）：「新增 X 页 · 更新 Y 页」（自 ingest_summaries 聚合 pages_created/pages_updated，说结果量不说过程量）；零产出明示「(N 个文件，未产出知识页)」（历史脏任务不再让文件数冒充产出）；含失败明细时「N 成功, M 失败」+「重试失败」入口（§13.3） | 重新编译（force）、导出 docx（§14） |
| failed | 失败原因（仅运行前校验失败，如项目已删除；文件级失败一律 completed 携「N 成功, M 失败」明细，不触发任务级 failed，见「失败隔离」） | 重试（重新触发增量）、重新编译 |
| stopped | 已停止 N/M | 继续编译（增量续跑）、重新编译 |

崩溃恢复横幅（is_resumed）+ 编译明细面板（CompilePanel，内嵌可折叠不遮内容：逐文件摘要列表 + 成功/失败/跳过计数 + 触碰页面 + 发现项计数；用户点「查看详情」或触发编译时展开，**不随活跃任务自动弹出**——2.6 §10 修订）。编译状态由父组件统一轮询下发（明细面板展开时 2s 高频，0.4 §8.1），终态自动刷新页面与发现项列表。

### 4.8 编译后画像提取（industry profile，2026-10-25）

编译终态（completed）后的附加提取步骤（`python/wiki/profile_service.py`，与 3.1 台账解析同模式）：把 Wiki 全局摘要/页面中的产业链知识结构化为项目产业画像，供订阅创建预填 `{产业}` 占位符（[2.11 §8.1](2.11scheduled-task-design.md)「从项目画像」渠道）。

**触发与执行**：`task_queue._run_per_file_ingest` completed 分支，在台账解析挂点旁经 `run_in_executor` 后台线程直调 `on_compile_complete_sync` —— 不阻塞 worker 事件循环；整体吞异常（提取失败绝不影响编译主流程，记日志、画像保持旧值，下次编译自动重试）。活动模型：kind=`profile_extract` 经 FunctionSource 注册进活动注册表（同 `ledger_parse`；进程内存态 `_RUNNING`，不建任务表——崩溃恢复依赖上游编译重放，提取是编译纯下游）。

**提取输入与产出**：输入 = `projects.wiki_overview` + 已编译页面内容（每页截断，总量受控）；一次 LLM 调用（llm_routing 档位 `profile` → settings 键 `wiki_profile_model`，未配置则全局默认档）；产出 = `[{"chain": "...", "segment": "..."}]` JSON 数组（chain=产业链名、segment=细分领域，可为空串；上限 5 条，白名单清洗后回写 `projects.industry_profile` + `profile_source='wiki_compile'`）。识别不出任何画像 → 存 `'[]'`（与 NULL=未提取区分，前端空态文案不同）。**manual 保护**：`profile_source='manual'` 的行自动提取跳过（人工修正优先）；显式「重新提取」动作（POST `/knowledge/projects/{id}/profile/extract`，[2.1 §7.3](2.1project-design.md)）可覆盖 manual——入口在画像行操作区，活动经注册表暴露进行中态。无已编译页面且 overview 为空 → 直接返回不动现状（不产空提取）。

**不改编译本体**：画像提取不触碰 ingest prompt 与 V2 解析器，纯编译 done 后下游步骤；不进入 `wiki_compile_tasks` 状态机与 ingest_summaries。

## 5. Wiki 健康检查（Lint）

### 5.1 结构层 Lint（无需 LLM）

`run_structural_lint`（`python/wiki/lint.py`）——确定性检查，快速免费：

| 检查 | 条件 | 修复建议 |
|---|---|---|
| empty-page | 内容为空或 <50 字符 | — |
| missing-source | 有内容但无 page_sources 溯源 | — |
| orphan | 无任何入链（页面数 >1 时） | suggested_source：最相关页面（token 重叠 cosine） |
| broken-link | 出链目标页面不存在 | suggested_target：bigram + Levenshtein 最相似页面 |
| no-outlinks | 无任何出链（页面数 >1 时） | suggested_target：同 orphan 算法 |
| orphan-review | 发现项关联的页面已全部删除 | — |

建议算法要点（实现规格见 §12.2.5）：token 索引（CJK 单字 + bigram + 非CJK词）+ cosine 归一化打分（相关页阈值 0.08）；死链建议用 Levenshtein 相似度（slug/短名/标题三路取最大，阈值 0.74，精确 basename 0.96 / 包含 0.82）叠加 bigram 命中加成。

**finding 契约（E2-2026-10 修订）**：每个结构类 finding 携带 `pages=[page_key]`，经 §5.4 落库为「PAGES:」行——前端据此渲染涉及页面跳转与死链修复的源页面定位（此前仅语义层有 PAGES 行，死链修复无从下手）；死链 title 携带 `[[dead_key]]`（供前端提取死链键与 sweep Stage1 提取）。

### 5.2 语义层 Lint（LLM 驱动）

`run_semantic_lint`（`python/wiki/semantic_lint.py`）——单次 LLM 调用审查全部已编译页面（仅 compiled/user_edited 且非空）：

- **五维度**：contradiction（跨页矛盾）/ stale（过时声明）/ missing-page（重要概念无专属页）/ suggestion（值得加入）/ explore-next（主动建议探索方向：补充资料 / 深入问题 / 页面合并）
- **输出格式**：`---LINT: {type} | {severity} | {title}---` block（severity: high/medium/low，PAGES 行列涉及页面）
- **missing-page 后置过滤**：LLM 常把已有页面报为缺失——对 page_key / title / basename 做 NFKC 归一化精确匹配，命中即滤除
- **语言匹配**：detect_language 自动检测 Wiki 主语言并注入输出语言指令（§12.2.14）
- token 节约：页面摘要（前 500 字 + tags 前 5）而非全文；lint 任务模型路由（§12.2.13）

### 5.3 Review 清扫（sweep-reviews）

`python/wiki/sweep_reviews.py` 两阶段自动解决（**触发：编译终态自动治理链，§12.2.16**——手动端点与 Lint 视图按钮已随 E3-2026-10 减点击改版删除；Stage1 纯本地，Stage2 复用治理链注入的 LLM 客户端）：

- **Stage 1 规则匹配**（快速免费）：missing-page / broken-link 的 title 提取页面引用（`[[...]]` 或「Type: 名 称」模式），页面现已存在 → auto_resolved；orphan 的页面现已入链 → auto_resolved——orphan title 由 lint 携带 `[[page_key]]`（E2-2026-10 修订：此前裸标题无法对应 inbound counts 的 key 口径，orphan 自动解决永不生效；现在 lint 出 title、sweep 消费点对 inbound counts 做同规则归一化匹配）
- **Stage 2 LLM 语义判断**（可选）：剩余项 40 条/批、最多 5 批（200 条成本上限）；LLM 对照页面索引返回 resolved/pending JSON；**保守策略**——解析失败或调用失败整批保持 pending

### 5.4 Lint 执行方式

`POST /wiki/projects/{id}/lint { mode }`：

- `structural`：纯本地，无需 LLM 就绪
- `semantic` / `full`：依赖 LLM，前置 `ensure_ready("wiki_compile")` 准入校验
- 全部 findings 统一写 `wiki_reviews`（稳定 ID 幂等）：语义类附 `[severity]` 前缀与 PAGES 行；结构类附 PAGES 行（§5.1 finding 契约）与建议链接后缀（「建议关联页面: [[X]]」/「建议链接到: [[X]]」）；无前缀发现项（摄入管线产出等）由前端按类型回落默认级别（contradiction=高 / stale・missing-page・data-gap=中 / suggestion・explore-next=低），避免整列「信息」致级别筛选失效
- 前端 Lint 视图（§7.1）：三模式触发、逐条/批量 dismiss、点击跳转涉及页面、**死链一键修复（真实修复；E3-2026-10 改服务端写路径）**——从 title 提取死链键、从 PAGES 行定位源页面 → `POST pages/{key}/fix-wikilink`（§9.1）：服务端正则替换 `[[dead]]`/`[[dead|别名]]` → `[[target]]`，不经用户编辑器写回——**不置 user_edited**（页面保持编译可更新，§6.4）+ 版本快照 + change_log(link_fixed) → 成功后 resolveReview(fixed)；源页无匹配（发现项已过时，页面已被修改）或无法定位源页时警示且不产生写操作。写路径以**读取时原文为 CAS 条件**（review M-1 2026-10-27：编译终态后台治理链与用户写路径并存，`UPDATE ... WHERE content = 读取快照` 防读-改-写丢失更新；失配返回 content_changed）——前端与「发现项已过时」分型提示（内容刚被其他操作修改，请刷新重试），自动治理链侧不核销发现项（§12.2.16）

### 5.5 发现项治理工作台（Lint 视图，E2-2026-10 第二步）

Lint 视图从「逐条忽略器」升级为治理工作台，按类型提供差异化处置：

**顶部治理面板**：按类型分组计数 chips（死链/矛盾/缺口/缺页/建议/孤儿…），点击即筛选——治理量一目了然，逐类清零。

**矛盾对比卡**（contradiction 且 evidence ≥2 条）：
- 两栏并排：每栏 = 出处页键 + 原文引用，附「查看页面」跳转；「以此为准」→ `POST /projects/{id}/reviews/{rid}/adjudicate { chosen: 索引 }`
- 后端对其余各侧页面执行 quote → 选中侧 quote 的替换（**替换以读取时原文为 CAS 条件**，review M-1 2026-10-27：防读-改-写窗口丢失更新，CAS 失配 content_changed 与原文失配同走下述 LLM 重定位纵深），**逐侧返回明细 status 四态**（E3-2026-10）：`replaced`（直接替换；重试时已应用侧视为达成 already_applied）/ `relocated`（原文失配但 **LLM 重定位**成功——以页内容喂 LLM（超 12000 字符截断，档位 lint）提取该原文的当前形态，输出过存在性校验（不在页内即弃，防幻觉）后替换）/ `vanished`（原文已消失——矛盾大概率随页面编辑消除）/ `manual_needed`（LLM 不可用、页超长截断或重定位失配——留人工）。替换侧 status=user_edited（编译保护）+ 版本快照；全部侧成功才 adjudicated 归档；任一侧未达成则保留待处理，前端逐侧呈现四态文案；编译进行中 409 拒绝（与并发摄入互斥，§4.4）且**前端前置禁用按钮**（compiling 下发，防无效点击）
- **vanished 终态卡**（E3-2026-10）：裁决未达成且存在 vanished 侧时，发现项卡内呈现终态决策卡——「矛盾已消除，标记解决」（resolveReview dismiss）/「打开页面核对」（跳转该页）——一次点击收尾，不让用户裸翻各页找；**仍有 manual_needed 侧时不出此卡**（review m-4 2026-10-27：「矛盾已消除」不成立，一键归档会连人工侧一起收掉）——改出「未更新」引导文案 + 「打开未更新页面」按钮（指向 manual 侧而非 vanished 页），人工处理完再归档
- 无 evidence 的存量矛盾（列上线前产出）：降级普通展示 + 提示手动核对

**缺口补料卡**（data-gap / missing-page）：
- 「上传补充材料」：内嵌文件选择 → `knowledge:uploadFile` 直传本项目知识库（复用上传通道，自动进解析队列）
- 上传后引导增量编译：Stage 2 注入缺口编号清单（§4.3），LLM 认定补上即 RESOLVES → auto_resolved——清单自动消失

**死链分型卡**（broken-link，前端实时分型兼容存量）：

| 分型 | 判定 | 处置 |
|---|---|---|
| 来源页缺失 | 死链目标 `src_` 前缀 | 提示来源文件未摄入/已删除 → 触发增量编译或忽略 |
| 结构页缺失 | 目标键 ∈ getSchemas 集合 | 提示结构页尚未编译 → 触发增量编译 |
| 疑似异名/幻觉 | 其余 | 有建议目标 → 一键修复（§5.4）；无建议 → 人裁（开源页手改或忽略） |

**清扫审查**（E3-2026-10 起无手动入口）：编译终态自动执行（§12.2.16），结果经通知中心（kind=governance）+ 时间线（change_log governance）+ 本视图列表呈现；原 header 按钮与 `wiki:sweepReviews` 通道已全链删除。**治理完成实时刷新**（review M-2 2026-10-27）：治理通知到达时 ActivityMonitor 广播 `app:governance-done`（窗口 CustomEvent，携 projectId），已打开的体检视图监听即重载发现项与 dedup 组——不依赖用户手动刷新或重新挂载（通知点击导航为兑底路径）；广播先于批量 Toast 分支派发（复审补口 2026-10-27：批量分支提前 return 不发逐条 Toast，治理信号不依赖 Toast、不缺席），编译详情面板（ProjectDetailPage）监听同一信号补拉快照刷新治理摘要行。

**重复页治理面板**（E3-2026-10 改造：检测自动化、合并批量化）：检测结果由自动治理链落库 `wiki_dedup_groups`（§3.9/§12.2.16），本面板**挂载时只读消费** `wiki:listDedupGroups`，无组不渲染面板；组卡 = 多选框 + 置信徽章 + 理由 + canonical radio 单选（按组 id 键控，默认首 slug）+「合并（N → 1）」与「忽略」（`wiki:dismissDedupGroup` → status=dismissed，重新检测不复活）；底部批量栏「合并所选（N 组）」多组一次确认 → 逐组 `wiki:dedupMerge`（LLM 内容合并 + 全站链接重写，§12.2.10；携 groupId 回写 status=merged），单组失败不中断、失败组保留供重试或忽略；**truncated 页（合并本身成功但仅部分正文并入，组后端已置 merged）随成功组移除并出独立 info 提示**（review m-3 2026-10-27：不再计入失败组伪装「可重试」）；**合并动作编译进行中前置禁用（重扫按钮同）** + 后端 409（review s-1/s-2 2026-10-27：最重写操作与编译互斥）；确认框单组/多组分义文案（列出将合并的页、保留哪页、其余并入后删除）；项目切换清空面板。

## 6. 增量更新机制

### 6.1 更新触发（事件驱动自动 + 通知模式，2026-10-27）

文件解析完成 → 计入待编译集合（实时口径，§3.7）→ 自动点火增量编译（§4.1 路径 A，全局开关 `auto_wiki_compile` 默认开；手动停止后 30 分钟冷却）或用户手动触发（§4.1 路径 B）。文件内容变更经重新上传产生新文件记录，进入下次编译（§3.7）。开关入口：设置页「处理并发」区「自动汇编」（`settings.concurrency.autoCompile`）。

### 6.2 增量编译策略

每次编译处理全部 pending 文件（无 ingested 记录，已摄入文件由 get_pending_wiki_files 排除）。逐文件串行连续执行——每份新材料的分析结果影响下一份的摄入上下文（index_summary / overview 随之更新）；单文件失败隔离（§4.7），不再逐文件暂停等待人工确认。

### 6.3 冲突处理规则

由 Stage 2 Prompt 规则约束（§4.3）：增量更新在已有内容基础上补充、不覆盖正确信息；信息冲突时保留各方说法并标注来源与时间；无法确认的信息标注「待核实」。跨源矛盾同时产出 contradiction 发现项供用户裁决（§4.4）。

### 6.4 更新范围控制：用户编辑保护

`status=user_edited` 的页面在摄入 Step 4 跳过（LLM 生成内容不覆盖用户编辑），计入「已处理」但 change_log 不记 updated——Step 4 以落库前实时状态重读判定（矛盾裁决/手动编辑发生在两次 LLM 调用窗口内时依然受保护，§4.4）。用户编辑入口：页面编辑器（§7.2）、Chat 归档页（§8.4）。

### 6.5 源文件删除对 Wiki 的影响

`cleanup_wiki_data_for_file`（文件删除时调用）：

- 删除 wiki_source_pages 摄入跟踪（先读 pages_touched）
- 删除该文件的全部 wiki_page_sources 溯源关联
- wiki_reviews.source_file_id 置 NULL（发现项保留，仅解除文件关联）
- **无剩余来源的 compiled 页直接删除**（2026-10-28 B2，替代原「标记 draft」）：
  - 理由：draft 无任何消费方与重编译路径——删除不点火编译（待编译集合是文件维度）、
    前端零消费 draft（Wiki Tab 照常可读、无置灰标记）、报告/Chat 不采信（§8.2）——
    滞留即死状态，且错误/敏感源文件的页面内容残留可读
  - 复用 delete_wiki_page 级联语义（死链 refs 剥离、他页引用清理、reviews 摘除），
    change_log 补记 action=source_removed（wiki_page_id=NULL 留时间线痕迹，§3.4）
  - 多来源页保留 compiled（剩余来源仍有效，内容随下次编译自然更新；单文件内容的
    级残留无法靠页面级操作消除，依赖下次编译，危害有限——不做页面重建，B1 评估过
    成本不成比例）
  - user_edited 页永不动（用户手工内容）；存量 draft 滞留页不清理（写入路径已断绝、
    量极小且无消费方，避免为极小存量引入删用户数据的迁移风险）

### 6.6 项目删除时 Wiki 级联清理

项目删除时随外键/级联清理全部 Wiki 数据（九表按 project_id 关联，含 wiki_dedup_groups ON DELETE CASCADE，§3.9），无独立流程。

### 6.7 Schema 变更处理

Schema 增删改（API，§9.1）不触发自动重编译：新增结构页在下次编译时作为指引注入；已删结构页对应的已有页面保留（其 page_type 仍为 structure）。Lint 的 missing-page / explore-next 可发现结构缺口。

## 8. 与 Chat / 报告生成的集成

### 8.1 知识优先级

三通道采信优先级 **Wiki > 知识库 > 互联网**（`python/report_generator/retrieval.py` 引用本节）：Wiki 页面是已编译的结构化"骨架"（一致、去重、带交叉引用），优先于原始碎片切片；互联网结果最末（时效性补充）。

### 8.2 报告生成集成

报告引擎检索主流程的 wiki 通道（详见 [2.5 §3.3](2.5report-design.md)，本节述 Wiki 侧契约）：

- **页面集**：仅 `compiled` / `user_edited` 状态页面（draft 未定稿不采信）
- **检索**：`search_wiki`（关键词 + 图邻居扩展，§12.2.7）——报告引擎按项目一次取全量页面集，逐节复用（`pages` 参数避免重复全表加载）
- **启用判定**：项目存在可采信页面即自动启用（`_detect_wiki_available`），无用户开关；通道降级语义与知识/互联网通道一致（2.5 §3.3 降级表）
- **截断**：每页 content 前 800 字符进知识卡片
- 通道实现存在一处返回值解包缺陷（空结果分支二元组），登记于 2.5 §7.1

### 8.3 Chat 接入 Wiki

项目 Chat 的 RAG 流程（`python/knowledge/rag.py` `_search_wiki_context`）：

```
用户消息 → search_wiki(query, top_k=5×2, enable_graph)
         → 上下文预算截断（context_budget：wiki 预算 = 窗口 50%，单页
           max(5000, 预算×30%)，§12.2.12）
         → 上下文组装：Wiki 页面区块（「=== Wiki 知识页面（结构化参考）===」）
           置于「原始知识库片段」之前——高权重骨架
         → sources 标注 content_type=wiki_page（引用面板区分展示）
```

异常静默降级（Wiki 检索失败仅告警，不影响 Chat 主流程）。

### 8.4 查询结果归档（Query → 知识复利闭环）

Chat 面板对回答执行「归档到 Wiki」：

- `POST /wiki/projects/{id}/archive { title, content, page_key?, source_question }`
- page_key 缺省 `chat_archive_{时间戳}_{随机后缀}`（防同秒碰撞）；已存在返回 409
- 归档页 status=**user_edited**（享受编辑保护，后续编译不覆盖）+ change_log(archived「从 Chat 归档: {问题前100字}」）

### 8.5 对质量的影响

- 报告：高权重的已编译结论替代碎片拼凑，跨章节口径一致；引用可溯源（wiki_page 类型的 source）
- Chat：结构化骨架先行，减少碎片误导；归档闭环让一次性回答沉淀为持久知识
- 代价：编译消耗 LLM 调用（每文件两次）；逐文件串行耗时与文件数线性相关，长时间编译可随时停止（已完成文件保留，重入增量续跑）

## 12. Python 模块实现规格（python/wiki/，15 文件）

### 12.2.1 Frontmatter 解析（parser.py）

`parse_compile_output_v2`（三元组 pages + reviews + overview；PAGE block 含 frontmatter 元数据行 type/title/refs/tags + OVERVIEW block）。元数据行容错：`[a, b]` 与 `- a` 两种列表风格；缺失默认 type=entity、title=page_key。块首/元数据行之间的空行不再终止 metadata 区（向后看首个非空行，仍是 meta 行则继续收集）——修复块首空行导致整块 frontmatter 被丢弃；权衡：正文首行恰为 meta 样式（如 `refs: x`）会被并入 metadata，属可接受契约。LINT block 解析（供语义 Lint）：type 别名归一（stale-claim→stale、data-gap→missing-page）、severity 白名单（非法回退 medium）、PAGES 行提取剥离。解析到 0 页时输出完整 LLM 原文告警日志（含 ``` 包裹/格式回显等常见失败模式提示）。

### 12.2.2 图谱数据分析（wiki_graph.py）

`get_graph_data(db, project_id, include_insights)`：wiki_pages.refs 构建有向图（仅指向存在页面的有效边）；节点附 type/label/linkCount/status/inDegree/outDegree/community。社区检测 Louvain（无向化、seed=42、失败回退单社区）。

### 12.2.3 图谱洞察（集成在 wiki_graph.py）

`_compute_insights`：**surprising connections**——跨社区边 +3、实体↔概念跨类型 +2、端点度 >5（hub）+1、无共同邻居 +1，总分 ≥3 入选取 top 20；**knowledge gaps**——孤立节点（总度 ≤1）、稀疏社区（内聚度 <0.15）、桥节点（连接 ≥3 社区，单点风险）。

### 12.2.4 Wiki-link 自动补全（wiki_enrich.py）

安全补全四步：候选词收集（各页 page_key 分段 + title，排除自身）→ LLM 对照正文返回 JSON 建议列表（术语→目标页，仅首次出现、跳过通用词，≤15 条/次）→ **代码执行替换**（LLM 不改写正文：首次出现 + 词边界校验 + 不嵌入既有 [[...]] 内 + 目标去重）→ 保留 frontmatter 区不补。入口：POST enrich-wikilinks——前端：Reader「补全链接」按钮（§10.2）。**并发防护**（复审 Major 2026-10-27）：入口编译进行中 409（与 fix-wikilink/adjudicate/merge 同互斥口径）；LLM 补链是秒级读-改-写窗口，写回以读取时原文作内容级 CAS 条件（update_wiki_page_content expected_content 参数，与 §5.4/§5.5 写路径同族）——窗口内用户编辑/治理链先行写入则拒绝整页覆盖（reason=content_changed），LLM 建议整批丢弃、无 enriched 时间线，前端 warning 提示 + 刷新详情。

### 12.2.5 结构层 Lint（lint.py）

§5.1 六检查的实现规格。索引构建：token 索引（title+slug+正文前 4000 字分词）与 CJK bigram 索引（title+slug+正文前 1000 字）；入链计数（refs + 正文 [[链接]] 补充口径）。建议算法常量：死链建议阈值 0.74、相关页阈值 0.08、basename 精确 0.96、包含 0.82、CJK 单字权重 0.35、候选上限 64、bigram 加成上限 0.15、公共 token 跳过（命中 >25% 页面数）。Levenshtein 双行 DP + 长度差预筛（>50% 直接 0 分）。

### 12.2.6 Chat 归档（routers/wiki.py archive 端点）

§8.4：随机后缀防碰撞 page_key、409 冲突、user_edited 状态、change_log(archived)。前缀级「从 Chat 归档」+ 问题前 100 字。

### 12.2.7 Wiki 检索引擎（wiki_search.py）

当前实现两路：**① 关键词**——page_key 精确匹配 +200、标题含完整短语 +50、正文短语每现 +20（计 10 次）、标题 token ×5 / 正文 token ×1（CJK 单字+bigram 分词、中英停用词表）；**④ 图邻居扩展**——top 结果（≤20 种子）一跳邻居按 Σ 1/(rank+1) 打分 ×0.5 缩放，配额 top_k 的 15-30%（基础覆盖高取低配额），结果附 graph_related_to 来源页。合并去重后截 top_k。`pages` 参数支持调用方预取页面集复用（报告逐节检索共享一次全表加载）。异常语义：`raise_on_error` 参数区分调用方——交互式搜索端点传 True（故障 500 透出，不伪装无结果）；RAG/报告管线默认 False（降级为空结果，§8.2/§8.3）。**未实现**：② 稠密向量检索与 ③ RRF 融合（模块 docstring 标注 Future；RRF_K 常量已定义未使用）。

### 12.2.8 Review 清扫（sweep_reviews.py）

§5.3 两阶段实现规格。**调用方（E3-2026-10）**：唯一入口为编译终态自动治理链（§12.2.16，llm_client 参数由治理链注入——None 时仅跑 Stage1）；原 REST 端点 `POST sweep-reviews` 与 `wiki:sweepReviews` 通道已删除。Stage1 规则：title 页面引用提取（`[[...]]` 优先、「Type: 名」回退、NFKC+分隔符归一匹配）；orphan 匹配在消费点对 inbound counts 做同规则归一化（key 归一单一收口，与提取侧对称）；Stage2：40 条/批 ≤5 批、LLM JSON 输出 resolved(id+reason)/pending、任何失败整批保守保持。resolve 动作统一 auto_resolved。

### 12.2.9 语义层 Lint（semantic_lint.py）

§5.2 实现规格。输入=已编译页面摘要（前 500 字+tags 前 5）；missing-page 误报过滤（page_key/title/basename 三变体 NFKC 归一精确匹配）；lint 任务模型路由；LLM 异常向上抛出（API 层 500 呈现用户，不静默）。

### 12.2.10 重复页面检测与合并（dedup.py）

三阶段：**提取摘要**（仅 entity/concept 页，frontmatter 后首段 200 字，≤100 页）→ **LLM 检测**（同义不同名/单复数/缩写全称/拼写变体，同 page_type 才可成组，输出 groups: slugs+reason+confidence——纯 LLM 判定，无嵌入辅助）→ **确认合并**（用户指定 canonical + duplicates：LLM 内容去重合并（各 4000 字、矛盾保留并标注）+ tags/refs/sources 并集落库（复审 Warning 2026-10-27 前计算后未持久化）+ canonical 自身 [[dup]] 引用同步改写（旧实现经 _rewrite_wikilinks 写库后又被 merged_content 覆盖回去残留死链）+ 全站 [[旧键]] 重写为 [[新键|别名]] + 删除重复页（canonical 写回成功后） + change_log(dedup_merge)）。**失败语义（E2-2026-10 修订）**：单个 dup 页 LLM 合并失败 → 保留该 dup 页（内容不丢）、不计入 merged、不重写链接，经返回值 `failed` 上报；超长截断经 `truncated` 上报；change_log 只记实际合并页。保守约束：不同 page_type 不合并、必须用户确认。**并发防护（复审 Warning 2026-10-27）**：治理链在编译终态后运行，合并的 409 门拦不住它——canonical 写回以读取原文为内容级 CAS 条件（§5.4/§5.5 同族 expected_content）：窗口内被用户编辑/他组合并先行写入 → 全组 `failed(reason=content_changed)` 拒绝，dup 保留待重试、组保持 pending（merged=0 不置 merged），失败路径零副作用；事务顺序=「先 CAS 提交 canonical（其自身 [[dup]] 引用在内存中改写）→ 后全站改链 + 删 dup」；全站链接重写逐页 CAS，快照失配重读重做一次（链接替换幂等），仍失配跳过记日志（漏改死链由下一轮治理发现）。**组落库（E3-2026-10）**：检测结果经 `replace_dedup_groups` 持久化 `wiki_dedup_groups`（§3.9：fingerprint 幂等、保留用户 merged/dismissed 裁决）；合并请求携 groupId，成功后置 status=merged（组消失不复活）。

### 12.2.11 页面级联删除（routers/wiki.py delete 端点 + database.py）

单事务五步：删 page_sources → 删页面级 change_log → reviews 的 affected_page_ids 剥离本页（清空则删 review）→ 其他页面 refs 剥离本键 → 删页面本体；随后补记项目级 change_log(deleted)。

### 12.2.12 上下文预算分配（context_budget.py）

字符预算（默认窗口 400K ≈ 128K token CJK）：index 5% / wiki 页面 50% / 历史与 system 30% / 响应预留 15%。单页截断 `max(5000, min(预算/页数, 预算×30%))`，累计超预算即停止纳入。消费方：Chat 的 Wiki 上下文（§8.3）。

### 12.2.14 语言检测与输出语言（detect_language.py）

### 12.2.16 编译终态自动治理链（auto_governance.py，E3-2026-10）

`on_compile_complete_sync(db, project_id, task_id, settings)`：task_queue completed 分支经 run_in_executor 后台线程直调（同 profile_service 挂点，§4.8），整体吞异常——治理失败只记日志，绝不影响编译主流程。执行主体 `_run` 三步顺序，**三步各自 try/except 隔离**（review s-3 2026-10-27：后段异常不吞前段已完成动作，汇总带已完成部分照常落库/时间线）：

1. **Review 清扫**：`sweep_reviews(db, project_id, llm_client)`（§12.2.8；Stage1 免费必跑，Stage2 依赖 llm_client）
2. **死链机械修复**：仅本 task 有页面产出（produced）时执行——扫描待处理 broken-link 发现项，有可靠建议目标的经 `fix_wiki_page_wikilink` 机械替换并核销（fixed），无建议/失配的原样保留留人工；单条失败隔离（一条写失败不影响其余修复）；**CAS 失配（content_changed，M-1）记日志不核销**——发现项仍真实，留下一轮治理或人工
3. **重复检测**：`extract_entity_summaries` ≥2 页才跑，`detect_duplicates` 结果经 `replace_dedup_groups` 落库（§3.9）；**dedup 档独立构造**（review m-1 2026-10-27：`get_task_settings(settings, "dedup")`，与手动合并端点同档同口径，不再误用 standard 档；构造失败仅跳过本步）

**LLM 三重守卫**（拿不到 llm_client 则仅 Stage1 + 死链修复条件不变）：①本 task 摄入摘要存在非 skipped 页面产出（produced）；②项目 30 分钟冷却（`_COOLDOWN_UNTIL` 进程内存态，重启清零；每轮拿到守卫即占冷却槽——高频连续编译不叠烧 token）；③LLM/嵌入就绪（复用 `wiki.auto_compile._readiness_ready("wiki_compile")` 同源判定）且 `resolve_model(standard)` 构造成功。LLM 用量经 UsageContext（source=wiki，purpose=sweep/dedup）体内自行 push（executor 线程，同 §12.2.15）。

**结果落库与可达**：`set_compile_governance_summary(task_id, summary)` 落任务行（随 compile-status 透出，**前端 CompilePanel 编译详情数据源**，review m-2 2026-10-27 更正——原文误写「toast 数据源」）+ change_log(action=governance，「自动治理：核销 X 条过时问题，自动修复 Y 条死链，检出 Z 组疑似重复页面」）+ **通知中心一条**（kind=governance，复用 wiki_compile 通道与导航映射，entity_id=task_id 避开未读查重）；**零动作不发通知**（没消息=没问题，免培训不打扰，§2.10）。

**消费侧**：CompilePanel completed 态解析 governance_summary 渲染治理摘要行（非零出动作摘要/全零出「无需处理」/损坏静默不渲染，m-2）；Lint 视图挂载重拉发现项与 dedup 组即见结果，**且治理通知到达即经 `app:governance-done` 广播实时刷新已打开的视图**（review M-2 2026-10-27：ActivityMonitor dispatchToasts 检测 governance 通知 → 窗口 CustomEvent → WikiLintView 监听重载——治理在后台跑数分钟，此前已打开的视图看不到结果；广播先于批量 Toast 分支派发且 ProjectDetailPage 监听同一信号补拉编译快照刷新面板治理行——复审补口 2026-10-27：#4 轮询终态即停，治理 summary 晚于终态落库需信号补拉）；通知点击直达 Wiki Tab（兑底路径）。

## 14. 知识册导出（V2.1，[0.6 §9](0.6v2-ux-redesign.md)）

> 知识册编译产物的 docx 导出，复用报告生成链的 docx 渲染器。实施计划见 [2026-10-24-v2.1-portfolio-weekly.md](superpowers/plans/2026-10-24-v2.1-portfolio-weekly.md)。

### 14.1 挂点与触发

- **入口**：WikiTab 顶部编译完成态状态条（`compileTask.status==='completed'`）新增「导出 docx」钮（与「重新汇编」同区；实现落地与原设「封面头部动作区」的偏差：重新汇编实际位于 WikiTab 顶部状态条非 WikiHomePage 组件，导出钮同区；状态条数据经 wiki:compileStatus 最新任务恢复，重启后入口可达）。编译中/失败/停止态隐藏。
- **交互**：点击 → `wiki:exportDocx` invoke → python 端点同步生成 → 返回落盘路径 → toast 成功 + `shell:showItemInFolder` 定位文件（ArchiveView/FilePreview 同款动线，复用既有通道零新增）。

### 14.2 数据流（§2.8 ②）

```
IPC wiki:exportDocx {projectId}
  → POST /wiki/{project_id}/export-docx（routers/wiki.py）
  → 拼接册内容：wiki_pages 按 wiki_schemas 目录序取已编译页 md（空 content 页排除；
    每页一级标题 + 页间分隔线）
  → report_generator.renderer.render_markdown_to_docx（asyncio.to_thread 下放，
    防事件循环阻塞；reports export 同款）
  → 落盘 {data_dir}/files/{project_id}/exports/wiki_{slug}_{YYYYMMDD-HHmm}_{8位随机后缀}.docx
    （实现落地与原设「{项目 workspace}/exports/」的偏差：项目无 workspace 目录，
    实挂知识文件目录下 exports/ 子目录，随项目删除级联清理，生命周期闭环同
    报告产物挂 content_path）
  → 返回 {path, pages}；前端 toast + 定位
```

- **零新表**：导出记录不落库（文件即产物）。文件名 = 时间戳（分钟粒度）+ 8 位随机后缀：同分钟重复导出/并发导出天然不同名，不覆盖旧导出（CodeReview m-1：确定性递增序号存在 check-then-act 竞态，随机后缀互斥）。
- **护栏**：空册（零有效内容页）409 `WIKI_EMPTY`（D1 契约带 code，前端据 errorCode 分型提示）；pandoc 渲染失败 → 500 透出 stderr 细节（CodeReview M-2：无包装时兜底 500 纯文本丢失诊断链）；渲染为本地确定性转换（非 LLM 调用），素材上限不适用于全量册（页数多时 pandoc 慢但确定性完成）；图片缺失 pandoc 仅 warning 不阻断（占位语义由 pandoc 天然保障）。
