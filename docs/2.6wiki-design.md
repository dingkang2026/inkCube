## 1. 背景与定位

### 1.1 核心理念

引入 **Karpathy LLM Wiki** 范式——知识不是被"存"起来的，而是被**编译**成更有价值的结构。

传统 RAG 的问题：每次提问都从碎片里重新拼答案，答完就散，知识没有积累。LLM Wiki 的思路相反：给 AI 安排一份长期工作——持续维护知识库，每次新资料输入都增量编译，产生**知识复利**。

**Wiki 的两大核心目标：**

| 目标 | 说明 |
|------|------|
| **服务报告** | Wiki 编译的结构化结论直接作为报告生成的高权重上下文，保证一致性和质量 |
| **Markdown 可视呈现** | Wiki 页面以 Markdown 渲染后供用户阅读浏览，让项目知识"看得见" |

Wiki 页面本质是 **Markdown 文档**——LLM 编译产出 Markdown，前端渲染后用户可直接阅读。不需要知识图谱、力导向图等重型可视化，Markdown 渲染本身就是最好的"可视"。

### 1.2 与 RAG 的关系

Wiki 不是替代 RAG，而是 RAG 的**上层建筑**——RAG 负责精准召回（机器检索），Wiki 负责知识沉淀（人+AI 可读）。

| 维度 | RAG（现有） | LLM Wiki（新增） |
|------|-----------|------------------|
| 知识形态 | 向量切片（机器检索） | 结构化页面（人+AI 可读） |
| 核心价值 | 精准召回 | 知识沉淀、一致性输出 |
| 人类可读性 | 低（碎片化切片） | 高（完整 Wiki 页面） |
| 查询方式 | 语义相似度匹配 | 结构化查询 + 语义搜索 |
| 知识积累 | 无积累（每次重新拼凑） | 持续编译，产生复利 |

### 1.3 架构：项目 Wiki + 基础库 RAG 直达

从核心目标“服务报告写作”出发，采用务实的简化架构：

- **项目 Wiki**（实施）：将碎片化项目文档编译为结构化结论，解决“碎片拼凑”和“一致性”问题
- **基础库 RAG 直达**（已实现）：基础库文件通过 RAG 直接检索注入，不做额外 Wiki 编译
- **基础库 Wiki**（可选延后）：如果未来基础库文件量大到 RAG 质量下降，再考虑增加

```
┌────────────────────────────────────────────────────────┐
│  基础库（RAG 直达，无需 Wiki 编译）                       │
│                                                         │
│  ┌──────────────────┐  ┌──────────────────┐            │
│  │ 招商基础库 RAG    │  │ 投资基础库 RAG    │            │
│  │ 政策、园区、产业   │  │ 估值、法规、行业   │            │
│  └────────┬─────────┘  └────────┬─────────┘            │
│           │   编译/报告时 RAG 检索注入  │                  │
│  ┌────────┴────────┐  ┌────────┴────────┐              │
│  │ 项目A Wiki       │  │ 项目B Wiki       │              │
│  │ 企业画像、政策匹配 │  │ 公司概况、财务分析 │              │
│  │ 落地方案…        │  │ 风险清单…         │              │
│  └─────────────────┘  └─────────────────┘              │
│  项目 Wiki（编译为结构化结论，直接服务报告）                 │
└────────────────────────────────────────────────────────┘
```

**为什么基础库暂不做 Wiki？**
- 基础库 RAG 已能精准检索到具体条款和数据
- 编译成摘要反而可能丢失细节（报告常需引用具体到“某条某款”）
- 基础库文件数量通常不多，RAG 检索质量已够用
- 减少一层复杂度，避免重编译时机、跨层一致性等维护成本

**项目 Wiki 的核心价值：**
- 把碎片化的项目文档编译成稳定结论（企业画像、政策匹配、落地方案）
- 报告生成时直接引用 Wiki 骨架 + RAG 补充细节
- 同一项目多次生成报告，结论一致
- **Markdown 渲染后用户可直接阅读**，项目知识不再是黑盒

### 1.4 三层架构映射（Raw → Wiki → Schema）

遵循 LLM Wiki 的三层架构理念，映射到 InkCube 现有系统：

| LLM Wiki 层 | InkCube 对应 | 说明 |
|---|---|---|
| **Raw 层** | 现有 RAG 的文档解析结果（项目 + 基础库） | 原始文件 + 解析后的 chunks，只读，AI 不可改 |
| **Wiki 层** | **新建** wiki_pages 表（仅项目维度） | AI 编译的结构化页面，AI 全权维护 |
| **Schema 层** | wiki_schemas 定义 | 按 project_type 决定 Wiki 页面结构 |

### 1.5 功能目的与工程要求

#### 功能目的

| # | 目的 | 衡量标准 |
|---|------|----------|
| F1 | 将碎片化项目文档编译为结构化 Markdown 知识页面 | 每个项目可生成 ≥ 1 个完整 Wiki 页面 |
| F2 | Wiki 结论直接服务报告生成，保证一致性 | 同一项目多次生成报告，核心结论一致 |
| F3 | Wiki 页面以 Markdown 渲染供用户阅读 | 前端渲染后可读、格式正确 |
| F4 | 支持增量编译，新资料可增量补充到已有 Wiki | 新文件不触发全量重建 |
| F5 | 编译过程可发现矛盾/缺失，反馈给用户 | REVIEW 机制可工作 |
| F6 | Chat 和报告可检索 Wiki 内容 | Chat 回答引用 Wiki 页面 |

#### 工程有效性要求

| # | 要求 | 设计保障 |
|---|------|----------|
| E1 | 编译独立于前端 | 后端 KnowledgeWorker 异步执行，状态持久化到 DB（§4.6） |
| E2 | 用户可控 | 通知 + 人工触发，不自动消耗 LLM 额度（§4.1） |
| E3 | 编译进度可见 | 前端轮询 compile-status API，状态条实时展示（§4.6.4） |
| E4 | 素材积累后一次编译 | pending_compile_count 累积，用户决定时机（§6.1） |

#### 工程健壮性要求

| # | 要求 | 设计保障 |
|---|------|----------|
| R1 | 错误自动重试 | 指数退避，最多 3 次，不需要用户干预（§4.6.3） |
| R2 | 单页失败不影响整体 | partial 状态，其他页面继续编译（§4.6.3） |
| R3 | 进程崩溃可恢复 | 重启后自动重置未完成任务为 queued（§4.6.3） |
| R4 | 数据一致性 | 编译事务性写入，要么全成功要么回滚；级联删除保证无孤儿数据（§6.6） |
| R5 | 源文件删除不丢内容 | 页面内容不自动删除，由 REVIEW 提示用户决策（§6.5） |
| R6 | LLM 输出不可信 | 解析失败重试；无法解析的 block 记录原始返回；格式错误不写入 DB（§4.6.3） |
| R7 | 并发安全 | 单项目页面并发上限可配置；手动触发天然避免多项目并发（§4.6.5） |

## 3. 数据模型

### 3.1 wiki_schemas 表

定义 Wiki 页面结构模板。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PK | Schema ID（如 `wiki_schema_recruitment`） |
| `project_type` | TEXT | `recruitment` / `investment` / `general` |
| `page_key` | TEXT | 页面标识（如 `enterprise_profile`） |
| `title` | TEXT | 页面默认标题 |
| `compile_hint` | TEXT | 编译指引（注入 LLM Prompt） |
| `base_lib_search_hints` | TEXT | JSON 数组，编译时应检索的基础库关键词/主题（用于 RAG 检索注入） |
| `position` | INTEGER | 页面在 Wiki 中的排序位置 |

### 3.2 wiki_pages 表

存储编译后的 Wiki 页面。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PK | 页面 ID（UUID） |
| `project_id` | TEXT FK | 所属项目 ID |
| `page_key` | TEXT | 页面标识（对应 schema 的 page_key） |
| `title` | TEXT | 页面标题（可被用户修改） |
| `content` | TEXT | 页面内容（Markdown 格式） |
| `status` | TEXT | `draft` / `compiled` / `user_edited` |
| `compile_version` | INTEGER | 编译版本号（每次增量更新 +1） |
| `last_compiled_at` | TEXT | 最后编译时间 |
| `last_compiled_file_id` | TEXT | 触发最近一次编译的文件 ID |
| `created_at` | TEXT | 创建时间 |
| `updated_at` | TEXT | 更新时间 |

**唯一约束**: `(project_id, page_key)` — 每个项目下每个 page_key 只有一页。

### 3.3 wiki_page_sources 表

来源追溯——记录每个 Wiki 页面的内容来自哪些原始文件。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PK | 记录 ID |
| `wiki_page_id` | TEXT FK | 关联 wiki_pages.id |
| `file_id` | TEXT FK | 来源文件 ID（关联 files 表，可以是项目文件或基础库文件） |
| `contribution` | TEXT | 贡献描述（如“提供了财务数据部分”） |
| `created_at` | TEXT | 关联时间 |

### 3.4 wiki_change_log 表

变更记录——Wiki 的"log.md"，只追加。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PK | 记录 ID |
| `project_id` | TEXT | 所属项目 ID |
| `wiki_page_id` | TEXT | 被修改的页面 ID（可为 null，表示新建） |
| `action` | TEXT | `created` / `updated` / `user_edited` / `source_added` |
| `trigger_file_id` | TEXT | 触发变更的文件 ID |
| `summary` | TEXT | 变更摘要（如"补充了2026年Q1财务数据"） |
| `created_at` | TEXT | 变更时间 |

### 3.5 wiki_reviews 表

编译过程中 LLM 发现的问题和建议——借鉴 llm_wiki 的 REVIEW 机制。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PK | 记录 ID（基于 type+title 的内容稳定 hash） |
| `project_id` | TEXT FK | 所属项目 ID |
| `type` | TEXT | `missing-page` / `contradiction` / `suggestion` / `confirm` |
| `title` | TEXT | 发现项标题 |
| `description` | TEXT | 详细描述 |
| `affected_page_ids` | TEXT | JSON 数组，关联的 wiki_page IDs |
| `source_file_id` | TEXT | 触发此发现的源文件 ID |
| `resolved` | INTEGER | 0=待处理, 1=已解决 |
| `resolved_action` | TEXT | 解决动作（`create_page` / `dismiss` / `auto_resolved`） |
| `created_at` | TEXT | 创建时间 |

**ID 稳定性**：与 llm_wiki 一致，review ID 基于 `type::normalizedTitle` 的 FNV-1a hash，相同内容产生相同 ID，避免重复。

### 3.6 projects 表新增字段

支持 Wiki 通知机制（§6.1）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `pending_compile_count` | INTEGER | 待编译文件计数（默认 0），文件变更时 += 1，用户触发编译后重置为 0 |

### 3.7 wiki_compile_tasks 表

编译任务状态跟踪——记录每次编译任务的状态、进度、错误信息，支持崩溃恢复和重试。详见 §4.6。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PK | 任务 ID（UUID） |
| `project_id` | TEXT FK | 所属项目 ID |
| `trigger_type` | TEXT | `file_upload` / `base_lib_update` / `schema_change` / `manual` |
| `trigger_file_id` | TEXT | 触发文件 ID（可为 null） |
| `status` | TEXT | `queued` / `analyzing` / `generating` / `storing` / `completed` / `failed` / `partial` |
| `stage` | TEXT | 当前阶段（`stage1_analysis` / `stage2_generation` / `store`） |
| `pages_total` | INTEGER | 待编译页面总数 |
| `pages_completed` | INTEGER | 已成功编译的页面数 |
| `pages_failed` | INTEGER | 失败的页面数 |
| `error_message` | TEXT | 错误信息（失败时记录） |
| `retry_count` | INTEGER | 已重试次数 |
| `max_retries` | INTEGER | 最大重试次数（默认 3） |
| `created_at` | TEXT | 创建时间 |
| `started_at` | TEXT | 开始执行时间 |
| `completed_at` | TEXT | 完成时间 |

## 4. 编译流程

### 4.1 编译触发：通知 + 人工触发

Wiki 编译**不自动执行**，采用“通知 + 人工触发”模式——系统检测到新素材后发通知，用户决定何时编译。

**完整数据流：**

```
用户上传文件（项目文件 or 基础库文件）
    │
    ▼
KnowledgeWorker 文件解析 pipeline（已有）：
  文本提取（PDF/Word/PPT → 纯文本）
    → 分块（chunking）
    → 向量化（embedding）
    → 存入向量数据库 + files 表
    │
    ▼
RAG chunks 入库完成
    │
    ▼
给 Wiki 发通知：项目 pending_compile_count += N
（不触发编译，仅标记“有新素材”）
    │
    ▼
用户在 Wiki Tab 看到提示：“有 3 个新文件待编译”  [编译]
    │
    ▼
用户点击「编译」→ 创建 wiki_compile_tasks 记录 → 开始编译
    │
    ▼
编译时读取 RAG chunks 作为素材（Wiki 不直接解析文件）
```

**为什么采用“通知 + 人工触发”？**

| 方面 | 自动编译 | 通知 + 人工触发 |
|------|---------|----------------|
| LLM 成本 | 每次上传都编译，可能浪费 | 用户决定何时编译，可控 |
| 并发控制 | 需要复杂的队列/并发配置 | 用户手动触发，天然串行 |
| 用户体验 | 黑盒，不知道何时在编译 | 用户主动决定，有掌控感 |
| 素材积累 | 上传一个编译一次 | 可以累积多个文件后一次编译 |

**Wiki 不直接解析文件**——它消费的是 RAG pipeline 已经处理好的 chunks。RAG chunks 是共享的：Chat 能读、报告生成能读、Wiki 编译也能读。

### 4.2 编译流程详细设计（两阶段 Ingest）

借鉴 llm_wiki 的两阶段 ingest 模式，编译分为"分析"和"生成"两步，提高编译质量：

```
┌─ Step 1: 确定编译范围 ──────────────────────────────────┐
│  读取 project_type 对应的 wiki_schemas                   │
│  查询已有 wiki_pages（判断首次编译还是增量更新）           │
│  确定需要编译/更新的 page_key 列表                       │
└──────────────────────────────────────────────────────────┘
        │
        ▼
┌─ Step 3: 收集 Raw 素材 ─────────────────────────────────┐
│  从项目 RAG chunks 中提取与当前 page_key 相关的内容       │
│  根据 Schema 的 base_lib_search_hints：                  │
│    → 检索关联基础库的 RAG chunks 作为参考上下文           │
│  输出：每个 page_key 对应的素材包                          │
└──────────────────────────────────────────────────────────┘
        │
        ▼
┌─ Step 4: Stage 1 分析（Analysis）──────────────────────┐
│  LLM 阅读素材包，输出：                                  │
│    • 关键概念和实体识别                                  │
│    • 建议创建/更新的页面列表                            │
│    • 页面间关联关系                                      │
│    • 发现的矛盾、缺失、建议（Review 候选）              │
│  此阶段不生成页面内容，只做"规划"                      │
└──────────────────────────────────────────────────────────┘
        │
        ▼
┌─ Step 5: Stage 2 生成（Generation）────────────────────┐
│  根据 Stage 1 的分析结果，LLM 输出：                    │
│    • PAGE blocks：每个页面的 Markdown 内容              │
│    • REVIEW blocks：发现的问题和建议                    │
│  解析器提取 blocks，写入 DB / 注入 review 队列          │
└──────────────────────────────────────────────────────────┘
        │
        ▼
┌─ Step 6: 存储与追溯 ────────────────────────────────────┐
│  写入/更新 wiki_pages 表                                  │
│  写入 wiki_page_sources（关联来源文件）                   │
│  追加 wiki_change_log                                     │
│  更新 compile_version                                     │
│  解析 REVIEW blocks → 写入 wiki_reviews 表               │
└──────────────────────────────────────────────────────────┘
```

**为什么分两阶段？**
- Stage 1（分析）让 LLM 先"理解"素材，规划页面结构，避免盲目生成
- Stage 2（生成）基于分析结果，生成更有针对性的内容
- 两阶段分别可用不同 prompt 策略，分析重"广度"，生成重"深度"

### 4.3 编译 Prompt 结构

**Stage 1 — 分析 Prompt：**

```
System:
  你是知识编译 Agent。分析以下原始资料，规划 Wiki 页面结构。

Context:
  ## 原始资料
  {从 RAG chunks 提取的相关内容}

  ## 已有 Wiki 页面（增量时）
  {现有页面的标题和摘要}

  ## 基础库参考（RAG 检索结果）
  {根据 search_hints 检索到的相关 chunks}

Instructions:
  1. 识别资料中的关键概念、实体、数据
  2. 建议哪些 page_key 需要创建或更新
  3. 标注发现的矛盾、缺失信息、建议
  4. 不要生成页面内容，只做分析和规划

Output: 分析报告（JSON 格式）
```

**Stage 2 — 生成 Prompt：**

```
System:
  你是知识编译 Agent。根据分析结果生成 Wiki 页面内容。
  {compile_hint}

Context:
  ## 原始资料
  {RAG chunks}

  ## 分析结果（Stage 1 输出）
  {Stage 1 的分析报告}

  ## 已有页面内容（增量时）
  {现有 wiki_page.content}

  ## 基础库参考
  {RAG 检索结果}

Instructions:
  1. 为每个需要创建/更新的页面生成 Markdown 内容
  2. 增量更新时，在已有内容基础上补充，不覆盖已有正确信息
  3. 信息冲突时，保留各方说法并标注来源和时间
  4. 无法确认的信息标注为「待核实」
  5. 使用 Markdown 格式
  6. 如果发现缺失页面、矛盾、建议，输出 REVIEW block

Output 格式:
  页面内容用 PAGE block 包裹：
  ---PAGE: {page_key}---
  (Markdown 内容)
  ---END PAGE---

  发现项用 REVIEW block 包裹：
  ---REVIEW: {type} | {title}---
  {description}
  ---END REVIEW---
```

### 4.4 REVIEW 协议

借鉴 llm_wiki 的 REVIEW block 机制，编译过程中 LLM 可主动发现问题并报告：

| REVIEW 类型 | 说明 | 示例 |
|---|---|---|
| `missing-page` | 资料涉及重要概念但当前 Schema 没有对应页面 | "资料多次提到‘税收优惠’，但无专属页面" |
| `contradiction` | 不同来源的信息存在矛盾 | "文件A说注册资本 5000万，文件B说 8000万" |
| `suggestion` | LLM 主动建议改进 | "建议补充竞争对手分析" |
| `confirm` | 需要用户确认的判断 | "根据资料推断企业处于成长期，是否准确？" |

REVIEW 项写入 `wiki_reviews` 表，用户可在 Wiki 界面查看和处理（处理动作包括：创建页面、标记已解决、忽略）。

### 4.5 基础库关联规则

项目 Wiki 编译时，自动检索关联基础库的 RAG chunks：

| 项目类型 | 自动关联基础库 |
|---------|-------------|
| 招商引资 | 招商基础库 RAG |
| 投资分析 | 投资基础库 RAG |
| 通用 | 不自动关联（用户可手动选择） |

关联方式：根据 Schema 的 `base_lib_search_hints`，从关联基础库中检索相关 chunks，作为参考上下文注入编译 Prompt。

### 4.6 编译状态与韧性

编译在后端 KnowledgeWorker 中异步执行，**完全独立于前端**。用户切换 Tab、关闭项目窗口、甚至重启应用，都不影响正在进行的编译。

#### 4.6.1 编译状态机

```
queued → analyzing → generating → storing → completed
    │          │           │          │
    └──────┴──────┴──────┘
                    │
                 failed（可重试）
                    │
              partial（部分页面成功）
```

| 状态 | 说明 |
|------|------|
| `queued` | 已入队，等待 worker 拾取 |
| `analyzing` | Stage 1 分析中（LLM 调用） |
| `generating` | Stage 2 生成中（LLM 调用） |
| `storing` | 解析 blocks，写入 DB |
| `completed` | 全部成功 |
| `failed` | 编译失败（可重试） |
| `partial` | 部分页面成功，部分失败 |

#### 4.6.2 状态持久化

新增 `wiki_compile_tasks` 表，记录每次编译任务的状态：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PK | 任务 ID（UUID） |
| `project_id` | TEXT FK | 所属项目 ID |
| `trigger_type` | TEXT | `file_upload` / `base_lib_update` / `schema_change` / `manual` |
| `trigger_file_id` | TEXT | 触发文件 ID（可为 null） |
| `status` | TEXT | 状态机中的状态 |
| `stage` | TEXT | 当前阶段（`stage1_analysis` / `stage2_generation` / `store`） |
| `pages_total` | INTEGER | 待编译页面总数 |
| `pages_completed` | INTEGER | 已成功编译的页面数 |
| `pages_failed` | INTEGER | 失败的页面数 |
| `error_message` | TEXT | 错误信息（失败时记录） |
| `retry_count` | INTEGER | 已重试次数 |
| `max_retries` | INTEGER | 最大重试次数（默认 3） |
| `created_at` | TEXT | 创建时间 |
| `started_at` | TEXT | 开始执行时间 |
| `completed_at` | TEXT | 完成时间 |

#### 4.6.3 错误处理与重试

| 错误类型 | 处理方式 |
|---------|----------|
| **LLM API 超时/网络错误** | 自动重试，指数退避（30s → 60s → 120s），最多 3 次 |
| **LLM 返回格式错误** | 无法解析 PAGE/REVIEW blocks → 重试 1 次，仍失败则标记 `failed` 并记录原始返回 |
| **单个页面编译失败** | 其他页面继续编译，任务标记 `partial`，失败页面生成 REVIEW 项 |
| **素材不足（RAG 无结果）** | 不视为错误，生成空页面 + REVIEW 项（`data-gap`） |
| **Python 进程崩溃** | 重启后扫描 `wiki_compile_tasks`，将 `analyzing`/`generating`/`storing` 状态的任务重置为 `queued`，自动重新执行 |

**重试策略**：
- 重试在 KnowledgeWorker 内部完成，不需要前端触发
- 每次重试记录到 `retry_count`，超过 `max_retries` 后标记 `failed`，不再自动重试
- 用户可在 Wiki 界面看到失败状态，手动点击「重试」

#### 4.6.4 前端状态展示

前端通过轮询 API 获取编译状态，不受 Tab 切换影响：

| API | 说明 |
|-----|------|
| `GET /wiki/projects/{project_id}/compile-status` | 返回当前/最近的编译任务状态 |

前端展示：
- Wiki Tab 顶部显示编译状态条（进度/状态/错误）
- 编译中：显示进度（如“3/6 页面已编译”）
- 失败：显示错误摘要 + 「重试」按钮
- 部分成功：显示成功/失败页面列表，失败页面可单独重试
- 用户切换 Tab 再回来，状态从 DB 恢复，不丢失

#### 4.6.5 并发控制配置

编译由用户手动触发，天然不会像自动触发那样大量并发。但仍需基础保护：

| 配置项 | 默认值 | 说明 |
|---------|--------|------|
| `max_concurrent_pages` | 3 | 单个项目一次编译最多几个页面并行（控制单次 LLM 调用大小） |
| `llm_timeout` | 120s | 单次 LLM 调用超时时间 |

- 全局项目并发控制**不需要**——用户手动触发，同一时间通常只有一个项目在编译
- 配置存放在 Python 后端配置文件（`python/data/config.json`），不暴露到前端 UI
- 修改配置后无需重启，下次编译时生效

## 5. Wiki 健康检查（Lint）

借鉴 llm_wiki 的 Lint 机制，定期检查 Wiki 内容质量。分两层：结构层（确定性检查）和语义层（LLM 驱动）。

### 5.1 结构层 Lint（无需 LLM）

确定性检查，速度快，无成本：

| 检查项 | 说明 | 处理建议 |
|---|---|---|
| `empty-page` | 页面内容为空或极短 | 触发重新编译 |
| `missing-source` | 页面没有任何来源追溯 | 检查编译流程是否正常 |
| `stale-page` | 页面长时间未更新，可能有新资料未编译 | 检查是否有未处理的新文件 |
| `orphan-review` | review 项关联的页面已被删除 | 自动标记已解决 |

### 5.2 语义层 Lint（LLM 驱动）

LLM 阅读 Wiki 页面，发现深层问题：

| 检查项 | 说明 | 处理建议 |
|---|---|---|
| `contradiction` | 不同页面间信息矛盾 | 创建 review 项，让用户裁决 |
| `stale-claim` | 页面中的声明已被更新的资料取代 | 触发增量更新 |
| `data-gap` | 重要维度缺少数据支撑 | 建议用户补充资料或创建 review |

### 5.3 Lint 执行方式

```
用户手动触发 / 编译完成后自动触发
    │
    ▼
结构层检查（遍历所有页面，检查空内容/来源/时效）
    │
    ▼
语义层检查（LLM 阅读页面，发现矛盾/过时/缺失）
    │
    ▼
结果写入 wiki_reviews 表（与编译 REVIEW 共用同一队列）
    │
    ▼
用户在 Wiki 界面统一查看和处理
```

Lint 结果与编译 REVIEW 共用 `wiki_reviews` 表和处理流程，用户无需区分来源。

## 6. 增量更新机制

### 6.1 更新触发（通知模式）

Wiki 增量更新采用**通知模式**——文件变更不自动触发编译，而是通知用户有新素材待编译：

| 变更来源 | 通知方式 |
|---------|----------|
| **项目文件**上传/删除/替换 | 项目 `pending_compile_count` 更新，Wiki Tab 显示提示 |
| **基础库文件**上传/删除/替换 | 查询关联项目，每个关联项目的 `pending_compile_count` 更新 |
| **项目-基础库关联**新建/取消 | 项目的 `pending_compile_count` 更新 |
| **Schema 变更** | 受影响项目的 `pending_compile_count` 更新 |

**通知机制：**

项目表新增 `pending_compile_count` 字段（INTEGER，默认 0）：
- 文件上传/删除/替换 → 对应项目 count += 1
- 基础库变更 → 关联项目 count += 1
- 用户点击「编译」→ count 重置为 0，开始编译

前端 Wiki Tab 根据 `pending_compile_count` 显示：
- count = 0：不显示提示
- count > 0：显示“有 N 个新文件待编译” + 「编译」按钮
- 用户可选择「全量编译」或「增量编译」（仅新文件）

### 6.2 增量编译策略

```
新文件解析完成（项目文件 or 基础库文件）
    │
    ▼
检索已有 Wiki 页面
    │
    ├─ 新文件内容与某页面相关 → 补充该页面（merge）
    ├─ 新文件包含全新主题 → 创建新页面（如果 Schema 允许）
    ├─ 新文件与已有信息冲突 → 保留双方，标注来源和时间
    └─ 新文件与所有页面无关 → 仅记录来源，不修改页面
```

### 6.3 冲突处理规则

| 情况 | 处理方式 |
|------|---------|
| 新信息与旧信息一致 | 补充来源引用，不修改内容 |
| 新信息补充旧信息 | 追加到对应段落，标注新来源 |
| 新信息与旧信息矛盾 | 保留双方说法，标注各自来源、时间、适用范围 |
| 旧信息明显过时 | 更新为新信息，旧信息移入变更日志 |

### 6.4 更新范围控制

**核心原则：每次只更新受影响的页面，不重建整套 Wiki。**

LLM 先判断新文件与哪些 page_key 相关，只对这些页面执行增量编译。

### 6.5 源文件删除对 Wiki 的影响

当项目文件或基础库文件被删除时，需要处理 Wiki 页面的关联关系：

| 情况 | 处理方式 |
|------|----------|
| 删除的文件是某页面**唯一**来源 | 页面标记为 `stale`，生成 REVIEW 项（`data-gap`），建议用户补充资料或手动删除页面 |
| 删除的文件是某页面**多个**来源之一 | 从 `wiki_page_sources` 移除关联记录，页面内容不变（其他来源仍支撑内容） |
| 删除的文件与所有页面无关联 | 无影响，仅清理 RAG chunks |

**不自动删除页面内容**——即使唯一来源被删，页面内容可能仍有价值（用户编辑过、或与其他未解析文件相关）。由 Lint/REVIEW 机制提示用户决策。

### 6.6 项目删除时 Wiki 级联清理

项目删除时，级联清理所有 Wiki 相关数据：

```
项目删除
    │
    ▼
DELETE FROM wiki_pages WHERE project_id = ?
DELETE FROM wiki_page_sources WHERE wiki_page_id IN (该项目的页面)
DELETE FROM wiki_change_log WHERE project_id = ?
DELETE FROM wiki_reviews WHERE project_id = ?
```

注意：wiki_schemas 是全局模板，不随项目删除。仅清理项目维度数据。

### 6.7 Schema 变更处理

当 wiki_schemas 表发生变更（如新增 page_key、修改编译指引）时，已有项目需要感知并响应：

| Schema 变更类型 | 处理方式 |
|---|---|
| **新增 page_key** | 检测受影响项目，更新 `pending_compile_count`，用户手动触发编译新页面 |
| **修改 compile_hint** | 不通知，下次编译时自然使用新指引 |
| **删除 page_key** | 对应页面标记为 `orphan`，生成 REVIEW 项让用户决策 |

## 8. 与 Chat / 报告生成的集成

### 8.1 知识优先级

Chat 问答和报告生成共用同一套知识优先级：

```
1. 项目 Wiki 页面（最高优先级 — 已编译的结构化知识）
2. 项目 RAG chunks（补充 Wiki 未覆盖的细节）
3. 关联基础库 RAG chunks（共享知识补充）
```

### 8.2 报告生成集成

报告生成引擎（`retrieval.py`）在检索阶段：
1. 先查询项目 Wiki 相关页面，作为高权重上下文注入
2. 再执行常规 RAG 检索补充细节（包括项目文档和基础库文档）

### 8.3 Chat 接入 Wiki

项目已有跨 Tab Chat 面板（见 [2.1project-design.md §4.4](2.1project-design.md)），Chat 检索范围已包含 Wiki 页面。Wiki 侧需要提供的衔接能力：

**Wiki 检索 API：**

| API | 说明 |
|-----|------|
| `GET /wiki/projects/{project_id}/pages/search?q=...` | 按关键词/语义检索 Wiki 页面，返回匹配的页面标题 + 内容摘要 |

**Chat 检索流程：**

```
用户在 Chat 中提问
    │
    ▼
Chat 后端并行检索：
  ├─ Wiki 页面检索（按 query 语义匹配，取 top-K 页面）
  ├─ 项目 RAG 检索（现有逻辑）
  └─ 基础库 RAG 检索（现有逻辑）
    │
    ▼
知识融合：
  Wiki 页面作为“骨架”上下文（结构化、高权重）
  RAG chunks 作为“细节”补充（碎片化、低权重）
    │
    ▼
LLM 综合回答，标注引用来源
```

**Wiki 页面检索策略：**
- 先按 page_key 匹配（query 中包含页面标题关键词时直接命中）
- 再按页面内容语义检索（对 wiki_pages.content 做 embedding 匹配）
- 返回 top-K 页面的完整内容，注入 Chat context

### 8.4 查询结果归档

Chat 回答后，用户可选择将有价值的回答保存为新 Wiki 页面，实现知识复利：

- 用户在 Chat 中得到回答 → 点击「保存为 Wiki 页面」
- 系统自动创建页面，写入 wiki_pages，关联来源页面
- 探索成果不会消失在聊天记录中

### 8.5 对质量的影响

| 维度 | 仅 RAG | RAG + Wiki |
|------|--------|-----------|
| 上下文质量 | 碎片化，需要 LLM 自行拼凑 | 结构化，直接可用 |
| 一致性 | 同一问题多次回答可能不同 | Wiki 保证一致性输出 |
| 来源追溯 | 追溯到 chunk 级别 | 追溯到页面 + 原始文件 |
| 生成效率 | 需要大量 chunks 拼凑 | Wiki 页面直接覆盖大部分内容 |
