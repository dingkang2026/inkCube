## 1. 背景与定位

### 1.1 核心理念

引入 **Karpathy LLM Wiki** 范式——知识不是被"存"起来的，而是被**编译**成更有价值的结构。

传统 RAG 的问题：每次提问都从碎片里重新拼答案，答完就散，知识没有积累。LLM Wiki 的思路相反：给 AI 安排一份长期工作——持续维护知识库，每次新资料输入都增量编译，产生**知识复利**。

**核心机制——逐文件增量摄入（Per-Source Ingest）：**

Wiki 的核心操作不是"批量编译"，而是**逐篇摄入**。每当一个新文件进入系统，LLM 会：
1. **读取完整原文**（不截断、不碎片化），深入理解全文内容
2. **创建来源摘要页**（source page），记录该文件的关键要点
3. **触碰 10-15 个相关页面**——创建或更新实体页、概念页、主题页，建立交叉引用
4. **更新 index.md**（内容目录）和追加 **log.md**（时间线）

> *"A single source might touch 10-15 wiki pages."* — Karpathy

这种模式确保：知识被**编译一次、持续更新**，而非每次查询重新推导。每摄入一篇资料，知识库的交叉引用更密、综合更深、矛盾更显。

**设计哲学：**

- **高质量整理 > 大规模摄入**：LLM Wiki 的重点不是“吞下更多资料”，而是“把知识整理得更好”。每次摄入都深入理解完整原文，建立交叉引用，发现矛盾和关联——这比简单地索引更多文件更有价值。
- **透明性与可解释性**：Wiki 页面是纯 Markdown，人类可读、可编辑、可审查、易于迁移。用户可以随时查看 Agent “记住”了什么，甚至手动修正错误的知识。不需要知识图谱、力导向图等重型可视化，Markdown 渲染本身就是最好的“可视”。
- **维护成本趋近于零**：维护知识库的繁琐部分不是阅读或思考，而是“记账”——更新交叉引用、保持摘要同步、标注矛盾。LLM 不会厌倦，不会忘记更新交叉引用，可以一次性处理 15 个文件。人类负责策展来源、引导分析、提出好问题；LLM 负责其余一切。

**Wiki 的两大核心目标：**

| 目标 | 说明 |
|------|------|
| **服务报告** | Wiki 编译的结构化结论直接作为报告生成的高权重上下文，保证一致性和质量 |
| **Markdown 可视呈现** | Wiki 页面以 Markdown 渲染后供用户阅读浏览，让项目知识"看得见" |

Wiki 页面本质是 **Markdown 文档**——LLM 编译产出 Markdown，前端渲染后用户可直接阅读。不需要知识图谱、力导向图等重型可视化，Markdown 渲染本身就是最好的"可视"。

### 1.2 与 RAG 的关系

Wiki 不是替代 RAG，而是 RAG 的**上层建筑**——RAG 负责精准召回（机器检索），Wiki 负责知识沉淀（人+AI 可读）。

| 维度 | RAG（现有） | LLM Wiki（新增） |
|------|-----------|------------------|
| 知识形态 | 向量切片（机器检索） | 结构化页面（人+AI 可读） |
| 核心价值 | 精准召回 | 知识沉淀、一致性输出 |
| 人类可读性 | 低（碎片化切片） | 高（完整 Wiki 页面） |
| 查询方式 | 语义相似度匹配 | 结构化查询 + 语义搜索 |
| 知识积累 | 无积累（每次重新拼凑） | 持续编译，产生复利 |

### 1.3 架构：项目 Wiki + 基础库 RAG 直达

从核心目标“服务报告写作”出发，采用务实的简化架构：

- **项目 Wiki**（实施）：将碎片化项目文档编译为结构化结论，解决“碎片拼凑”和“一致性”问题
- **基础库 RAG 直达**（已实现）：基础库文件通过 RAG 直接检索注入，不做额外 Wiki 编译
- **基础库 Wiki**（可选延后）：如果未来基础库文件量大到 RAG 质量下降，再考虑增加

```
┌────────────────────────────────────────────────────────┐
│  基础库（RAG 直达，无需 Wiki 编译）                       │
│                                                         │
│  ┌──────────────────┐  ┌──────────────────┐            │
│  │ 招商基础库 RAG    │  │ 投资基础库 RAG    │            │
│  │ 政策、园区、产业   │  │ 估值、法规、行业   │            │
│  └────────┬─────────┘  └────────┬─────────┘            │
│           │   编译/报告时 RAG 检索注入  │                  │
│  ┌────────┴────────┐  ┌────────┴────────┐              │
│  │ 项目A Wiki       │  │ 项目B Wiki       │              │
│  │ 企业画像、政策匹配 │  │ 公司概况、财务分析 │              │
│  │ 落地方案…        │  │ 风险清单…         │              │
│  └─────────────────┘  └─────────────────┘              │
│  项目 Wiki（编译为结构化结论，直接服务报告）                 │
└────────────────────────────────────────────────────────┘
```

**为什么基础库暂不做 Wiki？**
- 基础库 RAG 已能精准检索到具体条款和数据
- 编译成摘要反而可能丢失细节（报告常需引用具体到“某条某款”）
- 基础库文件数量通常不多，RAG 检索质量已够用
- 减少一层复杂度，避免重编译时机、跨层一致性等维护成本

**项目 Wiki 的核心价值：**
- 把碎片化的项目文档编译成稳定结论（企业画像、政策匹配、落地方案）
- 报告生成时直接引用 Wiki 骨架 + RAG 补充细节
- 同一项目多次生成报告，结论一致
- **Markdown 渲染后用户可直接阅读**，项目知识不再是黑盒

### 1.4 三层架构映射（Raw → Wiki → Schema）

遵循 Karpathy LLM Wiki 的三层架构理念，映射到 InkCube 现有系统：

| LLM Wiki 层 | InkCube 对应 | 说明 |
|---|---|---|
| **Raw 层** | 现有 RAG 的文档解析结果（项目 + 基础库） | 原始文件 + 解析后的 chunks，只读，AI 不可改 |
| **Wiki 层** | wiki_pages + wiki_source_pages + purpose.md + index.md + log.md + overview.md | AI 编译的结构化页面，AI 全权维护 |
| **Schema 层** | wiki_schemas 定义 | 按 project_type 决定页面类型、编译指引、摄入规则 |

**Wiki 层的页面类型：**

| 页面类型 | 说明 | 创建时机 |
|---------|------|----------|
| **来源页**（source） | 每篇 raw 文件对应一页，记录关键要点和来源元数据 | 每次摄入自动创建 |
| **实体页**（entity） | 人、组织、产品、技术等具名实体 | 摄入时发现新实体则创建 |
| **概念页**（concept） | 概念、方法、理论等抽象知识 | 摄入时发现新概念则创建 |
| **主题页**（topic） | 跨来源的综合分析、对比、研究主题 | 摄入时自动同步更新 |
| **项目结构页** | 按 project_type 预定义的 schema 页面（如企业画像、政策匹配） | 首次摄入时创建 |

### 1.5 功能目的与工程要求

#### 功能目的

| # | 目的 | 衡量标准 |
|---|------|----------|
| F1 | 将碎片化项目文档编译为结构化 Markdown 知识页面 | 每个项目可生成 ≥ 1 个完整 Wiki 页面 |

#### 工程健壮性要求

| # | 要求 | 设计保障 |
|---|------|----------|
| R1 | 错误自动重试 | 指数退避，最多 3 次，不需要用户干预（§4.6.3） |
| R2 | 单页失败不影响整体 | partial 状态，其他页面继续编译（§4.6.3） |

## 2. Wiki Schema 定义

Schema 是 Wiki 的“规则层”——定义页面类型、编译指引和摄入规则。

> *“The schema — a document that tells the LLM how the wiki is structured, what the conventions are, and what workflows to follow… **You and the LLM co-evolve this over time** as you figure out what works for your domain.”* — Karpathy

Schema 包含两类规则：

1. **项目结构页**（固定）：按 project_type 预定义的页面（如企业画像、政策匹配），在首次摄入时创建
2. **动态页面类型**（LLM 驱动）：来源页、实体页、概念页、主题页——由 LLM 在每次摄入时根据内容自动创建/更新

### 2.0 Schema 共同演化

Schema 不是一成不变的——用户和 LLM 在使用过程中共同演化它：

- **用户可通过 Chat 调整 Schema**：例如“增加一个‘供应链风险’页面”“修改企业画像的编译指引，加上 ESG 维度”
- **LLM 在 Lint 时建议 Schema 调整**：例如“建议新增‘税收优惠’页面，资料多次提到这个概念”
- **Schema 变更自动通知受影响项目**（见 §6.7），用户手动触发重新摄入
- Schema 变更记录到 wiki_schemas 表，变更历史可追溯

### 2.1 动态页面类型

每次摄入时，LLM 自动识别并创建以下类型的页面：

| 页面类型 | 说明 | 创建规则 | 示例 |
|---------|------|----------|------|
| `source` | 来源摘要页，每篇 raw 文件对应一页 | 每次摄入**必须**创建 | "XX公司商业计划书摘要" |
| `entity` | 实体页：人、组织、产品、技术 | 摄入时发现**新实体**则创建 | "华为技术" "张三" |
| `concept` | 概念页：概念、方法、理论 | 摄入时发现**新概念**则创建 | "对赌协议" "B轮融资" |
| `topic` | 主题页：跨来源综合分析 | 摄入时自动同步更新 | "行业竞争格局" "政策环境分析" |

**摄入时的页面触碰规则**（借鉴 Karpathy：一篇资料触碰 10-15 个页面）：

1. **必须**创建/更新该文件的来源页（source）
2. **必须**识别文中实体，创建新实体页或更新已有实体页
3. **必须**识别文中概念，创建新概念页或更新已有概念页
4. **必须**更新相关的主题页（topic）
5. **必须**检查与已有项目结构页的关系，补充相关内容
6. **必须**更新 index.md 和追加 log.md
7. **必须**更新 overview.md（全局摘要）

#### YAML Frontmatter 规范

每个 Wiki 页面**必须**包含 YAML frontmatter——借鉴 llm_wiki 的实现，让页面自带结构化元数据：

```yaml
---
type: entity                # source / entity / concept / topic / structure
title: "华为技术"           # 页面标题
sources:                    # 派生来源的原始文件标识
  - "raw/sources/华为BP.pdf"
refs:                       # 交叉引用的其他页面 page_key
  - "enterprise_profile"
  - "industry_chain"
tags: [tech, china]         # 标签
created: 2026-09-27         # 创建日期
updated: 2026-09-27         # 最后更新日期
---
```

frontmatter 的作用：
- **摄入时**：为 LLM 提供结构化上下文，帮助理解页面关系
- **Lint 时**：检查 sources 是否为空、refs 是否有效
- frontmatter 是内部机制，不对外暴露，用户无需感知

## 3. 数据模型

### 3.1 wiki_schemas 表

定义 Wiki 页面结构模板。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PK | Schema ID（如 `wiki_schema_recruitment`） |
| `project_type` | TEXT | `recruitment` / `investment` / `general` |

| `position` | INTEGER | 页面在 Wiki 中的排序位置 |

### 3.2 wiki_pages 表

存储编译后的 Wiki 页面（包含所有页面类型）。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PK | 页面 ID（UUID） |
| `project_id` | TEXT FK | 所属项目 ID |
| `page_type` | TEXT | 页面类型：`source` / `entity` / `concept` / `topic` / `structure` |
| `page_key` | TEXT | 页面标识（结构页对应 schema page_key；动态页为 LLM 生成的 slug） |
| `title` | TEXT | 页面标题（可被用户修改） |
| `content` | TEXT | 页面内容（YAML frontmatter + Markdown 正文） |
| `status` | TEXT | `draft` / `compiled` / `user_edited` |
| `refs` | TEXT | JSON 数组，显式依赖的其他页面 page_key（交叉引用） |
| `sources` | TEXT | JSON 数组，派生来源的 file_id 列表 |
| `tags` | TEXT | JSON 数组，标签 |
| `compile_version` | INTEGER | 编译版本号（每次增量更新 +1） |
| `last_compiled_at` | TEXT | 最后编译时间 |
| `last_compiled_file_id` | TEXT | 触发最近一次编译的文件 ID |
| `created_at` | TEXT | 创建时间 |
| `updated_at` | TEXT | 更新时间 |

**唯一约束**: `(project_id, page_key)` — 每个项目下每个 page_key 只有一页。

**page_type 说明**：
- `source`：来源摘要页，每篇 raw 文件对应一页
- `entity`：实体页（人、组织、产品、技术）
- `concept`：概念页（概念、方法、理论）
- `topic`：主题页（跨来源综合分析）
- `structure`：项目结构页（对应 §2.2 的 schema page_key）

### 3.3 wiki_page_sources 表

来源追溯——记录每个 Wiki 页面的内容来自哪些原始文件。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PK | 记录 ID |
| `wiki_page_id` | TEXT FK | 关联 wiki_pages.id |
| `file_id` | TEXT FK | 来源文件 ID（关联 files 表，可以是项目文件或基础库文件） |
| `contribution` | TEXT | 贡献描述（如“提供了财务数据部分”） |
| `created_at` | TEXT | 关联时间 |

### 3.4 wiki_change_log 表（log.md）

变更记录——对应 LLM Wiki 的 **log.md**，只追加，给 Wiki 一个演化时间线。

每条记录格式对应 log.md 的条目：`## [YYYY-MM-DD] ingest | 文件标题`

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PK | 记录 ID |
| `project_id` | TEXT | 所属项目 ID |
| `action` | TEXT | `ingest` / `update` / `user_edit` / `lint` / `query_archive` |
| `trigger_file_id` | TEXT | 触发变更的文件 ID（ingest 时为被摄入的文件） |
| `source_title` | TEXT | 来源标题（如文件名，用于 log.md 的标题部分） |
| `affected_page_keys` | TEXT | JSON 数组，本次操作触碰的所有 page_key（对应"触碰 10-15 页"） |
| `summary` | TEXT | 变更摘要（如"新建 3 页，更新 8 页，发现 2 个矛盾"） |
| `created_at` | TEXT | 变更时间 |

**与 log.md 的对应关系**：wiki_change_log 是 DB 存储形式，前端可渲染为 log.md 样式的只追加时间线。每条记录对应 log.md 的一行。

### 3.5 wiki_reviews 表

编译过程中 LLM 发现的问题和建议——借鉴 llm_wiki 的 REVIEW 机制。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PK | 记录 ID（基于 type+title 的内容稳定 hash） |
| `project_id` | TEXT FK | 所属项目 ID |
| `type` | TEXT | `missing-page` / `contradiction` / `suggestion` / `confirm` |
| `title` | TEXT | 发现项标题 |
| `description` | TEXT | 详细描述 |
| `affected_page_ids` | TEXT | JSON 数组，关联的 wiki_page IDs |
| `source_file_id` | TEXT | 触发此发现的源文件 ID |
| `resolved` | INTEGER | 0=待处理, 1=已解决 |
| `resolved_action` | TEXT | 解决动作（`create_page` / `dismiss` / `auto_resolved`） |
| `created_at` | TEXT | 创建时间 |

**ID 稳定性**：与 llm_wiki 一致，review ID 基于 `type::normalizedTitle` 的 FNV-1a hash，相同内容产生相同 ID，避免重复。

## 4. 编译流程（逐文件增量摄入）

### 4.1 编译触发：通知 + 人工触发

Wiki 摄入**不自动执行**，采用“通知 + 人工触发”模式——系统检测到新素材后发通知，用户决定何时摄入。

**完整数据流：**

```
用户上传文件（项目文件 or 基础库文件）
    │
    ▼
KnowledgeWorker 文件解析 pipeline（已有）：
  文本提取（PDF/Word/PPT → 纯文本）
    → 分块（chunking）
    → 向量化（embedding）
    → 存入向量数据库 + files 表
    │
    ▼
给 Wiki 发通知：项目 pending_compile_count += N
（不触发摄入，仅标记“有新素材”）
    │
    ▼
用户在 Wiki Tab 看到提示：“有 3 个新文件待摄入”  [摄入]
    │
    ▼
用户点击「摄入」→ 为每个待处理文件创建 ingest 任务 → 逐文件摄入
    │
    ▼
每个文件独立摄入：
  读取完整原文（files 表） → LLM 处理 → 触碰相关页面 → 更新 index/log
```

**核心区别：读取完整原文，不用 RAG chunks**

Wiki 摄入时**直接读取 files 表中的完整文本**，而非 RAG 的碎片化 chunks。原因：
- LLM Wiki 的核心是“深入理解一篇完整资料”，不是“从碎片中拼凑”
- 完整原文让 LLM 能发现跨段落、跨章节的关联和矛盾
- RAG chunks 是共享的（Chat/报告用），Wiki 摄入不依赖它们

**为什么采用“通知 + 人工触发”？**

| 方面 | 自动摄入 | 通知 + 人工触发 |
|------|---------|----------------|
| LLM 成本 | 每次上传都摄入，可能浪费 | 用户决定何时摄入，可控 |
| 并发控制 | 需要复杂的队列/并发配置 | 用户手动触发，天然串行 |
| 用户体验 | 黑盒，不知道何时在摄入 | 用户主动决定，有掌控感 |
| 素材积累 | 上传一个摄入一个 | 可以累积多个文件后一次摄入 |

### 4.2 单文件摄入流程详细设计

借鉴 llm_wiki 的实现，每个文件独立摄入，采用**两步链式思考**（Two-Step Chain-of-Thought）——分析和生成分开为两次 LLM 调用，显著提升质量：

```
┌─ Step 0: 缓存检查 ──────────────────────────────────────┐
│  计算源文件内容的 SHA-256 哈希                            │
│  查询 wiki_source_pages.content_hash 是否匹配          │
│  ├─ 匹配 → 跳过摄入（"未变更，跳过"）                │
│  └─ 不匹配 → 继续 Step 1                              │
└──────────────────────────────────────────────────────────┘
        │
        ▼
┌─ Step 1: 准备摄入上下文 ──────────────────────────────┐
│  读取 files 表中的完整文本（不截断）                      │
│  读取 purpose.md（Wiki 的目标和方向）                    │
│  读取 wiki_schemas（项目结构页指引）                      │
│  读取当前 index 等效数据（已有页面目录）                  │
│  读取 overview.md（全局摘要，让 LLM 了解 Wiki 现状）  │
│  读取 wiki_source_pages（检查是否已摄入/变更）            │
│  根据 Schema 的 base_lib_search_hints：                  │
│    → 检索关联基础库的 RAG chunks 作为参考上下文          │
└──────────────────────────────────────────────────────────┘
        │
        ▼
┌─ Step 2: LLM 分析（第一次调用）─────────────────────┐
│  LLM 读取完整原文，输出结构化分析：                    │
│    ① 关键实体、概念、论点提取                          │
│    ② 与已有 Wiki 内容的关联和矛盾                      │
│    ③ 推荐创建/更新的页面列表及原因                    │
│    ④ 推荐的知识结构变更（新实体、新概念）            │
│    ⑤ 推荐的基础库检索方向                              │
│  ※ 分析阶段不生成页面内容，只做"思考"              │
└──────────────────────────────────────────────────────────┘
        │
        ▼
┌─ Step 3: LLM 生成（第二次调用）─────────────────────┐
│  LLM 基于分析结果，生成实际 Wiki 文件：              │
│    ① 来源摘要页（source page）：含 YAML frontmatter  │
│    ② 实体/概念页：含 [[wiki-links]] 交叉引用        │
│    ③ 更新 index.md、log.md、overview.md              │
│    ④ REVIEW blocks：矛盾、缺失、建议、待核实项      │
│    ⑤ 推荐下一步探索方向（explore-next）            │
└──────────────────────────────────────────────────────────┘
        │
        ▼
┌─ Step 4: 存储与追溯 ────────────────────────────────┐
│  写入/更新 wiki_pages（所有触碰的页面，含 frontmatter）│
│  写入 wiki_source_pages（记录摄入状态 + content_hash） │
│  写入 wiki_page_sources（来源追溯）                      │
│  追加 wiki_change_log（log.md 等效）                     │
│  解析 REVIEW blocks → 写入 wiki_reviews 表               │
│  更新 index / overview 等效数据                         │
└──────────────────────────────────────────────────────────┘
```

> **为什么两步比一步好？**（借鉴 llm_wiki）
> 一步摄入时 LLM 同时"思考"和"写作"，容易顾此失彼。两步分离后：
> - 分析阶段可以专注理解，不被输出格式束缚
> - 生成阶段基于结构化分析，页面质量更高
> - 分析结果可缓存、可审查

> **思考参数与 400 降级**（v0.9.13）：现代模型思考模式普遍不可关闭（GLM / Kimi / MiniMax 等强制思考），仅可调档位且各厂商参数名差异大。Step 2 / Step 3 两次调用均由 LLM 客户端统一注入用户设置的思考参数（默认最低档 `reasoning_effort=low`，省 token 提速；可在设置中调档、清空或用自由 JSON 覆盖非标参数）；若端点因不支持该参数返回 HTTP 400，客户端自动回滚参数重试一次（且同实例记忆降级结论，两次调用仅首次双发）——非思考模型不再导致摄入必挂。能力探测入口见 0.0 §5.2（settings）与 0.3 §3.5（设置页）。

**批量摄入**：用户点击「摄入」时，如果有多个待处理文件，系统为每个文件创建独立的 ingest 任务，**逐个串行处理**。每个文件独立摄入、独立存储，前一个文件的摄入结果会影响后一个的上下文（因为 index 已更新）。

**摄入模式选择**：

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| **监督摄入**（默认） | 每篇摄入完成后，前端展示摘要和页面变更，用户可审阅、调整重点后再继续下一篇 | 重要资料、首次摄入、用户希望深度参与 |
| **批量快速摄入** | 连续自动处理所有待摄入文件，不等待用户确认 | 大量资料初步建库、用户已熟悉 Wiki 结构 |

> *“I prefer to ingest sources one at a time and stay involved — I read the summaries, check the updates, and guide the LLM on what to emphasize. But you could also batch-ingest many sources at once with less supervision.”* — Karpathy

监督摄入时，用户可在摄入结果页看到：
- 来源摘要页内容（LLM 提取的关键要点）
- 本次触碰了哪些页面（创建/更新列表）
- REVIEW 项（矛盾、缺失、建议）
- 操作按钮：「继续下一篇」「调整重点重新摄入」「跳过此文件」

### 4.3 摄入 Prompt 结构（两步式）

借鉴 llm_wiki 的两步摄入，Prompt 分为分析和生成两次调用：

**第一步：分析 Prompt**

```
System:
  你是知识分析 Agent。你的任务是深入阅读一篇原始资料，输出结构化分析。

  ## Wiki 目标（purpose.md）
  {项目的 wiki_purpose}

  ## Wiki 全局摘要（overview.md）
  {项目的 wiki_overview}

  ## 页面类型规则
  - source: 为该文件创建来源摘要页
  - entity: 识别文中的人、组织、产品、技术
  - concept: 识别文中的概念、方法、理论
  - topic: 更新相关的综合分析主题
  - structure: 补充与项目结构页相关的内容

Context:
  ## 原始资料（完整原文）
  {files 表中的完整文本，不截断}

  ## 当前 Wiki 索引
  {index.md 等效数据：已有页面的 page_key + title + 一句话摘要}

  ## 基础库参考（RAG 检索结果）
  {根据 search_hints 检索到的相关 chunks}

Instructions:
  1. 深入阅读完整原文，提取关键要点
  2. 识别关键实体、概念、论点
  3. 分析哪些已有页面需要更新，哪些新页面需要创建
  4. 发现跨源呼应或矛盾
  5. 推荐基础库检索方向

Output 格式:
  ## ANALYSIS
  key_entities: [{name, type, description}]
  key_concepts: [{name, description}]
  recommended_pages: [{page_key, type, action: create|update, reason}]
  cross_source_findings: [{finding, related_pages}]
  contradictions: [{description, sources}]
  base_lib_search_directions: [{query, purpose}]
  suggested_base_lib_queries: [{query}]
```

**第二步：生成 Prompt**

```
System:
  你是知识编译 Agent。基于分析结果，生成实际 Wiki 页面文件。
  每个页面必须包含 YAML frontmatter。
  在正文中使用 [[page_key]] 语法引用其他 Wiki 页面。

Context:
  ## 分析结果
  {第一步的分析输出}

  ## 相关已有页面内容（按需加载）
  {与当前资料最相关的已有页面内容，用于增量更新}

  ## 基础库补充资料
  {根据分析推荐的检索方向获取的 chunks}

Instructions:
  1. 创建来源摘要页（source），含 YAML frontmatter
  2. 创建/更新实体页和概念页，含 [[wiki-links]]
  3. 更新主题页和项目结构页
  4. 信息冲突时保留各方说法并标注来源和时间
  5. 无法确认的信息标注为「待核实」
  6. 更新 index.md 和 log.md
  7. 如果发现缺失页面、矛盾、建议，输出 REVIEW block
  8. 推荐下一步探索方向（explore-next）

Output 格式:
  ## SOURCE_PAGE
  page_key: source_{file_slug}
  title: {来源摘要页标题}
  frontmatter:
    type: source
    sources: ["{file_path}"]
    refs: [{page_key}]
    tags: [{tag}]
  content: {Markdown 正文}

  ## PAGE_UPDATES
  每个页面操作：
  ---PAGE: {page_key}---
  type: {entity|concept|topic|structure}
  action: {create|update}
  title: {页面标题}
  frontmatter:
    refs: [{page_key}]
    tags: [{tag}]
  content: {Markdown 正文}
  ---END PAGE---

  ## INDEX_UPDATE
  {更新后的 index 条目}

  ## OVERVIEW_UPDATE
  {更新后的 overview 摘要}

  ## REVIEWS
  ---REVIEW: {type} | {title}---
  {description}
  ---END REVIEW---

  ## EXPLORE_NEXT
  {建议的下一步探索方向}
```

### 4.4 REVIEW 协议

借鉴 llm_wiki 的 REVIEW block 机制，编译过程中 LLM 可主动发现问题并报告：

| REVIEW 类型 | 说明 | 示例 |
|---|---|---|
| `missing-page` | 资料涉及重要概念但当前 Schema 没有对应页面 | "资料多次提到‘税收优惠’，但无专属页面" |
| `contradiction` | 不同来源的信息存在矛盾 | "文件A说注册资本 5000万，文件B说 8000万" |
| `suggestion` | LLM 主动建议改进 | "建议补充竞争对手分析" |
| `confirm` | 需要用户确认的判断 | "根据资料推断企业处于成长期，是否准确？" |

REVIEW 项写入 `wiki_reviews` 表，用户可在 Wiki 界面查看和处理（处理动作包括：创建页面、标记已解决、忽略）。

### 4.5 基础库关联规则

项目 Wiki 编译时，自动检索关联基础库的 RAG chunks：

| 项目类型 | 自动关联基础库 |
|---------|-------------|
| 招商引资 | 招商基础库 RAG |
| 投资分析 | 投资基础库 RAG |
| 通用 | 不自动关联（用户可手动选择） |

关联方式：根据 Schema 的 `base_lib_search_hints`，从关联基础库中检索相关 chunks，作为参考上下文注入编译 Prompt。

### 4.6 purpose.md、index.md、log.md 与 overview.md

Wiki 维护四个特殊导航文件（DB 存储，前端渲染）：

**purpose.md（Wiki 的灵魂）**——借鉴 llm_wiki 的 purpose.md 设计：

> Schema 定义 Wiki **怎么运作**，purpose 定义 Wiki **为什么存在**。

- 定义 Wiki 的目标、关键问题、研究范围、演进论点
- LLM 每次摄入和查询时都读它，确保所有操作对齐目标
- 用户可在项目初始化时设定，也可通过 Chat 随时调整
- LLM 在 Lint 时可建议更新 purpose（“您的研究重点已转向 XX，是否更新 purpose？”）
- DB 存储为 projects 表的 `wiki_purpose` 字段（TEXT）

**index.md（内容导向）**：Wiki 中所有页面的目录，按类别组织。

- 每次摄入完成后自动更新
- 查询时 LLM 先读索引定位相关页面，再深入阅读
- 在中等规模（~100 个来源、数百个页面）下可替代向量 RAG
- DB 存储为 wiki_pages 表的查询结果（page_key + title + page_type + 一句话摘要）

**log.md（时间导向）**：什么时候发生了什么的追加记录。

- 只追加，不改写
- 每条记录格式：`## [YYYY-MM-DD] ingest | 文件标题`（可解析，兼容 `grep` 提取）
- DB 存储为 wiki_change_log 表（§3.4）
- 给 Wiki 一个演化时间线，帮助 LLM 理解最近发生了什么

**overview.md（全局摘要）**——借鉴 llm_wiki 的 overview.md 设计：

- Wiki 当前状态的“快照”——一页浓缩所有知识
- **每次摄入自动更新**——LLM 基于最新 index + 关键页面内容重新生成
- 新文件摄入时 LLM 读 overview，快速了解“Wiki 已经知道什么”
- 避免 LLM 每次都要读几十个页面才能理解 Wiki 现状
- DB 存储为 projects 表的 `wiki_overview` 字段（TEXT）

### 4.7 编译状态与韧性

摄入在后端 KnowledgeWorker 中异步执行，**完全独立于前端**。用户切换 Tab、关闭项目窗口、甚至重启应用，都不影响正在进行的摄入。

#### 4.7.1 编译状态机

```
                       ┌──────────────────────────────┐
                       │  监督摄入模式（supervised）   │
                       └──────────────────────────────┘

queued → ingesting → storing → completed
    │          │          │
    └─────┴─────┘
                 │
              failed（可重试）
                 │
           partial（部分页面成功）

监督模式额外状态：
  ingesting → waiting_review（每文件完成后暂停，等待用户审阅）
  waiting_review → ingesting（用户点击「继续」）
  任意运行中 → stopped（用户点击「停止」）
```

| 状态 | 说明 |
|------|------|
| `queued` | 已入队，等待 worker 拾取 |
| `ingesting` | LLM 摄入中（逐文件：读取原文 + 分析 + 生成页面） |
| `storing` | 解析输出，写入 DB，更新 index/log |
| `completed` | 全部成功 |
| `failed` | 摄入失败（可重试） |
| `partial` | 部分页面成功，部分失败 |
| `waiting_review` | 监督模式：当前文件摄入完成，等待用户审阅后继续 |
| `stopped` | 用户主动停止摄入 |

#### 4.7.2 状态持久化

详见 §3.8 wiki_compile_tasks 表。每个摄入任务的状态持久化到 DB，支持崩溃恢复。

#### 4.7.3 错误处理与重试

| 错误类型 | 处理方式 |
|---------|----------|
| **LLM API 超时/网络错误** | 自动重试，指数退避（30s → 60s → 120s），最多 3 次 |
| **LLM 返回格式错误** | 无法解析 PAGE/REVIEW blocks → 重试 1 次，仍失败则标记 `failed` 并记录原始返回 |
| **单个页面编译失败** | 其他页面继续编译，任务标记 `partial`，失败页面生成 REVIEW 项 |
| **素材不足（RAG 无结果）** | 不视为错误，生成空页面 + REVIEW 项（`data-gap`） |
| **Python 进程崩溃** | 重启后扫描 `wiki_compile_tasks`，将 `ingesting`/`storing` 状态的任务重置为 `queued` 自动重新执行；`waiting_review` 保持不变，等待用户回到 Wiki 界面手动确认继续 |

**重试策略**：
- 重试在 KnowledgeWorker 内部完成，不需要前端触发
- 每次重试记录到 `retry_count`，超过 `max_retries` 后标记 `failed`，不再自动重试
- 用户可在 Wiki 界面看到失败状态，手动点击「重试」

#### 4.6.4 前端状态展示

前端通过轮询 API 获取编译状态，不受 Tab 切换影响：

| API | 说明 |
|-----|------|
| `GET /wiki/projects/{project_id}/compile-status` | 返回当前/最近的编译任务状态 |

前端展示：
- Wiki Tab 顶部显示编译状态条（进度/状态/错误）
- 编译中：显示进度（如“3/6 页面已编译”）
- 失败：显示错误摘要 + 「重试」按钮
- 部分成功：显示成功/失败页面列表，失败页面可单独重试
- 用户切换 Tab 再回来，状态从 DB 恢复，不丢失

**状态-按钮对照表：**

| 任务状态 | 主按钮 | force | 次按钮 | force | 行为说明 |
|---------|--------|-------|--------|-------|----------|
| `completed` | — | — | 重新编译 | `true` | 清除全部 Wiki 数据，从零开始 |
| `stopped` | 继续编译 | `false` | 重新编译 | `true` | 继续=保留已有结果，从未完成处继续；重新编译=清除全部从零开始 |
| `partial` | 重试 | `false` | 重新编译 | `true` | 重试=增量重试失败文件；重新编译=清除全部从零开始 |
| `failed` | 重试 | `false` | 重新编译 | `true` | 重试=增量重试；重新编译=清除全部从零开始 |
| 新文件待编译 | 编译 | `false` | — | — | 增量模式，仅处理新文件 |

> 「重试」/「继续编译」= 非破坏性操作（`force=false`），保留已有结果；「重新编译」= 从零开始（`force=true`），清除全部 Wiki 数据（`wiki_pages`、`wiki_page_versions`、`wiki_reviews`、`wiki_change_log`、`wiki_source_pages` + 重置 `wiki_overview`），保留用户手动设置的 `wiki_purpose`。前端弹出二次确认对话框，防止误操作。「重新编译」作为通用兑底按钮，与任何状态的主操作按钮并行出现。

#### 4.6.5 并发控制配置

编译由用户手动触发，天然不会像自动触发那样大量并发。但仍需基础保护：

| 配置项 | 默认值 | 说明 |
|---------|--------|------|
| `max_concurrent_pages` | 3 | 单个项目一次编译最多几个页面并行（控制单次 LLM 调用大小） |
| `llm_timeout` | 120s | 单次 LLM 调用超时时间 |

- 全局项目并发控制**不需要**——用户手动触发，同一时间通常只有一个项目在编译
- 配置存放在 Python 后端配置文件（`python/data/config.json`），不暴露到前端 UI
- 修改配置后无需重启，下次编译时生效

## 5. Wiki 健康检查（Lint）

借鉴 llm_wiki 的 Lint 机制，定期检查 Wiki 内容质量。分三层：结构层（确定性检查）、语义层（LLM 驱动）、Review 清扫（摄入后自动清理）。

> 详细算法规格见 §12.2.5（结构层 Lint）、§12.2.9（语义层 Lint）、§12.2.8（Review 清扫）

### 5.1 结构层 Lint（无需 LLM）

确定性检查，速度快，无成本。借鉴 llm_wiki 的 `lint-structural-core.ts`（225 行），完整实现 token 索引 + bigram 索引 + Levenshtein 距离 + 相关页面推荐评分：

| 检查项 | 说明 | 修复建议算法 |
|---|---|---|
| `empty-page` | 页面内容为空或极短 | 触发重新摄入 |
| `missing-source` | 页面没有任何来源追溯 | 检查摄入流程是否正常 |
| `stale-page` | 页面长时间未更新，可能有新资料未编译 | 检查是否有未处理的新文件 |
| **`orphan`** | 页面没有任何入链 | **token 重叠度 + Cosine 归一化 + 同目录加分 → 推荐最应链接到它的页面** |
| **`broken-link`** | 死链（`[[target]]` 目标不存在） | **bigram 重叠 + Levenshtein 距离 → 推荐最近似页面（阈值 0.74）** |
| **`no-outlinks`** | 页面没有任何出链 | **token 重叠度 + Cosine 归一化 → 推荐最应链接的页面** |
| `missing-cross-ref` | 页面提到了其他页面但未建立交叉引用 | 自动补充 refs 双向链接 |
| `index-drift` | 页面存在但 index 中未列出（或反之） | 同步更新 index |
| `orphan-review` | review 项关联的页面已被删除 | 自动标记已解决 |

支持 Lint 配置（可选忽略）：`ignore_orphan` / `ignore_no_outlinks` / `ignore_pages`。

### 5.2 语义层 Lint（LLM 驱动）

LLM 阅读 Wiki 页面摘要（frontmatter + 前 500 字符），发现深层问题。输出格式升级为 `---LINT---` block：

| 检查项 | 说明 | 处理建议 |
|---|---|---|
| `contradiction` | 不同页面间信息矛盾 | 创建 review 项，让用户裁决 |
| `stale` | 页面中的声明已被更新的资料取代 | 触发增量更新 |
| `data-gap` | 重要维度缺少数据支撑 | 建议用户补充资料或创建 review |
| **`missing-page`** | 重要概念被频繁引用但无专属页面 | **建议创建新页面（后处理过滤已存在页面的误报）** |
| **`suggestion`** | 值得加入 Wiki 的问题或来源 | **建议补充资料或创建页面** |
| `broken-link` | 页面引用了不存在的 page_key | 清理引用或创建缺失页面 |
| `explore-next` | **LLM 主动建议下一步探索方向** | 建议用户补充的资料、值得深入的问题 |

**新增 missing-page 过滤：** LLM 常误报已存在页面的 missing-page，后处理阶段用 NFKC 归一化 + 精确匹配过滤误报。

> *“The LLM is good at **suggesting new questions to investigate and new sources to look for**.”* — Karpathy

`explore-next` 是 Lint 的主动探索建议能力，不仅是检查问题，还主动引导知识积累方向：
- “建议补充 XX 行业的最新报告，当前 Wiki 对该领域的覆盖较薄”
- “‘对赌协议’和‘估值调整’两个概念页内容高度重叠，建议合并”
- “建议查找 XX 公司的最新财报，当前数据已滞后 2 个季度”

### 5.3 Review 清扫（摄入完成后自动触发）

借鉴 llm_wiki 的 `sweep-reviews.ts`（463 行），摄入队列排空后自动解析待处理 REVIEW，两阶段自动解决：

```
摄入队列排空
    │
    ▼
Stage 1: 规则匹配（快速、免费）
  提取 review 标题中的页面名 → 检查对应页面是否已创建
  匹配: missing-page / broken-link / orphan → 自动 resolve
    │
    ▼
Stage 2: LLM 语义判断（处理剩余未解决的）
  每批 40 个，最多 5 批
  LLM 返回 JSON: { "resolved": [...], "reason": "..." }
  保守策略: 任何错误 → 该批全部保持 pending
    │
    ▼
结果写入 wiki_reviews 表
    │
    ▼
用户在 Wiki 界面统一查看和处理
```

Lint 结果与编译 REVIEW 共用 `wiki_reviews` 表和处理流程，用户无需区分来源。

### 5.4 Lint 执行方式

```
用户手动触发 / 摄入完成后自动触发（Review 清扫）
    │
    ▼
结构层检查（遍历所有页面，检查空内容/来源/时效/入链/出链/死链）
    │
    ▼
语义层检查（LLM 阅读页面摘要，发现矛盾/过时/缺失/建议）
    │
    ▼
Review 清扫（摄入后自动解析待处理 REVIEW，规则匹配 + LLM 语义判断）
    │
    ▼
结果写入 wiki_reviews 表（与编译 REVIEW 共用同一队列）
    │
    ▼
用户在 Wiki 界面统一查看和处理
```

## 6. 增量更新机制

### 6.1 更新触发（通知模式）

Wiki 增量更新采用**通知模式**——文件变更不自动触发编译，而是通知用户有新素材待编译：

| 变更来源 | 通知方式 |
|---------|----------|
| **项目文件**上传/删除/替换 | 项目 `pending_compile_count` 更新，Wiki Tab 显示提示 |
| **基础库文件**上传/删除/替换 | 查询关联项目，每个关联项目的 `pending_compile_count` 更新 |
| **项目-基础库关联**新建/取消 | 项目的 `pending_compile_count` 更新 |
| **Schema 变更** | 受影响项目的 `pending_compile_count` 更新 |

**通知机制：**

项目表新增 `pending_compile_count` 字段（INTEGER，默认 0）：
- 文件上传/删除/替换 → 对应项目 count += 1
- 基础库变更 → 关联项目 count += 1
- 用户点击「编译」→ count 重置为 0，开始编译

前端 Wiki Tab 根据 `pending_compile_count` 显示：
- count = 0：不显示提示
- count > 0：显示“有 N 个新文件待编译” + 「编译」按钮
- 用户可选择「全量编译」或「增量编译」（仅新文件）

### 6.2 增量编译策略

```
新文件解析完成（项目文件 or 基础库文件）
    │
    ▼
检索已有 Wiki 页面
    │
    ├─ 新文件内容与某页面相关 → 补充该页面（merge）
    ├─ 新文件包含全新主题 → 创建新页面（如果 Schema 允许）
    ├─ 新文件与已有信息冲突 → 保留双方，标注来源和时间
    └─ 新文件与所有页面无关 → 仅记录来源，不修改页面
```

### 6.3 冲突处理规则

| 情况 | 处理方式 |
|------|---------|
| 新信息与旧信息一致 | 补充来源引用，不修改内容 |
| 新信息补充旧信息 | 追加到对应段落，标注新来源 |
| 新信息与旧信息矛盾 | 保留双方说法，标注各自来源、时间、适用范围 |
| 旧信息明显过时 | 更新为新信息，旧信息移入变更日志 |

### 6.4 更新范围控制

**核心原则：每次只更新受影响的页面，不重建整套 Wiki。**

LLM 先判断新文件与哪些 page_key 相关，只对这些页面执行增量编译。

### 6.5 源文件删除对 Wiki 的影响

当项目文件或基础库文件被删除时，需要处理 Wiki 页面的关联关系：

| 情况 | 处理方式 |
|------|----------|
| 删除的文件是某页面**唯一**来源 | 页面标记为 `stale`，生成 REVIEW 项（`data-gap`），建议用户补充资料或手动删除页面 |
| 删除的文件是某页面**多个**来源之一 | 从 `wiki_page_sources` 移除关联记录，页面内容不变（其他来源仍支撑内容） |
| 删除的文件与所有页面无关联 | 无影响，仅清理 RAG chunks |

**不自动删除页面内容**——即使唯一来源被删，页面内容可能仍有价值（用户编辑过、或与其他未解析文件相关）。由 Lint/REVIEW 机制提示用户决策。

### 6.6 项目删除时 Wiki 级联清理

项目删除时，级联清理所有 Wiki 相关数据：

```
项目删除
    │
    ▼
DELETE FROM wiki_pages WHERE project_id = ?
DELETE FROM wiki_page_sources WHERE wiki_page_id IN (该项目的页面)
DELETE FROM wiki_change_log WHERE project_id = ?
DELETE FROM wiki_reviews WHERE project_id = ?
```

注意：wiki_schemas 是全局模板，不随项目删除。仅清理项目维度数据。

### 6.7 Schema 变更处理

当 wiki_schemas 表发生变更（如新增 page_key、修改编译指引）时，已有项目需要感知并响应：

| Schema 变更类型 | 处理方式 |
|---|---|
| **新增 page_key** | 检测受影响项目，更新 `pending_compile_count`，用户手动触发编译新页面 |
| **修改 compile_hint** | 不通知，下次编译时自然使用新指引 |
| **删除 page_key** | 对应页面标记为 `orphan`，生成 REVIEW 项让用户决策 |

## 7. 页面浏览与编辑

### 7.1 浏览视图

Wiki Tab 展示编译后的页面列表，支持：
- 左侧页面导航（按 Schema 定义的顺序）
- 右侧 Markdown 渲染内容（含 wiki-link 跳转）
- 来源追溯面板（可收起，显示引用了哪些原始文件）
- 变更日志（可收起，显示页面历史）

#### 7.1.1 Wiki-link 页面互联

Wiki 的核心价值在于**页面间的交叉引用和跳转**——这是 Wiki 区别于文档列表的关键。

**链接语法**：

| 语法 | 说明 | 示例 |
|------|------|------|
| `[[page_key]]` | 链接到目标页面，显示页面标题 | `[[enterprise_profile]]` → 显示“目标企业画像” |
| `[[page_key\|显示文本]]` | 链接到目标页面，显示自定义文本 | `[[risk_summary\|风险清单]]` → 显示“风险清单” |

**摄入时 LLM 必须使用 wiki-link**：

LLM 在生成/更新页面内容时，**必须**在正文中使用 `[[page_key]]` 语法引用其他 Wiki 页面。这是摄入 Prompt 的强制要求（见 §4.3），确保页面间形成互联网络。

**前端渲染行为**：

1. Markdown 渲染时，解析 `[[page_key]]` 为可点击链接
2. 点击后在 Wiki Tab 内导航到目标页面（不跳离当前视图）
3. 目标页面不存在时，显示为灰色虚线链接（提示“页面待创建”）
4. hover 时显示目标页面的一句话摘要（从 index 数据获取）

**双向链接面板**：

每个页面底部展示“反向链接”列表——哪些页面引用了当前页面。让用户看到知识的关联网络。

**知识图谱可视化**：

> *“Obsidian's graph view is the best way to see the shape of your wiki — what's connected to what, which pages are hubs, which are orphans.”* — Karpathy

Wiki Tab 内置轻量级知识图谱视图，定位为**辅助导航图**——帮用户快速理解“Wiki 里有什么、它们怎么关联、哪里是重点/空白”，然后引导用户去阅读具体页面。不是 Obsidian 式的重度知识图谱，而是 Wiki 的自然延伸视角。

**视觉风格**：融入应用整体浅色主题（`var(--bg-primary)` 等 CSS 变量），不使用独立深色主题。图谱是 Wiki 的一部分，不是“特殊模式”。

**布局结构**：

```
┌──────────────────────────────────────────────────────┐
│  图谱头部：返回 · 统计 · 搜索框 · 着色切换 · 洞察按钮 │
├──────────────────────────────────────────────────────┤
│  图例栏：类型色点 · 操作提示                              │
├─────────────────────────────────────┬───────────────┤
│  图谱 canvas (flex: 1)              │ 预览面板 (可选) │
│                                     │ (width: 280px) │
│  节点 · 曲线连线 · 标签             │ 页面摘要       │
│                                     │ 关联页面       │
│                                     │ [查看完整页面] │
│  ────────────────────────────────── │               │
│  洞察折叠条（默认收起，点击展开）  │               │
└─────────────────────────────────────┴───────────────┘
```

**交互设计**：

| 交互 | 行为 |
|------|------|
| 单击节点 | 右侧预览面板滑出（显示页面摘要、关联页面、操作按钮），不离开图谱 |
| 双击节点 | 聚焦模式：该节点居中放大，关联节点保留，其余淡出 |
| hover 节点 | 高亮该节点及其直接邻居，其余淡出；关联边加粗变色 |
| 预览面板「查看完整页面」 | 切换到页面阅读视图（离开图谱） |
| 缩放/拖拽画布 | 自由探索图谱 |
| 拖拽节点 | 手动调整节点位置（`enableNodeDragging: true`） |
| 搜索框 | 按标题/类型过滤节点 |
| 社区着色模式 | 切换为按社区着色，查看知识聚类 |

**首次打开引导**：图谱顶部显示可关闭的提示条：“这是你的 Wiki 知识地图。每个圆点代表一个 Wiki 页面，连线代表页面间的引用关系。圆点越大 = 被引用越多 = 知识枢纽。”

**预览面板**：与 Wiki 首页的列表点击预览保持一致的交互模式，解决“点击节点跳走后回不来”的上下文丢失问题。面板内容：

| 区域 | 内容 | 数据来源 |
|------|------|----------|
| 标题 | 页面标题 + 类型徽标 | `wiki_pages.title` + `page_type` |
| 统计 | 入链数 · 出链数 | 图谱邻接数据 |
| 摘要 | 页面正文第一段（去 frontmatter、去标题，截断 200 字） | `wiki_pages.content` 前端提取 |
| 关联页面 | 直接邻居列表（可点击切换预览） | 图谱邻接数据 |
| 操作按钮 | 「查看完整页面」「在图谱中聚焦」 | — |

> **摘要提取规则**：去除 YAML frontmatter（`---...---` 块）→ 跳过第一个 `# heading`（已是标题）→ 取下一个非空段落 → 截断到 200 字 → 如果以 `[[wiki-link]]` 开头则跳过取下一段。不需要后端新增字段，用现有数据即可。未来可优化为 LLM 生成的 `summary` 字段。

**小屏适配**：当图谱 canvas 宽度 < 600px 时，预览面板切换为**覆盖模式**（`position: absolute` + 半透明背景 `rgba(255,255,255,0.95)`），保证图谱始终有足够空间。关闭按钮突出显示。

**洞察折叠条**：位于图谱 canvas 底部，默认收起（一行高度），点击“洞察”按钮展开。**每条洞察可点击**，点击后图谱执行对应动作：

| 洞察类型 | 点击动作 |
|----------|----------|
| 意外关联（A ↔ B） | 高亮 A、B 两个节点 + 连线变蓝加粗 + 相机居中两个节点 |
| 知识空白 · 孤立节点 | 相机居中该节点 + 节点脉冲动画（吸引注意力） |
| 知识空白 · 稀疏社区 | 高亮该社区所有节点 + 相机缩放适配 |
| 知识空白 · 桥节点 | 桥节点脉冲动画 + 连接不同社区的边用不同颜色标注 |

不与右侧预览面板抢空间。

**孤儿页识别**：无入链的页面在图中显示为红色孤立节点，帮助用户发现需要补充关联的页面。

**图谱规模分级**：根据节点数量自动调整视觉参数，确保不同规模的 Wiki 都有好的体验：

| 规模 | 节点数 | 节点大小 | 标签策略 | 布局参数 |
|------|---------|---------|---------|----------|
| 小 | < 20 | 标准 × 1.5（偏大） | 全部显示 | 宽松（gravity=0.3） |
| 中 | 20–100 | 标准 | 按 linkCount 阈值显示 | 标准（gravity=0.5） |
| 大 | > 100 | 标准 × 0.7（偏小） | 仅枢纽节点（top 20% degree） | 紧凑（gravity=0.8） |

**阅读器 → 图谱定位**：从 Wiki 阅读器点击“图谱入口”时，传入 `highlightNode` 参数。图谱加载后自动：① 相机居中到该节点；② 该节点高亮（脉冲动画）；③ 预览面板自动打开。用户不需要在 100 个节点里重新找。

技术实现：前端使用 **graphology + sigma**（直接使用，WebGL 渲染），布局算法 **ForceAtlas2**（大图用 Web Worker），后端 Python 用 **networkx** 计算图结构（节点/边/社区检测）。详见 §12。

### 7.2 编辑能力

| 功能 | 说明 | 优先级 |
|------|------|:-----:|
| Markdown 预览 | 渲染后的页面内容 | P1 |
| 手动编辑 | 用户可直接编辑 Markdown 内容 | P2 |
| 触发重新编译 | 用户手动触发某个页面的重新编译 | P2 |
| 版本对比 | 对比不同版本的页面差异 | P3 |

**编辑标记**：用户手动编辑后，页面 status 变为 `user_edited`，后续自动编译不覆盖用户编辑（除非用户主动触发重新编译）。

>
> Wiki 侧的职责是：提供页面检索 API，让 Chat 能检索到 Wiki 内容。具体衔接设计见 §8.3。

## 8. 与 Chat / 报告生成的集成

### 8.1 知识优先级

Chat 问答和报告生成共用同一套知识优先级：

```
1. 项目 Wiki 页面（最高优先级 — 已编译的结构化知识）
2. 项目 RAG chunks（补充 Wiki 未覆盖的细节）
3. 关联基础库 RAG chunks（共享知识补充）
```

### 8.2 报告生成集成 ✅ 已实现（v0.9.12）

报告生成引擎（`retrieval.py`）在检索阶段：
1. 先查询项目 Wiki 相关页面，作为高权重上下文注入
2. 再执行常规 RAG 检索补充细节（包括项目文档和基础库文档）

实现要点：
- **通道接线**：`retrieval.py::_search_wiki_channel` 与 knowledge / internet 通道并行执行，原始结果统一进入知识卡片构建
- **页面过滤**：仅纳入已完成状态（`compiled` / `user_edited`）页面，排除 draft 半成品
- **自动启用**：`runner.py::_detect_wiki_available` 检测项目存在已完成页面时自动将 `wiki` 加入 data_sources（无用户开关，前端零改动）
- **采信优先级**：Wiki > 知识库 > 互联网，写入卡片构建 System Prompt，信息冲突时以更高优先级来源为准
- **效率**：`search_wiki` 新增 `pages` 参数，多 query 批量检索共享一次页面加载

### 8.3 Chat 接入 Wiki

项目已有跨 Tab Chat 面板（见 [2.1project-design.md §4.4](2.1project-design.md)），Chat 检索范围已包含 Wiki 页面。Wiki 侧需要提供的衔接能力：

> *“Answers can take different forms depending on the question — a markdown page, a **comparison table**, a **slide deck (Marp)**, a **chart (matplotlib)**, a **canvas**.”* — Karpathy

Chat 回答 Wiki 相关问题时，**输出格式根据问题类型自动适配**：

| 问题类型 | 输出格式 | 示例 |
|---------|---------|------|
| 知识查询 | Markdown 文本回答 | “XX 公司的核心业务是什么？” |
| 对比分析 | 对比表格 | “对比 A 公司和 B 公司的估值” |
| 趋势展示 | 图表（matplotlib） | “展示近 3 年营收趋势” |
| 汇报演示 | 幻灯片（Marp） | “生成一份投资分析摘要 PPT” |
| 关系梳理 | 思维导图 / 画布 | “展示 XX 项目的关联实体网络” |

归档为 Wiki 页面时，根据内容类型自动选择 page_type（对比→topic，分析→concept 等）。

**Wiki 检索 API：**

| API | 说明 |
|-----|------|
| `GET /wiki/projects/{project_id}/pages/search?q=...` | 三路混合检索 Wiki 页面（§12.2.7），返回匹配的页面标题 + 内容摘要 + 图谱邻居 |

> 检索架构借鉴 llm_wiki 参考实现（Rust 后端 2264 行），翻译为 Python 实现。详见 §12.2.7。

**Chat 检索流程（index-first + 三路混合检索）：**

借鉴 Karpathy 的 Query 操作，Chat 查询 Wiki 时**先读 index 定位候选页面**，再结合三路混合检索 + 图谱邻居扩展深入阅读：

```
用户在 Chat 中提问
    │
    ▼
Step 1: 读 index 定位候选页
  LLM 读取项目的 index.md 等效数据（页面目录）
  根据问题语义匹配，确定候选 page_key 列表
    │
    ▼
Step 2: 深入阅读候选页
  加载候选页面的完整内容
  同时并行检索 RAG 补充细节：
    ├─ 项目 RAG 检索（现有逻辑）
    └─ 基础库 RAG 检索（现有逻辑）
    │
    ▼
Step 3: 知识融合与回答
  Wiki 页面作为“骨架”上下文（结构化、高权重）
  RAG chunks 作为“细节”补充（碎片化、低权重）
  LLM 综合回答，标注引用来源
    │
    ▼
Step 4: 归档高价值答案（知识复利）
  如果回答包含跨源综合分析、对比、新发现，
  提示用户「是否保存为 Wiki 页面？」
  用户确认 → 创建新页面，更新 index，追加 log
```

### 8.4 查询结果归档（Query → 知识复利闭环）

> *“Good answers can be filed back into the wiki as new pages. A comparison you asked for, an analysis, a connection you discovered — these are valuable and shouldn’t disappear into chat history.”* — Karpathy

查询归档是 LLM Wiki **Query 操作的核心组成部分**，不是可选功能。它实现了“探索也是知识来源”的闭环：

- 每次高质量 Chat 回答都可能成为 Wiki 的新页面
- 归档时自动建立交叉引用（refs），更新 index.md，追加 log.md
- 下一次相关问题直接引用已归档页面，而不是重新综合
- 知识不仅来自“摄入”，也来自“探索”——**探索也是摄入**

### 8.5 对质量的影响

| 维度 | 仅 RAG | RAG + Wiki |
|------|--------|-----------|
| 上下文质量 | 碎片化，需要 LLM 自行拼凑 | 结构化，直接可用 |
| 一致性 | 同一问题多次回答可能不同 | Wiki 保证一致性输出 |
| 来源追溯 | 追溯到 chunk 级别 | 追溯到页面 + 原始文件 |
| 生成效率 | 需要大量 chunks 拼凑 | Wiki 页面直接覆盖大部分内容 |

#### 12.2.7 Wiki 检索引擎（`python/wiki/wiki_search.py`）

借鉴 llm_wiki 的 `search.rs`（Rust 后端 2264 行），翻译为 Python 实现。Wiki 检索采用**三路混合检索 + 图谱邻居扩展**，复用现有 `HybridRetriever` 基础设施：

```
search_wiki(query, project_id, top_k=20)
    │
    ├─ ① 关键词检索（Token Matching）
    │   tokenize_query(query) → 分词 + CJK bigram + 去停用词
    │   遍历项目 wiki_pages（DB 查询）
    │   对每个页面计算 score:
    │     - 文件名精确匹配 → +200
    │     - 标题包含完整短语 → +50
    │     - 正文每出现一次短语 → +20（最多计 10 次）
    │     - 标题 token 命中数 × 5
    │     - 正文 token 命中数 × 1
    │   输出: token_rank { page_key → rank }
    │
    ├─ ② 向量检索（Dense Embedding）
    │   复用 ChromaDB + bge-m3 本地模型
    │   wiki_pages 做 embedding 存入 ChromaDB（摄入时自动生成）
    │   按 page 聚合 chunks → blended score:
    │     top_chunk_score + sum(rest) × 0.3
    │   输出: vector_rank { page_key → rank }
    │
    ├─ ③ RRF 融合
    │   score = 1/(60 + token_rank) + 1/(60 + vector_rank)
    │   与现有 HybridRetriever 的 RRF 公式完全一致
    │
    └─ ④ 图谱邻居扩展（Graph Neighbor Expansion）
        从 top-K 结果中取种子页面（最多 20 个）
        基于 wiki-link 构建邻接图
        找种子的邻居页面（一度扩展）
        按种子排名加权排序邻居
        预留 15%-30% 的结果位给图谱邻居
        输出: graph_hits（标注 graph_related_to）
```

**摘要提取算法**（前端实现，在 `WikiGraphView` 内）：

```
extractSummary(content: string, maxLen = 200): string
  1. 去除 YAML frontmatter：匹配 /^---\n[\s\S]*?\n---\n/ 并移除
  2. 跳过第一个 Markdown 标题：匹配 /^#+ .+\n/ 并移除

  6. 如果截断位置不在句末，追加 "..."
```

### 12.4 关键算法参考

#### 12.4.1 Frontmatter 容错解析

```
输入: 原始文件内容
  │
  ├─ 严格模式: 文件顶部 ^---\n...\n---
  │   ├─ 匹配 → pyyaml.safe_load → 返回
  │   └─ 失败 ↓
  │
  ├─ 容错模式: 扫描前 6 行找 ---...--- 块
  │   ├─ 找到 → pyyaml.safe_load + wikilink 列表修复 → 返回
  │   └─ 未找到 → 返回 { frontmatter: {}, body: 全文 }
  │
  └─ wikilink 修复:
      related: [[a]], [[b]]  →  ["[[a]]", "[[b]]"]
```

#### 12.4.2 Levenshtein 修复建议

```
输入: broken_link_target = "entrpise_profil"（LLM 拼写错误）
  │
  ├─ Step 1: 从所有 page_key 构建 bigram 索引
  │     "enterprise_profile" → {"en", "nt", "te", "er", ...}
  │
  ├─ Step 2: 对每个候选计算 bigram 重叠度
  │     overlap(broken, "enterprise_profile") = 0.85
  │     overlap(broken, "risk_summary") = 0.12
  │
  ├─ Step 3: 计算 Levenshtein 编辑距离
  │     distance("entrpise_profil", "enterprise_profile") = 3
  │
  └─ Step 4: 返回最相似的候选
        建议: "entrpise_profil" → "enterprise_profile" (相似度 0.85)
```

#### 12.4.3 图谱邻居扩展算法

```
输入: ranked_results（融合后排序结果）, wiki_pages（所有页面含 wiki-links）, limit=20
  │
  ├─ Step 1: 构建邻接图
  │   遍历所有 wiki_pages 的 [[wiki-link]]
  │   建立无向邻接表: { page_key → set(neighbor_keys) }
  │   别名索引: page_key / title / filename 大小写不敏感 + 连字符/空格等价
  │
  ├─ Step 2: 选取种子
  │   seeds = ranked_results[:min(limit, MAX_GRAPH_SEEDS=20)]
  │   seed_set = set(seeds)  （用于排除已在结果中的页面）
  │
  ├─ Step 3: 一度扩展
  │   对每个种子（按排名 r）:
  │     遍历其邻居 neighbor:
  │       跳过 neighbor ∈ seed_set
  │       candidate_scores[neighbor] += 1.0 / (r + 1)
  │       candidate_seeds[neighbor].add(seed.title)
  │
  ├─ Step 4: 配额计算
  │   vector_coverage = min(vector_hits, limit) / limit
  │   ratio = MAX_RATIO(0.30) - (MAX_RATIO - MIN_RATIO) × vector_coverage
  │   graph_quota = ceil(limit × ratio), clamp(1, limit-1)
  │   （向量覆盖率高 → 预留 15%；低 → 预留 30%）
  │
  ├─ Step 5: 合并输出
  │   基础结果 = ranked_results[:limit - graph_quota]
  │   图谱结果 = top graph_quota 个候选（按 candidate_scores 降序）
  │   每个图谱结果标注 graph_related_to = [关联的种子标题]
  │
  └─ 输出: 合并后的 limit 个结果
```

#### 12.4.4 图谱洞察评分

```
对每条边 (A, B):
  score = 0
  ├─ A 和 B 属于不同社区 → +3
  ├─ A.type ≠ B.type → +2 (entity↔concept) / +1 (其他)
  ├─ A 是边缘节点(degree≤3) 且 B 是枢纽(top 10% degree) → +2
  └─ 边权重 < 0.3 → +1

  score ≥ 3 → 输出为“惊人关联”
```

#### 12.4.5 结构层 Lint 算法

```
输入: wiki_pages（所有页面含 outlinks/tokens）, config（可选忽略配置）
  │
  ├─ Step 1: 构建索引
  │   slug_map: { normalized_slug → page_index }
  │   token_index: { token → [page_indices] }（倒排索引）
  │   fragment_index: { CJK_bigram → [page_indices] }（bigram 索引）
  │   inbound_counts: { page_index → 入链数 }
  │
  ├─ Step 2: 检查 orphan（无入链）
  │   for page in pages:
  │     if inbound_counts[page] == 0 and not ignored:
  │       finding = { type: "orphan", severity: "info" }
  │       finding.suggested_source = related_candidate(page, "source")
  │         # token 重叠度 + Cosine 归一化 + 同目录加分
  │
  ├─ Step 3: 检查 broken-link（死链）
  │   for page in pages:
  │     for link in page.outlinks:
  │       if link not in slug_map:
  │         finding = { type: "broken-link", severity: "warning" }
  │         finding.suggested_target = broken_candidate(link)
  │           # bigram 重叠 + Levenshtein 距离
  │           # 阈值: similarity >= 0.74
  │
  ├─ Step 4: 检查 no-outlinks（无出链）
  │   for page in pages:
  │     if len(page.outlinks) == 0 and not ignored:
  │       finding = { type: "no-outlinks", severity: "info" }
  │       finding.suggested_target = related_candidate(page, "target")
  │
  └─ 输出: findings（含 suggested_source / suggested_target）
```

#### 12.4.6 Review 清扫算法

```
输入: pending_reviews（所有未解决的 REVIEW 项）, wiki_index（页面索引）
  │
  ├─ Stage 1: 规则匹配（快速、免费）
  │   for review in pending_reviews:
  │     names = extractCandidateNames(review)
  │       # review.title 中的页面名 + affectedPages 中的文件名
  │     for name in names:
  │       if pageExists(name, wiki_index):
  │         # 精确匹配: basename / title / kebab-case 等价
  │         auto_resolve(review)
  │         break
  │
  ├─ Stage 2: LLM 语义判断（剩余未解决的）
  │   每批 JUDGE_BATCH_SIZE = 40 个 reviews
  │   最多 MAX_JUDGE_BATCHES = 5 批
  │   Prompt: 列出 Wiki 页面索引 + 待判断 reviews
  │   LLM 返回: { "resolved": [review_id, ...], "reason": "..." }
  │   保守策略: 任何错误 → 该批全部保持 pending
  │
  └─ 输出: 已自动解决的 review 列表
```
