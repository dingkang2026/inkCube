# 打包安装设计

> 描述墨方 InkCube 桌面安装包的内容构成、构建流水线、首次启动初始化与运行时工具解析。架构总览见 [0.0architecture.md](0.0architecture.md)；开发环境搭建见 [0.1dev-guide.md](0.1dev-guide.md)。

## 1. 概述

安装包基于 electron-builder 生成 Windows NSIS 安装程序，采用**全捆绑分发**策略：任务智能体所需工具链（Python / uv / rg / ruff / pandoc）随安装包分发，用户零配置。

后端打包不使用 PyInstaller：RAG 重依赖（FlagEmbedding/torch、docling、rapidocr）为函数级延迟导入，PyInstaller 静态分析会丢失；改为捆绑 **python-build-standalone 解释器 + site-packages 依赖目录**，运行时由 Electron 直接 spawn 解释器运行后端代码。`requirements.txt` 是依赖唯一事实源。

| 机制 | 入口 | 职责 |
|------|------|------|
| 工具链准备（脚本/手动） | `resources/tools/`（不入库） | 默认 `scripts/prepare-tools.ps1` 按锁定版本下载并逐件校验；网络受限可按 §6.2 手动放置；build-installer.ps1 Step 1 全量校验 |
| 一键构建 | `scripts/build-installer.ps1` | 工具链 → 后端装配 → 前端构建 → electron-builder |
| 首装初始化 | `electron/tool-initializer.js` | 安装包资源解压到用户数据目录，版本变化时更新 |
| 运行时路径解析 | `python/tools/tool_resolver.py` | 环境变量 → 捆绑目录 → PATH 三级查找 |

## 2. 目标与约束

- **零配置**：用户安装后无需手动安装 Python、uv、rg、ruff、pandoc
- **体积可控**：安装包（NSIS LZMA）2026-10-25 实测 517 MB（v0.1.2，`differentialPackage: false` 后普通固实压缩；差分感知压缩时期为 627 MB）——python-backend 装配 1,512 MB（与 §4.1 一致）；AI 模型不随包，首次使用时下载
- **开发/生产同源**：开发阶段使用 conda 环境，业务代码不感知运行环境差异
- **平台优先级**：Windows 先行（NSIS）；macOS（dmg）/ Linux（AppImage）配置已就绪、未验证
- **可更新**：应用升级时按工具版本对比自动刷新用户目录中的工具链

## 3. 关键决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 分发策略 | 工具链全部捆绑（LibreOffice 除外） | 用户零配置，体验一致 |
| 后端打包 | python-build-standalone + site-packages 目录 | RAG 重依赖函数级延迟导入，静态打包工具无法覆盖；依赖完整性由 pip/uv 保证，无需维护 hiddenimports |
| 预置基础库 | 不捆绑种子资料 | 预置库初始为空容器，用户自行上传（见 [2.7](2.7baselib-rag-design.md)） |
| 生产路径传递 | python-manager 显式设置 `INKCUBE_*` 环境变量 | tool_resolver 的 `%APPDATA%/InkCube` 回退路径与 Electron userData 实际路径不一致，环境变量是解析的第一优先级，最可靠 |
| pandoc | 捆绑 | 约 30MB 可接受，避免用户为生成 DOCX 自行安装 |
| LibreOffice | 不捆绑，检测 + 引导 | 约 800MB 过大，且非所有用户需要（见 §7） |
| 首次初始化 | Electron 主进程复制到 userData | 避免向 Program Files 写入（需管理员权限） |
| Python 发行版 | 一份两用（见 §9） | 安装目录内副本只读跑后端；userData 副本作任务 venv 基底 |
| 预置模板 | 捆绑于安装包（只读） | 随版本更新，用户只能复制为自定义模板 |
| 卸载数据保留 | `deleteAppDataOnUninstall: false` + 卸载器询问 | 数据默认不随卸载丢失（重装后可用）；是否删除由用户在卸载时选择（`resources/installer.nsh` customUnInstall，静默卸载默认保留） |
| 安装范围 | `perMachine: true` | 机器级安装至 Program Files 标准位置（多用户共享）；代价是安装/卸载需管理员权限（per-user 免 UAC 方案未采用） |
| 安装包签名 | 暂未签名 | 未配置证书；正式分发前需决策签名路线（0.2 §10 优化清单） |

### 4.2 不捆绑的组件

| 组件 | 原因 | 处理方式 |
|------|------|---------|
| LibreOffice (~800MB) | 体积过大，非所有用户需要 | 运行时检测 + 状态展示（§7） |
| MS Office | 用户已有或自行安装 | 运行时 COM 检测 |
| AI 模型（bge-m3 等） | 体积大且按需使用 | 应用内下载（ModelManager，存入 userData/data/models） |
| 预置基础库种子资料 | 预置库定位为空容器 | 用户自行上传文档 |

```
│   ├── routers/ agent/ knowledge/ ...

├── tools/
│   ├── python-build-standalone/   ← Python 发行版（一份两用，见 §9）
│   │   └── python.exe
│   ├── uv.exe
│   ├── rg.exe
│   ├── ruff.exe
│   ├── pandoc.exe
│   └── tool-versions.json         ← 工具版本清单
├── skills/                        ← 内置 Skills（browser-fetch / ppt-master，seed.py 拷贝源，2.3 §2.2）

    └── mermaid.min.js             ← 离线 Mermaid 渲染
```

## 5. 运行时目录布局

安装后资源只读，可写数据全部落在 Electron userData 目录（Windows 为 `%APPDATA%/InkCube/`，由 productName 决定；productName 为纯 ASCII，避免中文路径在脚本/工具链上的编码问题）：

```
userData/
├── tools/                         ← 首装从安装包复制（tool-initializer.js）
│   ├── uv.exe  rg.exe  ruff.exe  pandoc.exe
│   └── tool-versions.json         ← 版本记录（含 app_version / initialized_at）
├── python/                        ← python-build-standalone 副本（任务 venv 基底）
├── data/                          ← 用户数据（INKCUBE_DATA_DIR 指向此处）
│   ├── inkcube.db                 ← 主数据库（23 张表 + FTS5）
│   ├── logs/                      ← app.log（Python 与 Electron 同写此文件）
│   ├── files/                     ← 知识库上传文件
│   │   └── {project_id}/{file_id}
│   ├── chroma/                    ← ChromaDB 向量库
│   ├── models/                    ← AI 模型（bge-m3 / docling）
│   ├── tasks/                     ← 任务工作区
│   │   └── {task_id}/
│   │       ├── .venv/             ← 基于 userData/python 创建的任务 venv
│   │       └── ...                ← 工作区文件 + agent state
│   ├── skills/                    ← Skill（第三方 SKILL.md 标准 + 内置 skill 由 seed.py 指纹幂等拷贝，2.3 §2.2）
│   ├── reports/                   ← 报告输出
│   │   └── {report_id}/           ← content.md / registry.json / checkpoints/
│   └── templates/                 ← 用户自定义模板（.inktpl）
└── tool-versions.json
```

要点：

- **只读与可写分离**：安装目录内资源随版本更新覆盖；userData 下数据跨版本保留
- **数据目录按需创建**：Electron 只负责 tools/python 复制；`data/` 下各业务子目录由 Python 后端在首次使用时创建（main.py 建 data/logs，各 router 建对应业务目录）
- **共享数据目录**：生产模式 Electron 将 `INKCUBE_DATA_DIR` 设为 `userData/data`，Python 与 Electron 写同一个 app.log、共用 db/models/files
- **卸载行为（2026-10-25）**：NSIS 卸载器删除安装目录、快捷方式与注册表卸载项；userData（`%APPDATA%/InkCube/`）默认保留——卸载器弹窗询问是否一并删除（默认保留，静默卸载 `/S` 保留）；手动彻底清理 = 删除 `%APPDATA%/InkCube` 整个目录（含 tools 约 250MB、python 约 110MB、data/ 下 db/chroma/models/tasks venv/uv-cache/files/reports/logs，总量可达数 GB）
- **单实例锁（2026-10-25）**：主进程 `requestSingleInstanceLock`，二次启动直接退出并聚焦已有窗口——多开会产生双后端抢写 SQLite，并在卸载/升级时翻倍文件锁面；Windows 下 dev 与打包版 userData 同为 `%APPDATA%/InkCube`（大小写不敏感），两者互斥

## 6. 构建流水线

### 6.1 build-installer.ps1（一键构建）

```
powershell -ExecutionPolicy Bypass -File .\scripts\build-installer.ps1
```

| 步骤 | 内容 | 失败处理 |
|------|------|---------|
| 1/5 工具链 | 校验 uv.exe / rg.exe / ruff.exe / pandoc.exe / tool-versions.json / python-build-standalone/python.exe 齐全；校验构建机 Python 可用（`PYTHON` 环境变量优先，PATH 兜底，WindowsApps 别名桩不算）——electron-builder 重建 better-sqlite3 需要 | 缺失即列出清单并终止 |
| 2/5 后端装配 | robocopy 拷贝 `python/` → `resources/python-backend/`（排除 `__pycache__` `.pytest_cache` `tests` `data` 及 `*.pyc`）；`uv pip install --python <捆绑解释器> --target resources/python-backend/site-packages --index-url <阿里云镜像> -r python/requirements.txt`；生成 sitecustomize.py 到 site-packages 顶层（pywin32 生产布局适配，机制见 §9.2） | robocopy 退出码 ≥8 或 uv 失败即终止 |
| 3/5 前端构建 | `npm run build`（Vite → dist-renderer/） | 失败终止 |
| 4/5 安装包 | `npx electron-builder --win`（NSIS） | 失败终止 |
| 5/5 汇总 | 列出 dist/ 下安装包产物与大小 | — |

装配与运行时使用**同一份解释器**（python-build-standalone），消除"构建时装、运行时缺"的版本断层。脚本统一调用 `npm.cmd` / `npx.cmd`，避免 PowerShell 执行策略拦截 npm.ps1。

### 6.2 工具链准备（resources/tools/）

### 6.3 源码入库边界

`.gitignore` 忽略 `resources/*`，保留 `resources/templates/`、`resources/skills/`、`resources/installer.nsh`（NSIS 卸载询问钩子）与 icon 三件套（`resources/icon.ico/.png/.icns`，由 `scripts/make-icons.py` 程序化生成）。tools/、python-backend/ 均为本地构建产物，不入库；`scripts/` 与 `electron-builder.yml` 入库。

## 7. 首次启动初始化

`electron/tool-initializer.js` 在 `app.whenReady()` 中最先执行（先于 Python 启动），由 `main.js` 调用 `ensureToolsInitialized()`。

### 7.1 判定逻辑（checkInitNeeded）

| 情况 | 结果 |
|------|------|
| 安装包内无 `resources/tools/tool-versions.json`（开发环境） | 跳过初始化 |
| userData 无 `tool-versions.json` | 首次启动，需要初始化 |
| uv / rg / ruff / pandoc / python 任一版本号与安装包不一致 | 需要更新 |
| 版本全部一致 | 跳过 |

### 7.2 复制内容（initializeTools）

1. 安装包 `resources/tools/` 顶层文件（uv.exe、rg.exe、ruff.exe、pandoc.exe、tool-versions.json）→ `userData/tools/`
2. `resources/tools/python-build-standalone/` → `userData/python/`（已存在则先删除再整体复制）
3. 写入 `userData/tool-versions.json`：源版本内容 + `app_version` + `initialized_at`

全部 IO 走 `fs.promises`（libuv 线程池），首装复制数百 MB 不阻塞 Electron 主进程事件循环，窗口保持响应。复制进度经结构化载荷（`{ phase, copied, total }`，每 25 文件节流上报）推送至 boot gate 呈现「N/M 个文件」，文案由 renderer i18n 渲染（主进程不硬编码语言）。

## 8. 外部依赖检测

不捆绑的外部依赖（LibreOffice / MS Office / git / ffmpeg）通过运行时检测暴露状态：

| 层 | 实现 | 说明 |
|----|------|------|
| API | `GET /system/deps/check` | git / ffmpeg 两项 `shutil.which` 检测，返回 available/path/version（2026-10-19 收敛：pandoc 随应用捆绑必有、不重复检测；LibreOffice/MS Office 走 `GET /models/libreoffice/status` 的 ModelManager 注册表精确检测，本端点简版 which 检测已删；`/system/tools/status` 端点连同 tool_resolver 的版本清单函数随 ToolChainStatus 全链删除——捆绑工具必有，无需状态页） |
| 转换时刻检测 | `ModelManager.check_office_converter()` | Windows 下优先 COM 探测 MS Office（Word.Application），失败则 `check_libreoffice()`（PATH → 注册表 → 常见安装位置三级） |
| 前端 | `src/features/settings/ExternalDepsSettings.tsx` | 经 IPC `system:checkDeps` 拉取 git/ffmpeg 两项 ✅/❌、版本、路径；LibreOffice 行经 IPC `models:libreofficeStatus` 补齐（显示 MS Office / LibreOffice 命中引擎）；提供"重新检测"按钮（2026-10-19：LibreOffice 状态卡自内部模型页迁入，ToolChainStatus 组件随之全链删除） |

## 9. 后端运行时与工具解析

### 9.1 一份 Python 发行版，两个用途

| 角色 | 位置 | 用途 | 隔离方式 |
|------|------|------|---------|
| 后端运行时 | `resources/tools/python-build-standalone/python.exe`（安装目录，只读） | spawn 运行 `resources/python-backend/main.py`，依赖经 PYTHONPATH 指向 site-packages | 不对其 pip install，保持只读 |
| 任务 venv 基底 | `userData/python/`（首装复制副本） | 创建任务 venv 的 `--python` 参数 | venv 机制隔离，用户代码不污染后端 |

### 9.2 生产启动链路（python-manager.js）

```
command: <resourcesPath>/tools/python-build-standalone/python.exe
args:    [<resourcesPath>/python-backend/main.py, --port, <动态空闲端口>]
cwd:     userData
```

| 环境变量 | 值 | 用途 |
|----------|-----|------|
| `INKCUBE_DATA_DIR` | `userData/data` | 数据目录（db/logs/files/models 共享） |
| `INKCUBE_RESOURCES_DIR` | `process.resourcesPath` | loader.py 读取预置模板 |
| `PYTHONPATH` | `<resourcesPath>/python-backend/site-packages` | 后端依赖 |
| `TIKTOKEN_CACHE_DIR` | `userData/data/tiktoken-cache` | tiktoken 编码数据缓存（o200k_base 数据文件需从 OpenAI CDN 下载且 tiktoken 内部无 timeout，CDN 不可达时后台线程阻塞但不影响启动；首次下载成功后永久离线可用） |
| `INKCUBE_{UV,RG,RUFF,PANDOC}_PATH` | `userData/tools/<name>.exe` | 工具解析第一优先级（tool-initializer 复制到 Electron userData，而非 tool_resolver 的回退路径，必须显式传递） |
| `INKCUBE_PYTHON_PATH` | `userData/python/python.exe` | 任务 venv 基底 |
| `INKCUBE_PARENT_PID` | Electron 主进程 PID | 后端 watchdog 检测父进程存活（见 [0.4](0.4lifecycle-design.md)） |
| `INKCUBE_ELECTRON_PATH` | 生产为 process.execPath；开发为 node_modules 内 electron | Python 侧 spawn mermaid-renderer |
| `PYTHONUTF8` / `PYTHONIOENCODING` / `PYTHONUNBUFFERED` | utf-8 / 1 | 编码与流式输出 |

> **sitecustomize.py（pywin32 生产布局适配）**：Python 只处理 site-packages 内的 `.pth` 文件，经 `PYTHONPATH` 注入的目录中的 `.pth` 不生效——pywin32.pth（把 `win32/`、`win32/lib/` 追加进 sys.path 并自举 pywintypes DLL）因此失效，`import win32com.client` 报 `No module named 'pywintypes'`。构建期（§6.1 Step 2）在 site-packages 顶层生成 `sitecustomize.py`：site.py 在解释器启动时经 sys.path 正常导入它（`PYTHONPATH` 项参与查找），模块内补齐 pywin32.pth 的三行路径追加，并经 `os.add_dll_directory` 注册 `pywin32_system32`（pywintypes/pythoncom 的 DLL 所在地），等价复刻 pywin32.pth 行为。该文件由 build-installer.ps1 自动生成，勿手工修改。

启动后轮询 `/health`（300ms 间隔，60s 超时——冷启动导入 transformers/torch/docling 链路实测 8~10s，环境 IO 波动下翻倍，15s 预算曾导致间歇性启动失败）；退出时 `POST /shutdown` → 2s → SIGTERM → 3s → SIGKILL（见 [0.4](0.4lifecycle-design.md)）。

### 9.3 tool_resolver.py 统一路径解析

所有工具查找统一走 `python/tools/tool_resolver.py`，工具注册表：uv / rg / ruff / pandoc（各对应 `INKCUBE_{NAME}_PATH` 环境变量与平台二进制名）。

`resolve_tool(name)` 查找优先级：

1. 环境变量 `INKCUBE_{NAME}_PATH`（生产由 python-manager 显式传入；开发/测试覆盖）
2. 捆绑目录（开发：`resources/tools/`）
3. `%APPDATA%/InkCube/tools/`（手动运行后端时的兼容回退）
4. 系统 PATH（`shutil.which`，开发环境 conda 激活后命中）

`resolve_python()` 查找优先级：

1. 环境变量 `INKCUBE_PYTHON_PATH`
2. `%APPDATA%/InkCube/python/`（兼容回退）
3. `resources/tools/python-build-standalone/`（开发环境）
4. `sys.executable`（兜底）

各工具模块（venv_manager / code_search / code_lint / code_format / package_manager / lsp_client / doc_generator）的查找逻辑均为对 `resolve_tool()` / `resolve_python()` 的一行委托。

### 9.4 开发环境兼容

开发阶段无需下载捆绑工具，后端由 conda 环境 `inkcube` 运行，工具经系统 PATH（conda Scripts 目录）解析。也可用环境变量显式覆盖：

```powershell
$env:INKCUBE_UV_PATH    = "$env:USERPROFILE\.conda\envs\inkcube\Scripts\uv.exe"
$env:INKCUBE_RUFF_PATH  = "$env:USERPROFILE\.conda\envs\inkcube\Scripts\ruff.exe"
$env:INKCUBE_PYTHON_PATH= "$env:USERPROFILE\.conda\envs\inkcube\python.exe"
```
