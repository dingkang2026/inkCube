# 2.11 通知与提醒设计（OS 系统通知 · 事务提醒 · 通知中心 · 信息类 kind）

> 来源：todo.md 通知/提醒五条待办。本文档为实施前置设计（coding-habits §2.8 三要素），
> 实施时与代码双向对齐（§2.1）；通知链路既有约定见 [0.4 §5.5/§6.4/§6.5](0.4lifecycle-design.md)。

## 0. 背景与范围

**消息黑洞**：Toast 与首页 feed 均只在 renderer 内呈现，窗口最小化/遮挡/失焦时用户不可见
（心跳照常拉取，数据不丢、只丢感知）；事务到期/逾期无任何提醒；历史通知无回溯入口；
通知 kind 只有终态四值（completed/failed/paused/awaiting_input），无信息类。

**范围**（todo.md 五条 → 四个工作项 + 一组开关）：

| 工作项 | 内容 | 分期 |
|---|---|---|
| B | OS 系统通知（补黑洞） | P0 |
| A | 信息类通知 kind（info/warning）+ 首个用例「模板文件已变更」 | P0 |
| C | 事务到期/逾期提醒 | P1 |
| D | 全局通知中心 | P1 |
| E | 通知设置开关（横切 B/C） | P0 出键，P1 出 C 键 |

**范围外**：声音自定义、免打扰时段、通知内容富媒体、邮件/推送等外部通道。

## 1. 设计决策记录

| # | 决策 | 理由与被否方案 |
|---|---|---|
| D1 | 逾期提醒**每天一条**（跨天重发），到期当天一条 | 提醒语义，错过即永远错过；被否：只发一次（应用当天未打开则提醒被跳过且不再补） |
| D2 | OS 通知弹出**同样即已读**（「弹出即已读」不变量延伸到所有弹出面） | 不已读会导致用户回窗后 ActivityMonitor 将其视为 fresh 再弹 Toast，重复打扰；已读历史由通知中心「全部」列表与 Windows 通知中心留存 |
| D3 | OS 通知仅**失焦或不可见**时发送（`document.hidden || !document.hasFocus()`），不提供「前台也发」开关 | 前台已有 Toast，双发冗余；开关数量克制，需要时再加 |
| D4 | 三个设置键分离：OS 总开关 / 声音 / 事务提醒 | 提醒类功能被讨厌风险高，独立可关 |
| D5 | 通知中心入口 = NavTabs **铃铛**（未读徽章）+ 首页动态区「查看全部」链接，面板挂 App 层全局单例 | 任何页面可达（L1 全局可见）；铃铛与链接共用同一 open 状态 |
| D6 | 模板文件变更**每日一扫**、每日最多一条（复用现有未读查重） | 「变更未处理」是持续状态，每天提示直至用户重新分析（重新分析更新 file_hash 后自然消停）；更细的「仅首次变更通知」需要额外每模板状态，不值 |
| D7 | 事务（affair）**不注册**进活动注册表 | 它无「进行中」态，不是长时活动（0.4 §2.7）；活跃归 registry、提醒/终态归 notifications，分层不变 |
| D8 | OS 通知触发逻辑在 renderer（ActivityMonitor），主进程只做无状态投递 | 单实现原则：基线/合并/i18n 全在 dispatchToasts，主进程第二套解析必然分叉（0.4 §6.4 「事件不解析」的延伸） |
| D9 | 按天查重用**新方法** `add_notification_daily`，不改现有 `add_notification` | 现有 11 个 emit 调用方的未读查重语义不动；提醒语义（跨天重发）与终态语义（未读期间只一条）本就不同 |

## 3. 后端设计

### 3.1 信息类通知 kind（A，P0）

[activity_events.py](../python/activity_events.py) 新增通用入口（对齐 `_emit_transfer` 的「上下文显式传入」模式）：

```python
def notify(db, *, entity_type, entity_id, project_id, container, kind, entity_title, detail=None):
    """信息类通知通用入口：走 _store_and_publish 收口，未读查重/投递与终态事件
    同实现；写入失败仅告警不影响业务。kind 用专用语义值（file_changed / due /
    overdue / …）；通用 info / warning 仅作无专用语义时的兜底。"""
```

不做 per-entity 包装函数，也不做 notify_warning/notify_info 薄包装（与 `complete_*` 不同：
信息类无行可查，上下文调用方自带；无消费方的包装 = 死代码，§2.9）。

### 3.2 事务到期/逾期提醒（C，P1）

[affairs_service.py](../python/affairs_service.py) 新增（与 `maybe_roll_daily` 同模式）：

```python
_last_reminder_date: str | None = None

def maybe_scan_reminders(db) -> bool:
    """每日一次提醒扫描（心跳入口调用，同日零开销）：
    due_date == today → notify(kind='due')；due_date < today → notify(kind='overdue')
    （前端色彩映射 due→info 蓝 / overdue→warning 黄，见 §6.2）。
    按天查重（add_notification_daily）→ 每事务每 kind 每天至多一条。
    首次调用即扫（覆盖应用当天中途启动）；开关关闭时不扫不置标记（开启当日补扫）。
    通知不隶属长时活动，不注册 registry（D7）。"""
```

- entity：`entity_type='affair'`，`entity_id=phase_task.id`，`entity_title=pt.title`，`project_id`，`container='project'`；
- detail：空（标题 + kind 已表达完整语义；后续如需带天数在 i18n 之外扩展）；
- 挂载点：[routers/activities.py `activities_status`](../python/routers/activities.py#L204) 内 `maybe_roll_daily(db)` 之后追加 `maybe_scan_reminders(db)`（复用心跳，不新增轮询端点，与 roll 同先例）；
- 扫描失败异常隔离（try/except + logger.warning），不影响 status 响应。

### 3.3 模板文件变更扫描（A 首个用例，P0）

[routers/forms.py](../python/routers/forms.py) 新增 `maybe_scan_template_changes(db)`（实施修订：原定 template_analyzer.py，但它是纯分析器无 db 依赖，且 `sha256_file`/`_file_changed` 判定与 ActivitySource fetch 先例（`active_form_templates`）均在 forms.py——扫描器随宿主落路由层，避免跨层反向 import）：

- 每日一次（`_last_change_scan_date` 同模式），心跳入口挂载（`maybe_scan_reminders` 之后，P1 前先挂在 roll 之后）；
- 遍历 `status='success' AND file_hash IS NOT NULL` 模板 → `_file_changed` 判定 → 命中：
  `notify(db, entity_type='form_template', entity_id=…, project_id=None, container='project', kind='file_changed', entity_title=name, detail=None)`；
- **detail=None（实施修订）**：后端零文案（activities.py 既有约定），detail 写中文硬编码违反 §2.3 双语要求——完整语义在 i18n 主键 `activity.form_template.file_changed` 表达（§6.5）；
- **查重用现有 `add_notification` 未读查重**（D6）：每日一扫 + 未读查重 = 每天最多一条，用户 Toast 已读后次日仍变更则再发，重新分析后 `file_hash` 更新自然停止；
- 单文件 hash 计算失败（文件被占用/删除）静默跳过该模板（下次扫描重试），不上抛。

> kind 语义澄清：kind 表示**通知类型**，不是严重级别——模板变更通知 kind='file_changed'，前端 Toast 色彩映射见 §6.2。kind 扩枚举：`info`/`warning` 是**通用信息类**，供无专用 kind 的场景；有明确语义的场景优先专用 kind（如 `file_changed`、`due`、`overdue`），i18n key `activity.<entity_type>.<kind>` 结构不变。

### 3.4 通知中心端点（D，P1）

[routers/activities.py](../python/routers/activities.py) 新增：

| 端点 | 方法 | 语义 |
|---|---|---|
| `/activities/notifications?offset=0&limit=50` | GET | 分页全量（含已读），`{items, total}`；limit 上限 200 |
| `/activities/notifications/read-all` | POST | 全部标记已读，`{ok, marked}` |
| `/activities/notifications/{id}` | DELETE | 单条删除（通知中心历史面行内操作，2026-10-20 审计补齐）；幂等 `{ok, deleted}`（不存在亦 ok，对齐 mark 系列风格；轻量易失数据不加确认弹层，keep=100 保留期不受影响） |

### 4.2 IPC 通道

| 通道 | 方向 | 语义 |
|---|---|---|
| `app:osNotify` | renderer → main（invoke，失败静默） | payload `{ title, body, silent, nav }`；main：`Notification.isSupported()` 不支持则丢弃；`new Notification({ title, body, silent })`，`on('click')` → `mainWindow.show()+focus()` + `webContents.send('app:osNotifyClick', nav)`，`n.show()`；`nav` = 完整 NotificationItem 字段子集（id/entity_type/entity_id/project_id/container/kind/entity_title），main 零 i18n 零路由知识（D8） |
| `app:osNotifyClick` | main → renderer（send） | renderer 监听 → `navigateToNotification(nav)`（复用现有导航） |
| `notifications:list` | renderer → main | → `GET /activities/notifications` |
| `notifications:delete` | renderer → main | → `DELETE /activities/notifications/{id}` |
| `notifications:readAll` | renderer → main | → `POST /activities/notifications/read-all` |

preload.js 无需改动（实施核实）：`on`/`invoke` 是全通道通用转发，任意新通道零改动可达。

## 5. 数据流（三要素②）

```
┌─ python ─────────────────────────────────────────────────────────────┐
│ 业务终态 11 组 emit ─┐                                              │
│ 提醒扫描器(每日) ────┼→ activity_events._store_and_publish ─┐       │
│ 模板变更扫描(每日) ──┘        │                               │       │
│                              ▼                               ▼       │
│                    notifications 表(写)              SSE activity:stream
└──────────────────────────────┬───────────────────────────────┬───────┘
                               ▼                               ▼
┌─ electron ───────────────────────────────────────────────────────────┐
│ activities:getStatus(IPC)        activities:subscribeStream→activity:stream
│ notifications:list / readAll(新增)      (kick 信号，200ms 节流)      │
│ app:osNotify(IPC)→Electron Notification→click→app:osNotifyClick     │
└──────────────┬──────────────────────────────────────────┬────────────┘
               ▼                                          ▼
┌─ renderer ───────────────────────────────────────────────────────────┐
│ ActivityMonitor（唯一新终态入口）                                     │
│   poll → applyStatus → ActivityContext(feed) → Toast / 首页 feed / 通知中心│
│   dispatchToasts ──失焦/不可见──→ app:osNotify                        │
│ app:osNotifyClick → navigateToNotification                          │
└──────────────────────────────────────────────────────────────────────┘
```

**端到端路径**：

| 列 | 路径 |
|---|---|
| 写（新终态/提醒） | 业务/扫描器 → `notify*/complete_*/fail_*` → `add_notification[_daily]`（查重）→ notifications 表 → SSE `_publish` |
| 事件 | SSE `activity:stream` → electron `activities:subscribeStream` → renderer `activity:stream` → kick（200ms 节流）→ 立即 poll |
| 读（实时面） | poll → `GET /activities/status`（心跳入口顺带跑 roll/两扫描器）→ ActivityContext → Toast / feed / 徽章 |
| 读（历史面，D） | 通知中心面板 → `notifications:list` → `GET /activities/notifications` → items+total |
| 写（已读） | dispatchToasts 弹出即已读 / 点击条目 / 「全部已读」→ `notifications:markRead` / `notifications:readAll` |
| 写（删除） | 通知中心条目行内删除 → `notifications:delete` → 历史面本地移除 + feed 视图隐藏（首页动态区不提供删除，速览非管理面） |
| 写（OS 通知） | dispatchToasts → `app:osNotify` → Electron Notification → click → `app:osNotifyClick` → navigateToNotification |

### 6.2 状态-界面映射（ActivityMonitor type 映射，现状 → 目标）

| kind | 现状 | 目标 |
|---|---|---|
| `failed` | error | 不变 |
| `paused` / `awaiting_input` | info | 不变 |

| `warning` / 专用 warning 类（`file_changed`、`overdue`） | —（不存在） | **warning**（黄） |

### 6.3 窗口状态 × 反馈面矩阵（B）

| 窗口状态 | Toast | OS 通知 | 说明 |
|---|---|---|---|
| 聚焦且可见 | 弹 | **不发**（D3） | Toast 足够 |
| 失焦但可见 | 弹 | 发 | 用户可能在看别的屏 |
| 不可见/最小化 | 弹（不可见） | 发 | SSE kick 仍即时（kick 不受 hidden 影响），回到应用时 feed/通知中心已有记录 |

### 6.4 关键交互规则与不变量

1. **弹出即已读**（D2）：Toast 与 OS 通知共用 dispatchToasts 内的单次 markRead，任何弹出面出现即算送达；
2. **单一实现**（D8）：合并（BATCH_LIMIT）、基线（baselineReady 首拉不弹）、i18n、markRead 全在 dispatchToasts，OS 通知只是渲染面附加；
3. **导航不变量**：`navigateToNotification` 新增 `affair` 分支 → `app:navigate-project-tab` `{projectId, tab:'affairs', container:'project', taskId: entity_id}`（taskId 走 ProjectDetailPage 既有 tabSignal 链路）；`form_template.file_changed` 复用现有 form_template 分支（模板管理页）；
4. **台账零增长**（§8）：通知中心「加载更多」与 read-all 是一次性查询；两扫描器挂心跳入口（同 `maybe_roll_daily` 先例）；OS 通知复用 dispatchToasts——0.4 §8.1 轮询台账不加行；
5. **清理边界**：通知中心历史受 `keep=100` 上限约束，超出即消失（设计预期，非缺陷）；
6. **单条删除语义**（2026-10-20）：删除仅作用于历史面与实时面视图（feed live 条目经视图层隐藏集合过滤，不改 ActivityContext 状态）；`keep=100` 保留期独立生效不受影响；分页游标（nextOffset）不回退——已加载尾部剩余条目照常「加载更多」。
